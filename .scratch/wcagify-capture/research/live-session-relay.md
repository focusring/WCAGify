# Rejected alternative: a live session through the extension

Researched 2026-09-23 and rejected because the evaluation must run offline from a durable artifact. Kept for a future effort.

- Viable and built before: an MV3 extension forwards `chrome.debugger` traffic over a WebSocket to a relay that impersonates a Chrome browser endpoint (`/json/version`, `ws://.../cdp`). agent-browser connects to any `ws(s)://` URL and only needs a `Browser.getVersion` reply. Closest implementations: oh-my-pi's MIT `browser-relay` (relay plus extension; ported for agent-browser in pi-agent-browser-native PR 199, validated with 30 tabs) and Playwright's extension relay (`packages/extension/src/relayConnection.ts`, token-gated, one tab group per client). OpenClaw documents the remote pairing shape: `wss://` only off loopback, connection-bound HMAC proofs.
- Blockers: Chromium treats every extension debugger client as untrusted, so `Target.setDiscoverTargets`, `createTarget`, `getTargets`, `attachToTarget`, `activateTarget` and `createBrowserContext` answer "Not allowed" and the relay must synthesise the whole Target and Browser surface agent-browser uses; the non-suppressible infobar detaches on dismissal; Chrome 155 policy can refuse attachment; `--allowed-domains` is rejected in CDP mode so containment moves into the extension; downloads and `Browser.grantPermissions` break.
- Without an extension: Chrome's `--remote-debugging-port` binds to loopback only, refuses non-IP, non-localhost Host headers, and since Chrome 136 requires a non-default `--user-data-dir`, so the commissioner's real logged-in profile cannot be exposed. The Chrome 144 remote-debugging toggle shows a permission dialog on every connection.
- Operational: the commissioner's browser must stay open for the whole audit (dedicated profile, sleep and memory saver off); N workers mean N tabs in one cookie jar, so one logout kills all; sessions must reattach by stable target id after reconnects.
