# 2.2.1 Timing Adjustable

Level A · WCAG 2.0+ · Guideline 2.2 Enough Time · Group: `motion`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)
· [Spec](https://www.w3.org/TR/WCAG22/#timing-adjustable)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#timing-adjustable)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-2-1-timing-adjustable/)
· ACT: [bc659a](https://www.w3.org/WAI/standards-guidelines/act/rules/bc659a/),
[bisz58](https://www.w3.org/WAI/standards-guidelines/act/rules/bisz58/)

## Requirement

> For each time limit that is set by the content, at least one of the following is true:
>
> - Turn off: The user is allowed to turn off the time limit before encountering it; or
> - Adjust: The user is allowed to adjust the time limit before encountering it over a wide range
>   that is at least ten times the length of the default setting; or
> - Extend: The user is warned before time expires and given at least 20 seconds to extend the
>   time limit with a simple action (for example, "press the space bar"), and the user
>   is allowed to extend the time limit at least ten times; or
> - Real-time Exception: The time limit is a required part of a real-time event (for example, an
>   auction), and no alternative to the time limit is possible; or
> - Essential Exception: The time limit is essential and extending it would invalidate the
>   activity; or
> - 20 Hour Exception: The time limit is longer than 20 hours.
>
> Note:
> This success criterion helps ensure that users can complete tasks without unexpected
> changes in content or context that are a result of a time limit. This success criterion
> should be considered in conjunction with Success Criterion 3.2.1, which puts limits on changes
> of content or context as a result of user action.

Terms (WCAG 2.2 glossary): **real time events**: "event that a) occurs at the same time as the
viewing and b) is not completely generated by the content" — both halves decide it, and the
glossary's own examples are the test: "A Webcast of a live performance (occurs at the same time as
the viewing and is not prerecorded)", "An on-line auction with people bidding (occurs at the same
time as the viewing)", "Live humans interacting in a virtual world using avatars (is not completely
generated by the content and occurs at the same time as the viewing)". A countdown the page itself
generates is not a real-time event, however live it looks. **essential**: "if removed, would
fundamentally change the information or functionality of the content, **and** information and
functionality cannot be achieved in another way that would conform" — both halves must hold, so a
limit whose purpose could be served another way that conforms is not essential.

## In plain terms

Every deadline the content itself sets must be removable, stretchable or postponable: the visitor
turns it off, sets it to ten times as long, or is warned in time and extends it with one simple
action. W3C ranks those three: "Disabling time limits is better than customizing the length of time
limits, which is better than requesting more time before a time limit occurs" — recommend them in
that order. "Any process that happens without user initiation after a set time or on a periodic
basis is a time limit" (Understanding): a self-refreshing page, a session that logs out, a checkout
countdown, a notice that vanishes, content advancing faster than it can be read. Only a real-time
event, a limit extending would invalidate, or one over 20 hours is exempt; people who read, type or
navigate slowly need that time to finish the task at all.

## Applies when

- Present, by the Understanding's own definition: "Any process that happens without user initiation
  after a set time or on a periodic basis is a time limit. This includes partial or full updates of
  content (for example, page refresh), changes to content, or the expiration of a window of
  opportunity for a user to react to a request for input." Concretely in a sample: a meta refresh
  with a delay (step 1); a `Refresh` response header (step 2); a timer value in the scripts (step
  3); the URL or the DOM changing on its own while the sample sits idle (step 4); a countdown (a
  `motion.js` `autoUpdating[]` entry with a high `changesIn5s` whose `textSample` reads as a clock
  or a bare number); a session or inactivity timeout (a warning dialog, a forced logout, a timer
  constant in the scripts); a window to act (place a bid, confirm seats, enter a one-time code); a
  message that disappears on a timer; content advancing faster than it can be read, since "It also
  includes content that is advancing or updating at a rate beyond the user's ability to read and/or
  understand it. In other words, animated, moving or scrolling content introduces a time limit on a
  user's ability to read content."
- Not present: no meta refresh that fires, no `refresh` response header, no timer in the step 3 scan
  or the step 3 recorder, and no URL or content change over 60 seconds idle in every state of the
  sample.
- Exception, Real-time: the limit belongs to a live event the content does not generate (auction
  bidding, live streaming, a shared game round) and "no alternative to the time limit is possible".
  Understanding: in an auction "it would be unfair to extend the time limit for any one particular
  user", so no extension, adjustment or deactivation is required.
- Exception, Essential: extending it invalidates the activity. Understanding's worked case is a
  ticket site that "gives the user two minutes to confirm a purchase before the seats are returned
  to the general pool", where "holding a ticket longer than that may invalidate the nature of the
  site" — and note what it expects even then: "the site does move as much of the process out of the
  time-critical period as possible, for instance allowing users to provide necessary information
  like name, payment method, etc., before entering the time-critical stage."
- Exception, 20 Hour: the limit is "longer than 20 hours", so above 72000 seconds; exactly 72000 is
  not exempt (ACT bc659a Failed Example 4 is `content="72000"`, Passed Example 3 is
  `content="72001"`).
- Security limits are in scope: "This success criterion applies only to time limits that are set by
  the content itself. For example, if a time limit is included in order to address security
  concerns, it would be considered to have been set by the content." Do not drop a session timeout
  because it is there for security.
- One security case is exempt: "Certain time limits implemented for security reasons, such as
  time-based / time-limited two-factor authentication tokens, can be considered essential, and may
  be exempt from this criterion" — record the one-time-code window as exempt here and check 3.3.7,
  3.3.8 and 3.3.9 in the `forms` pass instead.
- Out of scope: "Time limits set externally to content, such as by the user agent or by factors
  intrinsic to the Internet are not under the author's control and not subject to WCAG conformance
  requirements. Time limits set by web servers should be under the author's/organization's control
  and are covered" — a web server timeout is in scope, a browser or network timeout is not.
- Out of scope: "Non-timed server redirects (e.g., 3xx response codes) are not applicable because
  there is no time limit: they work instantly."
- Goes to 2.2.2 instead: "This success criterion is generally not applicable when the content
  repeats or is synchronized with other content, so long as the information and data is adjustable
  or otherwise under the control of the end user"; W3C names "scrolling text that repeats,
  captioning, and carousels".
- No time limit when the same information is reachable another way: "Content that operates on a
  timer does not need to be time adjustable if there is an alternative that does not rely on a
  timer." W3C's email toast: "Users are able to identify the arrival of email through other means,
  such as viewing the Inbox, so the disappearance of the message does not set a time limit on the
  ability to determine if new mail has arrived." The converse is the failing half: "If the user has
  no other means of discovering the same information (or performing the same function), then each
  message would need to meet this success criterion."
- A third party may hold the control: "In cases where timing is not an intrinsic requirement but
  giving users control over timed events would invalidate the outcome, a third party can control
  the time limits for the user (for example, granting double time on a test)" — an exam whose
  invigilator can grant extra time is not a fail on the absence of a control in the page.
- The `forms` unit walks the signed-in and multi-step states for 2.2.3, 2.2.5, 2.2.6 and 3.3.7 and
  notes "what the page says about expiry and whether input survives it" (groups.md); take its notes
  as candidates here, and hand it back anything found in step 6.

## axe-core

| Rule           | Decides                                   | Result → outcome                    |
| -------------- | ----------------------------------------- | ----------------------------------- |
| `meta-refresh` | a meta refresh delay over 0 up to 72000 s | violation → fail (100); else step 1 |

In the WCAG 2.0 A & AA rule set, on by default, `failure` only, impact Critical, selector
`meta[http-equiv="refresh"][content]` with `excludeHidden: false`. Its check parses the text before
the first `;`, `,` or space and passes the element when that text is not digits and dots, when the
delay is 0 or less, or when the delay is above 72000 (check options `minDelay: 0`, `maxDelay:
72000`); it fails the element when the delay is over 0 and at most 72000. The violation reads
"Delayed refresh under 20 hours must not be used" and its node target is the `meta` element.

ACT bc659a, which this rule implements, applies "to the first meta element in a document for which
all the following are true: the element has an `http-equiv` attribute value of `refresh`; and the
element has a valid `content` attribute value, as described in the meta refresh pragma directive."
Its single expectation: "For each target, the time from the `content` attribute value is between 0
and 72000 (20 hours). To determine the time, run the shared declarative refresh steps on the meta
element as described in the HTML refresh state." Its examples fix the operative reading: 0 passes,
72001 passes, 30 fails, exactly 72000 fails. Both of its assumptions change the outcome and neither
is checked by axe: "This rule assumes no functionality was provided by the website for the user to
adjust the timer" and "This rule assumes that the refresh was not essential, which is listed as a
valid exception to 2.2.1 Time Adjustable". So the violation is a fail at 100 once step 7 finds no
turn-off, adjust or extend control for that refresh and no exception; where step 7 finds one, record
`pass` and note the violation as an artefact of those assumptions.

ACT bisz58 has the same applicability and one stricter expectation, "For each target, the time from
the `content` attribute value is 0", and W3C maps it to 2.2.4 and 3.2.5, listing 2.2.1 only as a
secondary requirement: "This success criterion is less strict than this rule. This is because this
criterion allows redirects longer than 20 hours. Some of the failed examples satisfy this success
criterion." Decide this criterion by bc659a; never fail 2.2.1 on a delay above 72000.

Two more facts to carry into step 1. The axe rule tests every matching `meta` element while the
browser and ACT honour only the first valid one, so a violation on a later element is a false
positive: with `content="99999"` before `content="30"`, axe reports the second, which never fires.
And ACT's accessibility-support note: "Not all major web browsers parse the value of
the `content` attribute in the same way. Some major browsers, when they are unable to parse the
value, default to a 0 seconds delay, whereas others will not redirect at all."

Settles: the declarative meta refresh and redirect case on the element it flags
([F40](https://www.w3.org/WAI/WCAG22/Techniques/failures/F40),
[F41](https://www.w3.org/WAI/WCAG22/Techniques/failures/F41)). Leaves open: which meta element
actually fires; whether a turn-off, adjust or extend control exists for it; server-side timed
redirects ([F58](https://www.w3.org/WAI/WCAG22/Techniques/failures/F58)), session and inactivity
timeouts, countdown timers, script-driven expiry of a window to act, auction limits, reading limits,
vanishing messages, and for each whether a turn-off, adjust or extend option exists.

## Manual procedure

Steps 1 to 4 run in the initial state, steps 5 to 7 per candidate, step 8 per fail. Repeat steps 1
to 4 in every state of `recon/<sample>-states.md` that navigates or signs in, since a meta refresh,
a `Refresh` header and a session timer can all differ per state.

1. List every meta refresh and decide which one fires. `motion.js` and `structure.js` return
   `metaRefresh` from the first `meta[http-equiv="refresh" i]` whether or not its value is valid, so
   read the elements directly instead of trusting that string:

   ```bash
   agent-browser eval --stdin <<'JS'
   (() => {
     const metas = [...document.querySelectorAll('meta[http-equiv="refresh" i]')]
     let honoured = null
     const rows = metas.map((m, i) => {
       const content = (m.getAttribute('content') || '').trim()
       const head = content.split(/[;,\s]/)[0]
       const valid = /^[0-9.]+$/.test(head)
       if (valid && honoured === null) honoured = i
       const rest = content.slice(head.length).replace(/^[;,\s]+/, '').replace(/^url=/i, '').trim()
       const seconds = valid ? parseFloat(head) : null
       return { index: i, content, seconds, valid, url: rest || null }
     })
     return { count: rows.length, honoured, rows }
   })()
   JS
   ```

   The row at `honoured` is the ACT bc659a target and the only one the browser acts on. `seconds`
   over 0 and at most 72000 with a `url` is a redirect
   ([F40](https://www.w3.org/WAI/WCAG22/Techniques/failures/F40)); the same with `url` null is a
   reload of the same page ([F41](https://www.w3.org/WAI/WCAG22/Techniques/failures/F41)). `seconds`
   0 sets no time limit, `seconds` above 72000 takes the 20 Hour Exception, and a row with `valid`
   false never fires. F40 and F41 both make the failure conditional on five checks, all of which
   must come out false before the failure applies: the seconds value is present; it is "less than 1
   or greater than 72,000"; "the page qualifies for Real-time or Essential Exceptions"; "the user is
   provided an opportunity to turn off, extend, or adjust the timing of the page refresh" (step 7);
   and "the page does not refresh after the duration specified in the content attribute" (step 4
   confirms it does). Done when `honoured`, its `seconds`, its `url` and the five checks are in the
   findings file, or `count` is 0.

2. Read the response headers for a server-side refresh, which F58 names as the non-standard header
   `Refresh: {time in seconds}; url={URI of new location}` and which no probe and no axe rule sees:

   ```bash
   agent-browser eval --stdin <<'JS'
   (async () => {
     try {
       const r = await fetch(location.href, { method: 'HEAD', cache: 'no-store' })
       return { status: r.status, refresh: r.headers.get('refresh') }
     } catch {
       return { status: null, refresh: null, blocked: true }
     }
   })()
   JS
   ```

   A `refresh` value with a delay over 0 is
   [F58](https://www.w3.org/WAI/WCAG22/Techniques/failures/F58), whose three checks are: the page
   "automatically redirects to another page after some period of time without the user taking any
   action" (true here, or observed in step 4); it "qualifies for Real-time or Essential Exceptions"
   (false); and "the user is provided an opportunity to turn off, extend, or adjust the timing of
   the page refresh" (false, from step 7). Omitting the URL is allowed and gives "a periodically
   refreshing page, which causes the same problem". `blocked: true` means the fetch was refused
   (cross-origin or a blocking CSP): fall back to step 4's idle watch and record `cannot-tell` for
   the header. Done when the `refresh` value is recorded as a delay, as `null`, or as blocked.

3. Inventory the timers. Run the probe, scan the page scripts, then arm a recorder that catches the
   timers the scripts set later:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/motion.js
   agent-browser eval --stdin <<'JS'
   (async () => {
     const word = new RegExp(
       ['setTimeout', 'setInterval', 'session', 'timeout', 'expir', 'countdown', 'idle',
         'logout', 'warn', 'extend', 'refresh', 'deadline', 'remain'].join('|'), 'i')
     const num = /\d{3,}|\d+\s*\*\s*\d+|\b\d{1,3}\s*(?:s|sec|secs|m|min|mins|h|hour|hours)\b/i
     const tags = [...document.scripts]
     const texts = tags.filter((e) => !e.src).map((e) => e.textContent)
     for (const u of tags.filter((e) => e.src).map((e) => e.src).slice(0, 25))
       try { texts.push(await (await fetch(u)).text()) } catch {}
     return texts.flatMap((x) => x.split('\n')).map((l) => l.trim())
       .filter((l) => word.test(l) && num.test(l)).slice(0, 60)
   })()
   JS
   agent-browser eval --stdin <<'JS'
   (() => {
     window.__t221 = []
     for (const fn of ['setTimeout', 'setInterval']) {
       const original = window[fn]
       window[fn] = function (handler, delay, ...rest) {
         const ms = Number(delay) || 0
         if (ms >= 5000) {
           const at = (new Error().stack || '').split('\n')[2]
           window.__t221.push({ fn, ms, at: at ? at.trim() : null })
         }
         return original.call(this, handler, delay, ...rest)
       }
     }
     return { armed: true }
   })()
   JS
   ```

   The source scan catches the timers armed while the page loaded; the recorder catches the ones
   armed afterwards — on a click, on sign-in, and the re-arm a session timer does on every
   interaction — which the scan misses whenever the delay is a named constant
   (`setTimeout(logout, SESSION_IDLE)` returns nothing). Read it back at any point with:

   ```bash
   agent-browser eval --stdin <<'JS'
   (() => (window.__t221 || []).map((t) => ({ ...t, seconds: t.ms / 1000 })))()
   JS
   ```

   Each entry gives the delay in seconds and the source line that armed it; the recorder ignores
   delays under 5000 ms, which are animation and polling ticks rather than time limits, and step 5
   catches a message that vanishes faster than that. The patch is lost on `reload`, `open`, `back`
   and any navigation: re-arm it after each. Every returned scan line that
   pairs a number with a session, logout, expiry, warning or countdown word is a candidate: convert
   it to seconds and note whether it exceeds 72000. Add the step 1 delay, the step 2 header delay
   and every `autoUpdating[]` entry whose `textSample` drops between two runs. Done when each
   candidate is in the findings file with its source, delay in seconds and effect.

4. Watch and wait. Idle the page, touching nothing, and see what happens by itself:

   ```bash
   agent-browser get url
   agent-browser screenshot .notes/audit/evidence/<sample>--2.2.1-t0.png --full
   agent-browser wait 30000   # a numeric wait sleeps the whole time; run this line twice for 60 s
   agent-browser get url
   agent-browser screenshot .notes/audit/evidence/<sample>--2.2.1-t60.png --full
   agent-browser dialog status
   ```

   A changed `get url` is a timed redirect: F40 when step 1 explains it, F58 when step 2 does,
   F58 when neither does; the same URL with the page reloaded under a step 1 delay is F41. A changed
   screenshot region is a candidate for step 5. `dialog status` answers separately: a native
   `confirm()` warning blocks the page, never appears in `snapshot`, and makes every other command
   fail with "A JavaScript confirm dialog is blocking the page" — that message is itself the finding
   that a warning fired, and `dialog accept` answers yes, `dialog dismiss` no. With step 1 `count` 0
   or `honoured` null, step 2 `refresh` null, step 3 empty, and the same URL, screenshot and dialog
   status after the 60 seconds, record `not-present` for this state; do not sit out a delay step 1,
   2 or 3 already read from the source. Done when this state is `not-present` or has candidates.

5. Reading limits and disappearing content. Per candidate, `get text "<selector>"` twice 30 seconds
   apart, or `record start .notes/audit/evidence/<sample>--2.2.1-<slug>.webm`, `wait 20000`,
   `record stop` for a toast (when `record start` reports ffmpeg missing, take timestamped
   screenshots instead). Drop it when the content repeats and stays under the visitor's control
   (2.2.2), or when the same information stays available elsewhere — W3C's email toast passes
   because "Users are able to identify the arrival of email through other means". Keep it when it is
   the only carrier of its information and leaves before it can be read: then "each message would
   need to meet this success criterion". For a kept reading limit, four options satisfy the
   criterion and `snapshot -i` is where to look for each: pause and restart from where it stopped
   ([G4](https://www.w3.org/WAI/WCAG22/Techniques/general/G4)), a pause control on scripted
   scrolling ([SCR33](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR33)), a control
   that turns the limit off ([G198](https://www.w3.org/WAI/WCAG22/Techniques/general/G198)), or a
   control that shows the moving text "in a static window or area"
   ([SCR36](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR36)) — `click` it and
   confirm the whole text is then readable at the visitor's own speed. SCR36 is not available for
   text that cannot be shown at once (W3C: "a long chat conversation"); there the option is pause
   and restart. Test G4 and SCR33 by operating the control: the movement must stop and "not restart
   by itself", and on restart resume "from the point where it was stopped". Done when each candidate
   is applicable or dropped with its reason, and each applicable one has its option or a fail
   indicator.

6. Session, form and checkout limits. Repeat steps 1 to 4 signed in and after starting a multi-step
   form, re-arming the step 3 recorder after each navigation:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser wait 30000   # repeat; screenshot after each
   agent-browser screenshot .notes/audit/evidence/<sample>--2.2.1-form-t<n>.png --full
   ```

   `forms.js` `fields[]` records the `value` of every field a timeout would discard; keep the
   pre-expiry output beside the post-expiry one. Sit out a limit of 10 minutes or less in
   `wait 30000` steps; for a longer one take the value from step 3 and queue it for the human. Note
   what expiry costs: lost entries, a returned seat, a forced sign-in. Done when each state's limit
   has a measured or sourced length and a recorded cost, or the sample has no signed-in or
   multi-step state.

7. The six options, in the order the criterion lists them; stop at the first that holds.

   - **Turn off** ([G133](https://www.w3.org/WAI/WCAG22/Techniques/general/G133),
     [G198](https://www.w3.org/WAI/WCAG22/Techniques/general/G198)): `snapshot -i` the form's first
     page, the account settings and any preferences dialog for a checkbox, switch or link that
     removes the limit. G133 wants it on the first page of a multipart form ("Allow an additional 15
     minutes to complete each part of this form"), and asks a second check: "Check that if the
     checkbox is checked, additional time is provided to complete the form" — so `check "<sel>"`,
     then repeat step 6 and confirm the limit really moved. G198 adds where it must sit: "the
     mechanism should be available at or near the top of the page", "can be completed without a time
     limit itself and before the time limit for the page expires", and "Verify that the time limit
     for the page is long enough that a user can easily navigate to the mechanism even if they are
     10 times slower than most users". Measure that: the `focusables.js` `order[]` index of the
     control is how many tab stops precede it, and `eval` `Date.now()` before the first `press Tab`
     and again after activating it gives your own walking time — ten times that number is what the
     limit has to exceed. Holds when the control is reachable and operable before the limit is met
     and switching it on removes the limit.
   - **Adjust** ([G180](https://www.w3.org/WAI/WCAG22/Techniques/general/G180)): a control that sets
     the limit; `get html "<sel>"` on its select or number field and compare the maximum with the
     default. G180's own test is not the markup but the behaviour: set the limit to ten times the
     default, perform the timed action, wait past the default, and "Check that the time limit does
     not expire until the limit specified in step 2 has passed".

     ```bash
     agent-browser select "<sel>" "<largest value>"
     agent-browser get value "<sel>"
     agent-browser wait 30000   # repeat past the default limit
     agent-browser get text body
     ```

     Holds when the maximum is at least ten times the default, it is set before the limit is met,
     and the limit then expires at the new value, not the default. W3C's anchor for "ten times":
     "if 15 seconds is allowed for a user to respond and hit a switch, 150 seconds would be
     sufficient".

   - **Extend** ([SCR16](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR16) with
     [SCR1](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR1)): SCR16 puts the
     warning "20 seconds or more before the time limit occurs" as "a confirm dialog that states that
     a time limit is imminent and asks if the user needs more time. If the user answers 'yes' then
     the time limit is reset." Record across the warning:

     ```bash
     agent-browser record start .notes/audit/evidence/<sample>--2.2.1-warning.webm
     agent-browser wait 30000        # repeat until the warning shows; a numeric wait never gives up
     agent-browser dialog status     # a native confirm() warning blocks every other command
     agent-browser dialog accept     # answers "yes" to that confirm; dialog dismiss answers "no"
     agent-browser snapshot -i       # an in-page warning dialog appears here instead
     agent-browser find role button click --name "Extend"
     agent-browser record stop
     ```

     A condition wait is the wrong tool for a long limit: `wait --text "<warning text>"` gives up
     after 25000 ms with "Wait timed out after 25000ms". Measure the 20 seconds deterministically
     from the step 3 recorder: read `window.__t221` again the moment the warning appears and the
     newest entry is the grace timer SCR16 arms for the remainder, its `seconds` the time the
     visitor is given; otherwise take it from the recording's timeline. For the count, SCR1 allows
     either shape — the user "can extend the time limit to at least 10 times the default time limit,
     either by allowing the user to indicate how much additional time is needed or by repeatedly
     allowing the user to extend the time limit" — so either read a single larger value being
     accepted or repeat the extension and record how many times it was granted. Run `focusables.js`:
     the control's `order[]` entry must read `visible` true and `inAriaHidden` false, or there is
     nothing to activate; an empty `name` is 4.1.2, not this. Holds when 20 seconds or more pass
     between warning and expiry, one simple action extends it, and it extends at least ten times.

   - **Real-time Exception**: a live auction, live stream or shared live round the content does not
     generate, matching both halves of the glossary definition, with no alternative to the limit.
     Holds when the event is live and the limit cannot be replaced for one user without unfairness.
   - **Essential Exception**: extending invalidates the activity: a held seat, a timed exam, a
     time-based authentication token. Holds when both halves of the glossary definition hold; where
     that rests on the author's intent, queue it for confirmation rather than passing it.
   - **20 Hour Exception**: holds when the measured or sourced limit is above 72000 seconds.

   Done when each time limit is matched to one option or has a fail indicator.

8. Evidence. `highlight "<css>"` the countdown or warning, then `screenshot`; keep the step 5 or 7
   recording, the step 6 screenshots and the pre- and post-expiry `forms.js` output. Done when each
   fail has one.

## Deciding

- Fail (certainty ≥ 90): an axe `meta-refresh` violation on the step 1 `honoured` element, with no
  control and no exception found in step 7 — 100. A
  step 1 `honoured` delay over 0 and up to 72000 seconds with no control to turn it off (F41 for a
  reload, F40 for a redirect, ACT bc659a failed) — 95. A step 2 `refresh` header with a delay over 0
  and no control (F58) — 95. The URL changing by itself during the step 4 wait with nothing in the
  markup or the headers behind it (F58) — 95. A session or inactivity timeout under 20 hours that
  logs out or discards entries with no turn-off, no adjust and no warning — 90. With no turn-off and
  no adjust either: a warning leaving under 20 seconds (measured from the grace timer or the
  recording), or an extension that stops before ten repeats — 90; a countdown with no extend
  control, on neither a live event nor a held resource — 90; an adjust control set to its maximum
  that expires at the default anyway (G180 check 5 false) — 90.
- Fail (70–89): an extend control whose `focusables.js` entry reads `visible` false or
  `inAriaHidden` true, so there is nothing to activate inside the window — 85. A message carrying
  information available nowhere else that vanishes on a timer — 80. A turn-off or adjust control
  reachable only after the limit is met — 80. A turn-off control that carries a time limit itself,
  or sits so far down the page that ten times your own walk to it exceeds the limit (G198 check 2
  false) — 75. Content advancing past the reading speed of its own text with no pause or restart
  ([G4](https://www.w3.org/WAI/WCAG22/Techniques/general/G4)) — 75. A pause control that restarts
  the content by itself, or restarts it from the beginning instead of "from the point where it was
  stopped" (G4 checks 2 and 4,
  [SCR33](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR33) checks 3 and 6) — 75.
  An adjust control whose maximum is under ten times the default — 75. A checkbox for more time
  that changes nothing when checked (G133 check 2 false) — 75.
- Needs confirmation (50–69): a timeout read from the scripts or the recorder but longer than the 10
  minutes step 6 sits out — 65; ask for the configured session length and its warning. A server-side
  timeout this sample could not reach, or a step 2 `blocked: true` — 60; ask its length and effect.
  A limit the author may call essential, a seat hold or an exam — 60; ask whether extending it
  "would fundamentally change the information or functionality of the content" and whether it could
  be achieved another way that conforms. A vanishing message whose information may live elsewhere —
  60; ask where else the visitor can find it. A live-event limit an alternative may still serve — 55.
  A limit an invigilator or administrator can extend for the visitor (W3C's "granting double
  time on a test") — 55; ask whether that third-party control exists in practice.
- Pass: every time limit satisfies one of the six options — the turn-off control near the top and
  reachable before the limit is met and proven to remove the limit; an adjust control whose maximum
  is at least ten times the default and which the timed action then honours; a warning 20 seconds or
  more before expiry, extendable with one simple action at least ten times; a real-time or essential
  limit on both halves of its glossary test; or a limit above 72000 seconds. A `honoured` row with
  `seconds` 0, and every row with `valid` false, set no time limit and need nothing recorded.
- Not present: nothing refreshes, redirects, counts down, expires or vanishes on a timer in any
  state, and neither the source nor the headers hold a timer value.
- False positives to avoid: an axe `meta-refresh` violation on a `meta` element that is not the step
  1 `honoured` one — the browser never fires it. A `metaRefresh` string from `motion.js` or
  `structure.js` whose value is invalid and never fires: ACT bc659a treats
  `content="0: https://w3.org"`, `content="+5; https://w3.org"`,
  `content="foo; URL='https://w3.org'"`, `content="; 30"`,
  `content="-00.12 foo"` and an empty or missing `content` as inapplicable. A meta refresh delayed 0
  and a 3xx server redirect, which set no time limit. A carousel, looping ticker or caption track
  the visitor can control (2.2.2). A spinner while a request the visitor triggered is pending. A
  toast whose information stays available elsewhere. A countdown that only displays a future event.
  A URL that changes on its own only by gaining a hash or a tracking parameter. A limit set by the
  browser or network, not by the content. A time-based two-factor code window, which W3C allows as
  essential.

## Reporting

- File under: 2.2.1 for a time limit that cannot be turned off, adjusted or extended, and for a
  timed refresh or redirect. Changing context on the visitor's own action is 3.2.5 (AAA); an
  interruption arriving on a timer is 2.2.4 (AAA); re-entering data after a session expires is 3.3.7
  and re-authenticating 2.2.5 (AAA); content that merely lacks a pause control is 2.2.2; an unnamed
  extend button is 4.1.2 and one the keyboard cannot reach 2.1.1. The same timeout on other samples
  is one issue naming them.
- Title patterns: "Session expires after 15 minutes without warning", "Page refreshes itself every
  30 seconds", "Checkout countdown cannot be extended", "Error message disappears too quickly",
  "News ticker scrolls away before it can be read", "Server redirects the page after 10 seconds"
- Severity: High when expiry loses entered data, signs the visitor out mid-task or hides
  information available nowhere else. Medium when the limit only interrupts, or its warning leaves
  too little time or too few extensions. Low when the limit is generous and costs no data.
- Type: Technical for the timer itself: the meta refresh, the `Refresh` header, the session length,
  the warning dialog, the extend control. Design when a countdown or warning exists but is built so
  it cannot be used in time. Content when editorial copy sets the deadline (a promotion that
  vanishes).
- Evidence: the countdown or warning highlighted in a screenshot with the remaining time visible; a
  recording spanning the expiry; the filled form before expiry beside the emptied form after it,
  with the `forms.js` `fields[]` values from both runs.
- Recommendation: offer the three options in W3C's order of usefulness — off, then longer, then
  extendable. Let the visitor switch the limit off before it starts, near the top of the page, with
  a checkbox on the first page of the form
  ([G133](https://www.w3.org/WAI/WCAG22/Techniques/general/G133)) or a setting
  ([G198](https://www.w3.org/WAI/WCAG22/Techniques/general/G198)); or a control that sets it to ten
  times the default ([G180](https://www.w3.org/WAI/WCAG22/Techniques/general/G180)); or a warning at
  least 20 seconds early with one "Extend" button that works ten times
  ([SCR16](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR16) with
  [SCR1](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR1)). For reading limits add
  pause and restart from the point where it stopped
  ([G4](https://www.w3.org/WAI/WCAG22/Techniques/general/G4) with
  [SCR33](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR33)), and where the moving
  text would fit on screen at once, a control that shows all of it in a static area
  ([SCR36](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR36); it "does not apply
  when the text that is moving can not be displayed all at once on the screen", such as a long chat
  transcript, where pause and restart is the fix).

  ```html
  <meta http-equiv="refresh" content="30" />
  <!-- F41: reloads, nothing stops it -->
  <button type="button" id="refresh">Refresh now</button>
  <!-- replace it with this -->
  ```

  ```html
  <meta http-equiv="refresh" content="10; url=/new-page" />
  <!-- F40: timed redirect -->
  <p>This page has moved. <a href="/new-page">Go to the new page</a>.</p>
  ```

  Send a permanent move as a 3xx response from the server instead: it is instant, so it sets no time
  limit. For a five-minute script limit, SCR16's own shape warns at 4 minutes 40 seconds and leaves
  the last 20 seconds to answer:

  ```js
  setTimeout(userCheck, 280000) // 280 s = 4 min 40 s of a 300 s limit
  function userCheck() {
    if (confirm('Your session expires in 20 seconds. Do you need more time?')) resetLimit()
    else setTimeout(expire, 20000) // the remaining 20 s, SCR16's grace period
  }
  ```

- Related: 2.2.2 (a pause, stop or hide control for the same moving content), 2.2.4 (timed
  interruptions, AAA), 2.2.5 (re-authenticating without data loss, AAA), 3.2.5 (change of context,
  AAA), 3.3.7 (redundant entry after a timeout), 3.3.8 and 3.3.9 (the authentication step a
  time-limited code belongs to), 4.1.3 (the expiry warning announced as a status message). A single
  meta refresh with a delay fails all three at once, on different conditions: F41 fails 2.2.1 when
  all five of its checks are false, 2.2.4 when checks 1, 2, 4 and 5 are false, and 3.2.5 on checks 1
  and 4 alone — so a refresh with a control still fails none, and one above 20 hours still fails
  3.2.5. File it here and name the others only when the target level includes them.
