# 2.5.8 Target Size (Minimum)

Level AA · WCAG 2.2+ · Guideline 2.5 Input Modalities · Group: `pointer`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
· [Spec](https://www.w3.org/TR/WCAG22/#target-size-minimum)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#target-size-minimum)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-5-8-target-size-minimum/)
· ACT: none mapped to this criterion.

## Requirement

> The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when:
>
> - Spacing: Undersized targets (those less than 24 by 24 CSS pixels) are positioned so that if a
>   24 CSS pixel diameter circle is centered on the bounding box of each, the circles do not
>   intersect another target or the circle for another undersized target;
> - Equivalent: The function can be achieved through a different control on the same page that
>   meets this criterion;
> - Inline: The target is in a sentence or its size is otherwise constrained by the line-height of
>   non-target text;
> - User Agent Control: The size of the target is determined by the user agent and is not modified
>   by the author;
> - Essential: A particular presentation of the target is essential or is legally required for the
>   information being conveyed.
>
> Note 1: Targets that allow for values to be selected spatially based on position within the
> target are considered one target for the purpose of the success criterion. Examples include
> sliders, color pickers displaying a gradient of colors, or editable areas where you position the
> cursor.
>
> Note 2: For inline targets the line-height should be interpreted as perpendicular to the flow of
> text. For example, in a language displayed vertically, the line-height would be horizontal.

Terms (WCAG 2.2 glossary):

**targets**: "region of the display that will accept a pointer action, such as the interactive area
of a user interface component", with the Note that decides every overlap: "If two or more targets
are overlapping, the overlapping area should not be included in the measurement of the target size,
except when the overlapping targets perform the same action or open the same page." The unit is the
region that accepts the pointer, not the element: a 16 px icon inside a button with 12 px padding is
one 40 px target, and a `<label>` associated with a checkbox is part of that checkbox's target.

**pointer inputs**: "input from a device that can target a specific coordinate (or set of
coordinates) on a screen, such as a mouse, pen, or touch contact". Measure what a coordinate can
hit; a keyboard shortcut with no visible control carries no target and is out of scope here.

**bounding boxes**: "the smallest enclosing rectangle aligned to the horizontal axis within which
all the points of a shape lie. For components which wrap onto multiple lines as part of a sentence
or block of text (such as hypertext links), the bounding box is based on how the component would
appear on a single line." The 24 px circle is centred on this rectangle, never on the visible shape,
so a link that wraps is measured as if on one line and a clipped or concave shape can have its
circle centred on a point that lies outside the target itself.

**css pixels**: "visual angle of about 0.0213 degrees [...] This unit is density-independent, and
distinct from actual hardware pixels present in a display." `getBoundingClientRect()` and
`get box` already report CSS pixels: never convert for device pixel ratio, never re-measure zoomed.

**user agents**: "any software that retrieves and presents web content for users", with the example
"Web browsers, media players, plug-ins, and other programs — including assistive technologies — that
help in retrieving, rendering, and interacting with web content." The fourth exception covers only
what the browser draws for itself, and only while the author has left its size alone.

**essential**: "if removed, would fundamentally change the information or functionality of the
content, **and** information and functionality cannot be achieved in another way that would
conform". Both halves must hold: if a larger control could convey the same information, the
exception does not apply, whatever the author says.

## In plain terms

Every clickable or tappable thing (link, button, field, widget, click handler) must offer a solid 24
by 24 CSS pixel square inside its hit area, or enough clear space that a 24 px circle on its centre
touches no other target. This keeps people with tremors, spasticity, limited fine motor control,
thick fingers or a shaking bus from hitting the neighbour instead, and W3C adds that it "is also
useful for mouse or pen users" whose precision is reduced. Five exceptions narrow it; links in
running text and unmodified controls come up most. The measure is fixed in CSS pixels, so zooming
neither creates nor cures a failure, and a tiny target with nothing near it still passes.

## Applies when

- Present: any pointer target in the sample state: `targets.js` lists it in `targets` (links,
  buttons, fields, `summary`, widget roles, `[onclick]`, focusable elements) or `focusables.js`
  lists it in `clickableNotFocusable` (a script-driven card, row or icon). Two kinds of target
  appear in neither list and must be collected by hand in step 1: a roving-tabindex item whose role
  the probe's selector does not name (`treeitem`, `gridcell`, `menuitemcheckbox`, `menuitemradio`,
  `spinbutton`, `combobox`) or which carries no role at all, because `targets.js` drops
  `[tabindex="-1"]` and `clickableNotFocusable` drops anything with a `tabindex`; and `area`
  elements of an image map, which have no layout box at all. Roving `role="tab"`, `role="menuitem"`
  and `role="option"` items are listed, because the probe matches those by role whatever their
  tabindex. Every recorded state and both layouts (1280 and iPhone 16) count.
  - Out of scope while covered: "The requirement does not apply to targets while they are obscured
    by content displayed as a result of a user interaction or scripted behavior of content". W3C
    names four cases: "interacting with a combobox shows a dropdown list of suggestions",
    "activating a button displays a modal dialog", "content displays a cookie banner after page
    load", and "content displays a 'Take a survey' dialog after some period of user inactivity".
    The overlay's own controls stay in scope: "The requirement does however apply to targets in any
    new content that appears on top of other content."
  - Independent of zoom: "The requirement is independent of the zoom factor of the page; when users
    zoom in, the CSS pixel size of elements does not change. This means that authors cannot meet it
    by claiming that the target will have enough spacing or sufficient size if the user zooms into
    the page." Measure at each layout's own viewport, never at a zoomed one.
- Not present: a sample state with `counts.total` 0 and no `clickableNotFocusable` entry, in every
  state and layout: a text-only page with no link at all.
- Exceptions: five, and the first that holds ends the check for that target.
  - Spacing: `passes24: true` while `w` or `h` is below 24 — the 24 px circle clears every
    neighbouring target and every other undersized target's circle.
  - Equivalent: "there is another control that can achieve the underlying function that does meet
    the requirements of this success criterion" — a text link with the same `href` beside an icon
    link, a "Cancel" button beside a ×. It must sit on the same page and must itself pass.
  - Inline: `inline: true`, the target sits in a sentence (`links.js` `context: 'sentence'`) or its
    height is "constrained by the line-height of non-target text" (a footnote mark). W3C's reason
    bounds the exception: "text reflow based on viewport size makes it impossible for authors to
    anticipate where links may be positioned relative to one another" — true for links inside
    prose, not for a row of icon links that merely sits inside a `p` or `li`.
  - User Agent Control: `userAgentDefault: true` and no author rule on size, padding or font: an
    unstyled `select`, checkbox, radio or `range`, "the days of the month calendar in an
    `<input type="date">`", the browser scrollbar. The exception dies the moment the author sizes
    it: "If a scrollbar's dimensions have been modified by the author then there must be a passing
    amount of spacing between the scrollbar and the content of the page" (Figure 11).
  - Essential: map pins, because "the position of pins is analogous to the position of places shown
    on the map"; "an interactive data visualization where targets are necessarily dense"; a form in
    a jurisdiction that "legally require[s] online forms to replicate paper forms". Never
    probe-detectable, always a question for the human. W3C adds a duty that belongs in the
    recommendation: authors "are strongly encouraged to provide equivalent functionality through
    alternative means to the extent practical".

## axe-core

| Rule          | Decides                     | Result → outcome                            |
| ------------- | --------------------------- | ------------------------------------------- |
| `target-size` | 24×24 or clear 24 px circle | violation → fail (100); incomplete → step 2 |

`target-size` is `enabled: false` in axe-core's own defaults, so a bare `agent-browser a11y` returns
no `target-size` result: it runs only through `axe-page.mjs`, whose `--tags` carry `wcag22aa` when
the report targets AA or AAA at WCAG 2.2. The rule is `any: ["target-size", "target-offset"]`, so a
node passes when **either** sub-check passes: `target-size` takes "the largest unobscured area" of
the element and compares it to 24×24; `target-offset` measures the "safe clickable space" diameter
to the closest neighbour and passes it at 24. Neither is required when the other holds.

Read the message on each node in `.notes/audit/axe/<sample>[--<state>].json`; each names its own
follow-up:

- `Target has insufficient size (Wpx by Hpx, ...)` — violation: the box is under 24×24 and the
  offset check also failed. Fail unless step 1 finds an exception.
- `Target has insufficient size because it is partially obscured (smallest space is Wpx by Hpx...)`
  — violation: another element covers part of it; `W` and `H` are the measured uncovered area, quote
  them in the issue after step 2 confirms the cover is not a dismissible overlay.
- `Target has insufficient space to its closest neighbors. Safe clickable space has a diameter of
Npx instead of at least 24px.` — violation from `target-offset`: `N` is the gap figure for step 3.
- `Element with negative tabindex has insufficient size (...). Is this a target?` — incomplete: a
  roving-tabindex item. Step 2 answers the question; for tabs, menu items and toolbar buttons the
  answer is yes.
- `Element with negative tabindex has insufficient space to its closest neighbors (...). Is this a
target?` — incomplete, same question, spacing branch: answer it, then step 3.
- `Target has insufficient size because it is partially obscured by a neighbor with negative
tabindex (...). Is the neighbor a target?` and `Target has insufficient space to its closest
neighbors (...). Is the neighbor a target?` — incomplete: the _neighbour_ is the open question;
  click it or read its handlers in step 2.
- `Element size could not be accurately determined due to overflow content` and `Could not get the
target size because there are too many overlapping elements` — incomplete: axe gave up on the
  geometry; measure it with the step 2 helpers.

The rule only matches elements that pass every one of axe's `widget-not-inline` tests: the role type
is `widget`, the element is not an `area`, not in the SVG namespace, is focusable, is not a
`tabindex="-1"` widget nested inside a tabbable widget, and is not "in a text block". That last test
is broad: axe walks up to the closest block-level ancestor and skips the target when **any**
non-widget text is left there, so a row of six icon links inside an `<li>` that also holds one word
of text is never checked. It skips that test only when the target itself is `display: block`,
`flex`, `grid`, `inline-block`, `list-item` or a `table-*` value.

Settles: its violations (one on a native control marked `userAgentDefault: true` by `targets.js`
first gets step 1's author-CSS check) and its passes on rectangular targets outside a text-bearing
block while `clickableNotFocusable` is empty. Leaves open: every incomplete above, each with its
`target` selector in the axe JSON; everything the matcher never reaches (`area`, anything in the SVG
namespace, non-focusable click handlers, every `clickableNotFocusable` entry, elements whose role
type is not `widget`, `tabindex="-1"` items inside a tabbable widget, and every target in a block
that carries non-widget text); the touch layout and every opened state unless the script ran there;
rounded corners and `clip-path` (it measures the box); the equivalent and essential exceptions.

## Manual procedure

Work in CSS pixels at `set viewport 1280 900` first, then at `set device "iPhone 16"`. The `recon`
run of `targets.js` covers the default state at 1280; the touch layout and every opened state get
their own run. The probe prints `w` and `h` rounded and decides `passes24` on the unrounded box, so
a printed `24` with `passes24: false` is a fractional box below 24. Three more probe contracts
matter here: it drops disabled controls, and it reaches a `tabindex="-1"` element only when one of
its role selectors matches it (`button`, `link`, `checkbox`, `radio`, `switch`, `tab`, `menuitem`,
`option`, `slider`); for a checkbox or radio it takes the larger of the input box and its first
associated `<label>`, so a 13 px checkbox with a real label is scored on the label; and
`counts.failing24` has already dropped the `inline` and `userAgentDefault` entries, which makes it
the candidate count, not the fail count.

Confirm geometry by hand with this helper, which probes the corners of the 24×24 square centred on
the target, inset half a pixel so a border does not decide it (`scrollintoview "<selector>"` first,
or `elementFromPoint` returns null; the body stays inside the arrow function so that re-running it
on the same page does not redeclare `el`):

```bash
agent-browser eval --stdin <<'EOF'
(() => {
  const el = document.querySelector('<selector>'), r = el.getBoundingClientRect()
  const cx = r.left + r.width / 2, cy = r.top + r.height / 2, d = 11.5
  const own = (x, y) => { const t = document.elementFromPoint(x, y)
    return !!t && (t === el || el.contains(t)) }
  const sq = [[-d, -d], [d, -d], [-d, d], [d, d]].every(([a, b]) => own(cx + a, cy + b))
  return { w: r.width, h: r.height, radius: getComputedStyle(el).borderRadius,
    centre: own(cx, cy), fits24: r.width >= 24 && r.height >= 24 && sq }
})()
EOF
```

The square does not have to be centred. W3C: "it must be conceptually possible to draw a solid 24 by
24 CSS pixel square, aligned to the horizontal and vertical axis such that the square is completely
within the target (does not extend outside the target's area)", and "The 24 by 24px square has to be
aligned with the page, although the target itself could be skewed" (Figure 2). When the first helper
returns `fits24: false` on a box of 24 or more, scan for an off-centre square with this one before
recording the target as undersized. Run it only on a box under about 120 px in each dimension: a
larger box that fails at its centre is covered by something, not clipped.

```bash
agent-browser eval --stdin <<'EOF'
(() => {
  const el = document.querySelector('<selector>'), r = el.getBoundingClientRect()
  const own = (x, y) => { const t = document.elementFromPoint(x, y)
    return !!t && (t === el || el.contains(t)) }
  const fitsAt = (x, y) => [[0.5, 0.5], [23.5, 0.5], [0.5, 23.5], [23.5, 23.5], [12, 12]]
    .every(([a, b]) => own(x + a, y + b))
  if (r.width < 24 || r.height < 24) return { w: r.width, h: r.height, fits: false, why: 'box' }
  for (let y = r.top; y <= r.bottom - 24; y += 2) {
    for (let x = r.left; x <= r.right - 24; x += 2) {
      if (fitsAt(x, y)) return { w: r.width, h: r.height, fits: true,
        at: { dx: Math.round(x - r.left), dy: Math.round(y - r.top) } }
    }
  }
  return { w: r.width, h: r.height, fits: false, why: 'shape' }
})()
EOF
```

`fits: true` with an `at` offset: the target meets the size requirement, record the offset and stop.
`why: 'shape'`: no axis-aligned 24×24 square fits inside the shape, so the target is undersized and
goes to the spacing check. `why: 'box'`: the bounding box itself is below 24 in one dimension.

1. Classify the probe output at 1280: run `targets.js` (or read `recon`) and take every entry with
   `passes24: false`. `inline: true`: confirm it is in a sentence (`links.js` `context: 'sentence'`,
   or `get text` of the parent reads as prose around it); a row of icons that the heuristic caught
   inside a `p` or `li` loses the flag. `userAgentDefault: true` is only `appearance` other than
   `none`, plus no inline `style` on a `button`, so a class-styled control keeps it: run
   `get styles "<selector>"` (every computed property; grep `width`, `height`, `padding-`,
   `font-size`, `transform`, `scale`) and let an author value on any of them (a checkbox scaled to
   13 px, a `select` 20 px high) lose the flag. Every other entry is a candidate, as is each
   `clickableNotFocusable` entry from `focusables.js` whose `get box "<selector>"` is below 24 in
   either dimension, and every entry of 24 or more whose `nearest.distance` is 0 and whose
   `get styles` shows a `border-radius` or `clip-path`. Then collect the targets the probe's
   selector list never sees:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const probed = 'a[href], button, input:not([type="hidden"]), select, textarea, summary,' +
       ' [role="button"], [role="link"], [role="checkbox"], [role="radio"], [role="switch"],' +
       ' [role="tab"], [role="menuitem"], [role="option"], [role="slider"],' +
       ' [tabindex]:not([tabindex="-1"]), [onclick]'
     const extra = '[tabindex="-1"], [role="treeitem"], [role="gridcell"],' +
       ' [role="menuitemcheckbox"], [role="menuitemradio"], [role="spinbutton"], [role="combobox"]'
     return [...document.querySelectorAll(extra)].filter((el) => !el.matches(probed)).map((el) => {
       const r = el.getBoundingClientRect()
       return { selector: el.localName + (el.id ? '#' + el.id : ''),
         role: el.getAttribute('role'), tabindex: el.tabIndex,
         w: Math.round(r.width), h: Math.round(r.height),
         text: (el.textContent || '').replace(/\s+/g, ' ').trim().slice(0, 30) }
     }).filter((t) => t.w > 0 && t.h > 0 && (t.w < 24 || t.h < 24))
   })()
   EOF
   ```

   `probed` is `targets.js`'s own selector, so every entry returned is an element the probe never
   measured. Decide for each whether a pointer activates it — `click` it, or look for a handler on
   the composite's container — and treat every yes as a target, which is the same question axe's
   "Is this a target?" incomplete asks. An `area` of an image map has no layout box, so read its
   region instead — `get attr "<area selector>" shape` and
   `get attr "<area selector>" coords`, then scale the numbers by the image's rendered width over
   its `naturalWidth` before comparing them to 24. A page that styles its own scrollbar
   (`::-webkit-scrollbar` rules, or `scrollbar-width` other than `auto` in `get styles` on the
   scrolling element) loses the User Agent Control exception for it: the scrollbar then needs its
   own clear 24 px circle against the links beside it (Figure 11). Done when each `passes24: false`
   entry is inline, user-agent, or a candidate with `w`, `h` and `nearest`, and every
   roving-tabindex item, `area` and author-styled scrollbar carries a target/not-a-target verdict.

2. Measure each candidate and each axe incomplete target with the helpers. `fits24: true`: a solid
   24×24 square sits inside the target, so it passes on size whatever its `radius`. `fits24: false`
   on a box of 24 or more: rounded corners or `clip-path` cut the square away (Figure 3) — run the
   off-centre scan, and only `why: 'shape'` makes the target undersized. `centre` false: something
   covers the middle; read `focusables.js` `obscuredBy` for that selector. Content shown by an
   interaction or a script (a combobox list, a modal, a cookie banner, an inactivity survey dialog)
   puts what it covers out of scope "while they are obscured": dismiss it and measure again. Another
   target covering it: the "overlapping area should not be included", so measure the uncovered part
   (axe's `partially obscured` message already prints it as `smallest space is Wpx by Hpx`), unless
   both "perform the same action or open the same page", in which case the full box counts. A small
   control over or inside a large target (a magnifier on a product image, a × inside a chip) needs
   24×24 of its own: at 24×24 it passes even though it clips the large target, and any smaller its
   circle intersects the large target and it fails (Figure 9); the probe skips DOM-nested pairs, so
   this pair is always measured here. For an axe incomplete that asks "Is the neighbour a target?",
   `click` the neighbour or check it for a handler and a widget role; a decorative overlay is not a
   target and the incomplete resolves to a pass. Done when every candidate has a size verdict and an
   overlap verdict.

3. Check spacing for every candidate still undersized, following the test procedure of
   [C42](https://www.w3.org/WAI/WCAG22/Techniques/css/C42), which applies "For each undersized
   target that has no sufficiently large equivalent, that isn't in a sentence or otherwise
   constrained by the line-height of non-target text, that has had its size modified by the author,
   and whose presentation isn't essential": (1) "Draw a 24px diameter circle centered on the
   target's bounding box", (2) "Check that the circle from #1 does not intersect any other target",
   (3) "Check that the circle from #1 does not intersect any other undersized target's circle".
   C42's Expected Results are that "#2 and #3 are true", so both must hold: a target that clears
   its large neighbours can still fail on another undersized target's circle, and the reverse.
   `passes24` already ran both tests; verify a fail with `get box "<selector>"` on the
   target and on `nearest.selector`: the target's centre must lie at least 12 px from the nearest
   point of the neighbour's box, and at least 24 px from the centre of a neighbour that is itself
   undersized. Against a large neighbour this means a gap of at least 12 px minus half the
   undersized target's width (horizontally) or height (vertically) — 4 px for a 16 px target, which
   is exactly W3C's fix in Figure 10. Match each row against the worked figures: 24×24 icons pass
   with no gap; 20×20 icons with a 4 px gap pass; 20×20 icons with no gap fail (Figure 5); a row of
   16 px high buttons with nothing above or below passes (Figure 6); two rows of 16 px buttons 1 px
   apart fail (Figure 7); 24 px high menu items pass and 18 px high ones fail (Figure 8); a 16×16
   control abutting a large target fails (Figure 10). Whole rows fail together — report them as one
   defect. Done when every undersized candidate has `pass (spacing)` or a measured fail with its
   neighbour selector and gap.

4. Repeat in every state that adds or moves targets. In each recorded state (open menu, dialog,
   disclosure, error state) and after `hover "<selector>"` on rows or cards that reveal action
   icons, run `targets.js` again and do steps 1 to 3 on the new entries; an overlay's own controls
   are in scope even though what they cover is not. Wait out an inactivity dialog where the sample
   has one and measure its controls too. Then `set device "iPhone 16"`, `reload`,
   `wait --load networkidle`, and repeat the default state and the states; the hamburger menu, a
   condensed toolbar and stacked footer icons are the usual touch-only fails, and a fail in either
   layout is a fail. Return with `set viewport 1280 900`. Done when each state and layout has a
   probe run and a candidate list.

5. Excuse what the criterion excuses. For each remaining fail: Equivalent: search `links.js` for
   another link with the same `href` and `snapshot -i` for a control with the same function; when
   that control passes (its own `passes24: true` after steps 1 to 3), record `pass (equivalent)`
   with both selectors. Essential: record the reason (map pin, dense chart point, legal paper-form
   replica) and, when it is arguable, queue it for the human; note whether an alternative route to
   the same function exists, which is what W3C "strongly encourage[s]". A `role` of `slider`, a
   colour picker showing a gradient and an editable area are each one target (Note 1): measure the
   whole track, the whole gradient and the whole field, never the thumb, the pixel or the caret.
   Done when every fail is filed, excused with a reason, or queued.

6. Capture evidence in the layout where it fails: `highlight "<selector>"` then `screenshot <path>`
   for a row, `screenshot "<selector>" <path>` for a lone target. Done when every fail has an image
   and its measured size and gap.

## Deciding

- Fail (certainty ≥ 90): a `target-size` violation on a target that steps 1 and 5 left without an
  exception (100); a candidate whose unrounded `w` or `h` is below 24 and whose centre lies within
  12 px of another target's box (95); undersized menu items, tabs, pagination or toolbar buttons
  whose 24 px circle reaches the next one's box — 18 px items stacked, 20 px icons with no gap (95);
  an undersized target abutting or overlapping a larger target with a different action, short of the
  gap of 12 px minus half its own width or height (95); a control smaller than 24×24 placed inside
  or over a larger target with a different action (90); a centre-to-centre distance below 24 px
  between two undersized targets (90).
- Fail (70–89): a box of 24 or more whose rounded corners or `clip-path` leave the off-centre scan
  at `why: 'shape'`, with a neighbour inside the circle (85); a roving-tabindex item of a menu,
  tab list or toolbar that axe returned as an incomplete, measured below 24 with a neighbour inside
  its circle (85); an author-styled checkbox or radio whose box stays below 24 because no `<label>`
  is associated with it, with a neighbour inside its circle (85); a target inside a text-bearing
  block that axe skipped, measured below 24 with a neighbour inside its circle and not in a sentence
  (85); a native control the author resized below 24 with a touching neighbour (80); overlapping
  targets whose uncovered part is below 24 (80); an author-styled scrollbar with no clearance to the
  link or control beside it (80); a fail that appears only at iPhone 16 inside a third-party widget
  (80); a `clickableNotFocusable` element below 24 with a neighbour inside its circle (75); an image
  map `area` whose computed region is below 24 in either dimension with an adjacent area inside its
  circle (75).
- Needs confirmation (50–69): a nearby control that may be the equivalent (an icon link and a text
  link, a × and a "Cancel") (60): ask whether both do the same thing; map pins, chart points or a
  paper-form replica claimed essential (55): ask whether the position is the information and whether
  a larger alternative exists; an axe incomplete on a `tabindex="-1"` element with no visible click
  behaviour (55): ask whether it is a target; an axe incomplete naming the _neighbour_ as the open
  question, where the neighbour is an unnamed overlay (55): ask whether it is clickable; an axe
  incomplete of `too many overlapping elements` on a canvas or map widget both helpers could not
  measure (50): ask for the widget's documented hit sizes.
- Pass: every target in every recorded state and both layouts either fits a 24×24 square anywhere
  inside its area, or is undersized with a 24 px circle that clears every other target and every
  undersized target's circle, or is a recorded exception (inline, unmodified user-agent control,
  passing equivalent, essential with its reason).
- Not present: only a sample state with no pointer target at all, in every state and layout.
- False positives to avoid: links in sentences and running text; unstyled native controls,
  scrollbars and the date-picker popup; a 20 px icon with a 4 px gap on each side passes; a 16 px
  high row with nothing above or below passes; W3C is explicit that isolation is enough — "It is
  still possible to have very small, and difficult to activate, targets and meet the requirements of
  this Success Criterion, provided that the targets don't have any adjacent targets that are too
  close"; a target of 24×24 or more needs no spacing; a 24×24 target that clips a larger one passes
  (Figure 9); overlapping targets that "perform the same action or open the same page" are measured
  whole; targets under a cookie banner, modal, combobox list or inactivity dialog are out of scope
  while covered; a slider, a colour-picker gradient and a text field are each one target (Note 1),
  so the thumb and the caret are not measured; disabled controls are dropped by `targets.js` and are
  not targets; an axe pass on a target sitting in a block that carries non-widget text is not a
  result, because axe skipped it; zoomed viewports change nothing, the measure is CSS pixels; 44×44
  is 2.5.5 at AAA.

## Reporting

- File under: 2.5.8. A small target that is also too faint goes to 1.4.11 as a second issue; one
  with no accessible name to 4.1.2; a 44×44 shortfall to 2.5.5 when the target level is AAA. One
  issue per kind of target (all pagination buttons, the header icon row), naming every sample, state
  and layout.
- Title patterns: "Pagination buttons are too small and touch each other", "Mobile menu items are
  only 18 px high", "Close button of the cookie dialog is 16 px", "Remove icon sits on the chip with
  no space around it", "Custom scrollbar touches the links beside it"
- Severity: High when the crowded undersized target is a step in a task (submit, close, add to
  basket, the main navigation on touch) and no equivalent exists; Medium when it is secondary
  navigation or repeats across the product (footer icon rows, pagination, table row actions); Low
  when a passing equivalent sits nearby or one isolated pair misses narrowly.
- Type: Design by default: size, padding and gaps were chosen. Technical when a rule or markup
  causes it: no `min-width`/`min-height` on an icon button, a `label` not associated with its
  checkbox so only the 13 px box is clickable, `border-radius` clipping a 24 px box, a roving
  `tabindex="-1"` item styled smaller than its tabbable siblings. Content when an editor placed the
  icons or image links in a rich-text field.
- Evidence: an element screenshot at 1:1, or `highlight "<selector>"` before a page screenshot when
  a row is the subject, in the layout where it fails, with the numbers stated ("20 × 20 px, 0 px gap
  to the next button; needs 24 × 24 or a clear 24 px circle"), naming the neighbour that the circle
  reaches; a page screenshot at iPhone 16 for touch-only fails.
- Recommendation: give the target `min-width: 24px; min-height: 24px`, or keep the icon and add
  padding or margin until a 24 px circle clears the neighbours
  ([C42](https://www.w3.org/WAI/WCAG22/Techniques/css/C42)); associate labels with checkboxes so the
  label is part of the target. `.toolbar button { min-width: 24px; min-height: 24px; padding: 4px }`
  turns a 16 px icon into a 24 px target. Where the links themselves cannot grow, C42 puts the
  minimum on the container instead, so that "The links' 24 CSS pixel diameter circles will each be
  completely within their containing list items, so they won't intersect each other":

  ```css
  ol {
    display: flex;
    flex-wrap: wrap;
    list-style: none;
  }
  li {
    margin: 3px;
    min-height: 24px;
    min-width: 24px;
    text-align: center;
  }
  ```

  Where the visible icon has to stay small, enlarge the active area without enlarging the icon:

  ```css
  .icon-btn {
    position: relative;
  }
  .icon-btn::after {
    content: '';
    position: absolute;
    top: 50%;
    left: 50%;
    width: 24px;
    height: 24px;
    transform: translate(-50%, -50%);
  }
  ```

  Where Essential genuinely applies (map pins, a dense chart), keep the dense targets and add the
  equivalent route W3C asks for: a list of the same places or data points as full-size links below
  the visual.
