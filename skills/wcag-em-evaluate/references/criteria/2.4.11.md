# 2.4.11 Focus Not Obscured (Minimum)

Level AA · WCAG 2.2+ · Guideline 2.4 Navigable · Group: `keyboard`

Sources: [Understanding][understanding] ·
[Spec](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#focus-not-obscured-minimum) ·
[Plain English][plain] · ACT: none mapped to this criterion.

[understanding]: https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html
[plain]: https://aaardvarkaccessibility.com/wcag-plain-english/2-4-11-focus-not-obscured-minimum/

## Requirement

> When a user interface component receives keyboard focus, the component is not entirely hidden
> due to author-created content.
>
> Note 1:
> Where content in a configurable interface can be repositioned by the user, then only the initial
> positions of user-movable content are considered for testing and conformance of this success
> criterion.
>
> Note 2:
> Content opened by the _user_ may obscure the component receiving focus. If the user can reveal
> the focused component without advancing the keyboard focus, the component with focus is not
> considered visually hidden due to author-created content.

Terms (WCAG 2.2 glossary) — **user interface components**, verbatim; Note 1 decides what has to
stay visible when one control is built from several elements:

> a part of the content that is perceived by users as a single control for a distinct function
>
> Note 1: Multiple user interface components may be implemented as a single programmatic element.
> "Components" here is not tied to programming techniques, but rather to what the user perceives as
> separate controls.
>
> Note 2: User interface components include form elements and links as well as components generated
> by scripts.

The Understanding note that fixes what "the component" is measured on:

> This criterion evaluates the focused component, rather than the focus indicator. The component
> itself does not include the focus indicator when checking that "the component is not entirely
> hidden" - unless the focus indicator is inside the component, or focus is indicated by a change to
> the component itself.

and: "if the focus indicator is fully obscured, it would likely fail 2.4.7 Focus Visible". So an
external focus ring showing above a layer does not rescue a component whose own box is fully
covered; a ring drawn inside the component, or a focus style that changes the component itself
(`focusables.js` `focusStyleChanged` with a `background` or `border` change), is part of it.

## In plain terms

When a keyboard user tabs to a link, button or field, at least part of that control has to be on
screen: nothing the author laid over the page (a sticky header or footer, a cookie banner, a chat
widget, a non-modal dialog) may cover it completely. Partial cover is allowed at this level, and
the criterion judges the component, not its focus indicator; "for best visibility, none of the
component receiving focus should be obscured", which is the AAA criterion 2.4.12. Sighted keyboard,
switch, speech-input, sip-and-puff, onscreen-keyboard and scanning users otherwise lose the
interaction point and "may even think the system has become unresponsive". Magnification users see
a smaller portion of the page, and users with attention, short-term-memory or executive-function
limitations depend on being able to find the focus again.

## Applies when

- Present: the sample has focusable components (`focusables.js` returns a non-empty `order`) and,
  in any state, content that can lie over them: a `position: fixed` or `sticky` header, footer,
  banner, toolbar, toast, chat or feedback widget or non-modal dialog; an absolutely positioned
  overlay with a stacking context of its own; a `[popover]` or a `<dialog>` opened with `show()`
  (step 1 lists them). `order` entries with `obscured: true` are the first candidates.
- Not present: no fixed, sticky, popover or overlaying content in any state. Record "no sticky or
  overlaying content".
- Exceptions:
  - Note 1, user-movable content: a panel the user can drag, resize or dock is judged in its
    initial position only — "the author is only responsible for ensuring that the movable content
    in its initial position does not obscure the item receiving focus". The position after `reload`
    is that initial position; a position the evaluator dragged it to is out of scope.
  - Note 2, user-opened content: "If the user can bring the item with focus into view using a
    method without having to navigate back to the user-opened content to dismiss it, this criterion
    would be passed." The methods the Understanding names are "using the Escape key to dismiss the
    obscuring content; using keys to scroll the content in the viewport to reveal the item with
    focus; issuing a key to move between overlays".
  - Note 2 reaches only content "the user actively discloses". "Content pre-positioned by the author
    (such as a sticky footer), or content that appears without direct user initiation, such as
    system warnings, must not prevent the item receiving focus from being immediately visible in the
    viewport."
  - Non-persistent disclosures — "menu items, select element items, combobox lists (and other
    dropdown items), date picker calendars, and tooltips" — "do not fail this SC since they do not
    obscure the item with focus", because they close. They are back in scope when the author "allows
    such components to persist after the user has 1) activated one of the opened items or 2) moved
    the focus away from the triggering item and the additional content".
  - Modal dialogs: "A properly constructed modal dialog will always pass this SC" — it takes focus
    on appearance, keeps it and prevents interaction outside itself until dismissed. But "a
    dialog-like overlay that does not take focus on appearance and does not either constrain
    interaction to the overlay or dismiss itself on loss of focus (thus allowing focus to exit into
    the content behind it) will be at risk of failing this SC, where it is positioned such that it
    can obscure other focusable items."
  - Layers that displace or reflow content instead of overlapping it (an accordion pushing content
    down, a side panel that narrows the main column) cannot obscure anything: they are out of scope
    even when the user opened them.

## axe-core

No axe-core rule is tagged with this criterion and no ACT rule is mapped to it; everything below is
manual.

## Manual procedure

1. Inventory the layers and the probe's candidates. From the `focusables.js` run of this pass keep
   every `order` entry with `obscured: true`, with its `obscuredBy`, `role`, `name` and `box`; the
   probe tests one centred point, so it finds large overlays and misses sticky edges. Fix the
   baseline with `set viewport 1280 900`, then list the layers:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const isModal = (n) => {
       try { return n.matches(':modal') } catch (e) { return false }
     }
     const stacked = [...document.querySelectorAll('body *')].filter((n) => {
       const s = getComputedStyle(n)
       const over = s.position === 'fixed' || s.position === 'sticky' ||
         (s.position === 'absolute' && s.zIndex !== 'auto')
       return over && s.visibility !== 'hidden' && n.getBoundingClientRect().height > 0
     })
     const opened = [...document.querySelectorAll('[popover], dialog[open]')]
     const all = [...new Set([...stacked, ...opened])]
     return { total: all.length, layers: all.slice(0, 30).map((n) => {
       const r = n.getBoundingClientRect(), s = getComputedStyle(n)
       return { selector: n.localName + (n.id ? '#' + n.id : ''), position: s.position,
         y: Math.round(r.top), h: Math.round(r.height), z: s.zIndex, opacity: s.opacity,
         background: s.backgroundColor, role: n.getAttribute('role'),
         modal: isModal(n) || n.getAttribute('aria-modal') === 'true',
         popover: n.hasAttribute('popover') }
     }) }
   })()
   EOF
   ```

   For each layer record the viewport band it covers (`y`, `h`), whether it is opaque (`opacity`
   "1" and a `background` without an alpha below 1) and its origin: author-positioned (present at
   load or appearing without user action, such as a toast or system warning), user-opened
   (`recon/<sample>-states.md` names the control that opens it), user-movable (it has a drag, dock
   or resize handle) or modal (`modal: true`). Done when the findings file has one line per layer
   with band, stacking (`position`, `z`), opacity and origin, one line per probe candidate, and
   `total` is not larger than the number of listed layers (raise the `slice` and rerun if it is).

2. Save the coverage script once, then walk the page with real Tab presses and run it at every
   stop. [F110](https://www.w3.org/WAI/WCAG22/Techniques/failures/F110) sets the walk: "Tab through
   the links and controls on the page. Both progressing down through the page, and back up: check
   whether the focused element is completely obscured by other content."
   [C43](https://www.w3.org/WAI/WCAG22/Techniques/css/C43) sets the two checks per stop: #1 "the
   user interface component is not entirely hidden when it receives keyboard focus" (this
   criterion), #2 "no part of the user interface component is hidden" (2.4.12 at AAA). The script
   samples an 8 × 8 grid over the on-screen part of the focused component and reports what
   `elementFromPoint` returns there:

   ```bash
   cat > .notes/audit/recon/2.4.11-cover.js <<'EOF'
   (() => {
     const el = document.activeElement
     if (!el || el === document.body) return { active: 'body' }
     const desc = (n) => n.localName + (n.id ? '#' + n.id : '') +
       (n.getAttribute('class') ? '.' + n.getAttribute('class').trim().split(/\s+/)[0] : '')
     const r = el.getBoundingClientRect(), covers = new Map()
     const x0 = Math.max(r.left, 0), x1 = Math.min(r.right, innerWidth)
     const y0 = Math.max(r.top, 0), y1 = Math.min(r.bottom, innerHeight)
     const inViewport = x1 > x0 && y1 > y0; let points = 0, seen = 0
     if (inViewport) for (let i = 0; i < 8; i++) for (let j = 0; j < 8; j++, points++) {
       const top = document.elementFromPoint(x0 + (x1 - x0) * (i + 0.5) / 8,
         y0 + (y1 - y0) * (j + 0.5) / 8)
       if (!top || top === el || el.contains(top) || top.contains(el)) { seen++; continue }
       const s = getComputedStyle(top)
       covers.set(desc(top), { position: s.position, opacity: s.opacity,
         background: s.backgroundColor, backdropFilter: s.backdropFilter })
     }
     let clippedBy = null
     for (let n = el.parentElement; n && !clippedBy; n = n.parentElement) {
       const c = n.getBoundingClientRect()
       if (getComputedStyle(n).overflow !== 'visible' &&
         (r.right <= c.left || r.left >= c.right || r.bottom <= c.top || r.top >= c.bottom))
         clippedBy = desc(n)
     }
     return { active: desc(el), inViewport, clippedBy,
       visibleFraction: points ? +(seen / points).toFixed(2) : 0,
       coveredBy: [...covers].map(([selector, s]) => ({ selector, ...s })) }
   })()
   EOF
   agent-browser reload
   agent-browser record start .notes/audit/evidence/<sample>-2.4.11-walk.webm
   agent-browser press Tab
   agent-browser eval --stdin < .notes/audit/recon/2.4.11-cover.js
   ```

   Repeat the last two commands to the end of the tab ring, numbering the stops as you go (a
   finding reads "stop 37 of 61, the newsletter field"); Tab lands each stop at the bottom edge,
   under a sticky footer. The ring ends when `active` reads `body` or repeats the first stop. Then
   `reload`, `press End` and repeat with `press Shift+Tab` upwards (stops land at the top edge,
   under a sticky header); `record stop`. Per result: `1` with `clippedBy: null` is fine; between 0
   and 1 is partly covered, a pass here (note it for 2.4.12 when AAA is in scope); `0` with
   `inViewport: true` goes to step 3; `clippedBy` set, or `inViewport: false`, means the page clips
   the component or leaves it off screen instead of covering it with content (an off-canvas slide,
   a skip link at `left: -9999px`) — a clipped component keeps `visibleFraction: 1`, because the
   sampled points fall through to an ancestor: note it for 2.4.7 and 2.4.3, not here. Done when
   both walks are complete and every stop below 1 and every stop with `clippedBy` has a line.

3. Qualify every stop with `visibleFraction: 0`. Opaque: every `coveredBy` entry has `opacity` "1"
   and a `background` without an alpha below 1; a `backdropFilter` blur over a translucent
   background is not opaque. Then `highlight "<coveredBy selector>"` and
   `screenshot .notes/audit/evidence/<sample>-2.4.11-<slug>.png`: the box marks the layer, and
   entirely hidden holds when the image shows no trace of the component (a `highlight ":focus"`
   box paints under the layer). A `coveredBy` entry with `position` `static` or `relative` that is
   the component's own visual form (a `label` styled as a checkbox over a visually-hidden `input`)
   is the control the user perceives (glossary Note 1): record "visible as <selector>", pass it.
   Check displacement next: if opening the layer moved the stop's `box.y` or narrowed the main
   column so nothing overlaps, it displaces or reflows content and the stop passes with no further
   test. Otherwise branch on the origin from step 1:

   - Author-positioned (sticky header or footer, pre-positioned banner) — the stop fails
     ([F110](https://www.w3.org/WAI/WCAG22/Techniques/failures/F110)). No reveal test: Note 2 does
     not reach content the user did not disclose.
   - Toast, notification or system warning that appeared without user action — one escape, from the
     Understanding's third example, and it needs both halves. Focus moved into it on appearance: as
     soon as it appears, the cover script reports `active` inside the notification. It disappears on
     loss of focus: `press Tab` off it, rerun the step 1 listing, and the layer is gone. Both true
     is a pass; either one missing and the stop fails.
   - Dialog-like overlay (`role="dialog"`, `[popover]`, `dialog[open]` with `modal: false`) — it
     passes only through one of the three routes in the Understanding: it took focus on appearance;
     or it constrains interaction (from a stop inside it, `press Tab` around its whole ring and
     `active` never names an element outside it); or it dismisses itself on loss of focus (`press
Tab` until `active` is outside it, rerun the cover script, and the layer is gone from
     `coveredBy`). None of the three, and the stop fails. A dialog with `modal: true` that still let
     Tab reach a covered stop behind it is not modal for the keyboard: the stop fails here and the
     leak is noted for 2.4.3.
   - Non-persistent disclosure (menu, select list, combobox list, date picker, tooltip) — open it,
     activate one of its items, and separately `press Tab` until `active` is neither the trigger nor
     inside the disclosure; rerun the cover script each time. Still listed in `coveredBy` over the
     new stop means it persists against convention: the stop fails.
   - User-opened persistent layer (chat panel, feedback bar, side navigation) — the reveal test of
     Note 2, with focus left on the covered component throughout (a key that first needs Shift+Tab
     back into the panel is not a reveal): `press Escape`, rerun the script; then `press
ArrowDown` (`press ArrowUp` for a layer at the top, `press Space` on a link; on a text field
     only Escape counts), rerun; then `press F6` where a second overlay is stacked over the first,
     rerun. `active` unchanged and `visibleFraction` above 0 is a pass for the stop (record the
     key); `active` changed means the key moved focus, not a reveal.
   - User-movable panel — judged where it sits after `reload` (Note 1). Covering there is a fail;
     covering only after the evaluator dragged it is out of scope.

   Done when every covered stop has opaque yes/no, origin, the branch's outcome and, for
   user-opened layers, the reveal key or "none".

4. States and the 200 % variation. Repeat steps 1 to 3 in every state of
   `recon/<sample>-states.md` that adds or removes a layer: the cookie banner shown and then
   dismissed, a chat or feedback panel opened, a toast or sticky error summary displayed, a menu or
   date picker left open, a sub-navigation that becomes sticky after `scroll down 600`. Then
   `set viewport 640 900`, `reload`, rerun the step 1 listing, and where any layer is taller than at
   1280 walk the ring again with step 2 (a fixed layer rides the viewport, so its band cannot be
   matched against the probe's page-relative `box.y`); `set viewport 1280 900` afterwards. Done when
   each state and the 640 run have their own lines in the findings file.

5. Cross-check the focus indicator, which this criterion does not measure but points at. A stop with
   `visibleFraction` above 0 whose indicator is fully under the layer goes to 2.4.7 with the
   screenshot. A stop covered by a translucent, blurred or dimming overlay is a pass here, and the
   indicator "must be evaluated against the contrast requirements of 1.4.11 while its appearance is
   affected by the overlays": run `nontext-contrast.js` with the overlay in place and hand
   `focusIndicators[].ratio` and `passes3` for that selector to the `visual` pass. Done when every
   such stop is recorded under 2.4.7 or 1.4.11 with its selector, and none of them is filed here.

`snapshot` shows nothing about layering; coverage comes from `elementFromPoint` and the screenshot.
Focus inside a cross-origin `iframe` that a layer covers only partly is `cannot-tell` (the script
sees the frame box, not the control inside); a frame covered entirely fails like any component.

## Deciding

- Fail (certainty ≥ 90): after a real Tab or Shift+Tab, `visibleFraction: 0` with
  `inViewport: true`, every `coveredBy` entry opaque, and the layer is an author-positioned sticky
  header or footer ([F110](https://www.w3.org/WAI/WCAG22/Techniques/failures/F110)) — 95; the
  same under a cookie banner or other dialog-like overlay that did not take focus on appearance,
  does not keep Tab inside it and does not close when focus leaves it — 95; the same under a toast,
  notification or system warning that appeared without user action and neither took focus nor
  closed on loss of focus — 92; the same under a user-opened layer where Escape, ArrowDown or
  ArrowUp, Space and F6, each pressed with focus left on the covered component, leave `active`
  unchanged and `visibleFraction: 0` — 90; the same under a user-movable panel in the position it
  has after `reload`, since Note 1 protects only later positions the user chose — 90.
- Fail (70–89): a menu, combobox list, date picker or tooltip still in `coveredBy` after its item
  was activated or after focus left both it and its trigger, fully covering the new stop — 85; a
  covered stop found only at `set viewport 640 900` because the layer grows there — 80; a
  user-opened layer whose only reveal key also moves focus (Escape closes the panel and sends focus
  to its trigger) — 80; `visibleFraction: 0` under a layer that is not fully opaque (an alpha just
  under 1, or an opaque image inside a transparent container) with no trace of the component in the
  screenshot — 75; a stop at `visibleFraction: 1` whose screenshot shows an opaque
  `pointer-events: none` layer over the component — 75; a stop at `visibleFraction: 0` whose
  screenshot shows only the focus ring above the layer, the ring being drawn outside the component
  — 75.
- Needs confirmation (50–69): a layer listed as user-opened that also opens on its own (a chat
  widget expanding after a delay) — 60: ask whether it opens unprompted in production; a covered
  stop under a toast that disappears on its own — 55: ask whether it is timed the same in
  production and whether it closes on loss of focus; a `visibleFraction: 0` stop whose screenshot
  shows a faint outline through a dimmed overlay — 55: ask a sighted human whether the control is
  discernible.
- Pass: every stop of the forward and backward walks, in every state and at 640, has
  `visibleFraction` above 0 or is visible as its own rendering (step 3). A covered stop also passes
  when the layer over it does one of the things the Understanding accepts: it displaces the content
  below it (an accordion) or reflows it into a narrower column; it took focus on appearance and
  keeps the tab ring inside itself until dismissed; it opened into an empty area of the page; it
  hides or collapses when focus leaves it, or on a dedicated key; it is a properly constructed modal
  dialog; or it is user-opened and Escape, a scroll key or F6 reveals the component without changing
  `active`. Scroll padding that keeps every stop in view shows up as `visibleFraction: 1` at every
  stop of both walks ([C43](https://www.w3.org/WAI/WCAG22/Techniques/css/C43)).
- Not present: no fixed, sticky, popover or overlaying content in any state.
- False positives to avoid: the probe's `obscured: true` on its own (one centre point after
  centring; the real walk decides); partial cover of any size (a 2 px sliver passes here; 2.4.12
  at AAA); a covered focus ring with the component visible (2.4.7); a focus style that changes the
  component itself, which keeps the component visible; translucent, blurred or dimming overlays the
  component stays discernible through (1.4.11, not here); a modal dialog covering the page while
  focus is inside it, including a full-width modal cookie dialog; a notification that took focus and
  disappears when it loses it; an accordion or side panel that displaces or reflows content instead
  of overlapping it; a dropdown, date picker or tooltip that closes when focus leaves it; a `label`
  or wrapper that is the control's own rendering; a component the page clips or leaves off screen
  rather than covers (a skip link at `left: -9999px`, `opacity: 0`, a slide in an `overflow`
  container): 2.4.7 and 2.4.3, not this.

## Reporting

- File under: 2.4.11 for a component entirely hidden by a layer lying over it. A covered focus
  indicator with the component visible goes to 2.4.7, as does a component the page clips or leaves
  off screen; indicator contrast through a translucent overlay to 1.4.11; a popup that cannot be
  dismissed to 1.4.13 (the covered control stays here); focus leaking out of a dialog to 2.4.3,
  with the covered stops here; partial cover to 2.4.12 only when AAA is in scope. One issue per
  layer (the sticky footer is one issue naming every covered stop), naming every sample it is on.
- Title patterns: "Sticky footer hides focused links at the bottom of the page", "Sticky header
  hides focused controls when tabbing backwards", "Cookie banner covers the focused controls
  behind it", "Chat panel covers focused content and Escape does not close it", "Menu stays open
  and hides the controls behind it", "Notification covers the focused control until it times out"
- Severity: High when the hidden controls belong to a task (form fields, submit, checkout, primary
  navigation) or the layer is site-wide (sticky header or footer, cookie banner on every page);
  Medium when a few controls in one state are hidden and a scroll key brings them back; Low when
  the hidden controls are secondary (footer links) on one sample.
- Type: Technical when the fix is scroll padding, closing on focus loss or making the dialog
  modal; Design when the layer's size or placement itself has to change at a breakpoint.
- Evidence: the screenshot of the Tab stop with `highlight` on the covering layer (the hidden
  component leaves no trace in the image), the recording of the walk into the covered stop and,
  for a user-opened layer, a second screenshot after the reveal key with `highlight ":focus"` — or
  the recording of the reveal attempt when no key works. Name the stop by its number and its
  accessible name so the developer can reproduce the walk.
- Recommendation: reserve the layer's height with
  [C43](https://www.w3.org/WAI/WCAG22/Techniques/css/C43), which pairs page padding with scroll
  padding so the focused control can scroll clear of the fixed banner:

  ```css
  :root {
    --banner-height: 400px;
    --breathing-room: 20px;
  }
  @media (min-width: 50rem) {
    html {
      padding-bottom: var(--banner-height);
      scroll-padding-bottom: calc(var(--banner-height) + var(--breathing-room));
    }
    .cookie-banner {
      position: fixed;
      inset: auto 0 0 0;
    }
  }
  ```

  Use `scroll-padding-top` with the header's height for a sticky header, and un-fix the banner
  below the breakpoint so the small-viewport page stays usable. Alternatives: make the banner a
  modal dialog (take focus on opening, keep Tab inside, restore focus on close); close a
  notification when focus leaves it. For a user-opened panel, let Escape close it without moving
  focus, open it beside the content so it displaces or reflows rather than covers, or keep the tab
  ring inside it until it is dismissed. Where partial cover remains, reduce its degree and
  frequency: the authors' target is no obscuring at all.

- Related: 2.4.7 Focus Visible (indicator covered), 1.4.11 Non-text Contrast (indicator seen
  through a dimming overlay), 1.4.13 Content on Hover or Focus (dismissing a popup), 2.4.3 Focus
  Order (focus leaking out of a dialog), 2.4.12 Focus Not Obscured (Enhanced) at AAA.
