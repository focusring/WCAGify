# 3.3.8 Accessible Authentication (Minimum)

Level AA · WCAG 2.2+ · Guideline 3.3 Input Assistance · Group: `forms`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html)
· [Spec](https://www.w3.org/TR/WCAG22/#accessible-authentication-minimum)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#accessible-authentication-minimum)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-3-8-accessible-authentication-minimum/)
· ACT: none mapped to this criterion

## Requirement

> A cognitive function test (such as remembering a password or solving a puzzle) is not required
> for any step in an authentication process unless that step provides at least one of the
> following:
>
> - Alternative: Another authentication method that does not rely on a cognitive function test.
> - Mechanism: A mechanism is available to assist the user in completing the cognitive function
>   test.
> - Object Recognition: The cognitive function test is to recognize objects.
> - Personal Content: The cognitive function test is to identify non-text content the user
>   provided to the website.
>
> Note 1: "Object recognition" and "Personal content" may be represented by images, video, or
> audio.
>
> Note 2: Examples of mechanisms that satisfy this criterion include:
>
> - support for password entry by password managers to reduce memory need, and
> - copy and paste to reduce the cognitive burden of re-typing.

The four exceptions are alternatives to one another: **one** of them on a step is enough for that
step, and each step of the process is judged on its own.

Terms (WCAG 2.2 glossary):

**cognitive function test**: "A task that requires the user to remember, manipulate, or transcribe
information. Examples include, but are not limited to:

- memorization, such as remembering a username, password, set of characters, images, or patterns.
  The common identifiers name, e-mail, and phone number are not considered cognitive function
  tests as they are personal to the user and consistent across websites;
- transcription, such as typing in characters;
- use of correct spelling;
- performance of calculations;
- solving of puzzles."

The list is open — "include, but are not limited to" — so remembering, manipulating or transcribing
is the test, and a task that fits none of the five bullets still counts when it does one of those
three. The middle clause is the one that saves ordinary forms: asking for a name, an e-mail address
or a phone number is never a cognitive function test.

**mechanism**: "process or technique for achieving a result". Note 1: "The mechanism may be
explicitly provided in the content, or may be relied upon to be provided by either the platform or
by user agents, including assistive technologies." Note 2: "The mechanism needs to meet all success
criteria for the conformance level claimed." Note 1 decides most login forms in this criterion: the
content does not have to ship a password manager, it only has to leave the platform's paste and the
user agent's autofill working. Note 2 means a mechanism that is itself unreachable — a "show
password" toggle with no accessible name, a paste button that traps focus — does not count.

**non-text content**: "any content that is not a sequence of characters that can be
programmatically determined or where the sequence is not expressing something in human language".
Note: "This includes ASCII art (which is a pattern of characters), emoticons, leetspeak (which uses
character substitution), and images representing text." A typed answer is a sequence of characters
in human language, so a security question or a memorable word is never Personal Content.

**processes**: "series of user actions where each action is required in order to complete an
activity". Glossary Example 2 is "An account registration page requires successful completion of a
Turing test before the registration form can be accessed." — a gate is part of a process, but that
particular example is account creation, which the Intent puts outside this criterion; the process
this criterion reads is the series of actions that gets an existing user into their account.

## In plain terms

Getting into an existing account must not be a memory, transcription or puzzle test: no recalling a
password from memory, no retyping a one-time code by hand, no solving something to prove you are
human. A username-and-password form passes as it stands when a password manager can fill it and the
user can paste into it, because the browser's own paste and autofill are the Mechanism. Otherwise
the step needs a second way in that carries no such test — a passkey, a login link by e-mail, a
third-party login, a push approval, a hardware key — or its test has to be recognising objects or
picking out non-text content the user supplied earlier. Every login step counts, including a second
factor and account recovery, and creating the account does not. People with limitations of memory,
reading, numbers or processing are the ones shut out: "People with cognitive issues relating to
memory, reading (for example, dyslexia), numbers (for example, dyscalculia), or perception-
processing limitations will be able to authenticate irrespective of the level of their cognitive
abilities."

## Applies when

- Present: a state of the sample is a step of authenticating an existing account — a login form, a
  verification-code or PIN entry, a pattern or memorable-word step, a security question, an "enter
  characters 2, 6 and last of your password" step, a CAPTCHA or puzzle sitting on any of those, a
  re-authentication before a sensitive action, and account recovery. Detect it from `forms.js`
  `fields[]`: any `type: "password"`; any `autocomplete` holding `current-password`, `username`,
  `one-time-code` or `webauthn`; any `name`, `visibleLabelText` or `placeholder` matching code,
  passcode, PIN, OTP, digit, verification, token or memorable. Detect challenges from
  `structure.js` `iframes[]` whose `src` or `title` names recaptcha, hcaptcha, turnstile, arkose,
  funcaptcha, geetest or captcha, from `images.js` `images[]` with "captcha" in `src`, `alt` or
  `nearbyText`, and from the text "I'm not a robot" in `agent-browser snapshot`.
- Two probe facts shape that detection, so read them before trusting a field list.
  `autocompleteCandidate` is `"current-password"` for **every** `type="password"` control, a
  "confirm new password" box included, so it never distinguishes a login from a registration form;
  and the probe's purpose table has no one-time-code entry, so `autocompleteCandidate` is never
  `"one-time-code"` — read the real `autocomplete` attribute and the label for a code field. The
  probe also masks secrets: a password field comes back as `value: "(set)"` or `""`, so read a
  pasted secret back with `agent-browser get value`, never from `fields[].value`.
- Present in all of a multi-step process: "If there is more than one step in the authentication
  process, such as with multi-factor authentication, all steps need to comply with this success
  criterion to pass. There needs to be a path through authentication that does not rely on
  cognitive function tests." Evaluate the password step, the second factor and any device prompt
  as separate steps with separate outcomes.
- Present in recovery: "Being able to recover or change the email and password is an important part
  of authentication. If the user is authenticating with alternative information in order to recover
  their account, there needs to be a method that is not a cognitive function test."
- Present even when the test is conditional: "Some CAPTCHAs and cognitive function tests used for
  authentication may only appear in certain situations, such as when ad blockers are present, or
  after repeated incorrect password entry. This criterion applies when these tests are used
  regardless of whether they are used every time or only triggered by specific scenarios." A
  challenge that only shows after a wrong password is in scope at full weight.
- Not present: no state of the sample asks the user to prove who they are. Record `not-present` and
  name the states checked. Account creation is out: "This success criterion is focused on
  authentication of existing users. It does not cover creation of a username or initiation of an
  account." A CAPTCHA guarding a contact, comment, newsletter or search form guards no account
  either — its missing text alternative is 1.1.1, not this criterion.
- Exceptions, any one of which carries the step:
  - **Alternative** — "Another authentication method that does not rely on a cognitive function
    test": a passkey or WebAuthn button, a login link by e-mail
    ([G218](https://www.w3.org/WAI/WCAG22/Techniques/general/G218)), a third-party login over
    OAuth, a QR code scanned on a device, a push approval, a hardware key. It must be free of a
    cognitive function test all the way to a logged-in account, and an audio CAPTCHA does not
    qualify: "Some CAPTCHA systems have an audio alternative of the visible text. If the user needs
    to transcribe this audio, it cannot be used to meet the Alternative exception."
  - **Mechanism** — fields a password manager can fill and that accept a paste
    ([H100](https://www.w3.org/WAI/WCAG22/Techniques/html/H100)). Note 2 of the criterion names
    exactly these two: "support for password entry by password managers" and "copy and paste".
  - **Object Recognition** — "The cognitive function test is to recognize objects", in "images,
    video, or audio". "An object in this context means the general English definition ('a material
    thing that can be seen and touched') and can include vehicles and animals. If the test goes
    beyond recognition (e.g. multiply the number cats by the number of dogs), that does not meet
    the exception."
  - **Personal Content** — "The cognitive function test is to identify non-text content the user
    provided to the website", such as picking out a picture uploaded at registration. "Text-based
    personal content does not qualify for this exception as it relies on recall (rather than
    recognition), and transcription (rather than selecting an item)."
- Out of scope inside a step: moving a code from a second device to this one. "Evaluating whether
  or not the code can be seamlessly transferred from the secondary device to the primary device is
  outside of the scope for this success criterion. [...] it is assumed that provisions are in place
  that make the code available in the user's clipboard. Evaluating this criterion therefore only
  requires verification that the web content does allow pasting the clipboard content in the
  related authentication challenge field."
- The three factor kinds, for classifying a step: "knowledge (e.g., password, letters in a
  passphrase or memorized swipe path)"; "possession (e.g., a verification code generated or
  received on a device, or scanning of a QR code on an external device)"; "biometrics (e.g.,
  fingerprint scanning, facial recognition or keystroke dynamics)". Knowledge steps are cognitive
  function tests and need a mechanism or an alternative; possession and biometrics steps are not,
  unless they make the user transcribe something.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. `axe-page.mjs` prints
no 3.3.8 row for any state, so neither a violation nor an `incomplete` can arrive from it, and no
rule tagged with another criterion stands in: whether a field accepts a paste, whether a challenge
is a puzzle or an object-recognition grid, and whether another way into the account exists are all
behaviours a static rule engine never exercises. Leaves open: all of it — finding the steps, the
alternative per step, paste, autofill, entry format, challenge classification, recovery and second
factor. The field-markup half of [H100](https://www.w3.org/WAI/WCAG22/Techniques/html/H100) —
"each input for authentication includes an appropriate accessible-name" — overlaps the work the
4.1.2 and 1.3.5 files already do on this sample; read their findings rows for the login fields
before step 5 rather than repeating their checks, and file what they find under their own criteria.

## Manual procedure

Forms mode at `set viewport 1280 900`. Credentials, test accounts and the states that reach a login
come from `.notes/sample.md` and `recon/<sample>-states.md`. Never attempt more than two wrong
passwords on a real account, and stop before any step with a real-world effect (a code actually
sent by SMS, an account lock); an unreached step is `cannot-tell` named in the findings row, not a
pass.

The procedure runs the published tests of the three techniques in the pack.
[H100](https://www.w3.org/WAI/WCAG22/Techniques/html/H100): "Check that each input for
authentication includes an appropriate accessible-name" and "Check that each input for
authentication allows pasting", expected result "#1 and #2 are true" — steps 4 and 5.
[F109](https://www.w3.org/WAI/WCAG22/Techniques/failures/F109): "Check that the input field allows
the user to fill in the entire password or code in the format in which it was originally created"
and, if not, "check if there is an alternative authentication method present that satisfies Success
Criteria 3.3.8", the failure applying only "if both checks #1 and #2 are false" — steps 6 and 3.
[G218](https://www.w3.org/WAI/WCAG22/Techniques/general/G218) has five checks, of which a
browser-driven audit can reach only the first and the last: the e-mail-link feature can be found
and submitted, and the flow can be read for an object-recognition test, but "Check that the email
is received", "Check that selecting the link opens the website" and "Check that the user account is
logged in" need a mailbox this audit does not have. Record an e-mail-link alternative as present in
the content and put its end-to-end verification in the confirmation queue.

1. Reach every step of the authentication process. Open the entry point, then each state that leads
   to a step: the login dialog or page, "Forgot password", "Use another method", the second factor
   reached with the test account, and any re-authentication in front of a settings or payment page.

   ```bash
   agent-browser open <login url>
   agent-browser wait --load networkidle
   agent-browser snapshot -i
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.8-step1.png --full
   ```

   Number the steps in the order the user meets them and record for each its URL or state name and
   how it was reached. Done when every step has a number, a state name and a full-page screenshot,
   or no state is an authentication step and the outcome is `not-present` with the states listed.

2. Inventory the fields and challenges of each step. In that step's state run both probes and read
   the tree:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
   agent-browser snapshot -i
   ```

   From `fields[]` keep `selector`, `tag`, `type`, `name`, `nameSource`, `visibleLabelText`,
   `placeholder`, `autocomplete`, `disabled` and `visible` for every secret-bearing control: the
   username or e-mail box, every `type="password"`, every code, PIN, passcode or digit box, and
   every `select` inside the login fieldset. From `structure.js` `iframes[]` keep any frame whose
   `src` or `title` names a CAPTCHA vendor, with its `selector`. From the snapshot keep the text of
   any challenge prompt and the label of any "I'm not a robot" checkbox. Done when every step has
   its list of controls with selectors and its list of challenges, or is recorded as challenge-free.

3. Find the alternative on each step, before testing anything else — F109 and the criterion both
   let one alternative carry the whole step. Read the snapshot of that step for another way in
   ("Sign in with a passkey", "Use your security key", "Log in with Google", "Email me a login
   link", "Approve on your phone", a QR code), and confirm passkey markup:

   ```bash
   agent-browser get count "[autocomplete~='webauthn']"
   agent-browser get attr "#username" autocomplete
   agent-browser find role button click --name "Sign in with a passkey"
   agent-browser wait --load networkidle
   agent-browser snapshot -i
   ```

   `get attr` takes the selector first and the attribute second. Activating the alternative and
   reading the state it opens is what decides it: an alternative counts only when it is itself free
   of a cognitive function test, reaches the same account, and is offered on this step rather than
   buried behind a failed attempt. A "Forgot password" link is not an alternative to the login
   step — it starts the recovery process, which is its own step and gets its own row. Record per
   step "alternative: <which>" or "alternative: none"; a step with one is a pass whatever else it
   holds, and steps 4 to 8 only have to run on the steps that have none. Done when every step
   carries an alternative verdict with the control that provides it named.

4. Test pasting on every secret-bearing control of a step without an alternative. The audit browser
   cannot perform an operating-system paste: `navigator.clipboard.writeText` answers
   `NotAllowedError` until a real user gesture has happened on the page, a read back with
   `navigator.clipboard.readText()` is refused outright, and `press Control+v` (or `Meta+v`)
   leaves the focused field untouched even where no paste guard exists at all. Never read a fail
   out of an empty field after a key-press paste. Dispatch the paste event instead and watch what
   the page does with it:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const codeLike = /code|otp|pin|digit|token|passcode|verification/i
     const sels = ['#username', '#password', '#otp']
     return sels.map((sel) => {
       const el = document.querySelector(sel)
       if (!el) return { sel, error: 'not found' }
       const hint = `${sel} ${el.name || ''} ${el.getAttribute('autocomplete') || ''}`
       const sample = codeLike.test(hint) ? '482913' : 'Zq7!paste-test'
       el.value = ''
       el.focus()
       const dt = new DataTransfer()
       dt.setData('text/plain', sample)
       const init = { clipboardData: dt, bubbles: true, cancelable: true }
       const ev = new ClipboardEvent('paste', init)
       el.dispatchEvent(ev)
       return {
         sel,
         sample,
         prevented: ev.defaultPrevented,
         after: el.value,
         changed: el.value !== '',
         took: el.value.includes(sample),
         onpaste: el.getAttribute('onpaste'),
         readonly: el.readOnly,
         maxlength: el.getAttribute('maxlength'),
         autocomplete: el.getAttribute('autocomplete')
       }
     })
   })()
   EOF
   ```

   The probe clears the field first, so it can be re-run, and it sends a six-digit sample to a code,
   PIN or token field so that a digit-only sanitiser is not mistaken for a guard. Read each row
   against this table; `prevented` alone never decides, because a page may cancel the paste in
   order to write the value itself.

   | `prevented` | `changed` | Read as                                                                  |
   | ----------- | --------- | ------------------------------------------------------------------------ |
   | `false`     | either    | nothing cancelled the paste; the browser's own insertion runs — allowed  |
   | `true`      | `true`    | the page cancelled it and wrote the value itself (trim, split) — allowed |
   | `true`      | `false`   | the page cancelled the paste and put nothing in its place — **blocked**  |

   A row with `changed: true` and `took: false` is a handler that rewrote the pasted string: read
   `after` against `sample` and, on a password field, put "does a real password survive this
   handler?" in the confirmation queue, since F109 asks for the secret in the format it was created
   in. On a code field a digits-only rewrite of the digit sample is the widget working as intended.

   A blocked field on a step with no alternative is the Understanding's own fail: "if user agents
   and password managers are actively blocked from filling in the fields (for instance, by a script
   that prevents form fields from being automatically populated), or users are prevented from copy
   and paste operations (as they may rely on standalone/external third party password managers),
   then the page would fail this criterion unless an alternative is provided." Capture the
   `onpaste` value in the finding when it is set, as the evidence of the guard. A handler that
   reads `event.isTrusted` ignores this dispatch and reports `prevented: false`; when the page
   shows a message about pasting while the probe says allowed, record `cannot-tell` for that field
   and ask the owner. Done when every secret-bearing control on every alternative-free step has one
   of the three table rows and a verdict of allowed, blocked or `cannot-tell`.

5. Test the autofill half of [H100](https://www.w3.org/WAI/WCAG22/Techniques/html/H100) on the same
   controls. agent-browser carries no password manager, so autofill itself cannot be exercised;
   what can be tested is whether the page actively works against a filled value. Fill each control,
   move focus away, and read it back:

   ```bash
   agent-browser fill "#password" "Zq7!paste-test"
   agent-browser get value "#password"
   agent-browser press Tab
   agent-browser get value "#password"
   agent-browser focus "#password"
   agent-browser keyboard type "Zq7!paste-test"
   agent-browser press Tab
   agent-browser get value "#password"
   ```

   `get value` returns the real string for a password box, unlike the probe. A value that survives
   the blur is the pass. A value cleared on blur after both `fill` and `keyboard type` is a script
   working against any filler, password managers included — record it as blocked autofill. A value
   cleared only after `fill` while the typed one survives is a framework re-render, not a defect;
   record it as allowed. Take the field's `autocomplete` and `nameSource` from step 2 into the row
   for the recommendation, but never fail here on markup alone: `autocomplete="off"` is not a
   script that blocks filling, and a missing token belongs to 1.3.5 and a missing name to 4.1.2.
   Done when every control on every alternative-free step reads "value survives blur" or "value
   cleared by script", with the two commands that produced it.

6. Test the entry format ([F109](https://www.w3.org/WAI/WCAG22/Techniques/failures/F109)) on every
   password and code step: "Requiring users to authenticate by entering a password or code in a
   different format from which it was originally created is a failure [...] This applies
   irrespective of whether users are required to enter all characters in the string, or just a
   subset." First look for the prompt and the split controls:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const ORD = '(?:\\d+(?:st|nd|rd|th)|first|second|third|fourth|fifth|sixth|last)'
     const partial = new RegExp(`\\b${ORD}\\b[^.]{0,60}\\b(?:characters?|digits?|letters?)\\b`, 'i')
     const text = (el) => (el.textContent || '').replace(/\s+/g, ' ').trim().slice(0, 160)
     return {
       prompts: [...document.querySelectorAll('legend, label, p, h1, h2, h3, [role="heading"]')]
         .map(text)
         .filter((t) => partial.test(t)),
       selectsInForm: document.querySelectorAll('form select, fieldset select').length,
       oneCharBoxes: document.querySelectorAll('input[maxlength="1"], input[size="1"]').length,
       keypads: [...document.querySelectorAll('[role="grid"], [class*="keypad"], [class*="pin"]')]
         .map(text)
     }
   })()
   EOF
   ```

   A non-empty `prompts` is F109's second example verbatim — "A fieldset that prompts a user to
   'Enter the 2nd, 6th and last characters of your password'" — and a `selectsInForm` count on a
   password step is its third — "A password input fieldset composed of `<select>` elements that
   requires a user to select each character of a fixed-length password from individual dropdown
   fields". Then settle the one-character boxes, which F109 excepts only when the first box takes
   the whole code: "unless the user can paste the entire code in the first input, and the remaining
   inputs are populated automatically".

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const CODE = '482913'
     const boxes = [...document.querySelectorAll('input[maxlength="1"], input[size="1"]')]
     if (boxes.length === 0) return { boxes: 0 }
     boxes.forEach((b) => { b.value = '' })
     const dt = new DataTransfer()
     dt.setData('text/plain', CODE)
     const ev = new ClipboardEvent('paste', { clipboardData: dt, bubbles: true, cancelable: true })
     boxes[0].focus()
     boxes[0].dispatchEvent(ev)
     return {
       boxes: boxes.length,
       prevented: ev.defaultPrevented,
       caps: boxes.map((b) => b.getAttribute('maxlength') || b.getAttribute('size')),
       values: boxes.map((b) => b.value),
       filled: boxes.filter((b) => b.value).length
     }
   })()
   EOF
   ```

   `filled` equal to `boxes` is the excepted widget: the code was distributed and the format is
   kept. `filled` of 0 or 1 with every `caps` entry `"1"` is the failure: the native paste can
   leave at most one character in the first box. When `boxes` comes back larger than the number of
   boxes in the step on screen, the selector has caught a second group elsewhere on the page —
   narrow it to the step's own container (`'#otp-group input[maxlength="1"]'`) and run it again, so
   one widget's result is never read off another's. For the screenshot that shows the user's view,
   `agent-browser fill "<first box>" "482913"` then capture — a one-character box keeps the first
   digit and drops the rest. Decide nothing from `fill`, though: it does not fire the page's paste
   handler, so a widget that distributes on paste looks identical to a broken one under `fill`.
   Done when each password and code step reads "whole secret in one field", "code distributed
   across the boxes", or "format broken: <prompt, selects, or boxes>".

7. Classify every challenge on a step with no alternative, in the default state and in the state
   after one failed attempt, since a conditional challenge is in scope:

   ```bash
   agent-browser fill "#password" "wrong-on-purpose-1"
   agent-browser find role button click --name "Log in"
   agent-browser wait --load networkidle
   agent-browser snapshot -i
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.8-challenge.png --full
   ```

   A vendor CAPTCHA renders in a cross-origin iframe, which `agent-browser frame "<css>"` answers
   with "Frame not found" — but `snapshot` descends into it and gives its content its own refs, and
   `click "@e12"` on a ref inside that frame works, so the "I'm not a robot" checkbox can be
   activated and the challenge it opens can be read. Use the frame's `src` from step 2 only as a
   fallback when the snapshot shows the frame empty. Classify what the user is asked to do:
   - Distorted text to type, or an audio clip to transcribe — transcription, no exception.
   - An arithmetic prompt ("what is 7 + 4?") — "performance of calculations", no exception; the
     Understanding's Figure 7 is exactly this.
   - A logic, rotation, slider or jigsaw puzzle — "solving of puzzles", no exception; Figure 8 is a
     3D walrus to rotate to a given direction.
   - "Select all images with a car" — Object Recognition, which passes at this level. Note it in
     the findings row for 3.3.9, which does not except it, and leave it a pass here.
   - A grid that adds counting or arithmetic to the recognition — "If the test goes beyond
     recognition (e.g. multiply the number cats by the number of dogs), that does not meet the
     exception."
   - "Pick the picture you uploaded" — Personal Content, which passes; a typed answer about
     personal facts does not.
   - A bare "I'm not a robot" checkbox, an invisible score check or a Turnstile that resolves with
     no task — no cognitive function test at all; record it as no test and move on.
     Record `cannot-tell` for a challenge that never rendered a task in either state. Done when every
     challenge on every alternative-free step carries one of those classes with its screenshot.

8. Run steps 3 to 7 again on the second factor, the recovery route and any re-authentication, then
   collect the evidence. A code field passes on the same terms as a password field: it must accept
   a paste and keep the whole code in one entry, since "A service that requires manual transcription
   of a verification code is not compliant. As with usernames and passwords, it must be possible
   for a user to at least paste the code [...] and to allow user agents to fill in the fields
   automatically." Steps that ask for possession or biometrics are not cognitive function tests:
   "two-factor systems that do not rely on codes – including hardware authentication devices (such
   as YubiKey), secondary applications [...] that expect the user to confirm that it is indeed them
   trying to log in, and authentication methods provided by the user's operating system (such as
   Windows Hello, or Touch ID/Face ID on macOS and iOS) – are not a cognitive function test." A
   recovery route that rests on security questions or a memorable word is a knowledge step and
   needs its own alternative. Capture each defect in the state that shows it:

   ```bash
   agent-browser highlight "#password"
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.8-<slug>.png
   agent-browser record start .notes/audit/evidence/<sample>-3.3.8-<slug>.webm
   agent-browser record stop
   ```

   `record start` needs its output path; start it before redoing the paste or the code entry, then
   stop it. Done when every reached step has a verdict with its evidence files, and every unreached
   step a `cannot-tell` row naming what blocked it.

What the browser cannot show: whether a password manager would in fact recognise and fill the
fields (no manager is installed, so step 5 tests only the page's interference); what a challenge
asks when its frame renders nothing; which challenge a vendor is configured to serve under
suspicion of automation; whether an e-mail login link arrives and logs the account in; and anything
behind a step that needs a real device, a real SMS or a second account. Each of those is
`cannot-tell` with the question for the owner, never a pass.

## Deciding

- Fail (certainty ≥ 90): on a step with no alternative, a password, code or PIN control whose paste
  probe reads `prevented: true` with `changed: false`, so the page cancels the paste and leaves the
  field exactly as it found it — 95; a prompt for selected characters of a password or passnumber
  ("Enter the 2nd, 6th and last characters"), or a fieldset built from one `select` per character
  ([F109](https://www.w3.org/WAI/WCAG22/Techniques/failures/F109)) — 95; one-character code boxes
  where the dispatched paste fills none or only the first and every box caps entry at one character
  — 90; a distorted-text or audio-transcription CAPTCHA on a step with no alternative, read in full
  from the snapshot or the screenshot — 90; an arithmetic challenge on such a step — 90.
- Fail (70–89): a logic, rotation, slider or jigsaw puzzle on a step with no alternative — 85; an
  audio version that must be transcribed offered as the step's only other route, against "If the
  user needs to transcribe this audio, it cannot be used to meet the Alternative exception" — 85;
  security questions, a memorable word or any remembered typed answer as the only way through a
  step, including recovery — 85; an on-screen keypad or pattern grid with no field that takes a
  typed or pasted value — 85; an object-recognition grid that adds counting or arithmetic — 80; a
  filled value cleared on blur by script after both `fill` and `keyboard type` — 75; a challenge
  whose task the screenshot shows only in part but whose visible portion is text, arithmetic or a
  puzzle — 70.
- Needs confirmation (50–69): a challenge frame that rendered no task in either state — ask which
  challenge type is configured and whether it ever asks for typed text — 60; a page that tells the
  user pasting is not allowed while the paste probe reads allowed, so a handler may be checking
  `isTrusted` — ask whether paste is blocked in production — 60; a second factor, recovery or
  re-authentication step that could not be reached — ask for a test account or a description of the
  step — 55; an e-mail-link or third-party login offered as the alternative that could not be
  followed to a logged-in account ([G218](https://www.w3.org/WAI/WCAG22/Techniques/general/G218)
  checks 2 to 4) — ask the owner to confirm it completes — 55; a CAPTCHA the vendor serves only
  under suspicion of automation — ask what its fallback task is, and record that the criterion
  applies "regardless of whether they are used every time or only triggered by specific scenarios"
  — 55.
- Pass: every step reached either offers an authentication method free of cognitive function tests,
  or lets every one of its secret-bearing controls take a pasted value, keeps that value when focus
  leaves, and accepts the whole password or code in the format it was created in — one field, or
  boxes that a pasted code fills across — and every challenge it carries is object recognition, the
  user's own non-text content, or no task at all.
- Not present: no state of the sample is a step of authenticating an existing account.
- False positives to avoid: a paste handler that cancels the event and then writes the value itself
  to trim, split or strip it, which the probe shows as `prevented: true` with `changed: true`,
  whatever `took` says; a code widget
  that distributes a pasted code across its boxes, which F109 excepts by name; an empty field after
  `press Control+v`, which is the tool's inability to paste and not the content's; a field that
  `fill` leaves empty while `keyboard type` fills it, which is a framework re-render; a registration
  form, a password-creation form or a "confirm new password" box, none of which is authentication
  and all of which report `autocompleteCandidate: "current-password"` anyway; a CAPTCHA on a
  contact, comment, newsletter or search form, whose missing text alternative is 1.1.1; the
  username or e-mail field itself, since "The common identifiers name, e-mail, and phone number are
  not considered cognitive function tests"; `autocomplete="off"` while the paste probe reads
  allowed; a missing `autocomplete` token (1.3.5) or a missing accessible name (4.1.2) on its own;
  an image-grid object-recognition CAPTCHA at target level AA; a reCAPTCHA checkbox or an invisible
  score check with no task; a hardware key, push approval, QR scan, Windows Hello, Touch ID or a
  WebAuthn flow whose device method is a PIN the user set on their own operating system, since "The
  website is not enforcing any particular use"; an object-recognition task that needs local
  knowledge, since "Some forms of object recognition may require an understanding of a particular
  culture [...] it is not considered an accessibility-specific issue"; a password field that hides
  its characters or lacks a show-password toggle, which the Understanding raises as an improvement
  and not as a requirement of this criterion; a code that arrives on another device, which is out
  of scope as long as the field takes a paste.

## Reporting

- File under: 3.3.8 for a blocked paste or a script that clears filled credentials, for a secret
  that cannot be entered in the format it was created in, for a transcription, arithmetic or puzzle
  challenge, and for a recovery route that rests on remembered answers. One issue per step, named
  as the user meets it (login, second factor, recovery, re-authentication); a login shared by
  several samples is one issue that names the other samples. A missing `autocomplete` token goes to
  1.3.5 and an unnamed login control to 4.1.2, each as its own issue; a CAPTCHA image without a
  text alternative to 1.1.1; an object-recognition or personal-content challenge to 3.3.9 only when
  the target level is AAA; a code that expires before it can be fetched and pasted to 2.2.1.
- Title patterns: "Password field blocks pasting", "Verification code must be typed digit by
  digit", "Login asks for selected characters of the password", "Login requires solving a text
  CAPTCHA with no other way in", "Account recovery relies on security questions only", "The login
  form clears the password a password manager fills"
- Severity: High when the step sits on the only path into the account — the login form itself, a
  mandatory second factor, the sole recovery route — because the user group is locked out
  entirely; Medium when another route exists that this step does not offer, so the user has to find
  it (a login link reachable only through "Forgot password", a challenge that appears after a
  failed attempt and has no alternative on that screen); Low when the secret can still be pasted
  and only the automatic filling is unreliable, or when the step is a re-authentication the user
  can avoid by starting the task again. A challenge that appears only in certain situations is not
  a reason to go below Medium: the criterion applies to it either way.
- Type: Technical, always. The fix sits in the login code or the authentication service's settings
  — a paste handler, a blur handler, the markup of the fields, the challenge the vendor serves, or
  an extra login method — never in editorial copy or in the visual design.
- Evidence: a screenshot of the step in the state that shows the defect, with `highlight` on the
  control or the challenge — the field still empty beside the message about pasting, the single
  filled box out of six, the CAPTCHA task itself, the cleared password field after focus moved on;
  a recording when the defect is a sequence rather than a still, such as a value that vanishes on
  blur or a code that lands in one box and stops.
- Recommendation: let password managers fill the fields and let people paste into them — give every
  control a visible label, mark it with `autocomplete="username"`, `"current-password"` or
  `"one-time-code"`, and remove the handlers that cancel `paste` or clear the field on blur
  ([H100](https://www.w3.org/WAI/WCAG22/Techniques/html/H100)); take the whole password or code in
  one field, or keep the boxes and spread a pasted code across them; add a route with no cognitive
  function test, such as a login link by e-mail
  ([G218](https://www.w3.org/WAI/WCAG22/Techniques/general/G218)), a passkey or a third-party
  login; and where a CAPTCHA guards the login, replace a text, arithmetic or puzzle challenge with
  object recognition, or cut the need for it with the anti-abuse measures the Understanding names —
  rate-limited access, client geo-location and private client authentication.

  ```html
  <label for="email">Email</label>
  <input id="email" name="email" type="email" autocomplete="email" />

  <label for="password">Password</label>
  <input id="password" name="password" type="password" autocomplete="current-password" />

  <label for="otp">Verification code</label>
  <input id="otp" name="otp" inputmode="numeric" autocomplete="one-time-code" />
  ```

  ```js
  // Keep the boxes if the design needs them, but let one paste fill them all.
  boxes[0].addEventListener('paste', (event) => {
    event.preventDefault()
    const digits = (event.clipboardData.getData('text') || '').replace(/\D/g, '')
    boxes.forEach((box, i) => {
      box.value = digits[i] || ''
    })
    boxes[Math.min(digits.length, boxes.length) - 1].focus()
  })
  ```
