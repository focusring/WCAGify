# 1.4.4 Resize Text

Level AA · WCAG 2.0+ · Guideline 1.4 Distinguishable · Group: `visual`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)
· [Spec](https://www.w3.org/TR/WCAG22/#resize-text)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#resize-text)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/1-4-4-resize-text/)
· ACT: [b4f0c3](https://www.w3.org/WAI/standards-guidelines/act/rules/b4f0c3/),
[59br37](https://www.w3.org/WAI/standards-guidelines/act/rules/59br37/)

## Requirement

> Except for captions and images of text, text can be resized without assistive technology up to
> 200 percent without loss of content or functionality.

Terms (WCAG 2.2 glossary): **text**: "sequence of characters that can be programmatically
determined, where the sequence is expressing something in human language" — the rendered characters
are the subject, not the boxes or pictures around them. **images of text**: "text that has been
rendered in a non-text form (e.g., an image) in order to achieve a particular visual effect", Note:
"This does not include text that is part of a picture that contains significant other visual
content", Example: "A person's name on a nametag in a photograph." The note keeps the exception
narrow: a heading shipped as a PNG is excepted here and belongs to 1.4.5, while words inside a
photograph are neither excepted nor "text", so they decide nothing either way. **captions**:
"synchronized visual and/or text alternative for both speech and non-speech audio information needed
to understand the media content", Note 3: "Open Captions are any captions that cannot be turned off.
For example, if the captions are visual equivalent images of text embedded in video." Both closed
and open captions are outside the criterion; a transcript printed beside or under the player is not
a caption and is in scope. **assistive technologies**: "hardware and/or software that acts as a user
agent, or along with a mainstream user agent, to provide functionality to meet the requirements of
users with disabilities that go beyond those offered by mainstream user agents", whose Example list
opens with "screen magnifiers, and other visual reading assistants", and Note 3: "The distinction
between mainstream user agents and assistive technologies is not absolute. Many mainstream user
agents provide some features to assist individuals with disabilities." Browser page zoom and the
browser's own text-size setting are mainstream user-agent features and count; a screen magnifier
does not, so "it is legible under a magnifier" never rescues a sample. The Understanding adds **user
agent**: "any software that retrieves and presents web content for users".

The Intent fixes what the measurement means: "Content satisfies the success criterion if it can be
scaled up to 200% - that is, up to twice the width and height", and "Content satisfies the success
criterion if it can be scaled up to 200% using at least one text scaling mechanism supported by
user agents." So 200 % is a factor on each dimension, not on area, and one working mechanism is
enough — browser zoom ([G142](https://www.w3.org/WAI/WCAG22/Techniques/general/G142)) or an
author-provided control ([G178](https://www.w3.org/WAI/WCAG22/Techniques/general/G178)).

## In plain terms

All visually rendered text, "including controls and labels using text", has to reach twice its
default size through a plain browser feature such as page zoom, with nothing cut off, hidden,
overlapped or made inoperable. "The scaling of content is primarily a user agent responsibility";
"The author's responsibility is to create web content that does not prevent the user agent from
scaling the content effectively", which in practice means relative font sizes, boxes that grow with
their text, and form controls that follow. Every step on the way counts, not just the endpoint: "If
the resizing mechanism [...] offers incremental resizing steps between 100% and 200%, authors must
ensure that there is no loss of content or functionality at these incremental steps." It matters
for people with low vision, who "can read the larger text" only when the layout survives it.

## Applies when

- Present: every sample with visible text or text-based controls, which is every sample; any
  character in the 1280 px `snapshot -i` or baseline screenshot makes it applicable. Judge each
  layout the breakpoints produce: "As with most other success criteria, this criterion applies to
  each variation of the page that is automatically presented for various screen sizes (e.g. media
  query variations in a responsive site)."
- Not present: the sample's only visible text is captions on a video (`media.js` `tracks`, or
  burned-in open captions) or text inside images (`images.js` entries with no text nodes around
  them). This is rare; prefer an outcome over `not-present` whenever one paragraph, label or button
  text exists.
- Cannot tell: content the viewport commands cannot rescale, in practice a PDF rendered by the
  browser's plugin viewer or a document painted into a `canvas`. Record `cannot-tell`, name the
  file or the element, and send it to the confirmation queue rather than guessing.
- Exception, normative: "Except for captions and images of text". Captions are outside the
  criterion in both forms (Note 2 "Closed Captions", Note 3 "Open Captions"); images of text are
  judged by 1.4.5 and are only a 1.4.4 finding when the image carries text that the page needs and
  no scalable copy exists — the fix there is real text styled with CSS
  ([C22](https://www.w3.org/WAI/WCAG22/Techniques/css/C22)), since text in images cannot "be scaled
  according to settings in the browser".
- Exception, note: "The criterion does not apply to content or interface elements controlled by the
  user agent or platform. For instance, in most browsers, the title attribute on an element causes
  a tooltip to appear when the element is hovered with the mouse. Another example is that
  activating an `<input type="file">` to upload a file will open the platform's file browser. In
  both these examples, the size of the text is determined by the browser or platform, rather than
  the content author, and is therefore not covered by the criterion." The same covers the native
  `select` dropdown list, the date picker and the browser's own validation bubble. A custom
  combobox or a scripted tooltip is author content and is in scope.
- Exception, truncation: "In this type of user interface component, line wrapping is not required;
  truncation is acceptable if the component's full content is available on focus or after user
  activation and an indication that this information can be accessed, is provided to the user in
  some way besides the fact that it is truncated." The Understanding's two cases are a web-mail
  subject column where "activating the subject header takes the user to the full message with the
  full subject header", and a spreadsheet cell where "the full content of the cell is available to
  the user when the cell receives focus". Both parts are required: the full content _and_ an
  indication besides the ellipsis.
- Exception, breakpoints: "In an implementation where text does not consistently increase its size
  as people zoom in (such as when it is transformed based on a media query to adapt to small-screen
  usage), it must still be possible to get to 200% enlargement in order to satisfy the criterion."
  The Understanding works it out: "if at the default browser setting of 100% zoom, text is set at
  20px when the window is 1280 CSS pixels wide, at 200% zoom it will visually appear at twice the
  size. After zooming by 400% the page reflows to fit within the 320 CSS pixel viewport, the author
  may decide to set the page's text size to 10px. The text is now half the original size in CSS
  pixels, but as it has been enlarged to 400%, it is still displayed at twice the size compared to
  the default browser setting at 100% zoom. It is not required to achieve 200% text enlargement
  while remaining inside a specific breakpoint (as zooming may result in the variation for a new
  breakpoint becoming active), but it should still be possible to get 200% text enlargement in some
  way compared to the default 100% zoom." Step 2 measures exactly this: 20 px at 1280 and 10 px at
  320 is 4 × 10 / 20 = 2.0, a pass.
- Above 200 % nothing is required: "Content satisfies the success criterion if it can be scaled up
  to 200%", and the Understanding warns that past it "words may be too wide to fit into the
  horizontal space available to them, causing them to be truncated; layout constraints may cause
  text to overlap with other content when it is scaled larger". Defects that appear only at the
  320 px viewport are 1.4.10 material, never a 1.4.4 fail.
- Scrollbars are not a defect here: the Understanding's third example is "A user changes the scale
  of the content with the browser's full-page zoom function. All the content scales uniformly, and
  the browser provides scroll bars, if necessary."

## axe-core

| Rule            | Decides                                             | Result → outcome       |
| --------------- | --------------------------------------------------- | ---------------------- |
| `meta-viewport` | the viewport meta tag keeps zoom available (b4f0c3) | violation → fail (100) |

The rule sits in the default WCAG 2.0 A & AA set, so `scripts/axe-page.mjs` runs it on every state
and a violation is already in `.notes/audit/axe/<sample>[--<state>].json`; it produces no
`incomplete` result, so nothing here arrives as a pointer to a manual check.

Settles: the viewport meta tag and nothing else. It implements ACT b4f0c3, which applies "to each
content attribute on a meta element with a name attribute value of viewport" whose value "has the
user-scalable property" or "has the maximum-scale property", and carries two expectations that both
have to hold: Expectation 1, "the attribute value does not have a user-scalable property with a
value of no"; Expectation 2, "the attribute value does not have a maximum-scale property with a
value less than 2". The rule's own assumptions keep a failed outcome from settling the criterion —
a page may still satisfy 1.4.4 when "The page has no visible content", when "There is another
mechanism available to resize the text content" (a G178 control, step 6) or when "The content does
not need to reflow in order to fit in an area of 320 by 256 CSS pixels" — and its support note
adds "Desktop browsers ignore the viewport meta element [...] Only users with older mobile browsers
can experience issues tested by this rule", which is what the severity line below is built on. The
violation is still recorded as a fail at certainty 100 per the skill's convention.

Leaves open, all at 200 %: text clipped by `overflow: hidden`, `overflow: clip` or a fixed height
(ACT 59br37, [F69](https://www.w3.org/WAI/WCAG22/Techniques/failures/F69)); text or controls
overlapping, or covered by sticky or absolutely positioned elements (F69); popups and dialogs "that
aren't big enough for their content at the new font size" (F69); content or controls gone at the
640 px breakpoint; text in viewport units that never grows
([F94](https://www.w3.org/WAI/WCAG22/Techniques/failures/F94)); form controls that stay small
([F80](https://www.w3.org/WAI/WCAG22/Techniques/failures/F80)); sizes and positions computed in
script from pixel values, not from the rendered text
([SCR34](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR34)); truncation without a
way to the full content; losses at the incremental steps between 100 % and 200 %; an author
text-size control (G178) that can rescue a sample. ACT 59br37 is a proposed rule
with no axe implementation, so step 3 runs it by hand.

## Manual procedure

Repeat steps 3 to 5 with the cookie dialog, the main menu, a modal, an expanded section and the
form error state open when the sample has them. No screen reader is needed: the measurements and
the screenshots decide. Wrap every `eval --stdin` body in `(() => { ... })()`, so a second run in
the same page does not throw on a re-declared binding, and re-snapshot after every `reload` because
`@eN` refs go stale.

1. Record the 100 % baseline: the viewport meta tag, the size figures, the text that must survive,
   and typed-in field text (F80 and [C17](https://www.w3.org/WAI/WCAG22/Techniques/css/C17) both
   start with "Enter some text into text-based form controls that receive user entered text").

   ```bash
   agent-browser set viewport 1280 900
   agent-browser reload
   agent-browser wait --load networkidle
   agent-browser get attr 'meta[name="viewport"]' content
   agent-browser fill '<the first text field>' 'Resize test 200 percent'
   agent-browser screenshot .notes/audit/evidence/<sample>--1.4.4-100.png --full
   agent-browser snapshot -i > .notes/audit/evidence/<sample>--1.4.4-100.snapshot.txt
   agent-browser eval --stdin < <skill-dir>/scripts/probes/reflow.js
   agent-browser eval --stdin <<'EOF'
   (() => {
     const path = (el) => el.id ? `#${CSS.escape(el.id)}` : el.tagName.toLowerCase() +
       (el.classList.length ? `.${[...el.classList].slice(0, 2).join('.')}` : '');
     const med = (a) => (a.length ? a.sort((x, y) => x - y)[a.length >> 1] : null);
     const size = (s) => med([...document.querySelectorAll(s)].filter((el) => el.checkVisibility())
       .map((el) => parseFloat(getComputedStyle(el).fontSize)));
     const VU = /\d(?:s|l|d)?(?:vw|vh|vi|vb|vmin|vmax)\b/;
     const vwRules = [], sheets = { total: 0, unreadable: [] };
     const walk = (rules, media) => { for (const r of rules) {
       if (r.style) for (const p of ['fontSize', 'lineHeight', 'height', 'maxHeight'])
         if (VU.test(r.style[p] || '')) vwRules.push({ selector: r.selectorText, prop: p,
           value: r.style[p], media });
       if (r.cssRules) walk(r.cssRules, r.media ? r.media.mediaText : media); } };
     for (const s of document.styleSheets) { sheets.total++;
       try { walk(s.cssRules, ''); } catch { sheets.unreadable.push(s.href || 'inline'); } }
     return { vw: innerWidth, body: size('p, li, td, dd'),
       controls: size('a, button, input, select, textarea, label'),
       fields: size('input:not([type="checkbox"]):not([type="radio"]), textarea, select'),
       overflowXHidden: [document.documentElement, document.body]
         .some((el) => /hidden|clip/.test(getComputedStyle(el).overflowX)),
       vwRules, sheets,
       inlinePx: [...document.querySelectorAll('[style]')].filter((el) =>
         /(?:^|;)\s*(?:width|height|max-height|top|left|font-size)\s*:\s*[\d.]+px/
           .test(el.getAttribute('style')) && (el.innerText || '').trim().length > 0)
         .slice(0, 20).map((el) => ({ selector: path(el),
           style: el.getAttribute('style').slice(0, 80) })) };
   })()
   EOF
   ```

   End this step with step 5's form-control script, while the viewport is still 1280 × 900 and the
   field still holds the typed text. The `get attr` value is the b4f0c3 target, read here so the
   issue can quote it and so the check still happens when axe did not run. Parse it the way the rule
   does: `user-scalable=no` fails Expectation 1; `maximum-scale=1.0`, `maximum-scale=1.5` and
   `maximum-scale=yes` (the rule's failed example 4: "maximum-scale set to yes which translates to
   1.0") fail Expectation 2; `maximum-scale=2.0`, `user-scalable=yes` and `maximum-scale=-1` (a
   negative value "results in this value being dropped") pass; a missing tag, a tag with no
   `content`, an empty `content` and `content="width=device-width"` are inapplicable and decide
   nothing. Keep `body`, `controls` and `fields` (median font size in CSS px), `overflowXHidden`,
   `vwRules` (every `font-size`, `line-height`, `height` or `max-height` in a viewport unit, with
   its media query), `sheets.unreadable` (cross-origin stylesheets whose rules cannot be read, which
   is why a cause may be missing later), `inlinePx` (boxes and font sizes written into the `style`
   attribute, usually by script — the SCR34 candidates) and, from `reflow.js`, `visibleTextChars`
   and `hiddenBlocks` as the amount of text present at 100 %. Skip the `fill` when the sample has no
   text field; every other command runs on every sample. Done when the meta value, the three size
   figures, the two rule lists and the baseline screenshot, snapshot and `reflow.js` output are
   saved.

2. Zoom to 200 % and measure how much the text actually grew, then check the steps on the way.

   ```bash
   agent-browser set viewport 640 900
   agent-browser reload
   agent-browser wait --load networkidle
   agent-browser screenshot .notes/audit/evidence/<sample>--1.4.4-200.png --full
   agent-browser snapshot -i > .notes/audit/evidence/<sample>--1.4.4-200.snapshot.txt
   ```

   Rerun the step 1 script here, then after `set viewport 320 900` and `reload`. Enlargement at a
   viewport width W is `(1280 / W) × sizeW / size1280`: at 640 that is `2 × body640 / body1280`, at
   320 it is `4 × body320 / body1280`; the same for `controls` and `fields`. Text is resizable when
   the larger of the two reaches 2.0 (1.9 allowing for the rounding of a median in whole pixels) for
   every figure, which is the Understanding's own 20 px / 10 px arithmetic. A shortfall comes
   from a `vwRules` entry with `prop: "fontSize"` matching the text (F94: viewport units "are
   relative to the viewport, it means they cannot be resized by zooming or adjusting text-size") or
   from a breakpoint rule with a smaller `px` size; `clamp()` or `calc()` with an `em` or `rem` part
   still grows, so the figures and not the declaration decide. Then walk the incremental steps,
   which the Intent requires to be lossless as well:

   ```bash
   for w in 1024 853 731; do
     agent-browser set viewport $w 900
     agent-browser reload
     agent-browser wait --load networkidle
     agent-browser screenshot .notes/audit/evidence/<sample>--1.4.4-$w.png --full
   done
   agent-browser set viewport 640 900
   agent-browser reload
   ```

   Those widths are 125 %, 150 % and 175 % of a 1280 px window (1280 / 1.25 = 1024, 1280 / 1.5 =
   853.3, 1280 / 1.75 = 731.4, each rounded down to whole CSS pixels). Compare each with the
   baseline for text that is cut, overlapping or gone; a loss at one of them is a failure even when
   640 looks clean, and the step 3 script can be run at that width to name the container. Done when
   the enlargement figures for `body`, `controls` and `fields` at 640 and at 320, the cause of any
   shortfall, and the four zoom screenshots (640, 1024, 853 and 731) are recorded, with the
   viewport back at 640 × 900.

3. Find clipped text at the ACT 59br37 viewport of 640 by 512 ("equivalent to a viewport size of
   1280 by 1024 zoomed 200%"). The rule applies to a text node that "is visible", "has an HTML
   element as a parent in the flat tree", "has an ancestor in the flat tree with a computed
   overflow-x or overflow-y of hidden or clip", and "does not have an ancestor in the flat tree
   with an aria-hidden attribute value of true"; the script implements that, minus 1 px boxes. Both
   expectations are tested, each with its own exception: Expectation 1, "Each test target is not
   horizontally clipped by overflow of an ancestor in the flat tree when in a viewport size of 640
   by 512, except if the clipping ancestor has a computed white-space of nowrap, and a computed
   text-overflow that is not clip"; Expectation 2, "Each test target is not vertically clipped by
   overflow of an ancestor in the flat tree when in a viewport size of 640 by 512, except if the
   clipping ancestor has a used line-height equal to or greater than the height of its bounding
   box, or in case of a computed overflow-y of clip, its content box". The `box >= fs` term in the
   script keeps the vertical exception honest: the rule's passed example 3 is a single line with
   `height: 16px; line-height: 16px; font-size: 16px`, while its failed example 4 is
   `height: 10px; font-size: 16px` where the line itself is cut in half, and only the glyph test
   separates them. `1.2 * fs` is the fallback for `line-height: normal`, whose used value "depends
   on font specific metrics [...] major browsers are effectively using values close to 1.2".

   ```bash
   agent-browser set viewport 640 512
   agent-browser eval --stdin <<'EOF'
   (() => { const out = { scanned: 0, clipped: [], ellipsis: [] };
     const path = (el) => el.id ? `#${CSS.escape(el.id)}` : el.tagName.toLowerCase() +
       (el.classList.length ? `.${[...el.classList].slice(0, 2).join('.')}` : '');
     const clipper = (el, axis) => { for (let a = el; a && a !== document.documentElement;
       a = a.parentElement) { const o = getComputedStyle(a)[axis], b = a.getBoundingClientRect();
       if (/auto|scroll/.test(o)) return null;
       if (/hidden|clip/.test(o)) return b.width > 1 && b.height > 1 ? a : null; } return null; };
     const why = (el) => { const c = getComputedStyle(el); return { height: c.height,
       maxHeight: c.maxHeight, lineHeight: c.lineHeight, fontSize: c.fontSize,
       whiteSpace: c.whiteSpace, textOverflow: c.textOverflow,
       hiddenRight: el.scrollWidth - el.clientWidth,
       hiddenBelow: el.scrollHeight - el.clientHeight }; };
     for (let n, w = document.createTreeWalker(document.body, 4); (n = w.nextNode());) {
       const p = n.parentElement, txt = n.data.trim().slice(0, 60);
       if (!txt || !(p instanceof HTMLElement) || getComputedStyle(p).visibility === 'hidden' ||
         p.closest('[aria-hidden="true"], script, style, noscript, template')) continue;
       const r = new Range(); r.selectNodeContents(n); const t = r.getBoundingClientRect();
       if (t.width <= 1 || t.height <= 1) continue; out.scanned++;
       const x = clipper(p, 'overflowX'), y = clipper(p, 'overflowY'), kinds = [];
       if (x) { const c = getComputedStyle(x), cut = t.right > x.getBoundingClientRect().right + 1;
         if (cut && c.whiteSpace === 'nowrap' && c.textOverflow !== 'clip')
           out.ellipsis.push({ selector: path(x), text: txt });
         else if (cut) kinds.push('horizontal'); }
       if (y) { const c = getComputedStyle(y), b = y.getBoundingClientRect();
         const fs = parseFloat(c.fontSize), lh = parseFloat(c.lineHeight) || 1.2 * fs;
         const box = c.overflowY === 'clip' ? y.clientHeight : b.height;
         if (t.bottom > b.bottom + 1 && !(lh + 1 >= box && box >= fs)) kinds.push('vertical'); }
       if (kinds.length) out.clipped.push({ selector: path(x ?? y), kinds, text: txt,
         style: why(x ?? y) });
     } return out; })();
   EOF
   agent-browser set viewport 640 900
   ```

   Each `clipped` entry is a 59br37 failure candidate. Its `style.hiddenBelow` and
   `style.hiddenRight` are the clipping ancestor's own scroll overflow in px, the measurable form
   of the rule's definition of clipping — a node is clipped when "changing the overflow-x of all
   such ancestors to visible would cause more of the node to become visible" — so a figure above 1
   turns the screenshot into a confirmation instead of a judgement call, and a pair of zeroes means
   the box holds its text and the entry is a rounding artefact. Then `highlight "<selector>"`, take
   a page screenshot and confirm against the baseline that text is cut or lines are gone (a
   carousel may lose nothing); when `get count "<selector>"` is above 1, highlight the matching
   `wideElements[].selector` from step 4's `reflow.js` run instead. Read
   `style` for the cause and name it in the issue: a `height` in px with no room for the wrapped
   text (failed example 1), a `height` in `vh` that shrinks as the page zooms (failed example 2,
   and a `vwRules` entry with `prop: "height"`), a rule that only applies at this width (failed
   example 3, `@media screen and (max-width: 640px)`), a box shorter than its own font size (failed
   example 4), or `text-overflow: clip` on a `nowrap` box (failed example 5). Each `ellipsis` entry
   meets Expectation 1 but still needs the truncation exception, and the rule says so itself: its
   passed examples 2 and 3 add "A link to a full version of the poem [...] is not required by this
   rule, but is necessary to satisfy success criterion 1.4.4 Resize text." So `hover`, `focus` and
   `click` it, run `get attr "<selector>" title`, and look for the full text plus a visible cue
   besides the ellipsis. Done when every entry is judged with its pixel figure and its cause, and
   `scanned` is above zero.

4. Check for lost content and functionality at 640 by 900 (G142's test is exactly "Zoom content to
   200%" then "Check whether all content and functionality is available", and G179's is "Increase
   text size to 200%" then "Check whether all content and functionality is available"). Take a
   fresh `snapshot -i` and compare it with the step 1 snapshot: an item present at 100 % and absent
   at 200 % needs a replacement that reveals it (a menu button, a "more" toggle); `click @<ref>` it,
   re-snapshot, `press Escape`.

   ```bash
   diff .notes/audit/evidence/<sample>--1.4.4-100.snapshot.txt \
        .notes/audit/evidence/<sample>--1.4.4-200.snapshot.txt
   agent-browser eval --stdin < <skill-dir>/scripts/probes/focusables.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/reflow.js
   agent-browser eval --stdin <<'EOF'
   (() => {
     const path = (el) => el.id ? `#${CSS.escape(el.id)}` : el.tagName.toLowerCase() +
       (el.classList.length ? `.${[...el.classList].slice(0, 2).join('.')}` : '');
     const els = [...document.querySelectorAll('body *')].filter((el) => {
       const c = getComputedStyle(el);
       if (c.visibility === 'hidden' || el.closest('[aria-hidden="true"], script, style'))
         return false;
       const r = el.getBoundingClientRect();
       return r.width > 1 && r.height > 1 &&
         [...el.childNodes].some((n) => n.nodeType === 3 && n.data.trim()); });
     const out = [];
     for (let i = 0; i < els.length && out.length < 20; i++)
       for (let j = i + 1; j < els.length && out.length < 20; j++) {
         const a = els[i], b = els[j];
         if (a.contains(b) || b.contains(a)) continue;
         const ra = a.getBoundingClientRect(), rb = b.getBoundingClientRect();
         const ox = Math.min(ra.right, rb.right) - Math.max(ra.left, rb.left);
         const oy = Math.min(ra.bottom, rb.bottom) - Math.max(ra.top, rb.top);
         if (ox > 2 && oy > 2) out.push({ a: path(a), b: path(b),
           overlap: [Math.round(ox), Math.round(oy)],
           positioned: [getComputedStyle(a).position, getComputedStyle(b).position] });
       }
     return { pairs: out, textBlocks: els.length }; })()
   EOF
   ```

   Every `pairs` entry is a pair of text boxes that share screen space at 200 %, which is F69's
   first example ("it spills out of its container, and obscures the next paragraph") and its cause
   "Using absolutely positioned content" when `positioned` holds `absolute` or `fixed`; confirm each
   in the screenshot, because a sticky bar the page scrolls under is listed too and is only a defect
   when it stays on top of the text. In `focusables.js` read `order[].obscured` and `obscuredBy`: a
   control covered by a sticky header, cookie bar or floating button counts only when the 1280
   baseline run has it unobscured (F69). In `reflow.js` (it measures the current viewport)
   `wideElements` with the 640 `overflowXHidden` true hide what sits past the edge: `highlight` and
   screenshot to see whether that is text or a control; with it false they scroll, which the
   Understanding allows. Compare `visibleTextChars` and `hiddenBlocks` with the step 1 run: text
   that is there at 100 % and `display: none` at 200 % is lost unless a control reveals it. Then
   open every dialog, menu and popup at this width and screenshot each — F69's third cause is
   "Creating popups that aren't big enough for their content at the new font size" — and operate the
   task's controls. Done when every baseline item is accounted for, every overlap pair is judged,
   and every state has a screenshot.

5. Measure the text-based form controls, which F80 and C17 single out ("input boxes (text and
   textarea) as well as buttons"). Run this script twice: once at the end of step 1, while the
   viewport is still 1280 × 900 and the field is filled, and once here at 640 after re-filling the
   field, which the reloads of step 2 emptied.

   ```bash
   agent-browser fill '<the first text field>' 'Resize test 200 percent'
   agent-browser eval --stdin <<'EOF'
   (() => {
     const path = (el) => el.id ? `#${CSS.escape(el.id)}` : el.tagName.toLowerCase() +
       (el.classList.length ? `.${[...el.classList].slice(0, 2).join('.')}` : '');
     return [...document.querySelectorAll('input:not([type="hidden"]), textarea, select, button')]
       .filter((el) => el.checkVisibility()).slice(0, 40).map((el) => {
         const c = getComputedStyle(el), r = el.getBoundingClientRect();
         return { selector: path(el), tag: el.localName, type: el.type || null,
           fontSize: parseFloat(c.fontSize), w: Math.round(r.width), h: Math.round(r.height),
           cutText: /^(input|textarea)$/.test(el.localName) &&
             (el.scrollWidth > el.clientWidth + 1 || el.scrollHeight > el.clientHeight + 1),
           value: (el.value || '').slice(0, 30) }; }); })()
   EOF
   ```

   Match the two runs by `selector`. A control whose `2 × fontSize640 / fontSize1280` stays below
   1.9 while `body` reaches it is F80 — the failure's own example pairs
   `p, label { font-size: 1em }` with `input { font-size: 12pt }`, and C17 fixes exactly that pair
   with `input { font: inherit }`. A control whose `cutText` is false at 1280 and true at 640 hides
   what the user typed, the same failure seen from the box side; `w` and `h` show whether the box
   grew with it (C28 sizes such a box in `em`). `select` is left out of `cutText` because its
   scroll metrics do not describe the closed control, so judge a dropdown from the screenshot.
   Done when every visible text control has both figures and each mismatch is recorded with its
   selector.

6. When step 2 found a shortfall or steps 3 to 5 found a loss, look for the author's own text-size
   control (G178), because "Content satisfies the success criterion if it can be scaled up to 200%
   using at least one text scaling mechanism supported by user agents".

   ```bash
   agent-browser set viewport 1280 900
   agent-browser reload
   agent-browser wait --load networkidle
   agent-browser snapshot -i | grep -i -E 'text size|font size|larger|increase|A\+'
   ```

   G178's control is "links, buttons or linked images" — its examples are an "increase text size"
   button showing a big "T" with an upward arrow, "Increase text size" / "Decrease text size" links,
   a "Change text size:" label followed by "Up" and "Down", and a "Change text size" link leading to
   a list of named sizes. The step 1 viewport already satisfies G178's own first check ("Set the
   viewport size to 1024px by 768px or larger"). Click the control through every increment to its
   maximum, and after each increment rerun the step 1 script and steps 3 to 5: at 1280 there is no
   zoom factor, so enlargement is `bodyAfter / body1280` and must reach 2.0, and no increment may
   lose content or functionality ("no parts of the text are clipped, boxes do not overlap, controls
   are not obscured or separated from their labels"). Finally click the decrease control back and
   confirm the page returns to the baseline figures (G178 check #5). Done when the maximum
   enlargement, the per-increment losses and the return to default are recorded, with the viewport
   back at 640 × 900 and reloaded.

## Deciding

- Fail (certainty ≥ 90): `meta-viewport` violation (100; the G178 result is noted beside it, the
  outcome stands); read by hand, a `content` value with `user-scalable=no` (b4f0c3 Expectation 1)
  or with `maximum-scale` below 2 — `1.0`, `1.5`, or `yes`, which parses to 1.0 (Expectation 2)
  (95); a `clipped` entry with `style.hiddenBelow` or `style.hiddenRight` above 1 whose screenshot
  shows text cut or lines gone against the baseline, and no G178 mechanism rescues it (59br37, F69)
  (95); enlargement below 1.9 at both 640 and 320 for `body` or `controls` with a `vwRules`
  `fontSize` entry as the cause (F94) (95) or a breakpoint `px` rule as the cause (92); a clipped
  container whose `vwRules` entry sets `height` or `max-height` in a viewport unit (59br37 failed
  example 2) (92).
- Fail (70–89): an overlap `pairs` entry confirmed in the 200 % screenshot as text drawn over text
  or over a control (F69) (85), 88 when its `positioned` holds `absolute` or `fixed` and the
  screenshot shows the block sitting on top; `wideElements` at 640 whose cut-off part holds text or
  a control while the 640 `overflowXHidden` is true (F69) (85); a dialog, menu or popup whose text
  or buttons are cut inside it at 200 % (F69) (82); a baseline control absent at 200 % with no
  replacement that reveals it (80); a `hiddenBlocks` entry at 640 that carried content at 100 % and
  has no control that reveals it (80); a control `obscured: true` at 640 but not in the 1280
  baseline run that stays covered after scrolling (F69) (80); a form control whose font size ratio
  stays below 1.9 while `body` reaches it, or whose `cutText` turns true at 640 (F80) (80); a loss
  of text or of a control at 1024, 853 or 731 although 640 is clean (78); a G178 control whose
  maximum enlargement stays below 2.0 while zoom also falls short (80); an `inlinePx` element whose
  text is cut or overlapped at 640, with the pixel size written in the `style` attribute (SCR34)
  (75); an `ellipsis` entry whose full text stays out of reach after `hover`, `focus`, `click` and
  `get attr "<selector>" title`, and that appears nowhere else on the page, so the truncation
  allowance is not met (F69, 59br37 passed example 2) (78); an ambiguous `clipped` screenshot whose
  `hiddenBelow` and `hiddenRight` are both 0 (70).
- Needs confirmation (50–69): an ellipsis truncation whose full text is reachable only through a
  `title` tooltip or that has no visible cue besides the ellipsis (60): ask whether the full content
  is available on focus or activation and how it is indicated; content gone at 640 that looks like
  deliberate progressive disclosure (55): ask whether it is reachable another way; an overlap pair
  of a sticky bar and the text under it (55): ask whether the text stays readable while scrolling;
  clipped text in a third-party iframe (55); a shortfall with no `vwRules` entry while
  `sheets.unreadable` is non-empty, so the cause sits in a cross-origin stylesheet (50): ask for the
  CSS; a G178 control whose increments cannot be driven from the snapshot (55).
- Pass: enlargement reaches 1.9 on `body`, `controls` and `fields` at 640 or at 320 (or through a
  G178 control); no confirmed `clipped` entry; every baseline item present or reachable at 200 %;
  no overlap, obscuring or cut control text at 640 or at the 1024, 853 and 731 steps; every
  truncation meets the exception; zoom is allowed by the viewport meta tag.
- Not present: the sample's only visible text is captions or images of text.
- False positives to avoid: scrollbars at 200 % are expected, not a defect ("the browser provides
  scroll bars, if necessary") and horizontal scrolling at 640 is 1.4.10's business at 320; a
  hamburger menu replacing the navigation is relocation, not loss; `overflow: auto` or `scroll`
  containers scroll, including one nested inside a hidden ancestor (59br37 passed example 4);
  visually hidden (1 px) and `aria-hidden` text are outside 59br37 (inapplicable examples 4 and 5),
  and so is text whose parent is an SVG element (inapplicable example 2), which belongs to 1.4.5;
  a single line whose `line-height` equals its box height with the glyphs fitting is the vertical
  exception (passed example 3); `text-overflow: ellipsis` with a link to the full text is the
  horizontal exception plus the truncation allowance (passed example 2); collapsed panels hide text
  by design; a control obscured at 1280 too is 2.4.11, not a resize failure; `maximum-scale=-1` and
  a `content` of `width=device-width` pass or are inapplicable to b4f0c3; a breakpoint that shrinks
  the `px` size while the zoom factor still yields 2.0 is the Understanding's own 20 px / 10 px
  pass; anything that only breaks past 200 % is out of scope; and F69 carries the working group's
  own warning, "if the content passes the success criterion using any of the listed sufficient
  techniques, then it does not meet this failure".

## Reporting

- File under: 1.4.4. A viewport meta tag that blocks zoom is one site-wide issue under 1.4.4 that
  also names 1.4.10 (b4f0c3 maps to both); content that only breaks at 320 px belongs to 1.4.10; an
  unscalable heading or button that turns out to be a picture is 1.4.5. One issue per clipped
  component, per breakpoint rule or per form, and a shared header or footer defect names every
  sample it appears on.
- Title patterns: "Text is cut off at 200 % zoom in the <component>", "Zoom is blocked by the
  viewport meta tag", "Text does not grow when the page is zoomed", "Text overlaps other text at
  200 % zoom", "The <field> does not grow with the rest of the text", "The truncated <label> has no
  way to the full text"
- Severity: High when text or a control needed for the task is cut off, covered or gone at 200 %,
  or when a field hides what the user is typing, because the task is then unfinishable for everyone
  who zooms; Medium when secondary text is clipped or overlaps, when the text stays short of 200 %,
  or when the meta tag blocks zoom — b4f0c3's support note limits that last one to "users with older
  mobile browsers" — because the product stays usable but every page is harder work; Low for a
  truncated label whose full text is one click away, an easy workaround for a single item.
- Type: Technical for the meta tag, viewport units, `overflow: hidden`, fixed heights, pixel sizes
  written by script and form-control font sizes; Design when the zoomed layout needs a new
  arrangement before the code change makes sense; Content when an editor pasted a fixed-size box or
  an image of text into the body.
- Evidence: the 200 % page screenshot with `highlight "<selector>"` on the clipped, covered or
  missing container, next to the same region of the 100 % baseline; the `hiddenBelow` or
  `hiddenRight` pixel figure and the `style.height` value as the caption; the 1024, 853 or 731
  screenshot when the loss starts before 200 %; a GIF from `record start` / `record stop` when a
  control cannot be reached or a field cannot be read at 200 %; for the meta tag, quote `content`.
- Recommendation: remove `user-scalable=no` and any `maximum-scale` below 2 (b4f0c3); size text
  relative to its inherited size, in `em` ([C14](https://www.w3.org/WAI/WCAG22/Techniques/css/C14)),
  in per cent ([C12](https://www.w3.org/WAI/WCAG22/Techniques/css/C12)) or with a named size
  ([C13](https://www.w3.org/WAI/WCAG22/Techniques/css/C13): `xx-small`, `x-small`, `small`,
  `medium`, `large`, `x-large`, `xx-large`, `smaller`, `larger`); size the containers that hold text
  in `em` ([C28](https://www.w3.org/WAI/WCAG22/Techniques/css/C28)) or lay them out liquid
  ([G146](https://www.w3.org/WAI/WCAG22/Techniques/general/G146)) and set column widths in relative
  units so a column widens with its text
  ([C20](https://www.w3.org/WAI/WCAG22/Techniques/css/C20)), so that nothing clips when the text
  grows ([G179](https://www.w3.org/WAI/WCAG22/Techniques/general/G179)); let text-based form
  controls inherit the page size ([C17](https://www.w3.org/WAI/WCAG22/Techniques/css/C17), F80);
  compute script-set sizes and positions from the rendered text rather than from constants
  ([SCR34](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR34)); replace a
  viewport-unit `font-size` with a `rem`-based value or a `clamp()` with `rem` bounds (F94); replace
  a picture of a heading or a button label with real text styled in CSS
  ([C22](https://www.w3.org/WAI/WCAG22/Techniques/css/C22)). Keeping the page in HTML and CSS, which
  every current browser can zoom, is itself the sufficient technique
  ([G142](https://www.w3.org/WAI/WCAG22/Techniques/general/G142)), provided "the zoom function
  preserve[s] all spatial relationships on the page and [...] all functionality continues to be
  available"; an on-page control (G178) is the fallback when it cannot.

  ```html
  <!-- b4f0c3: keep zoom available -->
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  ```

  ```css
  /* C12, C13, C14: every size relative to the inherited one */
  body {
    font-size: 100%;
  }
  h1 {
    font-size: 2em;
  }
  small {
    font-size: smaller;
  }
  /* F94: a viewport-unit font-size cannot be zoomed; bound it with rem values */
  .callout {
    font-size: clamp(1rem, 1rem + 0.5vw, 1.5rem);
  }
  /* C28 and G179: .card { height: 120px; overflow: hidden } becomes a box that grows */
  /* 120px is 7.5em at the 16px default, so the text keeps its room and then takes more */
  .card {
    min-height: 7.5em;
  }
  /* C20: the column widens with the text instead of clipping it */
  #main-content {
    max-width: 70em;
  }
  /* C17 and F80: the fields and buttons follow the page text size */
  input,
  select,
  textarea,
  button {
    font: inherit;
  }
  ```

- Related: 1.4.10 when the same container also breaks at 320 px; 1.4.12 when overlap appears only
  with the spacing metrics; 1.4.13 for clipped hover or focus content; 1.4.5 when the unscalable
  text is a picture; 1.4.8 for the wider visual-presentation requirements the Understanding points
  to ("See also 1.4.8 Visual Presentation"); 2.4.11 when a sticky element covers the focused control
  at 100 % as well.
