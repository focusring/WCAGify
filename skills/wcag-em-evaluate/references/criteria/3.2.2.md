# 3.2.2 On Input

Level A · WCAG 2.0+ · Guideline 3.2 Predictable · Group: `forms` (also `keyboard`)

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#on-input) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#on-input) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-2-2-on-input/) ·
ACT: none mapped to this criterion

## Requirement

> Changing the setting of any user interface component does not automatically cause a change of
> context unless the user has been advised of the behavior before using the component.

Terms (WCAG 2.2 glossary), verbatim:

- **change of context**: "major changes that, if made without user awareness, can disorient users
  who are not able to view the entire page simultaneously". "Changes in context include changes
  of:" — "user agent"; "viewport"; "focus"; "content that changes the meaning of the web page".
  Its note: "A change of content is not always a change of context. Changes in content, such as an
  expanding outline, dynamic menu, or a tab control do not necessarily change the context, unless
  they also change one of the above (e.g., focus)." Its example: "Opening a new window, moving
  focus to a different component, going to a new page (including anything that would look to a
  user as if they had moved to a new page) or significantly re-arranging the content of a page are
  examples of changes of context." Those four items are the whole test: measure the user agent
  (window and tab count, browser dialog), the viewport (size, fullscreen), focus, and the meaning
  of the main content; judge nothing else.
- **user interface components**: "a part of the content that is perceived by users as a single
  control for a distinct function". Note 1: "Multiple user interface components may be implemented
  as a single programmatic element. 'Components' here is not tied to programming techniques, but
  rather to what the user perceives as separate controls." Note 2: "User interface components
  include form elements and links as well as components generated by scripts." So a scripted
  widget with no form markup is in scope, one element that the user reads as two controls counts
  as two components, and links are components — but activating a link is not changing a setting.
- **changing the setting** is defined in the Intent rather than the glossary, and it is the test
  for applicability: "Changing the setting of any user interface component is changing some aspect
  in the control that will persist when the user is no longer interacting with it. So checking a
  checkbox, entering text into a text field, or changing the selected option in a list control
  changes its setting, but activating a link or a button does not." The Intent's note: "This
  success criterion covers changes in context due to changing the setting or value of a control."

## In plain terms

The W3C "In Brief" states the whole duty: "Forewarn users if their context will change based on
their input." Changing what a control is set to (ticking a checkbox, picking a radio button,
choosing an option in a select, typing in a text field, toggling a pressed button) must not by
itself send the user somewhere else: no new page, window or tab, no focus jumping elsewhere, no
modal taking focus, no page whose meaning is suddenly different, unless text read before touching
the control says so — "Changes of context are appropriate only when it is clear that such a change
will happen in response to the user's action." Activating a link or a button is a request, not a
setting change. Blind and low-vision users do not see the jump, and per the Benefits section they
then discover "that the back button no longer behaves as expected"; people with cognitive
disabilities cannot tell what caused it or how to get back.

## Applies when

- Present: any state of the sample has a control whose setting "will persist when the user is no
  longer interacting with it": `forms.js` `fields[]` has an entry (text-like `input`, checkbox,
  radio, `select`, `textarea`, range, date, file), `snapshot -i` lists a `checkbox`, `radio`,
  `switch`, `slider`, `spinbutton`, `combobox`, `listbox`, `textbox` or `searchbox`, or a `button`
  with a pressed state; step 1 adds inline change handlers. Script-generated widgets with no form
  markup count (glossary note 2), and so does a group of toggle buttons used as answers. The
  cookie dialog, login dialog, filter panel and later form steps count.
- Not present: no state has such a control, only links and plain buttons ("clicking on a link is
  activating it, rather than changing its setting"). Record `not-present`, naming the states.
- Exceptions:
  - Advised beforehand: text the user meets before operating the control says what will happen
    ("Choosing a language reloads the page", "The cursor moves to the next box automatically"): a
    label, legend, `aria-describedby` text or an instruction above the form
    ([G13](https://www.w3.org/WAI/WCAG22/Techniques/general/G13)); found in `snapshot` before the
    control and in `forms.js` `visibleLabelText`, `legend` and `describedbyText`. G13 names three
    placements, and only the first two are visible in the page: "Provide instruction on the web
    page with reading order that precedes the user interface element that causes change of context
    by change of setting"; "For a multi-step process where users must complete particular steps in
    order to reach the user interface element where changes of setting would cause a change of
    context, provide the instruction as part of the process prior to the step where they would
    encounter the change of context"; and, for an intranet where training is required, "instruction
    is provided as part of the training" — that third one is invisible here and goes to the queue.
  - Content, not context: "This success criterion is automatically met if changes in content are
    not also changes of context." The Understanding's own passing example is the calendar form
    whose entry-type select reveals extra fields: "If the user selects the meeting option,
    additional fields are displayed on the page for entering the meeting participants. Different
    fields appear if the reminder option is chosen. Because only parts of the entry change and the
    overall structure remains the same, the basic context remains for the user." Dependent options
    reloading ([SCR19](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR19)), results
    filtering in place, a panel expanding: pass while url, window, viewport, focus and meaning stay.
  - Activation, not setting: the Understanding sorts buttons into three kinds. "Buttons that change
    state": "A button that has its state toggled, for example by using an aria-pressed attribute,
    is changing its setting. A button that becomes disabled when activated is changing its
    setting." — both in scope. "Buttons that submit data": "A button that submits a form and
    navigates the user to a new page is activating a control, not changing a setting." "Buttons
    that move focus": "A button that moves focus, for example to a newly opened modal dialog, a
    slide-out navigation panel, or the first item in a listbox is activating a control, not
    changing its setting." — both out of scope.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. The 3.2.2 row of the
`axe-page.mjs` output is always empty, and the data pack names no rule tagged elsewhere that
applies here, so this file cites no rule id. A static scan cannot see this defect at all: it lives
in handlers that only fire when a value changes, and its result (a new tab, a navigation, a moved
focus) is a different page state than the one axe measured.

## Manual procedure

Work at `set viewport 1280 900`, default state first, then every state in
`recon/<sample>-states.md` with a settable control (cookie dialog, login dialog, filter panel, each
form step, the error state after an invalid submit). Operate every control once: `addEventListener`
handlers leave no trace in the markup. A PDF form cannot be operated here: record `cannot-tell` and
queue it with the check of [PDF15](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF15) for the
human — "Tab to the button and check that it submits the form in response to user action to select
the button", or open the file "with a tool that is capable of showing the submit-form action". The
`keyboard` pass repeats steps 3 and 4 with the key variants on every widget it operates.

1. Inventory. Read `recon/<sample>-forms.json` (or run `forms.js`) and keep `fields[]`
   (`selector`, `tag`, `type`, `role`, `name`, `disabled`, `value`, `visibleLabelText`, `legend`,
   `describedbyText`) and `forms[]` (`selector`, `submitButtons`); read
   `recon/<sample>-focusables.json` and keep `order[]` (`index`, `selector`). This is step 1 of the
   [F37](https://www.w3.org/WAI/WCAG22/Techniques/failures/F37) procedure ("Find each form in a
   page") and the whole of [G80](https://www.w3.org/WAI/WCAG22/Techniques/general/G80) ("Find all
   forms in the content. For each form, check that it has a submit button"). Add the markup
   signals:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const t = n => n.localName + (n.id ? '#' + n.id : '') +
       (!n.id && n.classList[0] ? '.' + n.classList[0] : '');
     const S = 'input,select,textarea,[aria-pressed],[role=switch],[role=radio],' +
       '[role=checkbox],[role=option],[role=slider],[role=spinbutton]';
     const risky = /submit\(|location|open\(|focus\(|href/;
     const code = (e, as) => as.map(a => e.getAttribute(a) || '').join(' ').trim().slice(0, 120);
     const inline = [...document.querySelectorAll('[onchange],[oninput],[onblur]')]
       .map(e => ({ el: t(e), code: code(e, ['onchange', 'oninput', 'onblur']) }));
     const onclick = [...document.querySelectorAll(S)].filter(e => e.hasAttribute('onclick'))
       .map(e => ({ el: t(e), code: code(e, ['onclick']) }));
     const all = [...inline, ...onclick];
     return { inline, onclick,
       suspect: all.filter(i => risky.test(i.code)).map(i => i.el),
       named: all.filter(i => !risky.test(i.code)).map(i => i.el),
       noSubmit: [...document.forms].filter(f => !f.querySelector('button:not([type]),' +
         'button[type=submit],input[type=submit],input[type=image]')).map(t),
       pressed: [...document.querySelectorAll('[aria-pressed],[role=switch]')].map(t) };
   })()
   EOF
   ```

   `suspect` names handlers whose own text navigates, submits, opens or moves focus
   ([F36](https://www.w3.org/WAI/WCAG22/Techniques/failures/F36),
   [F37](https://www.w3.org/WAI/WCAG22/Techniques/failures/F37)). `named` is just as suspect: F37's
   own example is `<input type="radio" onclick="goToMirror(this);">`, whose handler text names a
   function that calls `window.open`, so read the function before deciding to skip it:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => { const f = window.goToMirror;
     return typeof f === 'function' ? String(f).slice(0, 300) : 'not a global'; })()
   EOF
   agent-browser get attr "#mirror_belnet" onclick
   ```

   `noSubmit` applies the list of [H32](https://www.w3.org/WAI/WCAG22/Techniques/html/H32) exactly
   (`<input type="submit">`, `<input type="image">` or `<button type="submit">`); a form in it is
   the shape F36 describes, because something else has to submit it. `pressed` and the
   `snapshot -i` widgets extend `fields[]`; `disabled` fields are skipped. Done when the findings
   file lists every settable control of the state with its selector, kind, its inline handler text
   if any, and the `order` index after it.

2. Context logger, written once per session; it prints everything the glossary calls a change of
   context — user agent, viewport, focus, and the meaning of the main content:

   ```bash
   cat > .notes/audit/recon/context-logger.js <<'EOF'
   (() => {
     const t = n => n.localName + (n.id ? '#' + n.id : '') +
       (!n.id && n.classList[0] ? '.' + n.classList[0] : '');
     const a = document.activeElement, h = document.querySelector('h1, h2');
     const main = document.querySelector('main, [role=main]') || document.body;
     return { url: location.href, title: document.title, scrollY: Math.round(scrollY),
       focus: !a || a === document.body ? 'BODY' : t(a),
       dialogs: [...document.querySelectorAll('dialog[open],[role=dialog],[role=alertdialog],' +
         '[aria-modal=true]')].filter(d => d.getClientRects().length).map(t),
       heading: h ? h.textContent.replace(/\s+/g, ' ').trim().slice(0, 60) : null,
       words: main.innerText.split(/\s+/).length,
       fields: main.querySelectorAll('input,select,textarea,button').length,
       viewport: innerWidth + 'x' + innerHeight, fullscreen: !!document.fullscreenElement };
   })()
   EOF
   agent-browser eval --stdin < .notes/audit/recon/context-logger.js
   agent-browser tab list
   agent-browser dialog status
   ```

   `heading`, `words` and `fields` together are the probe for "significantly re-arranging the
   content of a page": a form replaced by a confirmation drops `fields` to near zero while `url`
   holds. `viewport` and `fullscreen` catch a resized or fullscreened window, `tab list` a new one,
   `dialog status` a browser dialog that took focus out of the page. Done when the baseline line,
   the tab count and the dialog status of the state are in the findings file.

3. Change each setting and read the logger. This is step 2 of the F37 procedure ("For each form
   control that is a radio button, check box or an item in a select list, check if changing the
   selection of the control launches a new window"), widened to every settable control and every
   kind of context change. Per control, each change followed by `agent-browser wait 800`,
   `agent-browser tab list`, `agent-browser dialog status` and then the logger:

   ```bash
   agent-browser focus "input[name='phone']"; agent-browser keyboard type "0612345678"
   agent-browser focus "input[name='newsletter']"; agent-browser press Space
   agent-browser focus "select[name='lang']"; agent-browser press ArrowDown
   agent-browser focus "select[name='lang']"; agent-browser select "select[name='lang']" "nl"
   agent-browser focus "input[name='mirror'][value='belnet.be']"; agent-browser press Space
   agent-browser eval --stdin < .notes/audit/recon/context-logger.js
   ```

   A radio group, slider or combobox takes `press ArrowDown`, a pressed button `press Enter`;
   after each typed value also `press Tab` and read the logger again, then `press Shift+Tab` back
   into the field and out of it the other way, because F36 fires "even navigating backwards in the
   tab order". Type complete values: the defect fires on completion. Expected after typing, Space,
   ArrowDown or Enter: `focus` is the control itself, `url`, `title`, `dialogs`, `heading`,
   `fields`, `viewport`, `fullscreen` and the tab count as in the baseline, `dialog status` empty;
   after Tab: `focus` is the next `order` entry. Where the key changed nothing (`get value`,
   `is checked`), redo it with `click`, `check` or `select`; `select` sets a value without focusing
   the control, so `focus` it first or the logger reads `focus: BODY` from the tool. A new tab
   becomes the active tab, so `tab list` comes before the logger: `screenshot`, `tab close`, then
   the logger on the sample's tab. A browser dialog blocks everything until `dialog dismiss`. After
   a navigation: `back`, `wait --load networkidle`, fresh `snapshot`. Done when every control has a
   row "unchanged" or the logger fields that differ, with the key that produced it.

4. Arrow through the options without committing. F36 names this as its second problem: "with some
   form elements, the value of the field changes as each item is navigated with the keyboard, again
   accidentally submitting the form", and [H84](https://www.w3.org/WAI/WCAG22/Techniques/html/H84)
   gives the reason — "navigating through the options of the select element changes the value of
   the control". Per `select`, radio group and custom combobox or listbox:

   ```bash
   agent-browser get value "select[name='sort']"
   agent-browser focus "select[name='sort']"
   agent-browser press ArrowDown; agent-browser wait 800
   agent-browser eval --stdin < .notes/audit/recon/context-logger.js
   agent-browser press ArrowDown; agent-browser wait 800
   agent-browser eval --stdin < .notes/audit/recon/context-logger.js
   agent-browser get value "select[name='sort']"
   ```

   For a native `select` or a radio group, every arrow step commits a value in current user agents,
   so a per-option action is the F36 Example 2 shape ("A user using a keyboard will not be able to
   navigate past the first item in the menu"). For a custom combobox or listbox, arrowing must move
   `aria-activedescendant` only: re-run `snapshot -i` and confirm nothing else changed until
   `press Enter`. Where the control drives a dependent element, this is SCR19's second expectation:
   "Navigate to the trigger select element, navigate through the options but do not change the
   value" and "Check that the matching option values are still displayed in the associated element"
   — SCR19 passes only when both its expectations hold, the first being that committing a value
   does update the dependent element ("Check that the matching option values are displayed in the
   other select element"). Done when every option-list control has the two logger lines and a note
   "per-option action: yes | no".

5. Whole-form runs ([F36](https://www.w3.org/WAI/WCAG22/Techniques/failures/F36)), following its
   procedure exactly: "Enter data in all fields on page starting at top"; "Enter data in last field
   and exit from it (tab out of it)"; "Check whether leaving the last field causes change of
   context." For each entry of `forms[]`, `fill` every field with a valid value in source order,
   the last one with `focus` and `keyboard type`, then `wait 1500` and the logger without pressing
   anything; then `press Tab` to blur it and the logger again, as a `change` handler fires only
   there; then `press Shift+Tab` back in and `press Shift+Tab` out, the backwards exit F36 calls
   out. A submission, navigation or new step at any of those readings is the F36 pattern.
   `press Enter` in the last field next: implicit submission is activation, no defect; a `noSubmit`
   form that never submits is noted for 2.1.1. Done when each form has "submits on: button | value
   | blur | backwards blur | Enter only".

6. Advice ([G13](https://www.w3.org/WAI/WCAG22/Techniques/general/G13)) for every row of steps 3 to
   5 that is not "unchanged" — step 3 of the F37 procedure, "For each new window resulting from
   step 2, check if the user is warned in advance", and G13's own check, "Check to see that an
   explanation of what will happen when the control is changed is available prior to the control's
   activation". Run `snapshot -s "<form css>"` for the form in tree order, a plain `snapshot` for
   the text before it, plus `visibleLabelText`, `legend` and `describedbyText`; for a control in a
   later step of a process, also the text of the earlier steps in `recon/<sample>-states.md`.
   Advice counts when it precedes the control in the tree and names the effect (reload, new page,
   new window, focus moving); advice only in a `placeholder` or `title`, or an `aria-live` message
   after the change, goes to the queue. Two shapes that do count are G13's own examples: "A select
   dropdown at the top of a page includes options for German, French and Spanish. Instructions
   preceding the dropdown instruct the user that the language will be changed upon selecting an
   option", and "A 50-question online survey displays one question at a time, with each answer
   marked up as a toggle button. Instructions appear at the beginning of the survey that explain
   that users will be taken to the next question of the survey upon selecting an answer to each
   question." Done when each row has "advised: <text>" or "none".

7. Reading order of a dependent update. SCR19 covers an in-place update only under one condition:
   "It is important to note that the select item which is modified is after the trigger select
   element in the reading order of the web page. This ensures that assistive technologies will pick
   up the change and users will encounter the new data when the modified element receives focus."
   For every control whose change rewrote another element rather than the page:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const a = document.querySelector('#continent'), b = document.querySelector('#country');
     if (!a || !b) return 'missing';
     return { updatedFollowsTrigger:
       !!(a.compareDocumentPosition(b) & Node.DOCUMENT_POSITION_FOLLOWING) };
   })()
   EOF
   ```

   `true` with url, window, viewport and focus held is the SCR19 pass. `false` means the new data
   sits behind the user's reading position: queue it. Done when every in-place update has
   `updatedFollowsTrigger` recorded.

8. Classify each candidate without advice against Deciding, matching a row's whole condition, not
   one signal: `dialogs` grown counts only with `focus` inside it, a reload only when `focus`
   drops to `BODY`; a changed `heading` or halved `words` under a held `url`, `focus`, `dialogs`,
   `viewport` and tab count is a content change for the queue unless `fields` also collapsed, which
   is the "looks to a user as if they had moved to a new page" shape. Done when each candidate has
   a class and a certainty.

9. Evidence per fail: `record start .notes/audit/evidence/<sample>-3.2.2-<slug>.webm`, redo the
   change from step 3 or the arrow walk from step 4, `wait 1500`, `record stop`; back in the
   baseline state, `highlight "<control css>"` and
   `screenshot .notes/audit/evidence/<sample>-3.2.2-<slug>.png`; a screenshot of the destination,
   and the `tab list` output when a tab was opened. Done when every fail has the recording, both
   screenshots and its logger lines in the findings file.

## Deciding

- Fail (certainty ≥ 90): a select, radio, checkbox, switch or custom option whose value change
  opens a new tab or window (tab count grows) with no advice before it
  ([F37](https://www.w3.org/WAI/WCAG22/Techniques/failures/F37)) — 95; a value change that
  navigates to another page (`url` changes, `heading` differs, `focus` `BODY`) or submits the form
  with no advice, on the last field of a form, whether it is left forwards or backwards in the tab
  order ([F36](https://www.w3.org/WAI/WCAG22/Techniques/failures/F36)) or on any other control (a
  language select, a sort control that loads a new page) — 95; an option list where every arrow
  step fires the action, so the keyboard user cannot reach the later options at all (F36 Example 2)
  — 95; a complete value typed in a field that moves `focus` to another element with no advice
  (auto-advance) — 90; a value change that resizes the window, enters fullscreen or opens a
  differently sized window (`viewport` or `fullscreen` differs) with no advice — 90.
- Fail (70–89): a value change that opens a dialog (`dialogs` grows) and moves `focus` into it —
  85; a switch or pressed button (cookie consent toggle, view toggle) that reloads the page and
  drops `focus` to `BODY` — 85; a value change that replaces the main content so that the page
  "would look to a user as if they had moved to a new page" (`heading`, `words` and `fields` all
  change) while `url` and `focus` hold — 80; a filter or sort control that reloads the same page
  (same `heading`, results updated) and drops `focus` to `BODY` — 80; a new form step replacing the
  current one in the screenshot, `url` held and no submit pressed, after a value — 80; a value
  change that opens a browser dialog (`dialog status` non-empty), which takes focus out of the page
  — 75; `focus` moved to an error message or summary right after a value change, before any submit
  — 75; advice the user meets only after the control, later in tree order — 70.
- Needs confirmation (50–69): advice only in a `placeholder` or `title`, which the tree cannot
  prove is read before use — 60; vague advice ("This form is interactive"): ask whether it names
  the observed effect — 60; a dependent element rewritten by the change that sits before the
  trigger in reading order (step 7 `updatedFollowsTrigger` false), which SCR19 does not cover: ask
  whether a screen reader user meets the new data — 60; an intranet or authenticated application
  where G13's third placement may apply: ask whether the required user training describes this
  behaviour — 55; an in-place update where `heading` changes or `words` halves while url, focus,
  dialogs, viewport and the tab count hold: ask whether the meaning changed — 55; a live region
  replacing the main text: ask a screen reader user — 50; a change that only scrolls — 50. A PDF
  form that cannot be operated in the browser: `cannot-tell`, with the PDF15 check for the human.
- Pass: every settable control in every state, changed by key and by value and arrowed through
  without committing, keeps `url`, `title`, the tab count, `viewport`, `fullscreen`, `dialogs` and
  `focus` (on itself, or on the next `order` entry after Tab), or has advice before it that names
  the effect. Content updating under a held url, focus, viewport and window passes, including a
  select that only rewrites an element after it in reading order (SCR19). A select plus a button
  passes both H84 checks: "focus (including keyboard focus) on an option in the select element does
  not result in any actions" and "selecting the button performs the action associated with the
  current select value".
- Not present: no state has a control whose setting persists; links and plain buttons only.
- False positives to avoid: activation: a submit, "Go", "Show" or "Update" button beside the
  control ([H84](https://www.w3.org/WAI/WCAG22/Techniques/html/H84)), Enter in a text field
  (implicit submission), a button that submits a form and navigates, or that moves focus to a
  newly opened modal dialog, a slide-out navigation panel or the first item in a listbox; content
  changes: additional fields appearing for the chosen entry type (the Understanding's calendar
  example), dependent options reloading with focus held, results filtering in place, a panel or tab
  panel changing; the value of a native select changing as the user arrows through it, which is the
  user agent's own behaviour and only a defect when an action fires with it; an advised
  auto-advance (the Understanding's phone-number example, "This behavior of phone fields is
  described for the user at the beginning of the form"); a toggle-button survey that moves to the
  next question when the instructions at the start say it will (G13 example 2); focus moving to the
  next control because Tab was pressed; a `focus: BODY` after a bare `select` with `url` and the
  tabs held; a change that fires when the control merely receives focus (3.2.1).

## Reporting

- File under: 3.2.2 for every unannounced change of context caused by a setting change. A change
  that fires when the control merely receives focus is 3.2.1; a new window opened by a link or
  button is 3.2.5; focus landing somewhere illogical after an advised change is 2.4.3; a form with
  no way to submit is 2.1.1; the error text shown on change is 3.3.1; a checkout, legal or
  financial step submitted before the user could review it is also 3.3.4. A radio group, checkbox
  or select that _is_ advised beforehand passes here and still belongs in the report: per the F37
  note, "it will pass the requirements of 3.2.2 On Input if an indication or warning is added
  stating that selecting a radio button will result in a change of context; however, this scenario
  would still likely fail 2.1.1 Keyboard, since it's not possible (in current user agents) for a
  user to navigate through a set of radio buttons with the keyboard without triggering a change
  event" — record the pass here and raise the finding under 2.1.1. One issue per control or form;
  a site-wide component (language select, cookie toggles) names the other samples.
- Title patterns: "The language select navigates as soon as an option is chosen", "The form
  submits itself when the last field is filled", "Choosing a delivery option opens a new window",
  "Focus jumps to the next field while typing the phone number", "Arrowing through the sort menu
  loads a new page for every option", "Selecting a download mirror opens a new window"
- Severity: High when the change leaves the user on another page, window or step, or submits data
  they were still entering (language select, auto-submit of a checkout step, a new window from a
  radio group), or when the keyboard user cannot reach the later options of the control at all;
  the new window also breaks Back, which the Understanding names as the specific harm ("the back
  button no longer behaves as expected"). Medium when the user stays on the page but loses their
  place (auto-advance, focus into a dialog, a filter reload that drops focus), or the control is in
  a site-wide component; Low when the change is reversed in one step (a hash jump, a reload that
  keeps every entry).
- Type: Technical (the handler, the missing submit button, the `window.open`); Content when the
  behaviour is intended and only the advisory text before the control is missing.
- Evidence: the recording of the value change and what follows (navigation, new tab, focus jump),
  and for a per-option action the recording of the arrow walk showing the page leaving on the first
  option; the baseline screenshot with `highlight` on the control, a screenshot of the destination
  page, and the `tab list` output or the `get url` line that proves the window or page changed.
- Recommendation: let a button perform the action and act on it, not on the change
  ([G80](https://www.w3.org/WAI/WCAG22/Techniques/general/G80),
  [H32](https://www.w3.org/WAI/WCAG22/Techniques/html/H32),
  [H84](https://www.w3.org/WAI/WCAG22/Techniques/html/H84)); update dependent content in place,
  in an element that follows the trigger in reading order, without moving focus or navigating
  ([SCR19](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR19)); where the change
  must stay, describe it before the control
  ([G13](https://www.w3.org/WAI/WCAG22/Techniques/general/G13)); in a PDF form, use a submit button
  with the submit-form action ([PDF15](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF15)).
  Name the handler to drop and the button to add:

  ```html
  <!-- defect: the action fires on the value (F36, F37) -->
  <select name="lang" onchange="form1.submit();">
    …
  </select>
  <input type="radio" name="mirror" onclick="goToMirror(this);" />

  <!-- fix: the user asks for the action (G80, H32, H84) -->
  <label for="lang">Language</label>
  <select id="lang" name="lang">
    …
  </select>
  <button type="submit">Change language</button>

  <!-- or, where the behaviour must stay, advise first (G13) -->
  <p id="lang-note">Choosing a language reloads the page in that language.</p>
  <select id="lang" name="lang" aria-describedby="lang-note">
    …
  </select>
  ```

  H32 accepts `<input type="submit">`, `<input type="image">` or `<button type="submit">`; use
  `<button type="button">` instead when the action is scripted rather than a form submission.

  links, buttons and redirects too); 2.4.3 Focus Order (where focus lands after an advised
  change); 2.1.1 Keyboard (an advised radio group or select that still cannot be arrowed through,

  Error Identification; 3.3.4 Error Prevention (a legal, financial or data step submitted before
