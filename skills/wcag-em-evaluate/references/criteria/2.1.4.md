# 2.1.4 Character Key Shortcuts

Level A · WCAG 2.1+ · Guideline 2.1 Keyboard Accessible · Group: `keyboard`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)
· [Spec](https://www.w3.org/TR/WCAG22/#character-key-shortcuts) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#character-key-shortcuts) ·
[Plain English][plain] ·
ACT: [ffbc54](https://www.w3.org/WAI/standards-guidelines/act/rules/ffbc54/)

[plain]: https://aaardvarkaccessibility.com/wcag-plain-english/2-1-4-character-key-shortcuts/

## Requirement

> If a keyboard shortcut is implemented in content using only letter (including upper- and
> lower-case letters), punctuation, number, or symbol characters, then at least one of the
> following is true:
>
> - Turn off: A mechanism is available to turn the shortcut off;
> - Remap: A mechanism is available to remap the shortcut to include one or more non-printable
>   keyboard keys (e.g., Ctrl, Alt);
> - Active only on focus: The keyboard shortcut for a user interface component is only active when
>   that component has focus.

Terms (WCAG 2.2 glossary): **keyboard shortcuts**: "alternative means of triggering an action by
the pressing of one or more keys" — one key or several, so a two-key sequence is one shortcut.
**mechanism**: "process or technique for achieving a result", Note 1: "The mechanism may be
explicitly provided in the content, or may be relied upon to be provided by either the platform or
by user agents, including assistive technologies", Note 2: "The mechanism needs to meet all success
criteria for the conformance level claimed". Note 1 is why a turn-off supplied by the operating
system or the browser can satisfy the criterion (step 5, needs confirmation); Note 2 is why a
turn-off control that has no accessible name or cannot be operated by keyboard is not a mechanism.
**user interface components**: "a part of the content that is perceived by users as a single control
for a distinct function", Note 1: "Multiple user interface components may be implemented as a single
programmatic element. 'Components' here is not tied to programming techniques, but rather to what
the user perceives as separate controls", Note 2: "User interface components include form elements
and links as well as components generated by scripts". The third bullet is met only when the
shortcut belongs to the component the user perceives as one control, so a handler that happens to
fire while any link or any region has focus is not "the keyboard shortcut for a user interface
component".

## In plain terms

A shortcut that fires on one printable key (`s`, `?`, `/`, `1`, or a sequence such as `g` then `a`)
is triggered by anything that produces that character: dictated speech, a resting hand, a slip.
Speech users work in one mode that mixes dictation and commands, so "a spoken word can become a
barrage of single-key commands if the cursor focus happens to be in the wrong place" — W3C's example
is a colleague saying "Hey Kim" into an open microphone of a mail app, where the `y` archives the
message, the `k` moves down one conversation and the `m` mutes a thread. The author either scopes
the shortcut to its component, so it works only while that component has focus, or gives the user a
setting to turn it off or add a modifier (Ctrl, Alt). It matters to speech-input users, whose
dictation becomes key presses, and to keyboard users with tremor; remapping additionally helps users
with some cognitive disabilities, "since the same shortcuts can be assigned to perform the same
actions across different applications".

## Applies when

- Present: a script of the sample acts on a `keydown` or `keyup` whose `key` is a printable
  character pressed without Ctrl, Alt or Meta, and the action changes content (opens a panel,
  moves focus, navigates, selects, toggles, submits, plays or mutes). Signs: `aria-keyshortcuts`
  values without a modifier, `<kbd>` elements or "press ? for shortcuts" text, a shortcut help
  overlay, a hotkey library, a media player with page-wide hotkeys (`k`, `m`, `f`), and any key of
  the sweep in step 2 that changes content while nothing has focus. Sequences and Shift characters
  count. Probes that feed the steps: `structure.js` (`accesskeys`, `iframes`), `focusables.js`
  (`order[].selector` / `.role` for the plain-link retest in step 3), `media.js`
  (`media[].kind`, `.selector`, `.provider`, `.controls`) for player hotkeys.
- Applicability (ffbc54), all three at once: "the event's attribute `key` is a printable character
  key; and the event's method `getModifierState` returns false for each of the valid modifier keys;
  and the event causes changes in the content of the HTML document". A listener that reads keys but
  changes nothing is out of scope, and so is one that only acts with a modifier held.
- Changes in content (ffbc54 glossary), any one of: "visible changes: the rendered pixels change in
  any part of the document that is currently within the viewport or that can be brought into the
  viewport via scrolling"; "accessibility tree changes: any state, property or event of a node
  representing an accessible object of the accessibility tree changes, or any node is inserted in,
  or removed from the accessibility tree"; "audible changes: the audio rendered by the web page
  changes". The comparison is made "by comparing the web page before and 1 minute after the event
  firing", and ACT flags that "The arbitrary 1 minute time span [...] is not included in WCAG" — a
  change that arrives after the sweep's 150 ms window still counts, which is what step 3 re-checks.
- Printable characters (ffbc54 glossary): "a character that occupies a printing position on a
  display", i.e. Unicode categories Letter (LC, Ll, Lm, Lo, Lt, Lu), Number (Nd, Nl, No), Mark (Mc,
  Me, Mn), Punctuation (Pc, Pd, Pe, Pf, Pi, Po, Ps), Symbol (Sc, Sk, Sm, So) and Space (Zs).
  Accented and non-Latin characters are printable; Escape, Tab, the arrows and F1–F12 are not.
- Not present: no printable key, alone or in a sequence, changes content while the body or a plain
  link has focus, in any state, and no component declares or documents a single-character key.
- Exceptions: none in the text. Out of scope per the Understanding page: components "such as
  listboxes and drop-down menus" whose letter keys "are only active when the components have
  focus"; menus opened "with a single non-character shortcut (e.g., Alt or Alt+F) before pressing
  a single character key", which "makes the full path to invoking a menu a two-step shortcut that
  includes a non-printable key"; access keys, which "are generally (depending on the user agent)
  activated using modifier keys". Non-printable keys and shortcuts that need Ctrl, Alt or Meta are
  outside the criterion (ffbc54 Inapplicable Examples 1 and 2).
  [G217](https://www.w3.org/WAI/WCAG22/Techniques/general/G217) states the same carve-out
  positively: "If the keyboard shortcut is only active when a particular user interface component
  has focus, then the author does not need to provide an override mechanism."
- Not an exception, physical keys: "it's not relevant whether a shortcut can be activated using a
  single physical key on a keyboard, or if it requires a combination of keys to be pressed" — `?`
  is Shift+/ on a US keyboard and `é` is AltGr+e on a UK one, and both stay in scope. "What matters
  is that a shortcut relies on a printable character (letters, punctuation, numbers, symbol
  characters), and not the number of physical keyboard keys that users need to press to trigger it."
- Not an exception, sequences: "The success criterion also applies to situations where a shortcut is
  based on a sequence of character keys – for example, pressing G and then A in quick succession to
  trigger an action. While the individual character key presses don't immediately trigger the
  action, overall these types of shortcuts still rely on a series of character keys."
- Not an exception, legacy events: ffbc54 tests `keydown` and `keyup` only — "Keyboard events of
  type keypressed are considered legacy keyboard events and are thus ignored by this rule". A
  shortcut wired to `keypress` still fires on a character key, so judge it under the criterion text
  from the real press in step 3.

## Manual procedure

1. Inventory declared, documented and coded shortcuts. Ask the author first where the project gives
   access to one: F99 — "The test procedure suggests asking the author (often the developer of the
   site) whether keyboard shortcuts are used. If that information is trusted then the procedure can
   be simpler than pressing all the keys"; G217 — "the existence and nature of shortcut keys can
   often be determined simply by asking involved designers and developers". A trusted list shortens
   step 2; it never replaces step 3. Run `structure.js` and set its `accesskeys` aside (the user
   agent adds a modifier to them). Then collect what the page itself declares:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => ({ keyshortcuts: [...document.querySelectorAll('[aria-keyshortcuts]')]
        .map(e => ({ sel: e.tagName.toLowerCase() + (e.id ? '#' + e.id : ''),
                     keys: e.getAttribute('aria-keyshortcuts') })),
      kbd: [...document.querySelectorAll('kbd')].map(e => e.textContent.trim()),
      mentions: (document.body.innerText.match(
        /[^.\n]{0,60}(shortcut|sneltoets|hotkey|press \S{1,3} to)[^.\n]{0,60}/gi) || [])
        .slice(0, 10) }))()
   EOF
   ```

   Then read the scripts, which F99 names as the second source of candidates: "Viewing page scripts
   and searching for typical keyboard event handlers such as `document.addEventListener('keydown'
...)` or the handling of keyboard-related event properties with code such as `.key`, `.code`,
   `.charCode`, or `.keyCode` may establish the presence of scripts that intercept keyboard
   shortcuts without modification keys like ALT or Ctrl being held down at the same time."

   ```bash
   agent-browser eval --stdin <<'EOF'
   (async () => {
     const tags = [...document.querySelectorAll('script')];
     const texts = [tags.filter(s => !s.src).map(s => s.textContent).join('\n')];
     for (const s of tags.filter(s => s.src).slice(0, 20)) {
       try { texts.push(await (await fetch(s.src)).text()); } catch { texts.push(''); }
     }
     const body = texts.join('\n'), n = re => (body.match(re) || []).length;
     return {
       listeners: n(/addEventListener\(\s*['"`]key(down|up|press)['"`]/g),
       inlineHandlers: n(/\bon(keydown|keyup|keypress)\s*[=:]/g),
       props: { key: n(/\.key\b/g), code: n(/\.code\b/g), keyCode: n(/\.keyCode\b/g),
                charCode: n(/\.charCode\b/g) },
       guards: n(/(ctrlKey|altKey|metaKey|getModifierState)/g),
       literals: [...new Set([...body.matchAll(/\.key\s*===?\s*['"](.)['"]/g),
                              ...body.matchAll(/case\s*['"](.)['"]\s*:/g)]
                              .map(m => m[1]))].slice(0, 40)
     };
   })()
   EOF
   ```

   `literals` are single-character comparisons and are candidate keys; `guards` near zero with
   `listeners` above zero means nothing filters out modifier-less presses. A cross-origin script
   that fails to fetch returns an empty string, and F99 warns "As there are several ways of
   implementing character key events, this method is not considered reliable" — a zero count settles
   nothing, step 2 still runs. Add the keys any shortcut help overlay the page offers lists.
   Done when each candidate key or sequence is in the findings file with its action and its
   source (author, attribute, documentation, script).

2. Neutral state, then a synthetic sweep of the printable keys (in page, about fifteen seconds).
   F99 step 1: "If loading the page sets focus to an input, click on an empty part of the page to
   ensure that no inputs are in focus." Check it before sweeping:

   ```bash
   agent-browser press Escape
   agent-browser eval --stdin <<'EOF'
   (() => ({ active: document.activeElement.localName, id: document.activeElement.id || null }))()
   EOF
   ```

   `active` other than `body` means the page steals focus: `agent-browser click "body"` on an empty
   area, re-check, and note it — a page that parks focus in an editor hides its own global keys.

   ```bash
   agent-browser eval --stdin <<'EOF'
   (async () => {
     const plain = [...'abcdefghijklmnopqrstuvwxyz0123456789'];
     const unshifted = [...'/.,;\'[]\\-=`'];
     const shifted = [...'?:"+!@#$%^&*()_{}|<>~'];
     const set = [...plain.map(k => ({ key: k, shift: false })),
                  ...unshifted.map(k => ({ key: k, shift: false })),
                  ...shifted.map(k => ({ key: k, shift: true })),
                  ...plain.filter(k => /[a-z]/.test(k))
                    .map(k => ({ key: k.toUpperCase(), shift: true }))];
     const media = () => [...document.querySelectorAll('video,audio')]
       .map(m => [m.paused, m.muted, m.volume, m.playbackRate].join(',')).join(';');
     const state = () => [location.href, document.activeElement.localName, scrollY | 0,
                          media()].join('|');
     const pause = ms => new Promise(r => setTimeout(r, ms));
     let seen = 0; const obs = new MutationObserver(rs => { seen += rs.length; });
     obs.observe(document.documentElement, { childList: true, attributes: true, subtree: true });
     await pause(500); const baseline = seen, hits = [];
     for (const { key, shift } of set) {
       document.activeElement.blur(); const before = state(), was = seen, init = { key,
         bubbles: true, cancelable: true, shiftKey: shift,
         code: /^[a-zA-Z]$/.test(key) ? 'Key' + key.toUpperCase() : '' };
       const kept = document.body.dispatchEvent(new KeyboardEvent('keydown', init));
       document.body.dispatchEvent(new KeyboardEvent('keyup', init));
       await pause(150); const mutations = seen - was;
       if (!kept || state() !== before || mutations > 0)
         hits.push({ key, shift, prevented: !kept, stateChanged: state() !== before, mutations });
     }
     obs.disconnect(); return { baseline, tested: set.length, hits };
   })()
   EOF
   ```

   `tested` is 94: 36 letters and digits, 11 unshifted punctuation and symbol keys, 21 shifted
   symbols, and the 26 upper-case letters that cover F99's "Hold the Shift key and press the same
   keys again". `baseline` is the mutation count in 500 ms without any key; above 0 the page mutates
   on its own (ads, a carousel) and only keys whose `mutations` stand out count. A hit is
   `prevented: true` (a handler consumed the key), `stateChanged: true` (URL, focus, scroll or a
   player's `paused`/`muted`/`volume` changed, which is ACT's "audible changes") or `mutations`
   above 0, which covers ACT's "accessibility tree changes" because the observer watches attributes
   and child lists. The 150 ms window is shorter than ACT's one minute, so a delayed reaction shows
   up only in step 3. An abort means the last key navigated (`back`, list it, rerun without it).
   Skip the sweep where a key could change data (a mailbox, an editor); `isTrusted` checks defeat
   it, so step 3 covers every step-1 key regardless of what the sweep returned. Done when the hits
   are in the findings file.

3. Confirm each candidate with a real key press, one key at a time. F99 limits the set: "Do not
   press non-printing modifier and control keys such as Ctrl, Alt, Esc, Arrow keys and (where
   present) the function keys F1-F12. Also exempt are Space, Enter, Return, Tab, and the Delete
   key." In agent-browser 0.37 a `press "<printable key>"` sticks — some thirty `keydown` events,
   repeating until `reload` releases it — so `reload` follows every press; name evidence
   `<keyname>`, not the character.

   ```bash
   agent-browser screenshot .notes/audit/evidence/<sample>-2.1.4-<keyname>-before.png
   agent-browser press "<key>"
   agent-browser screenshot .notes/audit/evidence/<sample>-2.1.4-<keyname>-after.png
   agent-browser get url
   agent-browser snapshot
   agent-browser eval --stdin <<'EOF'
   (() => ({ media: [...document.querySelectorAll('video,audio')]
     .map(m => ({ src: m.currentSrc, paused: m.paused, muted: m.muted, volume: m.volume })) }))()
   EOF
   agent-browser reload
   agent-browser press "Shift+<key>"
   agent-browser reload
   ```

   It fired when focus moved or a panel, the URL, a state, a selection or a player changed: the two
   screenshots give ACT's "visible changes", the `snapshot` diff gives its "accessibility tree
   changes" and the media line gives its "audible changes". Take the after-screenshot again a few
   seconds later when the first one looks unchanged — the change window in ffbc54 is a minute. The
   Shift repeat is F99 step 3 and catches upper-case-only bindings. A sequence is two `press` calls
   in a row, then one `reload`. For keys of step 1 that did nothing from the body, repeat once with
   focus on a link in prose or navigation that is not inside a menu, menubar, listbox, tree or grid
   (`focus "<css>"` of an `order` entry of `focusables.js` with role `link`): handlers that only
   skip text fields fire there. Wrap a key that moves focus in `record start <file.webm>` and
   `record stop`. A key whose action must not repeat (send, delete, archive, pay) is judged from
   step 2 and the source and recorded `cannot-tell`. Done when each candidate is "fires from the
   body", "fires from a plain link" or "does nothing".

4. Test "Active only on focus" for every shortcut that fired. ffbc54 expectation, second branch:
   "focus: the event target is an inheriting semantic widget", which the rule explains as "each
   keyboard event is dispatched to an event target. The event target is the element that has focus.
   As such, the 'Active only on focus' requirement from Success Criterion 2.1.4 is implied by saying
   that the event target is an inheriting semantic widget." Focus its component (the list it moves,
   the player it controls):

   ```bash
   agent-browser focus "<component css>"
   agent-browser press "<key>"
   agent-browser reload
   agent-browser press "<key>"
   agent-browser reload
   ```

   A shortcut that works with the component focused and does nothing from the body (the reload puts
   focus back there) is scoped: record "Active only on focus" and stop for that key. Where the
   listener sits does not decide this — ffbc54 Passed Example 5 binds on `document.body` and still
   passes because the handler checks `document.activeElement === target`; the presses decide. The
   component has to be a widget in the tree (`snapshot` shows `listbox`, `combobox`, `grid`, `tree`,
   `menu`, `textbox`, `slider` or `button`); one that fires with focus anywhere inside a landmark,
   an `application` region or a plain `div` is global. `link` also inherits from `widget`, so
   ffbc54's focus branch reads as met when a plain link is the event target; the criterion asks for
   "The keyboard shortcut for a user interface component", the shortcut _of_ that component, so a
   handler that fires from any link in prose is global — record the fail and note the divergence.
   The tree shows the event target, not what a speech recogniser dictates; the outcome rests on the
   real presses. Done when each fired shortcut is "scoped" or "global".

5. Look for the turn-off or remap mechanism for every global shortcut
   ([G217](https://www.w3.org/WAI/WCAG22/Techniques/general/G217)). ffbc54 expectation, first
   branch: "disable/remap: there is at least one set of clearly labeled instruments to block events
   that use the same key as the test target and whose getModifierState method returns false for each
   of the valid modifier keys". Read that with three of its glossary entries: an instrument is "An
   HTML element that when activated allows an end-user to achieve an objective"; a set of clearly
   labeled instruments is one "where each instrument is in the same web page as the test target or
   can be found in a clearly labeled location from that web page", and clearly labeled means the
   target "can be found by activating 'identifiable' instruments which either lead the user to find
   the target, or to another page or page state from which this action can be repeated until the
   target is found" — "Whether or not the content is 'clearly labeled' depends on the starting point
   of the search", so search from this sample, not from the home page. A "blocked event makes no
   changes to the content of the web page", and events count as the same when `key`, `code`,
   `location`, `repeat` and `isComposing` match, so test the same key, not a neighbour.

   ```bash
   agent-browser find role link click --name "Settings"
   agent-browser find text "Keyboard shortcuts" click
   agent-browser snapshot
   ```

   Follow those from the sample, `snapshot` each page or state reached, and read the shortcut help
   overlay (often `?`) for a toggle. A toggle behind a control whose name says nothing about
   shortcuts or settings (ffbc54 Failed Example 2, "Open modal") is not clearly labeled; the same
   modal behind a button named "Control shortcuts" is (Passed Example 6). Operate a found control
   with the keyboard, return to the sample and repeat step 3: turn off holds when the plain key now
   does nothing from the body; remap holds when the plain key does nothing and `press Control+<key>`
   or `press Alt+<key>` does the action. Shift alone is not a remap: `S` is a printable character
   the criterion names ("upper- and lower-case letters"), and W3C counts Shift+/ for `?` as in scope
   — ffbc54 would treat the shifted event as inapplicable, and the Understanding note overrules that
   here. Every applicable key needs cover: ffbc54 passes only when "For each keyboard event causing
   changes in content, there exists an instrument" (Passed Example 3), though one instrument may
   cover several keys at once (Passed Example 4), so list the keys the control leaves untouched.
   Then check that it holds:

   ```bash
   agent-browser reload
   agent-browser press "<key>"
   agent-browser reload
   agent-browser wait 60000
   agent-browser press "<key>"
   agent-browser reload
   ```

   ACT assumes "After being disabled, the event remains disabled until being re-enabled again. If
   the event is re-enabled through other non-user controlled means (e.g. a timeout) then this rule
   may pass while Success Criterion 2.1.4: Character Key Shortcuts is not satisfied" — the minute of
   waiting is that check. A control with no accessible name or no keyboard operation is not a
   mechanism (glossary Note 2; ffbc54 leaves this out on purpose: "The instruments used to pass this
   rule (if any), must meet all level A Success Criteria in order to fully satisfy Success Criterion
   2.1.4"). Where the only turn-off claimed is an operating-system or browser setting, record
   `cannot-tell` and queue the question: glossary Note 1 allows a platform mechanism, and ACT agrees
   that then "failing this rule might not be a failure of the success criterion". Done when every
   global shortcut has "turn off", "remap" or "no mechanism, searched: <where>".

6. Repeat steps 2 and 3 for the keys of step 1 in every state of `recon/<sample>-states.md`
   (open menu, dialog, expanded section, player playing): handlers are often registered when a
   component mounts. Include the state G217 describes, where a compose or edit pane is open but
   focus sits outside it — "users may become confused about whether the keyboard focus is in a
   compose pane or the inbox and, while in the inbox, inadvertently delete a message by trying to
   compose a word containing the letter D". For a media player from `media.js` press `k`, `m`, `f`
   and `Space` with the body focused: a reaction is a global hotkey, and for a muted or volume
   change read the media line of step 3 rather than the screenshot. Keys of a cross-origin embed
   (`structure.js` `iframes`, then `frame <@ref>` of a YouTube player) fire only while the frame has
   focus and are scoped. Done when each state has its own line.

## Deciding

- Fail (certainty ≥ 90): a real press of one printable key, or of a documented sequence, with the
  body focused changes content and step 5 finds no turn-off or remap control on the sample or in
  the settings, account and help locations it links to
  ([F99](https://www.w3.org/WAI/WCAG22/Techniques/failures/F99), ffbc54 Failed Example 1) — 95; the
  shortcut help itself opens on `?` from the body, no mechanism — 95; a turn-off or remap control is
  used and the plain key still fires from the body — 90; a media player reacts to `k`, `m` or `f`
  with the body focused, no mechanism — 90; the only remap offered is Shift or another printable
  key — 90; a turn-off covers some shortcuts and leaves other keys of step 1 firing — 90 for the
  uncovered keys; the key moves focus to a search field or another control elsewhere on the page
  (the Understanding "Alternate Control" example, `s` jumping to the search bar) with no
  mechanism — 90.
- Fail (70–89): a disabled shortcut re-enables itself without the user re-enabling it, after the
  minute of step 5 or after navigating within the app (ACT assumption on re-enabling) — 85; a
  shortcut fires with focus anywhere in a landmark or container rather than on a widget, no
  mechanism — 85; the turn-off control is reachable only through a control whose name does not
  identify it (ffbc54 Failed Example 2) — 80; the turn-off control exists on another page but
  nothing on this sample leads to it (ffbc54: clearly labeled "depends on the starting point of the
  search") — 78; the control has no accessible name or no keyboard operation (mechanism Note 2)
  — 75; the shortcut fires from a plain link but not from the body, no mechanism — 75; a sweep hit
  that a real press reproduces only intermittently — 70.
- Needs confirmation (50–69): the sweep marked a key `prevented` but a real press changes nothing
  — 55; ask the human to press it on the live page. A turn-off setting that reverts on `reload`
  — 60; ask whether it is stored on the account. A turn-off that exists only as an operating-system
  or user-agent setting the product documents (mechanism Note 1) — 60; ask which platform setting
  blocks the key and on which platforms. A global shortcut on the space bar alone (ffbc54
  counts `Zs` as printable; the criterion text names letters, punctuation, numbers and symbols)
  — 55. A shortcut scoped to a landmark or group that users may perceive as one control (a whole
  gallery, a message list; user interface components Note 1, "what the user perceives as separate
  controls") — 65; ask "is <container> one control to you?". A key whose action must not repeat, so
  only the sweep and the source speak for it — 60; ask the developer to confirm the binding.
- Pass: every shortcut found in steps 1 to 3 is scoped to its widget (nothing from the body or a
  plain link, works with the widget focused) or has a turn-off or remap control that covers every
  key, is reachable through labeled controls from this sample, keyboard-operable, verified by
  pressing the key after using it, and still in force after a reload and after the minute of
  step 5, in every state of step 6. Widgets with first-letter typeahead pass as "Active only on
  focus".
- Not present: no printable key changes content from the body or a plain link, in any state, and
  no component declares or documents a single-character key. Record it only when steps 1, 2 and 6
  all came back empty — ffbc54 maps an inapplicable outcome to "success criterion needs further
  testing", so a state that could not be reached or swept is `cannot-tell`, not `not-present`.
- False positives to avoid: `accesskey` attributes (the user agent adds a modifier); shortcuts
  that need Ctrl, Alt, Meta or Cmd; Escape, arrows, Enter, Tab, Home, End, F-keys, Space on a
  button; typing into text fields and editors (an `@` or `/` picker inside the focused editor);
  native `<select>` and listbox typeahead; a menubar reached with Alt then a letter; the browser's
  own keys, which F99 names — "Firefox opens a page search when pressing Shift + / and a search in
  page links when pressing Shift + '", and Space scrolls — press Escape or click an empty part of
  the page to leave such a browser input before continuing; `<kbd>` in prose about another product;
  content that changes on its own between presses (compare against `baseline`).

## Reporting

- File under: 2.1.4. One issue per page or component that registers the shortcuts, listing every
  affected key; a site-wide handler is one issue that names every sample. The toggle's own defects
  go to 2.1.1 (not keyboard-operable) or 4.1.2 (no name or state).
- Title patterns: "Single-key shortcuts (<keys>) cannot be turned off or remapped", "Pressing
  <key> anywhere on the page <action> and cannot be disabled", "Player hotkeys <keys> work without
  the player having focus", "Shortcut setting is hidden behind an unlabeled control", "Turning off
  shortcuts leaves <keys> active", "Shortcut setting resets after reloading the page"
- Severity: High when a dictated or accidental key sends, deletes, archives, navigates away or
  moves focus out of the task, or the handler is site-wide; Medium when it opens an overlay,
  switches a view or changes a selection that Escape or one action undoes; Low when it toggles one
  harmless state with an obvious undo (mute on a player, a help panel with a close button).
- Type: Technical (the handler and the settings control are script and markup).
- Evidence: the before and after screenshots of the real press with the body focused, with
  `highlight "<css>"` on what changed and the key named in the text; the recording when the key
  moves focus or the action is a sequence; the settings screen when a mechanism is unlabeled or
  covers only part of the keys. For a key that only mutes, unmutes or starts audio, quote the
  player's `paused`, `muted` and `volume` values before and after — a screenshot cannot show it.
- Recommendation: give the user a persisted setting, reachable from every page through a labeled
  "Settings" or "Keyboard shortcuts" control, that turns single-key shortcuts off or makes them
  need a modifier ([G217](https://www.w3.org/WAI/WCAG22/Techniques/general/G217): a toggle button
  for the shortcuts, or a menu "where the user can reassign both the shortcut keys and the
  modifiers"); or bind the shortcut to its component so it fires only while that component has
  focus. Keep every command reachable another way as well — in W3C's disable example "The character
  key shortcuts are not the only way to carry out these commands."

  ```js
  document.addEventListener('keydown', (e) => {
    if (e.key !== 's') return
    if (settings.singleKeyShortcuts === 'off') return // Turn off
    if (settings.needsModifier && !e.getModifierState('Control')) return // Remap
    openSearch()
  })
  ```

  ```js
  list.addEventListener('keydown', (e) => {
    // Active only on focus: no setting needed
    if (e.key === 's' && document.activeElement === list) star(list.selectedItem)
  })
  ```

- Related: 2.1.1 Keyboard (the function must also be reachable without the shortcut, and the toggle
  must be keyboard-operable); 4.1.2 Name, Role, Value (the toggle's name and state); 2.4.3 Focus
  Order when the key throws focus somewhere unexpected (the shortcut here, the focus defect there).
