# 2.4.7 Focus Visible

Level AA · WCAG 2.0+ · Guideline 2.4 Navigable · Group: `keyboard`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#focus-visible) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#focus-visible) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-4-7-focus-visible/) ·
ACT: [oj04fd](https://www.w3.org/WAI/standards-guidelines/act/rules/oj04fd/)

## Requirement

> Any keyboard operable user interface has a mode of operation where the keyboard focus indicator
> is visible.

Terms (WCAG 2.2 glossary): **focus indicator**: "pixels that are changed to visually indicate when
a user interface component is in a focused state". Pixels, and nothing more: the criterion names no
shape, no thickness, no colour and no position, so the question at each stop is "did something
visible change", never "is the ring large or strong enough".

**user interface component**: "a part of the content that is perceived by users as a single control
for a distinct function", Note 1: "Multiple user interface components may be implemented as a single
programmatic element", Note 2: "User interface components include form elements and links as well as
components generated by scripts". Each option of a listbox, each item of a menu and each tab of a
tab list is a component of its own, even where one element holds them all and only that element
takes DOM focus (step 6).

**state**: "dynamic property expressing characteristics of a user interface component that may
change in response to user action or automated processes", "Examples include focus, hover, select,
press, check, visited/unvisited, and expand/collapse". Focus is one state among those: a cue that
only `:hover`, `:active` or `:visited` produces never stands in for it (step 3).

The Understanding adds the deciding sentence: "The focus indicator must not be time limited: when
the keyboard focus is shown, it must remain visible."

## In plain terms

Every link, button, field and widget a keyboard user lands on has to change some pixels on screen
for as long as it holds focus: the browser's own ring, an author outline, a border or background
change, an underline, the caret in a text field. The change may be small and may sit outside the
element; its size is 2.4.13's question (AAA), its contrast 1.4.11's. It matters to sighted keyboard
users, to people with motor impairments who cannot use a pointer and to people with attention or
memory limitations; the fix sits in code (a reset removed the ring) or in design (no focus state).

## Applies when

- Present: `focusables.js` returns a non-empty `order` in any recorded state — oj04fd's
  applicability is "any element which is part of sequential focus navigation in an HTML document" —
  or a composite widget whose items take focus with the arrows (`role` `tab`, `menuitem`, `option`
  or `radio` in `snapshot -i`).
- Not present: `order` is empty in every state and no widget moves focus with the arrows. oj04fd's
  two inapplicable examples are exactly these: a document with no focusable element
  (`<span>ACT rules</span>`), and one where "None of the focusable elements in this document are
  part of sequential focus navigation" (every candidate carries `tabindex="-1"`).
- Exceptions: none in the text.
- Mode of operation, the Intent verbatim, which is the only way this criterion is satisfied by
  something other than an always-on indicator: "'Mode of operation' accounts for user agents which
  may not always show a focus indicator, or only show the focus indicator when the keyboard is used.
  User agents may optimize when the focus indicator is shown, such as only showing it when a
  keyboard is used. Authors are responsible for providing at least one mode of operation where the
  focus is visible. In most cases there is only one mode of operation so this success criterion
  applies." So a ring shown only on keyboard use
  ([C45](https://www.w3.org/WAI/WCAG22/Techniques/css/C45)) passes and every verdict comes from a
  real `press Tab`, never a `click`; and a claim that some other mode carries the indicator is the
  rare case, to be named and reached before it counts (`needs confirmation`, step 7).
- Focusable, oj04fd's glossary, verbatim: "An element is focusable if one or both of the following
  are true: the element is part of sequential focus navigation; or the element has a tabindex value
  that is not null", with "Exception: Elements that lose focus during a period of up to 1 second
  after gaining focus, without the user interacting with the page the element is on, are not
  considered focusable" and its note "The 1 second time span is an arbitrary limit which is not
  included in WCAG." An element that hands focus away by itself within a second therefore leaves
  oj04fd with nothing to test, while the Understanding still lists
  [F55](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55) as a failure of this criterion:
  record it here as an F55 fail, never as a pass and never as out of scope.
- Focused, oj04fd's glossary, verbatim: "An element is said to be focused when the element matches
  the :focus pseudo-class uninterruptedly for a period of 1 second after a user stopped interacting
  with the page." That fixes the waits below: log the focused element straight after the press and
  again after `wait 1100`, and take the deciding screenshot after the second log.
- A `tabindex="-1"` element that only a script focuses (a skip-link target, a dialog container) is
  outside oj04fd's applicability: note it, no verdict.
- No size, shape or distance requirement, the oj04fd background verbatim: "WCAG 2.0 and 2.1 do not
  have any requirement of how big or small focus indicator should be, or how far or near from the
  focusable element it should be. Thus it is possible to pass this rule and Success Criterion 2.4.7
  Focus Visible with barely perceptible changes at the other end of the page. That would however
  still be an accessibility issue." Both halves bind: a faint or far-away change is a `pass` here,
  and it is written into the findings file as a note so the report can carry it under 2.4.13 (AAA)
  or 1.4.11.
- Contrast is 1.4.11's, the Intent verbatim: "Focus indicators are visual information required to
  identify the focused state of a user interface component. As generally focus indication is
  provided using non-text content (for instance, using borders/outlines), that means that they are
  also subject to Success Criterion 1.4.11 Non-text Contrast (Level AA)." A visible but low-contrast
  ring passes here and is filed under 1.4.11.
- Form is 2.4.13's, the Understanding's WCAG 2.2 note: "Keyboard focus indicators can take different
  forms. While this criterion does not specify what that form is, 2.4.13 Focus Appearance (Level
  AAA) provides guidance on creating a consistent, visible indicator, dealing with issues such as
  its size and shape."
- Pointer users are a best practice only, the Understanding's note verbatim: "There may be
  situations where mouse/pointer users could also benefit from having a visible focus indicator,
  even though they did not set focus to an element using the keyboard. As a best practice, consider
  still providing an explicit focus indicator for these cases." Never carry a fail for it.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. `scripts/axe-page.mjs`
prints no line for 2.4.7 in any state, so neither a clean axe run nor a violation of a neighbouring
rule moves this outcome. Settles: nothing. Leaves open: every point of the procedure below. oj04fd
says the same of its own automated part — "Any failed outcomes: success criterion is not satisfied",
"All passed outcomes: success criterion needs further testing" — so a state in which every Tab stop
changes a pixel is still carried through steps 3 to 7 before `pass` is recorded. The `visual` pass
(1.4.11) measures the contrast of the indicators found here; this pass records that one exists, that
it is distinguishable from the rest state and that it stays.

## Manual procedure

Work at `set viewport 1280 900`, default state first, then every recorded state, with the 2.1.2 Tab
walk (`recon/<sample>-tabwalk.txt`) and its logger (`.notes/audit/recon/focus-logger.js`); produce
them first when missing. No screen reader is involved: `snapshot -i` lists what can take focus,
never whether focus is visible. Viewport screenshots decide — `screenshot <path>`, never `--full`
and never an element crop: oj04fd asks for a changed pixel "inside the scrolling area of the
viewport", which is the viewport frame, and a crop cuts off a ring drawn outside the element's box.

1. Inventory. Press Tab once so that Chromium is in keyboard mode and applies `:focus-visible`
   rules to the programmatic focus the probe uses, then run `focusables.js` and bin `order`:

   ```bash
   agent-browser press Tab; agent-browser wait 300
   agent-browser eval --stdin < <skill-dir>/scripts/probes/focusables.js
   ```

   `focusStyle.outline` reads `"<style> <width> <colour>"`; the Chromium default ring reads with the
   style `auto`. Bin D first: `visible: false`, or a `box` with `w` or `h` of 0 or a negative `x` or
   `y`. Bin A: `visible: true` with `focusStyleChanged: false`. Bin B: a change while the outline's
   style is `none`, its width `0px` or its colour `rgba(0, 0, 0, 0)`, and `focusStyle.boxShadow` is
   `none`. Bin C: the rest. A bin A entry looks like this:

   ```json
   {
     "index": 7,
     "selector": "nav#main > ul > li:nth-of-type(3) > a",
     "role": "link",
     "visible": true,
     "focusStyleChanged": false,
     "focusStyle": {
       "outline": "none 0px rgb(0, 0, 0)",
       "boxShadow": "none",
       "border": "0px rgb(0, 0, 0)",
       "background": "rgba(0, 0, 0, 0)"
     }
   }
   ```

   A family is every entry with the same `tag`, `role` and `focusStyle`. Record `counts.focusable`,
   `counts.visible`, `counts.withoutFocusStyleChange` and `counts.obscured`. `counts.truncated:
true` means the probe stopped at its ceiling and the entries past it are only reached by the Tab
   walk, so walk the rest of the page with step 2 instead of binning it. Two kinds of entry land in
   bin A without a defect and are cleared in step 2, not here: the probe compares the element and
   its `::before`/`::after` only, so an indicator on a parent, sibling or child does not register —
   the sourced patterns are [C15](https://www.w3.org/WAI/WCAG22/Techniques/css/C15) Example 2, which
   styles the adjacent label (`input[type=checkbox]:focus + label`), and
   [SCR31](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR31), whose `onfocus`
   handler paints another element, the shape of oj04fd passed examples 3 and 4; and an element that
   refused programmatic focus, or already held focus while the probe ran, also reads
   `focusStyleChanged: false`. Done when every entry has a bin and N (the length of `order`) is in
   the findings file.

2. Pixel test for bins A and B, one entry per family, every family. oj04fd has one Expectation and
   this step is all of it: "For each target element, there is at least one device pixel inside the
   scrolling area of the viewport whose HSL color value is different when the element is focused
   from when it is not."

   ```bash
   agent-browser focus "<selector of the previous order entry>"   # order[0]: reload, then Tab
   agent-browser press Tab; agent-browser wait 400
   agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   agent-browser wait 1100
   agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   agent-browser screenshot .notes/audit/evidence/<sample>-2.4.7-<slug>-focused.png
   agent-browser eval --stdin <<'EOF'
   (() => { document.activeElement?.blur(); return document.activeElement.tagName })()
   EOF
   agent-browser wait 400
   agent-browser screenshot .notes/audit/evidence/<sample>-2.4.7-<slug>-blurred.png
   cmp -s .notes/audit/evidence/<sample>-2.4.7-<slug>-focused.png \
     .notes/audit/evidence/<sample>-2.4.7-<slug>-blurred.png && echo identical
   ```

   Both logger lines must name the element: the first says Tab reached it, the second says it is
   "focused" in oj04fd's sense (one uninterrupted second). A later `order` entry in the first line
   means the browser skips this one (hidden, or a handler swallowed Tab): reach it with
   `focus "<its selector>"` instead. `BODY` or an earlier element in either line is focus removed on
   receipt, the F55 candidate step 5 confirms: record both lines and go on. `identical` means no
   pixel changed: the oj04fd fail. Otherwise open both images and find the change: a ring, border,
   fill, underline, marker or caret is the family's indicator. A change only the diff reveals (an
   outline the colour of its background, a ring clipped to a sliver by `overflow: hidden`, a `color`
   shift of a few steps) is a fail that still takes judgement. A change that renders outside the
   captured viewport is no pixel "inside the scrolling area of the viewport": `scrollintoview
"<selector>"`, repeat the pair, and fail it only if the focused image is still unchanged. A text
   field with no ring passes when the caret shows and `get styles "<selector>"` gives a
   `caret-color` other than `rgba(0, 0, 0, 0)`, and equally when the field's text is selected on
   focus (Understanding Example: "a vertical bar is displayed in the field [...] OR all of the text
   is highlighted"). A continuously repainting page with no indicator found by eye is `cannot-tell`:
   queue it. Done when every family is "visible: <what>", "no pixel changed", "sliver", "F55" or
   `cannot-tell`.

3. Sight check for bin C and for every family that changed in step 2, one entry per family: the
   commands of step 2, then the focused image alone beside the blurred one. Three things are
   decided here.

   ```bash
   agent-browser get styles "<selector>"
   ```

   First, findability: the indicator must be locatable at 100 % without the diff; an outline in the
   colour of its background, or one only the diff reveals, is the fail of step 2; a faint but
   visible ring passes (1.4.11 measures it). Second, the rest state, which is
   [F78](https://www.w3.org/WAI/WCAG22/Techniques/failures/F78) beyond the removed ring — its
   Example 2 is `a {outline: thin dotted black}`, of which F78 says "This makes it impossible for
   users to determine which one in fact has the focus, even though the user agent does draw the
   focus indicator": compare the unfocused `outline-style`, `outline-width` and `outline-color` from
   `get styles` with the focused `focusStyle.outline` of step 1 and fail the family when they match.
   Its Example 3 is `a {border: medium solid black}`, where "the focus indicator is drawn just
   outside the border, but as both are black and the border is thicker than the focus indicator, it
   no longer meets the definition of 'visible'": fail the family when the rest-state border is
   thicker than the focused outline and carries the same colour. Third, the state that produced the
   change: a cue the blurred image already shows under the pointer is `:hover`, not focus — take the
   pair again with the mouse parked away from the element (`mouse move 5 5`) before deciding. Done
   when every family of bin C has a focused image, a description ("browser ring", "2px blue
   outline", "underline") and a rest-state comparison.

4. Hidden stops (bin D). Tab onto each as in step 2 and take the focused image: a skip link or a
   "hidden until focused" control that appears on focus passes; nothing appearing while the logger
   names the element is a fail (focus vanished for one press); an entry Tab never reaches is out of
   sequential focus navigation and out of oj04fd: no verdict. Done when each is "appears", "nothing"
   or "not reached".

5. Persistence and F55, one entry per family. After the focused image of step 2 or 3, `wait 2000`
   and `screenshot` again: the indicator must still be there, because "The focus indicator must not
   be time limited: when the keyboard focus is shown, it must remain visible"; one that fades or
   transitions away is a fail. Reproduce each F55 candidate of step 2 with the logger directly after
   `press Tab` and again after `wait 1200`, oj04fd's one-second frame: an element the logger no
   longer names by then lost focus by itself. Then look for the handler that did it:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => [...document.querySelectorAll('[onfocus], [onfocusin]')]
     .map(el => ({ el: el.localName + (el.id ? '#' + el.id : ''),
       on: el.getAttribute('onfocus') || el.getAttribute('onfocusin') }))
     .filter(x => /blur\s*\(/.test(x.on)))()
   EOF
   ```

   That finds F55's three published shapes — `onFocus="this.blur();"`, `onFocus="this.blur()"` and
   `onfocus="if(this.blur)this.blur();"` — and finds nothing when the handler was attached with
   `addEventListener`, in which case the two logger lines are the whole evidence. Done when every
   family is "stays" or "fades" and every F55 candidate is confirmed or cleared, with the handler
   quoted where the hunt found one.

6. Arrow-operated widgets: for each `role` `tablist`, `menubar`, `menu`, `listbox`, `tree`, `grid`
   or `radiogroup` in `snapshot -i`, Tab to its tabbable item, then `press ArrowDown` (`press
ArrowRight` when horizontal), `wait 300`, the logger and a `screenshot`. A roving-tabindex item
   (the logger moves) is judged as in step 2. With `aria-activedescendant` the logger stays on the
   container while `get attr "<container css>" aria-activedescendant` changes: the highlighted
   item's mark is the indicator and must show in the image, which is the shape
   [G195](https://www.w3.org/WAI/WCAG22/Techniques/general/G195) Example 3 describes — "As focus
   moves, the currently focused menu item changes its background to a different color". `press
Escape`, Tab on. Done when every widget is "items show focus" or fails.

7. States, schemes and frames. Repeat steps 1 to 6 for each state in `recon/<sample>-states.md`,
   opened with the keyboard (`focus "<trigger css>"`, `press Enter`). When `get styles body` changes
   after `set media dark`, `reload` and `wait --load networkidle`, redo steps 1 to 3 in that
   scheme, then `set media light`. For each `structure.js` `iframes` entry Tab into it from the
   outer walk: the viewport image shows the ring inside the frame; `frame "<iframe css>"` and
   `focusables.js` give the inner families, `frame main` returns. Frame content that never takes
   focus is 2.1.1's; content that takes it with no visible change fails here. Where the page offers
   a theme, a contrast setting or a "keyboard mode" that the author names as the mode of operation,
   switch it on with the keyboard and redo steps 1 to 3 in it; record how a user reaches that mode,
   since "In most cases there is only one mode of operation so this success criterion applies". Done
   when each state, scheme, frame and offered mode has entries.

8. Evidence for every fail, starting two entries before the element, then the rule that removed or
   masked the ring, where one exists:

   ```bash
   agent-browser focus "<selector of the order entry three before>"
   agent-browser record start .notes/audit/evidence/<sample>-2.4.7-<slug>.webm
   agent-browser press Tab; agent-browser wait 600; agent-browser press Tab; agent-browser wait 600
   agent-browser press Tab; agent-browser wait 600; agent-browser record stop
   agent-browser highlight "<selector>"
   agent-browser screenshot .notes/audit/evidence/<sample>-2.4.7-<slug>.png
   agent-browser eval --stdin <<'EOF'
   (() => {
     const walk = rs => [...rs].flatMap(r => [r, ...(r.cssRules ? walk(r.cssRules) : [])]);
     const rules = [...document.styleSheets].flatMap(s => {
       try { return walk(s.cssRules) } catch { return [] } });
     const where = r => (r.parentStyleSheet && r.parentStyleSheet.href) || 'inline style';
     const el = document.querySelector('<selector>');
     const applies = r => { try { return el.matches(r.selectorText) } catch { return false } };
     const out = { removed: [], lookalike: [] };
     for (const r of rules) {
       const s = r.style;
       if (!r.selectorText || !s) continue;
       const kills = s.outlineStyle === 'none' || s.outlineWidth === '0px' ||
         /transparent|rgba\(0, 0, 0, 0\)/.test(s.outlineColor);
       const replaces = s.boxShadow || s.borderStyle || s.borderWidth || s.backgroundColor ||
         s.textDecorationLine || s.filter;
       if (r.selectorText.includes(':focus') && kills && !replaces &&
         !r.selectorText.includes(':not(:focus-visible)'))
         out.removed.push(r.selectorText + ' { ' + s.cssText + ' } <- ' + where(r));
       if (!r.selectorText.includes(':focus') && applies(r) &&
         ((s.outlineStyle && s.outlineStyle !== 'none') || s.borderWidth))
         out.lookalike.push(r.selectorText + ' { ' + s.cssText + ' } <- ' + where(r));
     }
     return out;
   })()
   EOF
   ```

   A `removed` hit is F78 Example 1 (`:focus {outline: none}`): quote the selector and the
   stylesheet in the finding; `:focus:not(:focus-visible)` rules are the C45 pattern and are skipped
   on purpose. A `lookalike` hit is the rest-state outline or border of step 3, F78 Examples 2 and
   3: quote it beside the focused outline it hides. An empty `removed` list on a page that shows no
   ring means the removal is not in a readable stylesheet — a cross-origin sheet, an inline `style`
   attribute or a script — so the pair of step 2 stands as the evidence. A `blur()` in a focus
   handler (step 5's hunt, or the page script) is F55's evidence. Done when every fail has the
   recording, the highlighted image, the pair of step 2 and, where found, the rule.

## Deciding

- Fail (certainty ≥ 90): a visible `order` entry that the logger confirms focused after a real
  Tab press while the focused and blurred images are identical, in any state or scheme the author
  ships (oj04fd fails) — 95; the same with the F78 `removed` rule of step 8 found — 95; focus
  removed on receipt: after Tab the logger prints `BODY` or an earlier element and step 5 confirms
  it does not keep focus (F55) — 90; a text field with no ring and `caret-color: rgba(0, 0, 0, 0)`
  and no selection on focus — 90; an indicator gone in the two-second image while the logger still
  names the element — 90.
- Fail (70–89): a change only the diff reveals: an outline in the colour of the background it lies
  on, a sliver left by `overflow: hidden`, a `color` shift of a few steps — 80; a rest-state outline
  of the same style, width and colour as the focus outline, so focused and unfocused elements look
  alike (F78 Example 2) — 80; a rest-state border thicker than and the same colour as the focus
  outline, which the ring is drawn against and cannot be seen on (F78 Example 3) — 80; an indicator
  that renders only outside the scrolling area of the viewport while the element is scrolled into
  view — 85; a hidden stop (skip link, off-screen control) that takes focus and shows nothing — 85;
  a roving-tabindex item or `aria-activedescendant` option with no visible mark when the arrows
  reach it — 85; a family whose cue shows on one background and is gone on another (white section,
  grey section) — 80; a cue that the blurred image also shows because it comes from `:hover` and
  focus alone produces nothing — 80; frame content that takes focus with no visible change in the
  viewport image — 75.
- Needs confirmation (50–69): an indicator that appears only after a site setting, theme or
  "keyboard mode" switch — 60: ask whether that mode is meant as the mode of operation and how a
  user finds it; a page that repaints continuously so the pair cannot be compared and no ring is
  found by eye — 55: ask for a human look; a caret as the only cue that the image may have missed
  (blink phase) — 55: ask the human to type into the field; an indicator whose only pixels lie far
  from the element (the other end of the page), which passes the criterion — 50: ask whether it is
  findable in use, and record it as a note rather than an issue when it is.
- Pass: every family of every bin, in every recorded state, scheme and frame, shows a change of at
  least one pixel inside the scrolling area of the viewport after a real Tab or arrow press,
  findable without the diff, distinguishable from the element's rest state and still present after
  two seconds; every hidden stop appears on focus; no element hands focus on within a second.
- Not present: `order` is empty and no arrow-operated widget exists, in every state.
- False positives to avoid: the browser's default ring; a ring shown on keyboard focus and absent
  after `click` (C45: the keyboard mode is the mode of operation), and a missing indicator for
  pointer users generally, which the Understanding raises only as a best practice; a
  `focusStyleChanged: false` entry whose indicator sits on a parent, sibling or child (C15's
  adjacent label, SCR31's scripted paint, oj04fd passed examples 3 and 4), or that held focus while
  the probe ran — the step 2 image decides, never the probe; an `order` entry the browser never Tabs
  to; several elements sharing one indicator, since "WCAG does not require that the focus indicator
  for each focusable element is unique in appearance. Therefore, this rule can pass even if several
  focus indicators are identical"; a small, faint or distant but visible ring (size is 2.4.13,
  contrast 1.4.11; oj04fd: "it is possible to pass this rule and Success Criterion 2.4.7 Focus
  Visible with barely perceptible changes at the other end of the page"); a caret or a select-all
  highlight in a text field; a ring behind a sticky header (`obscured: true`, 2.4.11).

## Reporting

- File under: 2.4.7 for a missing, invisible, indistinguishable, vanishing or time-limited
  indicator. Focus removed on receipt (F55) is one issue under 2.1.1 naming 2.4.7 and 3.2.1; a
  visible ring below 3:1 is 1.4.11 (F78 names both); a ring behind a sticky header or overlay is
  2.4.11; ring size is 2.4.13, only when AAA is targeted; a trap without a ring is two issues (2.1.2
  and here). One issue per family and cause (the reset that removed every ring, the navigation
  links, the custom checkbox, the dark scheme), naming every sample and state.
- Title patterns: "Keyboard focus is not visible on <the main-menu links>", "The focus outline has
  been removed site-wide", "<The custom dropdown> shows no focus indicator", "The focus outline on
  <the product links> looks the same as their normal outline", "The focus outline disappears after a
  moment on <the filter buttons>"
- Severity: High when no control of the sample shows focus, or the loss sits on the task path
  (navigation, search, forms, consent dialog, dialog controls); Medium when one component family,
  one state or one scheme loses it while the rest of the page shows focus; Low when one
  convenience control or one hidden stop lacks it and the next press shows focus again.
- Type: Technical by default: a reset or component stylesheet removed the browser ring (F78), a
  script blurs (F55), a transition fades the ring. Design when the component's designed focus
  state is missing or indistinguishable from its rest state, or its colour equals the background.
- Evidence: the focused viewport image (nothing marks the element) beside the same view with
  `highlight "<selector>"` showing where focus is, the walk log line quoted in the body, and the
  recording of three Tab presses in which the ring disappears. For a rest-state defect, put the
  focused and unfocused images side by side so the reader sees that they match.
- Recommendation: keep or restore the ring the browser and the platform draw
  ([G149](https://www.w3.org/WAI/WCAG22/Techniques/general/G149),
  [G165](https://www.w3.org/WAI/WCAG22/Techniques/general/G165), whose point is that "If you use the
  native focus indicator, any system-wide settings for its visibility will carry over to the web
  page") by deleting the `outline: none` reset or scoping it to `:focus:not(:focus-visible)`
  ([C45](https://www.w3.org/WAI/WCAG22/Techniques/css/C45)):

  ```css
  /* fails (F78 Example 1): the ring is gone and nothing replaces it */
  :focus {
    outline: none;
  }
  /* passes: the keyboard ring is the mode of operation, the pointer state is styled separately */
  :focus-visible {
    outline: 3px solid #005a9c;
    outline-offset: 2px;
  }
  ```

  Where the design asks for its own indicator, give every focusable element one that contrasts on
  every background it appears over ([G195](https://www.w3.org/WAI/WCAG22/Techniques/general/G195):
  "a combination of a highly contrasting color, a thick line, and other visual indicators such as a
  glow"), and style the focus state on the element or on the label beside it with CSS
  ([C15](https://www.w3.org/WAI/WCAG22/Techniques/css/C15)):

  ```css
  input[type='text']:focus-visible {
    outline: 2px solid #0054ae;
    outline-offset: 2px;
  }
  input[type='checkbox']:focus + label,
  input[type='radio']:focus + label {
    background-color: #1e2eb8;
    color: #fff;
  }
  ```

  On a site with many background colours, use the two-colour indicator of
  [C40](https://www.w3.org/WAI/WCAG22/Techniques/css/C40) rather than one class per section: "As
  long as the two indicator colors have a contrast ratio of at least 9:1 with each other, at least
  one of the two colors is guaranteed to meet 3:1 contrast with any solid background color", each
  band at least 2 CSS pixels thick.

  ```css
  *:focus {
    outline: 2px #f9f9f9 solid;
    outline-offset: 0;
    box-shadow: 0 0 0 4px #193146;
  }
  ```

  C40 also warns against `box-shadow` on its own: "User agents commonly suppress the box-shadow
  property in forced-color modes, so authors should avoid relying on box-shadow alone to implement
  focus indicators. If box-shadow only styling is required, consider combining it with an outline:
  2px transparent solid property". Where a component cannot be reached with CSS — the indicator
  belongs on another element, or the environment has no `:focus` support —
  [SCR31](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR31) paints it from
  `onfocus` and clears it from `onblur`; prefer the CSS forms above where both are possible. Remove
  `blur()` from focus handlers (F55) and the transition that fades the ring away.
