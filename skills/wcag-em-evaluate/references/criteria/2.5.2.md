# 2.5.2 Pointer Cancellation

Level A · WCAG 2.1+ · Guideline 2.5 Input Modalities · Group: `pointer`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)
· [Spec](https://www.w3.org/TR/WCAG22/#pointer-cancellation)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#pointer-cancellation) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-5-2-pointer-cancellation/)
· ACT: none mapped to this criterion.

## Requirement

> For functionality that can be operated using a single pointer, at least one of the following is
> true:
>
> - No Down-Event:
>   The down-event of the pointer is not used to execute any part of the function;
>
> - Abort or Undo:
>   Completion of the function is on the up-event, and a mechanism is available to abort the function
>   before completion or to undo the function after completion;
>
> - Up Reversal:
>   The up-event reverses any outcome of the preceding down-event;
>
> - Essential:
>   Completing the function on the down-event is essential.
>
> Note 1:
> Functions that emulate a keyboard or numeric keypad key press are considered essential.
>
> Note 2:
> This requirement applies to web content that interprets pointer actions (i.e., this does not
> apply to actions that are required to operate the user agent or assistive technology).

Terms (WCAG 2.2 glossary):

**functionality**: "processes and outcomes achievable through user action". The unit under test is
the function, not the element: a control that previews on press and opens on release carries two
functions and is judged twice, and one bullet has to be true for each.

**single pointer**: "an input modality that only targets a single point on the page/screen at a
time – such as a mouse, single finger on a touch screen, or stylus." Its Note fixes the scope:
"Single pointer interactions include clicks, double clicks, taps, dragging motions, and
single-finger swipe gestures. In contrast, multipoint interactions involve the use of two or more
pointers at the same time, such as two-finger interactions on a touchscreen, or the simultaneous
use of a mouse and stylus." Clicks, double clicks, taps, long presses, drags and one-finger swipes
are all in scope here; a pinch, a two-finger rotate or a mouse-plus-stylus action is multipoint and
is not judged by this criterion at all (it is 2.5.1).

**down event**: "platform event that occurs when the trigger stimulus of a pointer is depressed",
with the note "The down-event may have different names on different platforms, such as 'touchstart'
or 'mousedown'." In a browser the three names to look for in script are `mousedown`, `touchstart`
and `pointerdown`; `pointerdown` fires for mouse, touch and stylus alike.

**up event**: "platform event that occurs when the trigger stimulus of a pointer is released", with
the note "The up-event may have different names on different platforms, such as 'touchend' or
'mouseup'." The `click` event is the implicit up-event: W3C calls it "device-independent" and says
it "also works for touch and keyboard interaction".

**mechanism**: "process or technique for achieving a result", with Note 2: "The mechanism needs to
meet all success criteria for the conformance level claimed." The abort or undo control is itself
part of the sample: an Undo that no keyboard reaches, that carries no accessible name, or that only
a hover reveals, does not satisfy the second bullet — verify it before recording a pass on it.

**essential**: "if removed, would fundamentally change the information or functionality of the
content, **and** information and functionality cannot be achieved in another way that would
conform". Both halves must hold. W3C narrows it further for this criterion: "Completing the
function on the down-event is only permitted when it is essential that the up-event not be used."

## In plain terms

Nothing may happen while the mouse button or the finger is still down; the function runs on
release, so a user who pressed the wrong thing can slide off the control and let go without
triggering it. Where the author does use the down-event, the release must undo it, an abort or an
undo must exist, or the down-event timing must be essential (a key that types a character, an
on-screen piano key). Native controls already fire `click` on release, so the defect is almost
always a script handler on `mousedown`, `touchstart` or `pointerdown`. It matters for people with
limited mobility or tremor, who press and land off target; for people with low vision, who cannot
see what sits under the pointer; and for people with cognitive disabilities, who may not notice
that something fired and may not know how to get back.

## Applies when

- Present: any functionality a single pointer can operate: every link, button, form control and
  custom widget in `snapshot -i`; every `targets.js` `targets[].selector` (the same inventory the
  2.5.8 step builds); every `focusables.js` `clickableNotFocusable` entry (script-driven, so the
  likeliest to use the down-event); draggable items (`[draggable="true"]`, sortable lists, kanban
  cards, `role="slider"` thumbs); press-and-hold previews; canvas games; on-screen keyboards; and
  the same inside every `structure.js` `iframes` entry (`frame "<css>"`, then `frame main`). Every
  recorded state counts, including the controls inside a dialog, a menu and an error state.
- Not present: a state with no operable element at all (no link, button, field, widget, draggable).
- Exceptions: the four bullets are the ways to pass, judged per function, and one of them suffices.
  - No Down-Event: the press changes nothing but the pressed, hover or focus styling.
  - Abort or Undo: "Completion of the function is on the up-event" _and_ an abort before
    completion or an undo after it, which the evaluator must find and operate.
  - Up Reversal: the release puts the state back, "the user is returned to their prior point, and
    has effectively cancelled the operation" — a press-and-hold preview, a video that plays while
    held, a transient popup that disappears on release.
  - Essential (Note 1): "Functions that emulate a keyboard or numeric keypad key press are
    considered essential" — a soft-keyboard key that types a character or a digit. W3C names two
    further essential patterns: "an activity that emulates a physical on-press trigger, such as
    when playing an on-screen piano keyboard", and "a program for shooting skeets where waiting
    for the 'up' event would invalidate the precise timing necessary for the activation"; F101
    repeats them as "a musical instrument like a set of piano keys" and "an on-screen control for
    a game where a fast and immediate response is required". Recognise the pattern, not the claim.
  - Essential carries no undo duty: "Undo is not a requirement of the down-event Essential
    exception" — do not fail a keypad or piano key for lacking one.
  - Note 2 takes out "actions that are required to operate the user agent or assistive
    technology": text selection, scrolling, a native `select` or date picker opening on press, a
    native range thumb, the long-press context menu, and, per G210, "gestures provided by the user
    agent (such as horizontal swiping to move through the browser history or vertical swiping to
    scroll through page content) or the operating system", including screen-reader gestures.

## Manual procedure

Work at `set viewport 1280 900`, then under `set device "iPhone 13"` (step 5). The test is
behavioural, `mouse down` and `mouse up` as separate commands; the tree lists the controls but
never when a handler ran. Save the three helpers under `.notes/audit/` and rerun them with
`agent-browser eval --stdin < <file>`; each is an IIFE, so a rerun in the same page does not throw.
The fingerprint (`pc-state.js`) is read around a press, and twice with no press first so a field
that moves on its own (a clock in `text`, a rotating carousel in `on`) leaves the comparison:

```bash
agent-browser eval --stdin <<'EOF'
(() => { const n = s => [...document.querySelectorAll(s)].filter(e =>
  e.getBoundingClientRect().width > 0 && getComputedStyle(e).visibility !== 'hidden').length;
return { url: location.href, title: document.title, text: document.body.innerText.length,
  scrollY: Math.round(scrollY),
  dialogs: n('dialog[open], [role="dialog"], [role="alertdialog"]'),
  popovers: n('[popover], [role="tooltip"]'),
  expanded: n('[aria-expanded="true"]'), menus: n('[role="menu"], [role="listbox"]'),
  on: n('[aria-pressed="true"], [aria-checked="true"], [aria-selected="true"], :checked'),
  playing: [...document.querySelectorAll('video, audio')].filter(m => !m.paused).length,
  active: document.activeElement && document.activeElement.outerHTML.slice(0, 80) }; })()
EOF
```

`playing` and `popovers` carry the two Up Reversal patterns W3C names (a video that plays while
held, a transient popup), so step 3 can read them instead of guessing from the screenshot.

The scan (`pc-scan.js`) is [F101](https://www.w3.org/WAI/WCAG22/Techniques/failures/F101)'s
listener check. F101 states its own limit: "The automated test would not be sufficient to make a
pass/fail determination, but it can help narrow down the number of potentially problematic
controls." A hit is never a verdict:

```bash
agent-browser eval --stdin <<'EOF'
(() => { const re = /\b(?:on)?(mousedown|touchstart|pointerdown)\b/gi;
const path = el => { const p = []; for (; el && el.nodeType === 1; el = el.parentElement)
  p.unshift(el.tagName.toLowerCase() + (el.id ? '#' + el.id : '')); return p.join(' > '); };
const read = url => { try { const x = new XMLHttpRequest(); x.open('GET', url, false); x.send();
  return x.status < 400 ? x.responseText : null; } catch { return null; } };
const inline = [...document.querySelectorAll('*')].filter(el => ['onmousedown', 'ontouchstart',
  'onpointerdown'].some(k => el.hasAttribute(k) || el[k])).map(path);
const inDoc = new Set([...document.scripts].map(s => s.src).filter(Boolean));
const extra = performance.getEntriesByType('resource').map(r => r.name)
  .filter(u => /\.m?js(\?|$)/.test(u) && !inDoc.has(u)).slice(0, 40);
const sources = [...[...document.scripts].map(s => ({ src: s.src || 'inline',
  text: s.src ? null : s.textContent })), ...extra.map(u => ({ src: u, text: null }))];
const scripts = sources.map(s => { const body = s.text ?? read(s.src);
  if (body === null) return { src: s.src, readable: false }; const hits = {};
  for (const m of body.matchAll(re)) { const k = m[1].toLowerCase(); hits[k] = (hits[k] || 0) + 1; }
  return { src: s.src, readable: true, hits }; });
return { scanned: scripts.length, unreadable: scripts.filter(s => !s.readable).length,
  inline, scripts: scripts.filter(s => !s.readable || Object.keys(s.hits).length),
  draggable: [...document.querySelectorAll('[draggable="true"],[role="slider"]')].map(path) }; })()
EOF
```

`extra` catches bundle chunks pulled in by dynamic `import()`, which never appear in
`document.scripts`; `unreadable` counts cross-origin files the XHR could not fetch.

1. Inventory the functions. `snapshot -i` in the default state and in each recorded state (open
   menu, dialog, expanded section, error state); run `focusables.js`, `targets.js` and the scan,
   and rerun the scan inside each `iframes` entry. List every `inline` selector, every
   `clickableNotFocusable` entry, every custom widget (a `role` of `button`, `link`, `menuitem`,
   `tab`, `option`, `switch`, `checkbox`, `slider` or `treeitem` on an element `get html` shows is
   not the native one), every `draggable` entry, one native link, button and input per type as the
   [G212](https://www.w3.org/WAI/WCAG22/Techniques/general/G212) baseline, and any press-and-hold,
   canvas or keyboard-like control. A script's `hits` cannot be tied to elements: with hits, test
   every custom widget. Done when each function has a selector and a kind, and every script with
   `readable: false` is noted as unknown listeners.

2. Press each listed control without releasing, then release off the control. This is G212's test:
   "Activate the down-event then move the pointer outside the target before triggering the
   up-event, and then release the pointer to trigger the up-event", then "check that the action was
   not triggered when the pointer is released outside of the hit area for the target", and "if the
   action is triggered, check that the action is reversible"; G212 passes on "#2 or #3".

   ```bash
   agent-browser scrollintoview "<selector>"
   agent-browser get box "<selector>"        # e.g. {"x":320,"y":180,"width":96,"height":40}
   agent-browser tab list
   agent-browser eval --stdin < .notes/audit/pc-state.js
   agent-browser mouse move 368 200          # x + width / 2 = 368, y + height / 2 = 200
   agent-browser mouse down
   agent-browser wait 800
   agent-browser eval --stdin < .notes/audit/pc-state.js
   agent-browser screenshot .notes/audit/evidence/<sample>-2.5.2-<slug>-held.png
   agent-browser wait 1200
   agent-browser eval --stdin < .notes/audit/pc-state.js
   agent-browser mouse move 280 200          # x - 40 = 280, clear of the control
   agent-browser mouse up
   agent-browser eval --stdin < .notes/audit/pc-state.js
   agent-browser tab list
   ```

   Confirm the release point is free before using it, and move to a page margin when it is not:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => { const sel = 'a,button,input,select,textarea,summary,[onclick],[draggable="true"],' +
     '[role="button"],[role="link"],[role="menuitem"],[role="tab"],[role="option"]';
   const e = document.elementFromPoint(280, 200);
   return { tag: e && e.tagName, onControl: !!(e && e.closest(sel)) }; })()
   EOF
   ```

   A changed `active` (focus moves on press) and a pressed, ripple or hover style are the press,
   not the function. `url`, `title`, `dialogs`, `popovers`, `expanded`, `menus`, `on`, `playing`,
   `scrollY` or `text` changed at the second or third read, or `tab list` gained an entry: the
   down-event executes the function, go to step 3; the third read after the extra 1200 ms catches a
   long-press handler that fires while the pointer is still down. Unchanged at every read: No
   Down-Event, sliding off aborts, G212's check #2 holds: pass. Changed only at the last read,
   after the release outside the box: still No Down-Event, so the criterion is met, but G212's
   check #2 fails — record pass with the note that releasing outside the hit area still fires, and
   report it as an advisory finding only. Then `click "<selector>"` once to see the function run;
   `back` or `reload` if it navigated. For a destructive control (delete, pay, send) on a
   production sample stop at the scan: pass when every script is readable without hits, else
   `cannot-tell` naming the hits. Done when every control is pass, down-event or `cannot-tell`.

3. Classify each down-event execution against F101's four conditions — "controls are set to
   activate functionality on the down-event of a pointer", "no further mechanism to abort or undo
   is available", "the up-event does not reverse the outcome of the activation", "it is not
   essential for the functionality to execute and complete on the down-event" — which its Expected
   Results restate over its own three-step procedure as "If #1 is true, and #2 and #3 are false
   then the content fails the Success Criterion". All four must hold for a fail, so test the three
   escapes in this order:
   - Up Reversal: `mouse move` to the centre, `mouse down`, `wait 800`, fingerprint, `mouse up` in
     place, fingerprint; the last read equal to the baseline (`popovers` back down, `playing` back
     to 0, `dialogs` back down) is the release reversing the press: pass.
   - Abort or Undo: after the release `snapshot -i` for a confirmation dialog that has not yet
     applied the change, or an Undo control; `click` it and see the fingerprint return to the
     baseline: pass, recording the mechanism. Check the mechanism itself first (glossary Note 2):
     it has a name in `snapshot -i` and `press Tab` reaches it; an Undo that vanishes on its own
     is a content time limit, so record the observed delay and raise it under 2.2.1 as well.
   - Essential: the control types a character or a digit, emulates a key (Note 1), is an
     instrument key, or is a game control needing "a fast and immediate response": pass, naming
     which W3C pattern it matches, and do not ask for an undo. A timing claim that matches none of
     those patterns: needs confirmation.
   - None of the three: fail per F101.
     Done when each down-event function carries a bullet name, "F101 fail" or "needs confirmation".

4. Drag-and-drop ([G210](https://www.w3.org/WAI/WCAG22/Techniques/general/G210)) for each
   `draggable` entry and each sortable, kanban or tree item (the inventory serves 2.5.7 too).
   G210's procedure checks whether the action "can be reversed by" (1) "releasing the picked-up
   item outside a drop target", (2) "dragging the picked-up item back to its old position", (3) "a
   confirmation dialog or an undo control appears after the item has been dropped", and passes when
   "at least one option of #1, #2, #3 is true". `record start
.notes/audit/evidence/<sample>-2.5.2-<slug>.webm`, then the step 2 sequence with two extra moves
   after `mouse down`: `mouse move <centre x + 15> <centre y + 15>`, then `mouse move <x> <y>` to a
   page margin the point helper of step 2 reports as `onControl: false` and that sits outside every
   drop target, `mouse up`, `get box "<item>"` and the fingerprint. Item back in its original box,
   fingerprint unchanged: test 1 passes. Where the layout leaves no space outside the drop targets
   (G210's second kanban example: "there is no screen space outside the kanban columns"), test 1
   cannot be performed — record that and go straight to test 2. Otherwise `drag "<item>"
"<target>"` and `snapshot -i`: a confirmation dialog before the change applies, or an Undo
   control that restores it (`click` it, `get box` back to the original): pass (test 3); else
   `drag "<item>" "<original position>"` returns it with nothing else changed: pass (test 2);
   none: fail. `record stop`. A native `draggable` item stays put while its drag image follows the
   pointer, so judge it by where it lands; one that `drag` leaves untouched too is not
   pointer-draggable: drop it. Done when every draggable has a G210 test number, "no outside
   space, test 2 only" or a fail.

5. Touch. `set device "iPhone 13"`, `reload`, `wait --load networkidle`, rerun the scan and repeat
   step 2 for controls only this layout has (menu button, bottom sheet, swipe cards). `mouse down`
   raises `pointerdown` with `pointerType: "mouse"` and no touch event at all, so two handler kinds
   stay invisible to it: a `touchstart` listener, and a `pointerdown` listener gated on
   `pointerType === 'touch'`. For every `touchstart` or `pointerdown` hit and every
   `ontouchstart` handler send both with the third helper, `pc-touch.js`, the selector filled in:

   ```js
   ;(() => {
     const el = document.querySelector('<selector>'),
       r = el.getBoundingClientRect()
     const x = r.x + r.width / 2,
       y = r.y + r.height / 2
     const t = new Touch({
       identifier: 1,
       target: el,
       clientX: x,
       clientY: y,
       pageX: x + scrollX,
       pageY: y + scrollY
     })
     el.dispatchEvent(
       new TouchEvent('touchstart', {
         bubbles: true,
         cancelable: true,
         touches: [t],
         targetTouches: [t],
         changedTouches: [t]
       })
     )
     el.dispatchEvent(
       new PointerEvent('pointerdown', {
         bubbles: true,
         cancelable: true,
         pointerId: 1,
         pointerType: 'touch',
         isPrimary: true,
         clientX: x,
         clientY: y
       })
     )
     return 'touchstart + pointerdown sent'
   })()
   ```

   Read the fingerprint, then send `'touchend'` the same way with `touches: []` and
   `targetTouches: []`, plus `'pointerup'` with the same options, and read it again. Executed after
   the down pair and not reversed by the up pair: down-event, classify per step 3. `TouchEvent is
not defined`, or a handler that ignores untrusted events (`isTrusted` is false on everything
   dispatched here): `cannot-tell` for touch, naming the handler. A drag tested on touch may also
   be unreachable in real use, since G210 records that on touchscreens "AT generally consumes
   path-based or multipoint gestures so they would not reach the authored content" — note it for
   the hand-over rather than as a fail here. `set viewport 1280 900`. Done when each control has a
   touch verdict or `cannot-tell`.

6. Record and prove. One line per function in the findings file: selector, kind, the bullet it
   satisfies (No Down-Event, Abort or Undo, Up Reversal, Essential), or the fail with its F101
   condition and, for a drag, its G210 test number. For every fail keep the `-held.png` taken with
   the button down, a `highlight "<selector>"` page screenshot showing the outcome already on
   screen, and for a drag the `.webm`:

   ```bash
   agent-browser highlight "<selector>"
   agent-browser screenshot .notes/audit/evidence/<sample>-2.5.2-<slug>.png
   ```

   Done when every fail has a held screenshot plus an outcome screenshot, every drag fail has its
   recording, and every `cannot-tell` names what blocked it.

## Deciding

- Fail (certainty ≥ 90): F101's four conditions all hold — the function done at the second or third
  fingerprint while the button is held (navigation, a new tab, a modal dialog opened or closed, a
  form submitted, a purchase or upload started, content removed, moved or saved), not reversed by
  `mouse up` in place, no confirmation or Undo, and no W3C essential pattern (95); a dialog Close
  button that discards entered data on press, F101's own Example 1 (95); a draggable moved or
  deleted on release outside every drop target with neither a drag-back nor a confirmation or Undo,
  so none of G210's three tests passes (90).
- Fail (70–89): the same execution seen only through the synthetic `touchstart` / `pointerdown`
  pair of step 5 (80); a press that switches a tab, toggles an accordion, changes a selection or
  moves the page and stays so after release, reversible only by another activation (75); a drag
  reverted only through a control the evaluator had to hunt for (75); an Undo control that exists
  but is unreachable by `press Tab` or has no accessible name, so it fails the mechanism
  definition's Note 2 (75); an outcome the screenshot shows but the fingerprint missed (70).
- Needs confirmation (50–69): a down-event activation whose timing claim matches none of W3C's
  essential patterns — not a key press, not an instrument key, not a fast-response game control
  (60): ask whether up-event activation would defeat the function; a press that opens a transient
  menu, popover or tooltip that stays open and closes with Escape or a click outside, nothing else
  changed (65): ask whether dismissal counts as the undo; a destructive control that could only be
  scanned, on an unreadable bundle (55): ask for a staging sample; a scan hit in a readable script
  that no control reproduced (50): ask which component it drives.
- Pass: every single-pointer function, in every recorded state, in every frame, with mouse and with
  touch, either does nothing before release, reverses on release, has a confirmation or Undo the
  evaluator operated and could reach by keyboard, or matches an essential pattern; every draggable
  passes one of G210's three tests.
- Not present: only a sample state with no operable element at all.
- False positives to avoid: native `a`, `button` and inputs fire `click` on release (G212); a text
  field placing its caret on pointer-down passes, because G212 calls that "trivially reversible" —
  "the user realizes they made a mistake after pressing down the control, they can simply move
  their pointer away from the hit area while still holding down the pointer, then release their
  pointer and the event is not triggered"; a native `select`, date picker or range thumb acting on
  press, text selection, scrolling and the long-press context menu are the user agent (Note 2);
  focus moving, `:active`, ripple or pressed styling on `mouse down` is not the function; a
  press-and-hold preview or a video that plays only while held passes by Up Reversal; a keypad,
  piano or fast-response game key passes by Essential and needs no undo; firing on release outside
  the target still meets No Down-Event (an advisory note, not a fail); a slider whose value follows
  the pointer and can be dragged back before release has an abort; a kanban with no space outside
  its columns passes on the drag-back test alone; a two-finger or pinch interaction is out of scope
  here; `pointerdown` that only starts a drag or sets pointer capture, or `touchstart` that only
  calls `preventDefault` or draws a ripple, does not execute the function.

## Reporting

- File under: 2.5.2. A drag with no keyboard operation goes to 2.1.1, one with no single-pointer
  alternative to 2.5.7; an unexpected change of context on press is noted under 3.2.2 as well; a
  legal, financial or data-deleting action that fires on press with no confirmation is also 3.3.4.
  One issue per control pattern (all kanban cards, the Close button), naming every sample and state.
- Title patterns: "Menu opens on press, not on release", "Close button discards the form on
  press", "Cards dropped outside a column are deleted with no undo", "Slider commits on press"
- Severity: High when the down-event function is destructive or leaves the task (submits, deletes,
  buys, navigates away, closes a dialog with entered data) or a drag that moves data cannot be
  aborted; Medium when it changes navigation or a state that takes several steps to reverse; Low
  when one more press reverses the outcome.
- Type: Technical, always: the defect is event wiring or a drop handler without a revert.
- Evidence: the `-held.png` screenshot taken while the button is down, `highlight "<selector>"` on
  the pressed control, the outcome already on screen; for a drag, the `record start` /
  `record stop` GIF of the item released outside a target and not returning; the scan hit quoted.
- Recommendation: run the function from `click` (or from `pointerup` after checking the pointer is
  still inside the control's box) and remove the `mousedown`, `touchstart` and `pointerdown`
  handlers ([G212](https://www.w3.org/WAI/WCAG22/Techniques/general/G212), failure
  [F101](https://www.w3.org/WAI/WCAG22/Techniques/failures/F101)); on touch, trigger only on
  `touchend`:

  ```js
  // F101 Example 1 — the failure
  trigger.addEventListener('mousedown', closeDialog)
  trigger.addEventListener('touchstart', closeDialog)
  trigger.addEventListener('pointerdown', closeDialog)

  // G212 — one input-agnostic handler on the up-event replaces all three
  trigger.addEventListener('click', closeDialog)
  ```

  Where the down-event has to stay (grabbing a draggable, capturing the pointer), keep it for the
  grab only and complete the function on release. For a drag, offer one of G210's three routes:
  revert an item released outside a drop target, let it be dragged back to its old position, or
  confirm the drop or offer Undo afterwards
  ([G210](https://www.w3.org/WAI/WCAG22/Techniques/general/G210)).

- Related: 2.5.7 (single-pointer alternative to the drag), 2.5.1 (path-based and multipoint
  gestures), 2.1.1 (the same function from the keyboard), 2.5.8 (target size), 3.2.2 (change of
  context on input), 3.3.4 (a confirmation or reversal for legal, financial and data changes),
  2.2.1 (an Undo offer that expires on its own).
