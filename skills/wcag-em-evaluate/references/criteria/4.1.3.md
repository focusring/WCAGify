# 4.1.3 Status Messages

Level AA · WCAG 2.1+ · Guideline 4.1 Compatible · Group: `keyboard` (also `forms`)

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#status-messages) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#status-messages) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/4-1-3-status-messages/) ·
ACT: none mapped to this criterion

## Requirement

> In content implemented using markup languages, status messages can be programmatically
> determined through role or properties such that they can be presented to the user by assistive
> technologies without receiving focus.

Terms (WCAG 2.2 glossary): **status messages**: "change in content that is not a change of
context, and that provides information to the user on the success or results of an action, on the
waiting state of an application, on the progress of a process, or on the existence of errors".

## In plain terms

When the page adds, changes or removes a short message about what just happened ("5 results",
"Added to basket", "Saving…", "Upload 40 %", "3 errors") while focus stays put and no new page
loads, its container has to carry a live-region role or property so a screen reader announces it
where the user is; blind and low-vision users cannot see text appear elsewhere on the screen. Only
messages the page shows are judged ("not to force authors to generate new status messages"); their
wording is 3.3.1 and 3.3.3.

## Applies when

- Present: a state in which a user action or a running process adds, changes or removes text, an
  icon, a badge or a spinner that reports the success or result of the action, a waiting state,
  progress, or errors, with focus and URL unchanged. Detect it with the logger of step 2 after
  every trigger the `keyboard` and `forms` passes operate (listed in step 1) and with
  `structure.js` `liveRegions[]` for prepared containers; messages may be inserted off screen for
  assistive technology only, so the logger, not the screenshot, is the inventory.
- Not present: no trigger in any state produces such a change and `liveRegions[]` is empty: static
  pages, or every action loads a new URL or opens a dialog. Record the triggers operated.
- Exceptions: none in the criterion text; the definition excludes a change of context ("Since the
  dialog takes focus, it is defined as a change of context and does not meet the definition of a
  status message"; likewise a new page, or focus moved to the message, a summary or the first
  invalid field: 3.2.2, 2.4.3, 3.3.1), content "exposed or hidden when a user interacts with a user
  interface component" (menu, select, accordion, tree, tab: 4.1.2), and new questions or fields
  added after an answer. The list of search results is content; "18 results returned" or "No
  results returned" beside it is the status message.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual, and a clean
`scripts/axe-page.mjs` run proves nothing here. The `forms` pass re-checks this on every error and
success state it triggers (Situation B: ARIA19 with G83, G84, G85, G177 or G194; Situation A:
ARIA22 with G199) with steps 2 to 4 and 6 below.

## Manual procedure

Work by keyboard at `set viewport 1280 900`, default state first, then every state in
`recon/<sample>-states.md`. `snapshot` shows `status`, `alert` and `log` nodes with their text; the
logger of step 2 shows `aria-live` on plain elements and when a container got its role; what a
screen reader would say stays with the baseline assistive technologies, never a `cannot-tell`.

1. Inventory the prepared containers and the triggers:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
   agent-browser snapshot -i
   ```

   `liveRegions[]` (`selector`, `role`, `ariaLive`, `ariaAtomic`, `text`) are the containers set
   up before any message (ARIA22 test step 1); an empty one is correct. From `snapshot -i` list
   every control whose outcome is reported in place: search, filter, sort, add to basket, like,
   copy, save, upload, load more, undo, submits and validated fields. Done when both are listed.

2. Install the logger after each page load (a navigation clears it):

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const SEL = '[aria-live],[role="status"],[role="alert"],[role="log"],output';
     const t = n => n.localName + (n.id ? '#' + n.id : n.classList[0] ? '.' + n.classList[0] : '');
     const txt = ns => [...ns].map(n => n.textContent).join(' ').replace(/\s+/g, ' ').trim();
     const before = new Set(document.querySelectorAll(SEL));
     const S = window.__status = { log: [], t0: performance.now() };
     new MutationObserver(ms => ms.forEach(m => {
       const kind = m.type === 'attributes' ? 'attr' : m.type === 'characterData' ? 'changed'
         : m.addedNodes.length ? 'added' : 'removed';
       const el = m.target.nodeType === 1 ? m.target : m.target.parentElement;
       const n = kind === 'added' && m.addedNodes[0].nodeType === 1 ? m.addedNodes[0] : el;
       const text = (kind === 'attr' ? m.attributeName + '=' + n.getAttribute(m.attributeName)
         : kind === 'added' ? txt(m.addedNodes) : kind === 'removed' ? txt(m.removedNodes)
         : txt([m.target])).slice(0, 120);
       if (!n || !text) return;
       const r = n.closest(SEL);
       S.log.push({ ms: Math.round(performance.now() - S.t0), kind, node: t(n), text,
         region: r && t(r), ariaLive: r && r.getAttribute('aria-live'),
         role: r && (r.getAttribute('role') || (r.localName === 'output' ? 'output' : null)),
         atomic: r && r.getAttribute('aria-atomic'), regionExisted: r && before.has(r),
         regionRendered: r && !!r.getClientRects().length, visible: !!n.getClientRects().length });
     })).observe(document.body, { childList: true, subtree: true, characterData: true,
       attributes: true, attributeFilter: ['role', 'aria-live', 'aria-busy', 'aria-valuenow',
       'aria-valuetext', 'hidden'] });
     return 'observing, ' + before.size + ' live containers present';
   })()
   EOF
   ```

   `region` is the changed node's nearest live container; `regionRendered` is `false` for
   `display: none` and `hidden`, `true` for a clip class. Done when it returns "observing".

3. Operate one trigger, wait, read the log; repeat for every trigger of step 1:

   ```bash
   agent-browser focus "button.add-to-basket"; agent-browser press Enter; agent-browser wait 1500
   agent-browser eval --stdin <<'EOF'
   (() => { const S = window.__status, a = document.activeElement, out = { url: location.href,
     active: a.localName + (a.id ? '#' + a.id : '') + (a.name ? '[name=' + a.name + ']' : ''),
     log: S.log }; S.log = []; return out })()
   EOF
   agent-browser snapshot
   ```

   `url` changed, or `active` moved to the new content, a dialog or another control: a change of
   context, record "not a status message (change of context)" and go on. Otherwise sort the
   `added`, `changed` and `removed` entries by `text`: success or result ("Added", "Saved", "5
   results", "No results"), waiting ("Loading…", a spinner's label), progress ("40 %") or errors
   ("Enter a valid email", "3 errors") is a status message; result rows, a revealed panel, new
   fields and a control's toggled label are content. For a process longer than a second read at
   `wait 500` and again after `wait 8000`. Done when every entry is "status" or "content".

4. Judge each status entry ([F103](https://www.w3.org/WAI/WCAG22/Techniques/failures/F103) through
   the tree). Exposed: `region` is set, `ariaLive` is not `off`, `regionExisted` and
   `regionRendered` are `true`, and `role` is `status`, `alert`, `log` or `output` or `ariaLive` is
   `polite` or `assertive`; or another entry in the same read carries the same information under
   those conditions (a screen-reader-only container doubling a visible toast; a clip class still
   reports `visible: true`). Not exposed: `region` is `null`; `ariaLive` is `off`; `regionRendered`
   is `false`; an `attr` entry sets `role` or `aria-live` on the container at the same `ms` as the
   text or later ("if the role or property is not set before the dynamic content is added, this
   also predicts a failure"). Doubtful: `regionExisted: false` (the container arrived with its
   message, ARIA22 step 1 unmet); an `added` or `changed` entry whose `node` sits inside `region`
   and carries part of the string only ("3" for "3 items") while `atomic` is not `"true"` and
   `role` is not `status` or `alert` (implicitly atomic). Done when every status entry is exposed,
   not exposed or doubtful.

5. Waiting states, progress and icons. A spinner or "Loading…" is a waiting-state message and
   follows step 4; its `removed` entry with no replacement text and no change of context is noted
   as "end of wait not conveyed". `aria-busy` `attr` entries are a property, not a live
   announcement: alone they are doubtful. `aria-valuenow` entries on a `role="progressbar"` with
   no `added` or `changed` entry in a live container are not exposed ("because the progressbar
   role is not a live region, screen readers won't announce updates to those values", ARIA25); a
   feed of entries (chat, activity) is exposed by `role="log"` (ARIA23). A tick, a filled heart, a
   red dot or a badge with no text: find it by comparing `screenshot` before and after, run
   `images.js` and read its `name`: the Understanding splits these over "a combination of" 1.1.1
   for the text alternative and 4.1.3 for "an appropriate role", so a missing `name` is a 1.1.1
   defect and `region: null` is the 4.1.3 defect, with or without a `name`. Done when every
   process and every visual-only change is classified.

6. Evidence. `highlight` the message and `screenshot` right after the trigger; a toast that
   vanishes, a spinner or a progress bar gets a recording around the trigger:

   ```bash
   agent-browser record start .notes/audit/evidence/<sample>-4.1.3-basket-toast.webm
   agent-browser focus "button.add-to-basket"; agent-browser press Enter; agent-browser wait 800
   agent-browser highlight ".toast"
   agent-browser screenshot .notes/audit/evidence/<sample>-4.1.3-basket-toast.png
   agent-browser record stop
   ```

   Done when every fail has a screenshot or recording and its log entry and `active` quoted.

## Deciding

- Fail (certainty ≥ 90): a status message added or changed with `url` and `active` unchanged,
  `region: null`, and no same-information entry in a live container in the same read, F103 (95); a
  form error injected on submit or blur under the same conditions, F103 with the Situation B
  techniques (95); the container has `aria-live="off"` or `regionRendered: false` (90); the
  container's `role` or `aria-live` is set in the same read as the text or later (90).
- Fail (70–89): the container arrives together with its message, `regionExisted: false` (80); a
  progress bar whose only change is `aria-valuenow` or `aria-valuetext`, no text in a live
  container (80); an icon or badge that is the whole status, has a `name` and sits in no live
  container (80); a status icon with no `name` and `region: null`, filed under 1.1.1 too (75).
- Needs confirmation (50–69): only a number changes in a non-atomic container ("3" for "3 items"):
  ask whether the whole string should be announced (65); a waiting indicator removed with no end
  message and no change of context: ask whether the result is conveyed another way (60);
  `aria-busy` toggling as the only signal of a wait (55); a change whose status nature is unclear
  (a count in a tab label, "Filters applied" beside the filtered list) (55). A message inside an
  iframe that `frame` cannot enter is `cannot-tell`, with its `src` from `structure.js` `iframes[]`.
- Pass: every status message in every state, after every trigger, is or is inside a rendered
  container that existed before the action with `role` `status`, `alert` or `log`, `output`, or
  `aria-live` `polite` or `assertive`; or an equivalent message is; or a script announces it
  straight to the accessibility API with `ariaNotify` (ARIA27); or it is a change of context.
- Not present: no trigger in any state adds, changes or removes a status message; no live regions.
- False positives to avoid: changes of context (a dialog that takes focus, a new URL, focus moved
  to a summary or the first invalid field, a native validation bubble: 3.2.2, 2.4.3, 3.3.1);
  content revealed by expand and collapse, tabs, menus and selects, and a widget's own state
  attributes (4.1.2); newly added questions or fields; the result rows themselves; server-rendered
  messages on a fresh page load; the `removed` entry of a message that was exposed when it
  appeared; `role="alert"` on a success message (chatty, only a future failure); `aria-atomic`
  absent on `role="status"` (implicitly `true`); a ticker (2.2.2).

## Reporting

- File under: 4.1.3 for a status message with no role or property, a container that is hidden,
  born with its content or given its role late, a progress bar without live text, and a status
  icon outside a live container; the error wording goes to 3.3.1 and 3.3.3, an icon without text
  alternative to 1.1.1, focus moved to a message to 3.2.2, widget states to 4.1.2, a ticker to
  2.2.2. One issue per message mechanism: a toast component used by five triggers is one issue
  naming them and the other samples that use it.
- Title patterns: "The search result count is not announced", "The 'added to basket' message is
  not announced", "Form errors appear without a live region", "Upload progress is not announced"
- Severity: High when the message is the only feedback on the outcome of a task in scope (order
  placed or failed, form errors that block submission, save failed, a session about to expire);
  Medium when the outcome can be found elsewhere in the tree with effort (a basket count in the
  header, the results list itself) or the defect is a site-wide toast component; Low when the
  message is a courtesy with an obvious alternative ("copied", "saved" next to a switch).
- Type: Technical (the role or property is missing in markup or script).
- Evidence: the page screenshot right after the trigger with `highlight` on the message (or the
  spot it vanished from), the trigger named; a recording for a toast, a spinner or a progress bar.
- Recommendation: put an empty container in the DOM at load and write the message text into it:
  `role="status"` for results and success
  ([ARIA22](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA22),
  [G199](https://www.w3.org/WAI/WCAG22/Techniques/general/G199)), `role="alert"` for errors
  ([ARIA19](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA19)), `role="log"` for sequential
  updates ([ARIA23](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA23)), `aria-live="polite"`
  text beside a progress bar ([ARIA25](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA25));
  keep it rendered (a clip class, never `display: none`) and add `aria-atomic="true"` when the
  whole string must be read. Example: `<div role="status" aria-atomic="true" id="msg"></div>`
  and, after the action, `document.getElementById('msg').textContent = '5 results found'`.
- Related: 3.3.1 and 3.3.3 (the error text itself); 4.1.2 Name, Role, Value (widget states,
  `aria-invalid`); 1.1.1 Non-text Content (status icons); 3.2.2 On Input and 2.4.3 Focus Order
  (focus moved to the message instead); 2.2.2 Pause, Stop, Hide (auto-updating live content).
