# 3.3.1 Error Identification

Level A · WCAG 2.0+ · Guideline 3.3 Input Assistance · Group: `forms`

Sources: [Understanding][understanding] ·
[Spec](https://www.w3.org/TR/WCAG22/#error-identification) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#error-identification) ·
[Plain English][plain] · ACT: [36b590][act]

[understanding]: https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html
[plain]: https://aaardvarkaccessibility.com/wcag-plain-english/3-3-1-error-identification/
[act]: https://www.w3.org/WAI/standards-guidelines/act/rules/36b590/

## Requirement

> If an input error is automatically detected, the item that is in error is identified and the error
> is described to the user in text.

Two things must hold at once, both in text: the _item_ in error is identified, and the _error_ is
described. The Understanding: "This SC requires that users be provided with information about the
nature of the error, including the identity of the item in error."

Terms (WCAG 2.2 glossary) — **input error**, verbatim; its note is what makes an empty required
field an error at all:

> information provided by the user that is not accepted
>
> Note:
>
> This includes:
>
> - Information that is required by the web page but omitted by the user
>
> - Information that is provided by the user but that falls outside the required data format or
>   values

ACT 36b590 decides on **form field error indicators**, its glossary term, verbatim; the list of
error kinds widens what counts as an indicator beyond field validation, and the note stops a red
border being read as an error by itself:

> Any text, or non-text content, or an element that has presentation indicating that an error was
> identified which appears to be related to some user input into, or the lack of user input into
> some element. These could be different types of errors, for example:
>
> - missing input, for example a required form field that was left empty
> - incorrect input, such as an invalid password
> - input not in an expected format, expected range, or of an allowed value
> - timing error, such as session timeouts or expiration of an allowed action
> - authentication or authorization errors
>
> Note: An error indicator can be a separate element in the page, but it can also be part of a form
> control. For example a red outline on a form control is often used to indicate an error. Not all
> red outlines are indicators of an error though. This depends on the presentation of the form
> control in relation to other elements on the page.

## In plain terms

When the browser, a script or the server rejects what someone typed or left empty, the page has to
say so in words: which field, and what is wrong with it. A red border, an icon, a shake or a moved
focus may come on top, never alone — "the only requirement is for errors to be presented to users
in text or a text alternative", and "it is not sufficient to only re-display the form without
providing any hint that the submission failed". This serves people who are blind, have low vision
or a colour vision deficiency, and people with cognitive, language and learning disabilities "who
have difficulty understanding the specific reason why a form submission failed". The fix wording is
3.3.3, the programmatic exposure 4.1.2 and 4.1.3; inline, summary, alert or dialog are all fine.

## Applies when

- Present: a sample state with a field that can reject input. `forms.js` returns `fields[]` and a
  field has `required` or `ariaRequired`, a constraining `type` (email, url, number, date, month,
  week, time, datetime-local, range — `tel` and `text` constrain nothing by themselves), a
  `pattern`, `min`, `max`, `step` or `minlength` attribute (step 1), a password confirmation, a
  terms checkbox, or a submit that a server validates (login, contact, checkout, newsletter,
  registration, address lookup). `novalidate` on a `forms[]` entry means the browser will not block;
  a non-zero `inputsWithoutForm` means fields outside any `<form>`, a scripted widget driven from
  the button beside it. A number or date with `min`/`max` that the page silently clamps counts even
  though nothing is refused (step 3). Errors already on arrival (`visibleErrors[]`, `ariaInvalid`,
  `errormessageText`) count; so does every state's form. ACT's error kinds add two more triggers to
  look for: an expired session or an expired action, and a refused login or authorisation.
- Not present: no state offers a field that takes input (`fields[]` holds only buttons), or no
  form or widget ever rejects anything: after steps 2 and 3 each accepted empty and wrong input
  with no bubble, no message, no marked field and no changed value. Record `not-present` and list
  what was submitted and where each submit went (`get url`).
- Exceptions: the criterion text has none. Scope notes from the Understanding and from ACT 36b590
  that change an outcome:
  - Programmatic exposure is out of scope here: "This type of programmatic information is not
    required for this success criterion, but may be covered by other criteria such as 4.1.2 Name,
    Role, Value." A missing `aria-invalid` or `aria-describedby` beside visible in-tree text is not
    a fail here.
  - The fix is out of scope here: "What the user should do to correct the item in error is covered
    by 3.3.3 Error Suggestion." The Understanding's own calibration: "For instance, 'Email is not
    valid' would pass 3.3.1, but 'Please provide a valid email address in the format
    name@domain.com' also conveys how it can be fixed and passes both."
  - Placement is free: "This criterion does not mandate any particular way in which errors should
    be displayed. Depending on the situation, it may be more suitable for all errors to be listed
    at the start or before a form. In other cases, it may be more appropriate to show errors
    inline [...] Errors could also be listed in an alert, or dialog." Never fail a form for
    choosing a summary over inline messages, or the other way round.
  - Native HTML validation passes: user agents "automatically prevent the submission of incomplete
    or invalid forms, and display generic error messages", set focus back to the first field in
    error, and "In most common user agent and screen reader combinations, the screen reader will
    announce the error message and the programmatic name of the focused field. While this meets the
    requirements of this success criterion", four disadvantages are recorded with the pass, not
    against it: "the message may not be permanent, or fail to scroll with the page"; the message is
    not magnified when the user has zoomed, so "the message may be too small for users to read";
    the default messages "are generally quite generic" and may not meet 3.3.3; "If several errors
    are present, only the first error message is exposed". Close the note with the Understanding's
    own caveat — "developers will need to carefully consider if native browser validation is
    accessibility supported" — and put it in the findings file.
  - Errors on another page: ACT 36b590 "does not test form field error indicators shown on a
    different page than that of the test target". A server that answers a submit with a different
    URL is judged as that page's own state; record the URL from `get url` and evaluate it there.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. ACT 36b590 has no axe
4.12.1 implementation either, so `scripts/axe-page.mjs` prints nothing for 3.3.1 and proves nothing

## Manual procedure

1. Inventory the forms in the default state and in every state that adds fields (login dialog,
   newsletter, search, filters, cookie preferences, each step of a multi-step form):

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser get attr "input[name='postcode']" pattern
   agent-browser get attr "input[name='age']" min
   ```

   From `forms[]` note `selector`, `novalidate` and `submitButtons`; from `fields[]` every visible,
   non-`disabled` field with `required`, `ariaRequired` or a constraining `type`, plus fields
   already in error (`visibleErrors[]`, `ariaInvalid === 'true'`, `errormessageText`). `get attr`
   takes the selector first and the attribute second, and reads `pattern`, `min`, `max`, `step` and
   `minlength`, which the probe does not return; write each value down, because step 3 needs a value
   that lies outside it. `counts.requiredWithoutIndication` predicts which fields an empty submit
   will reject (the mark itself is 3.3.2; [ARIA2][aria2] is advisory here). When `inputsWithoutForm`
   is non-zero, group those fields by their nearest shared container and take the `button` in it as
   the submit; treat each group as a form for the steps below. A form whose submit has real-world
   effects (order, payment, account, mail to a real address) takes the test data from `index.md`;
   without such data block its request (`network route "<url>" --abort`), judge client-side
   detection only and record server-side detection as `cannot-tell`. Done when every form and
   group has its constraint list, its submit control and a submit decision.

2. Trigger the "omitted" error. Leave every field empty, mark the document so a round trip to the
   server is detectable, submit, then read what changed:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => { window.__wcagemMark = Date.now(); return { marked: true, url: location.href } })()
   EOF
   agent-browser click "form.contact button[type='submit']"
   agent-browser wait 1500
   agent-browser get url
   agent-browser eval --stdin <<'EOF'
   (() => ({ samePage: typeof window.__wcagemMark === 'number', url: location.href }))()
   EOF
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser snapshot
   ```

   `samePage: false` means the document was replaced: the submit reached the server and came back.
   Four routes:

   (a) The browser blocked it: URL unchanged, `samePage: true`, no new text in the snapshot. The
   native bubble is browser UI — it is in neither the DOM nor the accessibility tree, and a page
   `screenshot` does not capture it. Read it from the validity API instead:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const form = document.querySelector('form.contact')
     const active = document.activeElement
     return {
       focused: active ? active.name || active.id || null : null,
       focusedMessage: active && active.validationMessage ? active.validationMessage : null,
       invalid: [...form.elements]
         .filter((el) => el.willValidate && !el.validity.valid)
         .map((el) => ({ field: el.name || el.id, message: el.validationMessage }))
     }
   })()
   EOF
   ```

   `validity.valid` reads the state without firing `invalid` events, so this probe cannot itself
   create the error text it is looking for. A non-empty `focusedMessage` identifies the field (it
   holds focus, its label from `fields[]` is announced with it) and describes the error in text:
   pass for this route, record "native validation" with the four caveats from "Applies when". An
   `invalid` array longer than one entry is the "only the first error message is exposed" case that
   step 6 counts. On a `novalidate` form the API still returns messages the user never sees: that
   form's real route is (c) or (d).

   (b) The page reacted: `visibleErrors[]` gained entries, `ariaInvalid` turned `true`, an `alert`,
   `alertdialog` or `dialog` role appeared in the snapshot, or `dialog status` shows a
   `window.alert` (the [SCR18][scr18] pattern) — quote its text, then `dialog accept`. Go to
   step 4.

   (c) The submit was accepted: `samePage: false` or the URL advanced, and the new state confirms
   the submission (thank-you text, an order number). Nothing was detected for empty input, so
   nothing is required here; note whether any success feedback exists at all ([G199][g199],
   advisory, never a fail here) and hand the missing detection to 3.3.4 when the form is legal,
   financial or data-modifying.

   (d) The submit was rejected with no hint: the form comes back — `samePage: false`, or the URL is
   the form's `action`, or `fields[].value` is empty again — and the snapshot holds no message, no
   marked field and no `alert`. The Intent names exactly this: "In the case of an unsuccessful form
   submission, it is not sufficient to only re-display the form without providing any hint that the
   submission failed." Record a fail at certainty 95. The only thing separating (d) from (c) is the
   absence of a confirmation and the form still being on screen, so quote both.

   Done when every form has (a), (b), (c) or (d) recorded, with the observed text quoted, `samePage`
   noted and the URL before and after written down.

3. Trigger the "wrong format or value" error, one constrained field at a time with the rest valid.
   Submit as in step 2, and test on-blur validation as well, since many scripts validate per field:

   ```bash
   agent-browser fill "input[name='email']" "not-an-address"
   agent-browser press Tab
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser snapshot -s "form.contact"
   ```

   Use the Understanding's own examples of input errors as the test values, matched to the fields
   the sample has: "the user fails to enter the proper abbreviation in a state, province, or region
   field"; "the user enters a state abbreviation that is not a valid state"; "the user enters a non
   existent zip or postal code"; "the user enters a birth date 2 years in the future"; "the user
   enters alphabetic characters or parentheses into their phone number field that only accepts
   numbers"; "the user enters a bid that is below the previous bid or the minimum bid increment".
   Add an email without `@`, a number or date outside the `min`/`max` read in step 1, a password
   confirmation that differs, a value outside a combobox's list, and the terms checkbox left
   unchecked.

   Re-read `fields[].value` after an out-of-range number or date. A value the page silently moved
   into range is still an input error: "If a user enters a value that is too high or too low, and
   the coding on the page automatically changes that value to fall within the allowed range, the
   user's error would still need to be described to them as required by the success criterion."

   Done when every constrained field was rejected once or shown to accept anything, with the value
   sent, the value left behind and the reaction recorded for each.

4. Judge each error state against ACT 36b590.

   Applicability, verbatim: the rule applies to "each HTML element that has one of the following
   semantic roles: checkbox, combobox, listbox, menuitemcheckbox, menuitemradio, radio, searchbox,
   slider, spinbutton, switch or textbox". `input type="password"`, `file` and `color`, and the
   date and time inputs, map to none of those roles; judge them on the criterion text alone, with
   the same three questions.

   Two background rules shape the mapping before any expectation is checked: "A single form field
   error indicator can be related to multiple test targets" (one summary above the form covers
   every field it names) and "A single test target can be related to multiple form field error
   indicators" (a red border, an adjacent icon, an inline message and a summary entry are four
   indicators for one field). Collect every indicator per field first; each expectation needs only
   one indicator to satisfy it, and it need not be the same indicator for all three.

   For each field with at least one indicator, check all three — a rule with three expectations is
   unmet if any one of them is unmet:
   - Expectation 1, identification: "Each test target either has no form field error indicators, or
     at least one of the form field error indicators allows the identification of the related test
     target, through text, or through non-text content, or through presentation." Presentation
     alone is enough: a message immediately below the field, or the field itself marked, identifies
     it. A summary naming a label that occurs in two groups ("Name" under Shipping and under
     Billing) without naming the group identifies nothing (failed example 5).
   - Expectation 2, visible text: "Each test target either has no form field error indicators, or
     at least one of the form field error indicators describes: the cause of the error, or how to
     resolve it, in text that is visible." Either branch satisfies it — "Enter a date in the past"
     resolves without naming the cause and still meets it. A red border, an icon, a red asterisk, a
     shake, a `title` tooltip and a placeholder the typed value hides are not visible text.
   - Expectation 3, text in the tree: "Each test target either has no form field error indicators,
     or at least one of the form field error indicators describes: the cause of the error, or how
     to resolve it, in text that is included in the accessibility tree or included in the accessible
     name or accessible description of the test target." Two places, not one: the message element's
     own text in the `snapshot`, or the field's `describedbyText` / `errormessageText`
     (`aria-errormessage` never appears in `describedbyText`).

   Read the indicators with the probe's limits in mind:
   - `visibleErrors[]` needs both an error-like hook (`role="alert"`, any `aria-live`, a class or id
     containing `error` or `invalid`, `.field-error`, `.form-error`) and one of the words
     error / fout / invalid / ongeldig / required / verplicht / must / moet / incorrect in its text;
     it keeps at most 30 entries and truncates each to 160 characters. A real message worded "Vul
     een geldig e-mailadres in" or "Enter a date before today" is missed by it, and a long summary
     is cut: take the wording from the `snapshot` diff, not from the probe.
   - `visibleErrors[].forField` is filled only when some control points at the element with
     `aria-describedby` or `aria-errormessage`. `null` means no programmatic link, not that the
     message identifies nothing; adjacency and wording are judged from the snapshot and the
     screenshot.
   - The probe's visibility test is a non-zero box plus `visibility` and `[hidden]`, so a message
     clipped into a screen-reader-only rectangle still lands in `visibleErrors[]`. Settle
     expectation 2 from the screenshot.
   - `describedbyText` and `errormessageText` read `textContent` whether or not the element is
     rendered, so neither proves expectation 3 on its own:

     ```bash
     agent-browser is visible "#email-error"
     agent-browser get styles "#email-error"
     agent-browser snapshot -s "form.contact"
     ```

     `display: none` (failed example 3) keeps the text out of the page and out of the tree;
     `aria-hidden="true"` (failed example 4) keeps a visible message out of the tree; text drawn by
     `::before` or baked into an image is in neither. Text absent from the `snapshot` subtree is
     not in the tree.

   Last, check that the text describes _this_ field's error: "Please fill the field correctly"
   above two fields (failed example 1) or "There are errors in the form" alone identifies nothing,
   and a bare "Invalid value for age." describes no cause (failed example 2).

   Worked example, the newsletter field on a `novalidate` form: submit empty; `visibleErrors[]`
   returns `{ text: 'Invalid', forField: null, role: null }`, `fields[].ariaInvalid === 'true'`,
   and the screenshot shows a red border with that word under the field. Expectation 1 is met
   (adjacency plus the marked field, "through presentation"); expectation 3 is met (the word is in
   the snapshot); expectation 2 is unmet, because "Invalid" states neither the cause nor the
   resolution. Rule unmet, one issue, certainty 75.

   Done when each field in error has the three expectations marked met or unmet with the quoted
   text and the indicator that satisfied each one.

5. Read the tree for what it can and cannot show: `snapshot` lists `alert` and `status` roles with
   their text, a field's invalid state and the message element's text; it does not show whether a
   screen reader announces an injected message (4.1.3) or reads the description on focus (4.1.2).
   Here text in the tree is enough. Record `cannot-tell` only for a form that could not be
   submitted (step 1), one whose error text lives in a `canvas` or a third-party widget the
   snapshot does not expose, or one in an iframe `frame` cannot enter. Done when each form has
   either three expectation verdicts or a `cannot-tell` with its reason noted.

6. Several errors at once: submit with two or more fields wrong and count the messages against the
   fields in error. Native validation showing only the first is acceptable (Understanding); a
   script that shows one generic message for several fields, or marks every field red with one
   message naming none, is unmet on expectation 1. A summary that names every field in error, and
   links each name to its field, is the pattern to recommend ([G139][g139], advisory). A message
   that vanishes: `record start` before the submit and count the seconds it stays.

   ```bash
   agent-browser record start .notes/audit/evidence/<sample>-3.3.1-toast.webm
   agent-browser click "form.contact button[type='submit']"
   agent-browser wait 6000
   agent-browser record stop
   ```

   Done when the number of fields in error, the number of messages, the field each message names
   and the message lifetime are noted.

7. Evidence for every fail: a screenshot of the error state with the field and its indicator (or
   the empty spot where the text should be) drawn; a recording when the message moves or vanishes:

   ```bash
   agent-browser highlight "input[name='email'], .field-error"
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.1-contact-email.png
   ```

   For route (a) the bubble is not in the image: screenshot the focused field and put the
   `validationMessage` string in the findings file as the quoted text. Record for every form the
   submitted values, the quoted message text (or "none"), the indicator type, the three verdicts
   and the URL before and after the submit. Done when every fail has a screenshot path and this
   record.

## Deciding

- Fail (certainty ≥ 90): input is rejected (submission blocked, `ariaInvalid` set, a border, icon
  or background change, a value moved into range) outside route (a) of step 2, and no text in the
  state describes the error: colour, icon, animation or focus move only (95); the form re-displayed
  after a rejected submit with no message anywhere, route (d) of step 2 (95); error text exists but
  is hidden from sight (`display: none`) or from the tree (`aria-hidden="true"`), ACT 36b590 failed
  examples 3 and 4 (90); the error is conveyed only by an image or icon that carries no text
  alternative, so there is neither "text or a text alternative" (90); `aria-invalid="true"` or a
  marked field with no visible text for it in a form with `novalidate` or a script that suppresses
  the native bubble (90); a refused login, or a submission rejected because the session or the
  allowed action expired, returned with nothing in text anywhere — the entry was not accepted and
  ACT lists authentication and timing errors among the errors an indicator reports (90).
- Fail (70–89): one generic message for several fields that names none ("Please fill the field
  correctly", "Something went wrong", "Check the form") (85); the only text is a `title` tooltip
  or a placeholder the typed value hides (85); the message is in the tree but visually hidden
  (clipped screen-reader-only text) while sighted users get colour alone, expectation 2 unmet (85);
  a summary whose field names are ambiguous because the label repeats in two groups (80); a message
  next to no field and naming no label ("This field is required" in a banner above a ten-field
  form) (80); a value clamped into range with no text (80); message text drawn by a pseudo-element
  or an image of text, absent from the tree (75); a visible message tied to the field that states
  neither the cause nor the resolution ("Invalid", "Error", "✕"), ACT failed example 2 (75).
- Needs confirmation (50–69): a toast that vanishes in seconds and leaves only a colour mark on
  the field: ask whether the message can stay (60); a message between two fields that names
  neither, where either could be the one in error (60); the only indicator is a red outline on a
  page that also outlines non-error controls in red, "Not all red outlines are indicators of an
  error though": ask a sighted human whether it reads as an error (55); a message the evaluator
  cannot read, in a canvas or a third-party widget whose text the snapshot does not expose (55).
- Pass: for every rejected input in every submitted form and state, at least one visible text that
  is in the tree identifies the field (by label, by adjacency, by holding focus) and states what is
  wrong (missing, not valid, out of range, not accepted) or how to fix it; a native bubble with a
  non-empty `validationMessage` counts. All three ACT expectations met is not by itself a pass for
  the criterion — its outcome mapping reads "All passed outcomes: success criterion needs further
  testing" — so also settle the fields the rule's applicability leaves out (password, file,
  colour, date and time inputs) and the errors it does not test (those shown on a different page).
- Not present: no field that takes input in any state, or every form and widget accepts empty and
  wrong input without any detection.
- False positives to avoid: colour and icons in addition to text ("It is perfectly acceptable to
  indicate the error in other ways such as through the use of an image, color, or other visual
  indicator, in addition to the text description"), including the Understanding's own example of a
  unique character to search for plus a yellow highlight; a summary instead of inline messages, or
  the other way round (placement is not mandated); only the first error under native validation;
  "Email is not valid" with no fix, which "would pass 3.3.1" per the Understanding while the
  missing suggestion is 3.3.3; a shared message referenced from the submit button rather than from
  the fields, when it names the labels (ACT passed example 2); a field that simply has no error
  indicator, which the rule passes (passed example 3); a form that accepts anything; required marks
  absent before submit (3.3.2); a visible, in-tree message without `aria-invalid` or
  `aria-describedby` (4.1.2, 1.3.1).

## Reporting

- File under: 3.3.1 for no text, hidden text, text that does not identify the field, and text that
  does not say what is wrong. A message with no fix goes to 3.3.3; a colour-only error also names
  1.4.1 in its text; an injected message not announced to 4.1.3; a missing `aria-invalid` or
  association to 4.1.2 or 1.3.1; missing required marks to 3.3.2; no detection at all on a legal,
  financial or data-modifying form to 3.3.4. One issue per form; a shared component (site-wide
  login dialog, footer newsletter) names the other samples.
- Title patterns: "Contact form marks errors with colour only", "Login error does not say which
  field is wrong", "Checkout error messages are hidden from assistive technology", "Registration
  form reloads without saying the submission failed", "Error message says only 'Invalid'"
- Severity: High when the form completes a task in scope (login, checkout, application, contact)
  and rejected input is shown without text, so a screen-reader or colour-blind user cannot learn
  why it fails; Medium when text exists but is generic or names no field on a multi-field form, or
  the component is site-wide; Low when one optional field (newsletter, filter) has an obvious cause.
- Type: Technical when the text is missing, hidden or detached from the field (fix in markup or
  script); Content when a message exists but its wording names no field or no cause.
- Evidence: screenshot of the error state after submit with `highlight` on the field and the
  message or its absence, the submitted values named in the text; for a native bubble, the focused
  field plus the quoted `validationMessage`, since browser UI is not in the image; a GIF when the
  message appears and vanishes, when the page reloads with nothing to show, or when only a shake or
  colour change signals the error.
- Recommendation: show, next to the field or in a summary above the form, visible text that names
  the field and says what is wrong: [G83][g83] for omitted required input, [G85][g85] for a wrong
  format or value, [G84][g84] for a value outside an allowed list. Validate on the client and put
  the description in an alert ([SCR18][scr18]) or write it into the page with script
  ([SCR32][scr32]); keep it in the tree and tie it to the field with `aria-invalid` and
  `aria-describedby` ([ARIA21][aria21]); inject script-detected errors in a live region or alert
  dialog ([ARIA19][aria19], [ARIA18][aria18]). Minimal inline fix:

  ```html
  <label for="email">Email</label>
  <input id="email" type="email" aria-invalid="true" aria-describedby="err-email" />
  <p id="err-email">Error: Email is required. Enter it as name@example.com.</p>
  ```

  For a summary, name every field in error and link each name to its field so users can jump to it
  ([G139][g139], advisory), and move focus to the summary once it is rendered:

  ```html
  <div role="alert" tabindex="-1" id="form-errors">
    <h2>There are 2 problems with this form</h2>
    <ul>
      <li><a href="#email">Email is required. Enter it as name@example.com.</a></li>
      <li><a href="#age">Age must be at least 1.</a></li>
    </ul>
  </div>
  ```

  Advisory additions: confirm a successful submission in text as well ([G199][g199]), and mark
  required fields with `aria-required` before anything is submitted ([ARIA2][aria2]; the visible
  mark itself belongs to 3.3.2). [PDF5][pdf5] and [PDF22][pdf22] are the equivalents for PDF forms
  and apply only when the sample is a PDF, not to a browser-driven audit of an HTML page.
