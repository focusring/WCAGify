# 3.3.3 Error Suggestion

Level AA · WCAG 2.0+ · Guideline 3.3 Input Assistance · Group: `forms`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)
· [Spec](https://www.w3.org/TR/WCAG22/#error-suggestion)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#error-suggestion)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-3-3-error-suggestion/)

## Requirement

> If an input error is automatically detected and suggestions for correction are known, then the
> suggestions are provided to the user, unless it would jeopardize the security or purpose of the
> content.

Terms (WCAG 2.2 glossary): **input error**: "information provided by the user that is not accepted
[...] This includes: Information that is required by the web page but omitted by the user [and]
Information that is provided by the user but that falls outside the required data format or
values". Both halves are in scope: an omission and a wrong format each need their own suggestion,
on the same field if it can fail both ways.

**user agent** (Understanding, Key Terms): "any software that retrieves and presents web content
for users". The browser is one, so its own validation bubble can carry the suggestion: "The content
author may provide the description of the error, or the user agent may provide the description of
the error based on technology-specific, programmatically determined information." (Intent). Nothing
in the criterion requires the suggestion to sit in the page.

## In plain terms

When the page, a script or the browser rejects what the user typed and a correct entry is known,
the error text says how to put it right: the expected format or an example, the correct entry, the
allowed values or the nearest match, or what was left out. 3.3.1 makes the page say that something
is wrong; this one makes it say what to do next, so that people with cognitive limitations, who
"may find it difficult to understand how to correct the errors", and people who are blind or have
impaired vision, who "may not be able to figure out exactly how to correct the error", finish the
form instead of abandoning it. Nothing is owed where no correction is knowable, or where naming it
would give away a secret.

## Applies when

- Present: the sample, in any state, has a field whose input can be rejected automatically:
  `required` or `aria-required`, `type` email, url, tel, number, date or time, a `pattern`, `min`,
  `max`, `minlength`, `maxlength` or `step`, a select, radio group, combobox or datalist, a text
  field whose label asks for a value from a known set (month, country), or a form whose script or
  server validates on blur or submit. Detect with `forms.js` and step 1.
- Situations (they pick the test to run and the technique to cite, and a field can be in both):
  - **Situation A**, "If information for a field is required to be in a specific data format":
    pattern, length, range, type-constrained and coded fields (postcode, IBAN, reference number).
    Judged with [G85](https://www.w3.org/WAI/WCAG22/Techniques/general/G85) and
    [G177](https://www.w3.org/WAI/WCAG22/Techniques/general/G177).
  - **Situation B**, "Information provided by the user is required to be one of a limited set of
    values": select, radio group, datalist, combobox, and free-text fields whose value must come
    from a known set. Judged with [G84](https://www.w3.org/WAI/WCAG22/Techniques/general/G84) and
    [G177](https://www.w3.org/WAI/WCAG22/Techniques/general/G177).
  - Understanding note: "In some cases, more than one of these situations may apply. For example,
    when a mandatory field also requires the data to be in a specific format." A field carrying two
    labels is passed only when every one of its failure modes gets a suggestion.
- Not present: no state has a control that takes input — `fields[]` also lists buttons and the ARIA
  widgets the probe collects (`role` textbox, combobox, listbox, checkbox, radio, switch, slider,
  spinbutton, searchbox, and `contenteditable="true"`) — or every blur and submission is accepted
  whatever is entered; record what was entered and submitted.
- Exceptions:
  - "unless it would jeopardize the security or purpose of the content": a login that answers
    "email or password incorrect" without saying which, a password, PIN, one-time code or
    security-question field, a CAPTCHA, a quiz or exam answer, a voucher or access code whose valid
    values are the secret. The error is still identified (3.3.1); the correction may stay unsaid.
    Record pass for that field and quote the exception in the note.
  - "suggestions for correction are known": nothing is owed where the page cannot know a better
    value (a free-text message refused by a server fault, a username already taken where no
    alternative is computed). Record the reason with the pass.

## axe-core

No axe-core rule and no ACT rule is mapped to this criterion: `scripts/axe-page.mjs` prints nothing

Settles: nothing. Leaves open: every step below.

## Manual procedure

The `forms` pass reaches each error state once for 3.3.1, 3.3.2, 3.3.3 and 4.1.3; this file reads
them for the suggestion only. Work at `set viewport 1280 900` in every state that holds fields.

1. Inventory the constraints and fix each field's situation. Run the probe, then the helper:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser eval --stdin <<'EOF'
   (() => [...document.querySelectorAll('input, select, textarea')].map(el => ({
     selector: el.id ? '#' + el.id : `${el.localName}[name="${el.name}"]`, type: el.type,
     willValidate: el.willValidate, required: el.required, title: el.title || null,
     pattern: el.getAttribute('pattern'), min: el.min || null, max: el.max || null,
     step: el.step || null, minLength: el.minLength > 0 ? el.minLength : null,
     maxLength: el.maxLength > 0 ? el.maxLength : null,
     listed: el.list ? el.list.options.length : el.options ? el.options.length : null,
     noValidate: el.form ? el.form.noValidate : null
   })).filter(f => f.willValidate && (f.required || f.pattern || f.min || f.max || f.step
     || f.minLength || f.maxLength || f.listed
     || /^(email|url|tel|number|date|time|month|week)$/.test(f.type))))()
   EOF
   agent-browser get attr "#postcode" title
   ```

   For each field write down what the page can reject (omission, format, range, length, a value
   outside the set) and what the user is already told beside it (`visibleLabelText`,
   `describedbyText`, `placeholder`, `title`). `get attr` takes the selector first and the attribute
   second; read `title` that way on every field the helper reports with a `pattern`, because that
   `title` is what the native bubble prints instead of the bare "Please match the requested format."
   Then label each field Situation A, Situation B or both, per "Applies when". `willValidate` keeps
   out the disabled, readonly and hidden fields the browser never validates and that take no user
   input. Add back the fields without native constraints whose label names a known set (month,
   country) or a coded value (postcode, IBAN, customer number): scripts and servers validate those,
   server-side detection included. `noValidate: true` suppresses the native bubbles, so on that form
   every message has to come from the page or the script. Done when every field has its rejectable
   inputs, its situation label and its visible instruction, or "accepts anything".

2. Trigger the omission errors — "required by the web page but omitted by the user". Leave every
   required field empty and submit, using the name from `forms[].submitButtons`; then blur one
   required field on its own:

   ```bash
   agent-browser find role button click --name "Send"
   agent-browser wait --load networkidle
   agent-browser focus "#email"
   agent-browser press Tab
   ```

   Under native validation the browser reports one field at a time, the first invalid one in source
   order; to reach a later field, `fill` every earlier required field with a valid value and submit
   again, and repeat until each required field has had its turn. Done when each required field has
   produced a message (step 4) or is recorded as never validated.

3. Trigger the format and value errors — "falls outside the required data format or values". Take
   one field at a time with the rest valid, `fill` a value that breaks it, blur, then submit:

   ```bash
   agent-browser fill "#email" "name.example.com"
   agent-browser press Tab
   agent-browser fill "#date" "31-02-2024"
   agent-browser select "#month" ""
   agent-browser find role button click --name "Send"
   agent-browser wait --load networkidle
   agent-browser get url
   ```

   Situation A values: an email without "@", "abc" in a telephone or number field, "31-02-2024" in
   a date field, the wrong shape for a `pattern`, a number below `min`, one character under
   `minlength`. Situation B values: "12" in a field that asks for a month name (the Understanding's
   own example), "Chicargoo" in a city field, a word outside a datalist or combobox, a select left
   on its placeholder option. A field labelled with both situations gets both treatments, and a
   required field gets step 2 as well: its omission message says nothing about its format. `get url`
   separates a server round trip from a script check — a changed URL or a re-rendered page is
   server-side detection, an unchanged URL is the browser or a script. Done when every constrained
   field has been rejected once per situation that applies to it, or recorded as accepting the wrong
   value.

4. Read every message that appeared and tie it to its field. Four channels carry them:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser snapshot -i
   agent-browser get text "#form-errors"
   agent-browser dialog status
   agent-browser eval --stdin <<'EOF'
   (() => [...document.querySelectorAll('input, select, textarea')]
     .filter(el => !el.validity.valid).map(el => ({ message: el.validationMessage,
       title: el.title || null, nativeValidation: Boolean(el.form) && !el.form.noValidate,
       selector: el.id ? '#' + el.id : `${el.localName}[name="${el.name}"]`,
       why: ['valueMissing', 'typeMismatch', 'patternMismatch', 'tooLong', 'tooShort',
         'rangeUnderflow', 'rangeOverflow', 'stepMismatch', 'badInput', 'customError']
         .filter(k => el.validity[k]) })))()
   EOF
   ```

   (a) Page text: `visibleErrors[]` (`text`, `forField`, `role`, `ariaLive`), plus `fields[]`
   `describedbyText` and `errormessageText` with `ariaInvalid`. The probe only collects elements
   whose text matches `error|fout|invalid|ongeldig|required|verplicht|must|moet|incorrect`, so a
   bare suggestion ("Use DD-MM-YYYY") never shows up there; it keeps at most 30 entries and cuts
   each `text` at 160 characters, so read the full wording with `get text "<css>"` on the message
   element before judging it, and read the snapshot for the messages the regex missed. `forField` is
   filled only when the message id is referenced by `aria-describedby` or `aria-errormessage`; a
   message that merely sits next to the field comes back `null` there and still counts as provided.
   (b) The accessibility tree: `snapshot -i` lists `alert`, `status` and `alertdialog` nodes with
   their text and name. (c) The native bubble: in neither the DOM nor the tree. `message` is the
   text the browser holds, in its own locale, and it reaches the user only when `nativeValidation`
   is true, the submit was not cancelled by script and the field is the one the browser reported.
   `patternMismatch` with `title` null gives only "Please match the requested format."; with a
   `title` the browser prints that `title` with it; `customError` is the page's own text, set by
   `setCustomValidity`. (d) A script `alert()`: `dialog status` right after the submit shows the
   text, then `dialog accept`; that is the
   [SCR18](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR18) shape, advisory for
   this criterion. Quote its text before accepting the dialog and check what is left on the page
   afterwards, because the technique itself notes that "A more helpful notification to the user
   would be to highlight the controls with problems and add information to the page about the nature
   of the errors and how to navigate to the controls that require data fixes." Done when every
   rejected field has its message text and channel, or "no text at all" (3.3.1).

5. Judge each message against its situation. Situation A
   ([G85](https://www.w3.org/WAI/WCAG22/Techniques/general/G85)): the text has to do one of three
   things — "Provide examples of the correct data entry for the field", "Describe the correct data
   entry for the field", or "Show values of the correct data entry that are similar to the user's
   data entry, with instructions to the user as to how to enter one of these correct values should
   the user choose to do so." Situation B
   ([G84](https://www.w3.org/WAI/WCAG22/Techniques/general/G84)): "It should include the list of
   values if possible, or suggest the allowed value that is most similar to the entered value"; the
   Understanding's two answers for a month field that received "12" are "Choose one of: January,
   February, March, April, May, June, July, August, September, October, November, December." and "Do
   you mean 'December'?", and either one alone is enough. Suggested correction text
   ([G177](https://www.w3.org/WAI/WCAG22/Techniques/general/G177)) is checked on two counts, both
   required by the technique's own test: the suggestion is presented ("Error detected. Did you mean:
   6 days, 6 weeks, 6 months or 6 years?"), and "the suggestions are provided next to the form field
   or a link to the suggestions is provided close to the form field". An omission is answered by
   naming what is missing ("Enter your email address", or "This field is required" beside a labelled
   field). The Understanding's first example is the whole shape in one line: the failed submission
   "describes an input error in place in the page along with the correct input and offers additional
   help for the form field that caused the input error".

   A message that only states rejection ("Invalid", "Error", "Check this field", "Please match the
   requested format.") passes when the correct entry stands visible in the error state, beside the
   field or in a summary that names it (label, instruction, `describedbyText`, `errormessageText`):
   confirm with `is visible "<css>"`; a hint that lived only in the placeholder is gone under the
   typed value. Run `is visible` on the message element too: a correction in visually hidden text
   reaches screen reader users alone, so queue it rather than failing it. An `alertdialog`
   ([ARIA18](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA18)) carries one extra check here:
   3.3.1 needs its contents to identify the input error, and for this criterion the technique adds
   "Determine whether contents of the alertdialog suggests how to fix the error" — "For Success
   Criterion 3.3.3, check #7 is also true." A dialog that names the field and says only "Error"
   fails here while passing 3.3.1. A summary above the form that lists the fields in error and links
   to each one is [G139](https://www.w3.org/WAI/WCAG22/Techniques/general/G139), advisory: it helps
   the user reach the field, and it carries the suggestion only when the summary text itself states
   the correct entry. Every vague message then goes through the Exceptions above: pass it with the
   reason where a suggestion would jeopardise security or purpose, queue it where that is arguable
   (a booking reference, a customer number whose format is public). Done when every message is pass,
   fail with certainty, queued or exempt.

6. Apply each suggestion and resubmit. A suggestion is a suggestion for correction only when the
   value it names is accepted:

   ```bash
   agent-browser fill "#date" "31-12-2024"
   agent-browser find role button click --name "Send"
   agent-browser wait --load networkidle
   agent-browser get url
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   Enter exactly what the message proposed — the example, the described entry, the offered value —
   submit, then read `visibleErrors[]` and `snapshot -i` again: either that field's message is gone
   and the form moved on, or the same field is rejected a second time. Success feedback in words
   ("Registration was successfully submitted", "The message was successfully sent") is
   [G199](https://www.w3.org/WAI/WCAG22/Techniques/general/G199), advisory here: where the form has
   it, it settles the question without reading the next page; where it is absent, the changed `get
url` and the disappearance of that field's message are the evidence, which is what
   [SCR32](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR32) also tests for ("Enter
   a valid value in the field(s) associated with the displayed error message and verify that the
   error message is removed"). A message whose own proposal is rejected again is a failure of this
   criterion, not a near miss. Where the submit has real-world effects (order, payment, account,
   mail to a real address) take the values from `index.md`, or stop before the final submit and
   record `cannot-tell` for that form. Done when every suggestion has been applied and accepted, or
   recorded as rejected again, or as not submittable.

7. States. Repeat steps 2 to 6 in each step of a multi-step form, each dialog with fields and each
   variant a choice reveals:

   ```bash
   agent-browser click "#customer-type-business"
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser frame "iframe[title='Payment']"
   agent-browser frame main
   ```

   Fields in a third-party iframe: `frame "<css>"`, repeat the steps, `frame main`; a frame that
   cannot be entered is `cannot-tell`, named in the findings file. A form delivered as a tagged PDF
   is judged on [PDF22](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF22) instead — the viewer's
   own alert dialog has to describe the error in text — and agent-browser can neither fill nor
   validate it: record `cannot-tell` for that document, name it in the findings file and send it to
   the human queue. Done when every state with fields is probed or listed as not reached.

8. Evidence for every fail: the error state with the field and its message drawn:

   ```bash
   agent-browser highlight "#postcode, #postcode-error"
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.3-postcode.png
   agent-browser record start .notes/audit/evidence/<sample>-3.3.3-toast.webm
   agent-browser record stop
   ```

   Quote `message` from step 4 where the bubble cannot appear in the screenshot, and record before a
   submit whose message disappears on its own. Record per fail the field label, the entered value,
   the message text, its channel, the situation label, and what beside the field states the correct
   entry. Done when every fail has a screenshot path and that record.

## Deciding

- Fail (certainty ≥ 90): a `pattern` field whose only message is the browser's "Please match the
  requested format." — no `title`, no page text and nothing beside the field stating the format
  (95); a message that proposes a value which the form rejects again on resubmit in step 6 (90); a
  one-word or symbol message ("Invalid", "Error", "!") while the format or allowed set is known and
  appears nowhere in the error state (90); a Situation B field rejecting the value with no list of
  allowed values, no nearest match and no list anywhere on the page (90).
- Fail (70–89): "Enter a valid X" or "Incorrect X" for a format that is not self-evident (date,
  postcode, phone, reference number, IBAN, password policy) with the format shown nowhere in the
  error state (85); the same with the format in a placeholder now hidden by the typed value (75); a
  custom validator under `novalidate` replacing a helpful browser bubble with a generic message
  while nothing beside the field states the format (85); an `alertdialog` whose contents identify
  the error but do not say how to fix it while the correct entry is known, ARIA18 check #7 (85); a
  field in both situations (or required and format-constrained) whose omission message is helpful
  while its format message stays generic (80); a summary listing the fields in error with no
  correction, no inline message and nothing beside the fields stating the correct entry (80); the
  correction present only in a summary that names no field, on a form with several constrained
  fields (75).
- Needs confirmation (50–69): a code-like field (voucher, booking reference, customer number) with
  a vague message: ask whether stating the format would jeopardise the field's purpose (60); a
  correction carried only by visually hidden text (`is visible` false) while the visible message
  stays generic: ask whether it is owed visibly too, the criterion does not say so in words (60); a
  correction that exists but sits far from its field with no link near the field (G177 check #4):
  ask whether users find it (65); a "Did you mean" seen for one input that may not fire for others:
  ask what the matcher covers (60); a message that vanished unrecorded, or an `alert()` dismissed
  before its text was quoted: ask for its text (55); a self-evident format (email, URL) refused with
  "Enter a valid X" and no example: ask whether an example is owed (60).
- Pass: every automatically detected input error, in every walked state and for every failure mode
  of the field, gives the user — in visible text, in a user-agent bubble, in an alert or alert
  dialog, or beside the field — an example of the correct entry, a description of it, the allowed
  values, the nearest match, or what is missing; and the value it proposes is accepted on resubmit
  (step 6); or the exception applies.
- Not present: no field in any state is validated; every entry, even an empty one, is accepted.
- False positives to avoid: "This field is required" beside a labelled field; "Do you mean
  'December'?" without the list, and the list without a nearest match — the Understanding accepts
  either alone; the browser's own bubbles ("Please include an '@' in the email address"), provided
  by the user agent, and a bubble whose helpful wording comes from `title`; a suggestion beside the
  field or in a summary rather than inside the message; a missing link from the summary to the field
  (G139 is advisory), a missing success message (G199 is advisory) and an `alert()`-only validator
  (SCR18 is advisory here) — record these as remarks, never as fails; a login, code, CAPTCHA or quiz
  that stays vague; a rejection whose acceptable value the page cannot know; a red border with no
  text at all (3.3.1); data lost on re-display (3.3.7); the message's association or announcement
  (1.3.1, 4.1.3).

## Reporting

- File under: 3.3.3 when the error is identified but nothing in the error state says how to correct
  it. A rejection with no text at all goes to 3.3.1 naming this criterion; a format never stated
  before the error is a 3.3.2 issue of its own; a message not tied to its field is 1.3.1, one not
  announced 4.1.3. One issue per form or per message pattern (every "Invalid" of one validation
  library), listing the fields with label, entered value and message.
- Title patterns: "Error messages do not say how to correct the input", "Date field rejects the
  value without giving the expected format", "Month field rejects the value without listing the
  allowed months"
- Severity: High when the form cannot be completed without guessing because the format or rule
  appears nowhere on the page (reference number, password policy, a strict date shape), or the
  message proposes a value the form rejects again; Medium when the format is shown elsewhere on the
  page but the message stays generic, or the defect sits in a site-wide component; Low when one
  optional or self-evident field (email, URL) is generic.
- Type: Technical when a `title`, a validator message, a value list or a "did you mean" mechanism
  must be added or wired; Content when the message is editorial copy and only its wording changes.
- Evidence: the error state with `highlight` on the field and its message; the bubble text quoted
  where the screenshot cannot show it; a GIF when the message appears and disappears on its own, or
  when the suggested value is entered and rejected a second time.
- Recommendation: make each message name the expected format with an example, describe the correct
  entry, or list or offer the allowed values
  ([G85](https://www.w3.org/WAI/WCAG22/Techniques/general/G85) for a format,
  [G84](https://www.w3.org/WAI/WCAG22/Techniques/general/G84) for a limited set,
  [G177](https://www.w3.org/WAI/WCAG22/Techniques/general/G177) for the suggested text, placed next
  to the field or linked from close to it); give every `pattern` a `title`; add the text through
  script ([SCR32](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR32)) or in an alert
  dialog whose contents also say how to fix the error
  ([ARIA18](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA18),
  [SCR18](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR18)); link the summary to
  the field ([G139](https://www.w3.org/WAI/WCAG22/Techniques/general/G139)) and confirm the
  corrected submission in words
  ([G199](https://www.w3.org/WAI/WCAG22/Techniques/general/G199)); in a tagged PDF form use
  [PDF22](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF22). Situation A example:
  `<input id="pc" pattern="\d{4} ?[A-Za-z]{2}" title="Four digits and two letters, e.g. 1234 AB">`
  with the message "Enter the postcode as four digits and two letters, for example 1234 AB".
  Situation B example: `<input id="month" aria-invalid="true" aria-errormessage="month-err">` with
  `<p id="month-err">Enter a month name. Choose one of: January, February, March ... December. Do
you mean "December"?</p>`.
- Related: 3.3.1 Error Identification (no text identifies the error); 3.3.2 Labels or Instructions
  (format not stated up front); 4.1.3 Status Messages (not announced); 1.3.1 (not associated with
  the field); 1.4.1 (colour only); 2.4.3 (focus after an error); 3.3.7 (data lost on re-display).
