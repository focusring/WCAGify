# 2.5.1 Pointer Gestures

Level A · WCAG 2.1+ · Guideline 2.5 Input Modalities · Group: `pointer`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#pointer-gestures) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#pointer-gestures) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-5-1-pointer-gestures/) ·
ACT: none mapped to this criterion.

## Requirement

> All functionality that uses multipoint or path-based gestures for operation can be operated with
> a single pointer without a path-based gesture, unless a multipoint or path-based gesture is
> essential.
>
> Note:
> This requirement applies to web content that interprets pointer actions (i.e., this does not
> apply to actions that are required to operate the user agent or assistive technology).

Terms (WCAG 2.2 glossary), each quoted because it decides an outcome here.

**functionality**: "processes and outcomes achievable through user action". The unit under test is
the outcome — next slide shown, map zoomed in, Delete revealed on a list item, last action undone,
value set, list refreshed — never the widget that produces it. One finding per function, so a
carousel that swipes forward and backward is two functions and both need a route.

**single pointer**: "an input modality that only targets a single point on the page/screen at a
time – such as a mouse, single finger on a touch screen, or stylus." Note: "Single pointer
interactions include clicks, double clicks, taps, dragging motions, and single-finger swipe
gestures. In contrast, multipoint interactions involve the use of two or more pointers at the same
time, such as two-finger interactions on a touchscreen, or the simultaneous use of a mouse and
stylus." The Note is the only definition of _multipoint_ the criterion has: two or more pointers at
the same time. It also settles that a single-finger swipe is a single pointer interaction and still
fails, because the criterion bars path-based gestures separately from multipoint ones.

**essential**: "if removed, would fundamentally change the information or functionality of the
content, **and** information and functionality cannot be achieved in another way that would
conform". Both halves must hold. The second almost never does for a carousel, a map or a
swipe-to-reveal row, which is why the exception is reserved for the cases named below.

**dragging movement** (Key Terms of this Understanding page, the term that draws the line with
2.5.7): "an operation where the pointer engages with an element on the down-event and the element
(or a representation of its position) follows the pointer until an up-event". A component that
tracks the pointer wherever it goes is a drag, not a path; step 2 separates them by bending the
route off the straight line.

The Intent supplies the two terms the spec text uses but the glossary does not define.

**path-based gesture**: "an interaction where the movement of the pointer along a specific path
matters. Examples of a path-based gesture include swiping/'flicking' (which is only recognized when
the user moves in a mostly straight line from the start-point to the end-point), having to move a
pointer strictly along a specific path, and other gestures which trace a prescribed path such as
drawing a specific shape." The start and end points are not the test: "For many gestures, the exact
start- and end-points themselves are not relevant – what matters is that the overall gesture
(mostly) follows a particular path", and a flick counts "as long as the 'flick' gesture is
horizontal, is of sufficient length, and is performed above a specific speed". Speed and straight
line are therefore part of what step 2 must reproduce.

**multipoint gesture**, by example: "a two-finger pinch/spread zoom, a split tap where one finger
rests on the screen and a second finger taps, or a two- or three-finger tap or swipe." A split tap
and a three-finger tap trace no path at all and still fail without a single-pointer route.

## In plain terms

W3C's own summary is the whole test: "Let users operate touchscreens with one finger and reduced
gestures" by providing "single-point operation for all functions". Whatever the page lets a user do
by swiping, flicking, pinching, spreading, rotating with two fingers, tracing a shape or moving
along a prescribed path, it also lets them do with one tap or click on a control: a Next button
beside a swipe carousel, plus and minus buttons on a pinch-zoom map, an Undo button instead of a
drawn "Z". W3C names the acceptable replacements exactly: "a tap, click, double tap, double click,
long press, or click & hold". It serves people who "use a specialized or adapted input device such
as a head pointer, eye-gaze system, or speech-controlled mouse emulator", people whose pointing
method "lack[s] the capability or accuracy to perform multipoint or path-based gestures", and
people with cognitive or learning disabilities who "may not understand the custom gesture
interaction intended by the author". A keyboard route alone does not satisfy it.

## Applies when

- Present: a component that interprets pointer movement along a path, or more than one pointer at
  once: swipe or flick carousels, swipe-to-reveal list items, pull-to-refresh, maps and image
  viewers with pinch zoom or two-finger rotate, drawing and signature pads, gesture commands (draw
  a shape to undo, a two- or three-finger tap), custom sliders that lose the thumb off the track.
  Step 1 lists the candidates, step 2 confirms each by performing the gesture. Every recorded state
  counts: a carousel behind a tab, a map in a dialog, a list in a filtered view, a signature pad
  that only the last step of a form reaches, the error state of that form.
- Not present: no step 1 candidate in any state, or every candidate ignores both the mouse route
  and the dispatched touch gesture of step 2 and no on-page text tells the user to gesture.
- Exception, "unless a multipoint or path-based gesture is essential": "An exception is made for
  functionality that is inherently and necessarily based on complex paths or multipoint gestures.
  For example, entering your signature may be inherently path-based (although acknowledging
  something or confirming your identity need not be)." The parenthesis is the working test: when
  the outcome is _acknowledgement_ or _identity_, a typed name or a checkbox reaches it and the
  exception fails its second half. When the drawn path is itself the outcome (a sketch, a
  whiteboard, a handwriting exercise) it holds.
- Out of scope, the normative Note: gestures "defined by the operating system, user agent, or
  assistive technology". W3C's own examples: "swiping down from the top of the screen to see system
  notifications", "horizontal flicking motions implemented by browsers for navigating back or
  forward within the page history, or vertical flicking gestures to 'fling' page content (or
  content inside natively scrollable containers) to scroll it", and "gestures used to operate a
  screen reader on a touchscreen device, such as swiping left or right to move the screen reader's
  cursor to the previous or next element".
- Out of scope, dragging: "This success criterion does not apply to gestures that involve dragging
  in any direction, not restricted or limited to a specific path." Those are 2.5.7, and the
  boundary is decided by the bend test of step 2, not by how the component looks.
- Sliders, in W3C's words: "the vast majority of sliders (either provided natively by user agents,
  or implemented by the content using scripting) use 'pointer capture' – once the user has
  'grabbed' a slider thumb, they can 'drift' from the horizontal or vertical track of the slider
  while changing the value", so "operating a slider is only considered a dragging movement, rather
  than a path-based gesture". Only "the rare instances where a slider has been implemented in a way
  where straying from the track 'loses' the user's grip on the slider thumb" are in scope here, and
  then "the slider may fail the requirements of both this criterion and Success Criterion 2.5.7".
- Draggable carousels, same rule: "these only count as requiring a path-based gesture if they
  expect the user to perform a precise movement along a path in order to move the content."
- The alternative may not itself be a drag: "New in WCAG 2.2: Note that the single pointer
  non-path-based alternative can't exclusively rely on a dragging movement, as this would fail the
  requirements of 2.5.7 Dragging Movements." A drag-only route (a scrubber, a draggable thumb) is
  not a path-based gesture, so it does not fail _this_ criterion on its own; record it as a 2.5.7
  finding in the same pass rather than closing the component as a clean pass.
- A keyboard route is not the alternative: "keyboard operability is not sufficient to conform to
  this success criterion. That is because some users rely entirely on pointing devices". F105 says
  the same: keyboard support "may serve to meet Success Criterion 2.1.1 Keyboard", while "The point
  of Success Criterion 2.5.1, however, is to ensure that pointer users who on many devices will
  have no keyboard available, have alternative ways of operating the function via simple pointer
  input."

## axe-core

No axe-core rule is tagged with this criterion, and no probe has a gesture field, so everything
below is manual and the inventory of step 1 is the only detection. Two probes are read for the
_alternative_ controls, never for detection: `focusables.js` `order` (`name`, `role`, `box`,
`visible`, `obscured`, `obscuredBy`) names Next, Previous, Zoom in, Zoom out, Undo and Clear
controls that already exist, which shortens step 3; `targets.js` `targets` (`w`, `h`, `passes24`)
sizes a control once it is found, for the 2.5.8 split in "Reporting". `structure.js` `iframes`
(`selector`, `src`, `title`) lists the frames each step must be repeated inside.

## Manual procedure

Work at phone size, then repeat at desktop size:

```bash
agent-browser set device "iPhone 16"
agent-browser set viewport 390 844
agent-browser reload; agent-browser wait --load networkidle
```

Verified facts about that setup in 0.37, each of which changes what the steps can conclude:

- `set device` accepts only `iPhone 15`, `iPhone 16`, `iPhone 16 Pro`, `iPhone 17`, `iPad`,
  `iPad Pro`, `Pixel 9` and `Galaxy S25`; other names error out with the supported list.
- `set device` alone leaves a page that has no viewport meta laid out at 980 CSS px, so the
  `set viewport 390 844` line is what actually produces phone width; it keeps the phone user agent
  and resets the device pixel ratio to 1.
- `set device` sets the user agent and the viewport only. It does not emulate touch:
  `navigator.maxTouchPoints` stays 0 and `'ontouchstart' in window` is false, so a component that
  listens for `touchstart` alone never responds to `hover`, `click` or the `mouse` commands.
- The `Touch` and `TouchEvent` constructors are present all the same, which is what makes the
  dispatch in step 2 possible.
- `mouse move` / `mouse down` / `mouse up` deliver **trusted** `pointerdown`, `pointermove`,
  `pointerup` and `mousedown` events, so the mouse route genuinely exercises a Pointer-Event or
  Mouse-Event implementation (Swiper, Hammer, Leaflet). The button stays down across separate CLI
  invocations, so a drag may be written as four commands.
- The dispatched `TouchEvent`s of step 2 are untrusted: they reach author listeners but never drive
  user-agent behaviour. Verified on a native `overflow-x: auto` strip, whose `scrollLeft` stayed 0.
  A change after a dispatched gesture therefore always means author script ran.
- `set viewport 1280 900` restores desktop width but keeps the phone user agent, and so does a new
  tab. For the desktop pass on a site that sniffs the user agent, run `agent-browser close` and
  `agent-browser open <url>` first; that restores the desktop user agent.

Run every step in the default state, in each recorded state, and inside each `structure.js`
`iframes` entry (`frame "<css>"`, then `frame main`). `snapshot -i` shows controls and names and
never shows a gesture handler: only a performed gesture followed by a change shows a gesture
function. Record `cannot-tell` for a component the emulation cannot gesture on that has no step 3
control.

1. Inventory the candidates. F105's own advice is the method: "you can find path-based gestures by
   exploring the content on a touchscreen, or checking the page code for the existence of specific
   event handlers such as touchstart or touchend."

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const q = (s) => [...document.querySelectorAll(s)];
     const sel = (e) => e.localName + (e.id ? '#' + e.id : '') + [...e.classList].slice(0, 2)
       .map((c) => '.' + c).join('');
     const vis = (e) => { const r = e.getBoundingClientRect(); return r.width > 0 && r.height > 0 };
     const lib = new RegExp('swiper|slick|flickity|glide|splide|embla|hammer|leaflet|mapbox|' +
       'openlayers|maps\\.google|signature|fabric|konva|panzoom|photoswipe|hammerjs', 'i');
     const touchAction = q('body *').filter((e) => vis(e) && !/^(auto|manipulation)$/.test(
       getComputedStyle(e).touchAction));
     return {
       touchAction: touchAction.map(sel).slice(0, 40),
       touchActionCount: touchAction.length,
       libraries: [...document.scripts].map((s) => s.src).filter((s) => lib.test(s)),
       widgets: q('[class*="swiper" i],[class*="carousel" i],[class*="slider" i],' +
         '[class*="slick" i],[class*="signature" i],[class*="draw" i],[class*="swipe" i],' +
         '[class*="gallery" i],[class*="pinch" i],[class*="zoom" i],' +
         '[ontouchstart],[ontouchmove],[onpointermove],[ongesturestart],canvas,' +
         'input[type="range"],[role="slider"],.leaflet-container,.mapboxgl-map,.ol-viewport,' +
         '.gm-style,.pswp').filter(vis).map(sel),
       gestureText: (document.body.innerText.match(new RegExp(
         '.{0,30}\\b(swipe|flick|pinch|spread|two fingers?|rotate|draw|trace|' +
         'pull to refresh)\\b.{0,30}', 'gi')) || []).slice(0, 10)
     };
   })()
   EOF
   ```

   Handlers added with `addEventListener` stay invisible in the DOM, so every signal counts: a
   `touchAction` entry (anything other than `auto` or `manipulation` means the author took the
   gesture over), a `libraries` hit, a `widgets` match or a `gestureText` phrase makes the element
   a candidate. `touchActionCount` above 40 means the first list is truncated and the widgets list
   carries the rest. The candidate is the component, not its parts: the `.swiper` container, not a
   slide; the `.leaflet-container`, not a tile. Cross-read `focusables.js` `order` for `name`
   values like "Next", "Previous", "Zoom in", "Undo": a component that already has them is likely a
   pass and step 3 only has to confirm it. Done when every candidate is in the findings file with
   the signal that flagged it.

2. Perform the gesture and name the function. Run the mouse route first, because it delivers
   trusted pointer events and catches every Pointer-Event implementation:

   ```bash
   agent-browser screenshot "<component>" .notes/audit/evidence/<sample>-2.5.1-<slug>-before.png
   agent-browser get box "<component>"
   agent-browser mouse move <x + 0.8 * w> <y + 0.5 * h>; agent-browser mouse down
   agent-browser mouse move <x + 0.6 * w> <y + 0.5 * h>
   agent-browser mouse move <x + 0.2 * w> <y + 0.5 * h>
   agent-browser mouse up; agent-browser wait 800
   ```

   If nothing changed, dispatch the touch gesture. Substitute the component selector and set the
   four knobs at the top: a left swipe is `dx = -160, dy = 0`; an up swipe is `dx = 0, dy = -160`;
   a stroke is `dx = 80, dy = 60`; `pinch = true` with `span = (i) => 20 + 15 * i` spreads two
   fingers apart, and `span = (i) => 140 - 15 * i` pinches them together.

   ```bash
   agent-browser eval --stdin <<'EOF'
   (async () => {
     const el = document.querySelector('<component>');
     const pinch = false, dx = -160, dy = 0, steps = 8, span = (i) => 20 + 15 * i;
     const r0 = el.getBoundingClientRect();
     const cx = r0.left + r0.width / 2, cy = r0.top + r0.height / 2;
     const sig = () => { const s = getComputedStyle(el), b = el.getBoundingClientRect();
       return [location.href, document.body.innerText.replace(/\s+/g, ' ').slice(0, 4000),
         el.outerHTML.length, s.transform, s.backgroundPosition, Math.round(b.x), Math.round(b.y),
         el.scrollLeft, el.scrollTop, scrollX, scrollY].join('|') };
     const hash = (s) => { let h = 0; for (let i = 0; i < s.length; i++)
       h = (h * 31 + s.charCodeAt(i)) | 0; return h };
     const before = sig();
     const at = (i, id) => pinch ? [cx + (id === 1 ? -1 : 1) * span(i), cy]
       : [cx - dx / 2 + dx * i / steps, cy - dy / 2 + dy * i / steps];
     const T = (id, i) => { const [x, y] = at(i, id); return new Touch({ identifier: id, target: el,
       clientX: x, clientY: y, pageX: x + scrollX, pageY: y + scrollY }) };
     const fire = (type, i) => { const ts = (pinch ? [1, 2] : [1]).map((id) => T(id, i));
       const live = type === 'touchend' ? [] : ts;
       el.dispatchEvent(new TouchEvent(type, { touches: live, targetTouches: live,
         changedTouches: ts, bubbles: true, cancelable: true })) };
     const sleep = (ms) => new Promise((f) => setTimeout(f, ms));
     fire('touchstart', 0);
     for (let i = 1; i <= steps; i++) { await sleep(16); fire('touchmove', i); }
     await sleep(16); fire('touchend', steps); await sleep(800);
     const after = sig();
     return { changed: before !== after, before: hash(before), after: hash(after) };
   })()
   EOF
   ```

   `changed` is the verdict, not the component's own HTML. A gesture's outcome very often lands
   outside the component or leaves its markup byte-identical, and both cases were verified: a
   carousel whose slide text went from "1" to "2" kept the same `innerHTML.length`, and a pinch-zoom
   map reported `innerHTML.length` 0 before and after while the page's zoom readout went from 1 to 7.
   That is why `sig()` also reads the page's own text,
   the computed `transform` and
   `backgroundPosition`, the component's position, and the element and window scroll offsets. On an
   element with no handler at all it returns `changed: false`, so a false positive costs nothing.

   Then look at the outcome: `screenshot "<component>" ...-after.png`, `get url`,
   `snapshot -i -s "<component>"`, and for a slider `get attr "<slider>" aria-valuenow` (selector
   first, attribute second; the reverse order errors with "Element not found"). Name the function
   from the difference: next slide, zoom in, Delete and Archive revealed, stroke drawn, list
   refreshed, last edit undone.

   Now decide path or drag. Repeat the mouse route slowly with the same start and end point but
   arcing 60 px off the straight line. Content that keeps tracking the pointer through the arc, or
   an outcome that survives it, is a dragging movement: strike it here and record it for 2.5.7. An
   outcome that needs the straight, fast route is path-based. A pinch, spread, two-finger rotate,
   split tap or three-finger tap is multipoint whatever its path, and is in scope on that ground
   alone. No change from either route: strike the candidate, unless `gestureText` or a library hit
   says otherwise, in which case carry it to step 3 and record `cannot-tell` if nothing is found.
   Done when every candidate is named path-based, multipoint, dragging, struck or `cannot-tell`.

3. Find the single-pointer route ([G215](https://www.w3.org/WAI/WCAG22/Techniques/general/G215),
   whose test is "Check that single pointer operable controls exist over or adjacent to the content
   slider that advance to adjacent chunks of content"; the
   [F105](https://www.w3.org/WAI/WCAG22/Techniques/failures/F105) test is the same check — "Check
   that controls are available through which the same function can be carried out via simple taps
   or clicks" — with "If check #1 is false then the content fails the Success Criterion").

   `reload`, `wait --load networkidle`, `snapshot -i -s "<component's parent>"` — scoping to the
   parent, not the component, because arrows and dots are usually siblings. `(no interactive
elements)` in that output is already most of a fail. Candidates to look for: Next, Previous,
   dots or tabs, Zoom in, Zoom out, Reset, Undo, Clear, Refresh, a More actions button on a list
   row, a Type tab on a signature pad. W3C accepts any of "a tap, click, double tap, double click,
   long press, or click & hold", so also try `dblclick "<component>"` for double-tap zoom and a
   long press (`mouse move` to its centre, `mouse down`, `wait 800`, `mouse up`).

   Hit-test every candidate before believing it. `click` prints `✓ Done` even when the element was
   never operated — verified on a `display: none` button and on one parked at `left: -9999px`,
   neither of which ran its handler — and `is visible` reports `false` for an `opacity: 0` button
   whose click does fire, so neither output may decide this step:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const sels = ['<control 1>', '<control 2>'];
     return sels.map((s) => {
       const e = document.querySelector(s);
       if (!e) return { s, found: false };
       const r = e.getBoundingClientRect(), st = getComputedStyle(e);
       const hit = document.elementFromPoint(r.left + r.width / 2, r.top + r.height / 2);
       const hitsSelf = !!hit && (hit === e || e.contains(hit));
       const offscreen = r.right <= 0 || r.bottom <= 0 ||
         r.left >= innerWidth || r.top >= innerHeight;
       return { s, found: true, w: Math.round(r.width), h: Math.round(r.height),
         display: st.display, visibility: st.visibility, pointerEvents: st.pointerEvents,
         offscreen, clipped: st.clip !== 'auto' || st.clipPath !== 'none', hitsSelf,
         hitTag: hit ? hit.localName : null,
         usable: r.width > 0 && r.height > 0 && st.display !== 'none' &&
           st.visibility !== 'hidden' && st.pointerEvents !== 'none' && !offscreen && hitsSelf,
         name: (e.getAttribute('aria-label') || e.textContent || '').trim().slice(0, 40) };
     });
   })()
   EOF
   ```

   `usable: true` means a pointer can reach it. The six cases were checked against whether a real
   `click` dispatched the handler and the probe agreed with every one: a button whose hit target is
   its own inner icon span → usable; `opacity: 0` → usable; `clip-path: inset(50%)` → not usable;
   `display: none` → not usable; off-screen → not usable; `pointer-events: none` → not usable.
   `clipped: true` on its own never disqualifies a control, because the Understanding accepts
   carousel buttons that are "visible (for instance, as large arrow icons) or visually hidden (but
   still operable with a pointer)" — only the hit test decides.

   Then confirm the control reaches the outcome: `click "<control>"`, `wait 800`, and compare
   against the step 2 `after` hash by re-running the `sig()`/`hash()` pair on its own. Cover the
   whole function, not a piece of it: Previous as well as Next, Zoom out as well as Zoom in, every
   option the swipe revealed. F105's swipe-to-reveal example fails precisely on a partial route —
   "One or more of these options are not available after the item is first opened with a single tap
   or click." G215 wants the controls "over or adjacent to" the component; a route that lives far
   away or on another page goes to the confirmation queue instead of counting as a pass. A route
   that is itself a swipe or flick does not count, and a route that is only a drag is recorded for
   2.5.7 as described under "Applies when".

   Finally repeat at desktop width: `set viewport 1280 900` (or `close` then `open <url>` for a
   user-agent-sniffing site), `reload`, and re-run step 2's mouse route and this step. A control
   present in one layout only is recorded against the layout that lacks it. Done when every gesture
   function has "tap route: <control>" or "none", per layout.

4. Custom sliders ([G216](https://www.w3.org/WAI/WCAG22/Techniques/general/G216), test: "Check that
   the value of the control slider (range) can be set with a tap or click using a pointer").

   A native `input[type="range"]` passes: verified that a click on its track sets the value
   (50 → 90) and that the thumb keeps following the pointer 80 px off the track (19 → 11), which is
   pointer capture — a dragging movement, not a path. Leave it alone unless step 1 listed a pointer
   handler or `touch-action: none` on it.

   For each `[role="slider"]` or custom track, first decide whether it is path-based at all:

   ```bash
   agent-browser get box "<thumb>"
   agent-browser mouse move <thumb cx> <thumb cy>; agent-browser mouse down
   agent-browser mouse move <thumb cx + 40> <thumb cy>
   agent-browser get attr "<slider>" aria-valuenow
   agent-browser mouse move <thumb cx + 80> <thumb cy + 80>
   agent-browser get attr "<slider>" aria-valuenow
   agent-browser mouse up
   ```

   A value that keeps changing at the second reading is pointer capture: hand the slider to 2.5.7
   and take it out of this criterion. A value that stops at the first reading has lost its grip off
   the track — this is W3C's "rare instance", in scope here and in 2.5.7 both. Worked example on a
   slider that loses grip: `aria-valuenow` went 0 → 18 while the pointer stayed on the track and
   stayed 18 once it moved 80 px below it.

   For a path-based slider, look for the G216 routes: "A simple fallback for activation without a
   path-based gesture is to make the control slider track clickable", and "Providing controls
   (e.g., arrow buttons) as alternative also allows incrementing or decrementing the value with
   taps or clicks." Tap the track at a quarter and at three quarters of its width (`mouse move
<x> <y>`, `mouse down`, `mouse up`), reading `get attr "<slider>" aria-valuenow` after each; a
   value that jumps to the tapped point is the route, and so are plus/minus or arrow steppers in
   `snapshot -i` that pass the step 3 hit test, or a number field beside the slider. On the same
   worked example the track tap left the value at 18, so it has neither route. Done when each
   slider is "dragging (2.5.7)", "path-based, route: <track tap | steppers | field>" or
   "path-based, none".

5. Drawing surfaces and gesture commands. A stroke on a `canvas` that leaves a mark is path-based.
   The exception applies when the drawing itself is the outcome — a sketch, a whiteboard, a
   handwriting exercise — and then record `pass` with the reason.

   A signature pad turns on what the signature is _for_: "entering your signature may be inherently
   path-based (although acknowledging something or confirming your identity need not be)". It
   passes when a typed-name field, a Type tab, an upload or a checkbox reaches the same
   confirmation (`snapshot -i -s "<pad's parent>"`, then the step 3 hit test on whatever is found);
   with nothing of the kind, queue it for the human rather than deciding intent.

   A gesture that runs a command needs a control that runs the same command. F105's Example 1 is
   the canonical fail: "A web application implements an interface where drawing a 'Z' on the screen
   undoes the last action. There is no other way to undo the action." Search for the control by
   name — `find role button click --name "Undo"`, which errors with "No element found:
   getByRole('button', { name: 'Undo' })" when it is absent, and that error is the finding — then
   re-run the step 2 signature to confirm the button reaches the same outcome the gesture did.
   Done when each surface and each gesture command is "exempt (reason)", "route: <control>",
   "queue" or "none".

6. Evidence and reset. For every fail, record the gesture working and the tap doing nothing:

   ```bash
   agent-browser record start .notes/audit/evidence/<sample>-2.5.1-<slug>.webm
   # the step 2 gesture for this component
   agent-browser wait 800
   agent-browser click "<component>"; agent-browser wait 800
   agent-browser record stop
   agent-browser highlight "<component>"
   agent-browser screenshot .notes/audit/evidence/<sample>-2.5.1-<slug>.png
   agent-browser set viewport 1280 900
   ```

   `record` needs ffmpeg on the machine and writes 30 fps `.webm`. For a slider, replace the click
   with a single `mouse move` + `mouse down` + `mouse up` on the track so the recording shows the
   value not moving. For a control that only the desktop layout has, take a second screenshot at
   1280 px with the same `highlight`. Done when every fail has its recording and a screenshot of
   the component with no usable control beside it, and the viewport is desktop again.

## Deciding

- Fail (certainty ≥ 90): a path-based swipe or flick changes the page (step 2 `changed: true`) and
  no control that passes the step 3 hit test reproduces the outcome in that layout
  ([F105](https://www.w3.org/WAI/WCAG22/Techniques/failures/F105)) — 92; an option revealed by a
  swipe on a list row is missing after a tap on the row (F105 Example 1, swipe-to-reveal) — 92; a
  drawn shape or a multi-finger gesture runs a command that no control runs (F105 Example 1, the
  drawn "Z") — 95; a pinch, spread, two-finger rotate, split tap or three-finger tap whose outcome
  no button, select or double tap reproduces — 90; a path-based slider (value frozen once the
  pointer leaves the track) whose track ignores taps and that has no stepper or number field
  ([G216](https://www.w3.org/WAI/WCAG22/Techniques/general/G216)) — 90.
- Fail (70–89): the only candidate control reports `usable: false` (off-screen, covered,
  `display: none`, `pointer-events: none`, clipped away) and no other route exists — 85; controls
  exist at 1280 px and are `display: none` at phone width, where the gesture is the only route —
  85; the control covers part of the function only (Next without Previous, Zoom in without Zoom
  out, two of the three swipe options) — 80; a gesture-capable library is loaded, `gestureText`
  tells the user to swipe or pinch, the emulation changed nothing and `snapshot -i` on the parent
  reports no interactive elements — 75.
- Needs confirmation (50–69): a signature pad with no typed, upload or checkbox alternative — 60:
  ask whether the drawn signature is essential or whether acknowledging/confirming identity is the
  real outcome; a route that exists but far from the component or on another page, against G215's
  "over or adjacent to" — 60: ask whether it counts as operating the same function; a two-finger
  rotate or tilt whose only control resets north — 55: ask whether rotating serves a task; a WebGL
  map, a `canvas` app or a cross-origin frame that neither the mouse route nor the dispatch moved,
  with no control — 55: ask the human to try it on a touch device.
- Pass: every gesture function found in step 2, in every state and every layout, has a tap, click,
  double tap, double click, long press or click & hold route that passes the step 3 hit test and
  reaches the whole outcome; every custom slider is either pointer-capture (2.5.7's business) or
  settable by a track tap, a stepper or a field; every drawing surface is exempt with its reason or
  has its alternative.
- Not present: no component in any state interprets a path-based or multipoint gesture.
- False positives to avoid: drag and drop, map panning, a carousel or slider whose content follows
  the pointer through the 60 px arc (2.5.7, not here); a control that looks hidden but passes the
  hit test — the Understanding explicitly blesses arrows that are "visually hidden (but still
  operable with a pointer)", and an `opacity: 0` button does receive the click; a native
  `overflow` scroller or scroll-snap strip, which the user agent flings and which the dispatched
  touch events provably do not move; the browser's back-swipe and page pinch zoom (a
  `user-scalable=no` that blocks the latter is 1.4.4, not this); screen reader swipes and other
  assistive-technology gestures; a native `input[type="range"]`; a keyboard route, which is neither
  a pass nor a fail here ("evaluated independently" — its absence is 2.1.1); a drawing whose path
  is the outcome; a `touch-action` value that is merely `manipulation`.

## Reporting

- File under: 2.5.1 for every function that a pointer can reach only through a path-based or
  multipoint gesture. Split the rest out: a route that exists but only by dragging is 2.5.7; no
  keyboard route at all is a separate issue under 2.1.1; an unnamed Next or Zoom button is 4.1.2; a
  control smaller than 24 × 24 px is 2.5.8; a shake or tilt gesture is 2.5.4. One issue per
  component — carousel, map, swipe list, signature pad — naming the other samples it repeats on.
- Title patterns: "The <carousel> can only be advanced by swiping", "The map only zooms by
  pinching", "Swipe actions on <items> have no tap alternative", "<Action> requires drawing a
  gesture", "The <slider> can only be set by following its track", "Carousel arrows disappear at
  phone width", "Rotating the <viewer> needs two fingers"
- Severity: High when the gesture is the only route to content or to a step of a task — a slide
  with unique content, Delete or Archive on a list row, zooming a map to read it, signing to submit
  a form. Medium when the same content or outcome is reachable another way on the page, or when the
  control covers only part of the function. Low when a usable control already sits beside the
  component and the gap is a small one, such as a missing Reset.
- Type: Technical when the fix is script and markup — a click handler, arrows unhidden at phone
  width, a clickable track. Design when the component needs controls it was never designed with and
  space has to be found for them.
- Evidence: the phone-width screenshot with `highlight` on the component, framed so the absence of
  a control beside it is visible; the step 6 recording as a GIF, showing the gesture changing the
  content and the tap changing nothing; for a slider, the value before and after the track tap;
  for controls that only the desktop layout has, both widths side by side.
- Recommendation: [G215](https://www.w3.org/WAI/WCAG22/Techniques/general/G215) — add controls
  that a single tap operates for every gesture outcome, placed over or adjacent to the component
  and present at every viewport width: Next and Previous plus dots for a carousel, Zoom in and Zoom
  out for a map, a More actions button on each row for swipe-to-reveal, an Undo button for a
  gesture command. The button carries the whole outcome, so wire it to the same API the gesture
  calls:

  ```html
  <button type="button" class="carousel-next">Next slide</button>
  ```

  ```js
  document.querySelector('.carousel-next').addEventListener('click', () => swiper.slideNext())
  ```

  [G216](https://www.w3.org/WAI/WCAG22/Techniques/general/G216) for a slider that loses its grip
  off the track — make the track itself set the value on click, and add steppers for fine
  adjustment:

  ```js
  track.addEventListener('click', (e) => {
    const r = track.getBoundingClientRect()
    const ratio = Math.min(1, Math.max(0, (e.clientX - r.left) / r.width))
    setValue(Math.round(min + ratio * (max - min)))
  })
  ```

  For a signature pad, a Type tab that accepts the name as text reaches the same acknowledgement
  and leaves the drawn signature as an option rather than the only route.

- Related: 2.5.7 Dragging Movements — the drag side of the same component, and the criterion a
  drag-only alternative fails; a slider that loses its grip off the track fails both. 2.1.1
  Keyboard — F105: keyboard support "may serve to meet Success Criterion 2.1.1 Keyboard" but never
  this one, so file it separately when the component has no keyboard route either. 2.5.2 Pointer
  Cancellation — the control that is added must act on the up-event, which F105 names as its
  related failure. 2.5.8 Target Size (Minimum) and 4.1.2 Name, Role, Value — the added controls
  need size
  and an accessible name. 2.5.4 Motion Actuation — shaking or tilting the device rather than
  gesturing on it.
