# 3.3.7 Redundant Entry

Level A · WCAG 2.2+ · Guideline 3.3 Input Assistance · Group: `forms` (also `consistency`)

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#redundant-entry) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#redundant-entry) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-3-7-redundant-entry/) ·
ACT: none mapped to this criterion

## Requirement

> Information previously entered by or provided to the user that is required to be entered again
> in the same process is either:
>
> - auto-populated, or
> - available for the user to select.
>
> Except when:
>
> - re-entering the information is essential,
> - the information is required to ensure the security of the content, or
> - previously entered information is no longer valid.

Terms (WCAG 2.2 glossary): **processes**: "series of user actions where each action is required in
order to complete an activity", with two glossary examples: "Successful use of a series of web
pages on a shopping site requires users to view alternative products, prices and offers, select
products, submit an order, provide shipping information and provide payment information." and "An
account registration page requires successful completion of a Turing test before the registration
form can be accessed." — a gate such as a Turing test is part of the process, and so are the steps
behind it. **essential**: "if removed, would fundamentally change the information or functionality
of the content, **and** information and functionality cannot be achieved in another way that would
conform" — both halves must hold before the essential exception applies; an author preference for
re-typing is not enough.

## In plain terms

Inside one activity — a checkout, a registration, an application wizard, a form that comes back
with errors — each piece of information is asked once. Where a later step needs something the user
typed earlier, or something the site itself gave them (a customer number, an order reference), the
content fills it in or offers it on that same page: a pre-filled field, a list to pick from, a
"same as" checkbox, visible text to copy. "The autocomplete feature of browsers is not considered
sufficient because it is the content (the website) that needs to provide the stored information for
a redundant entry, or avoid asking for the same information again." It matters most to people with
cognitive or memory disabilities, who give up or re-enter the value wrongly under the fatigue of a
long process, and to switch-control and voice-input users, for whom every entry costs effort.

## Applies when

- Present: the sample is a step of a process — `index.md` describes it as `<process>, step
<n>/<total>:`, `.notes/sample.md` lists it under "Processes", or `recon/<sample>-states.md` has
  wizard steps under one URL — or a state has a form with a submit button (`forms.js` `forms[]`
  with a non-empty `submitButtons`) that is re-displayed with errors or leads to a next step, or
  the sample is a results page for a query typed on it or on another sample.
- Present as well when the site provided the value: a reference, customer, case or quote number, a
  generated username or a total shown on an earlier step and asked for here. The criterion covers
  "information previously entered by or provided to the user", both directions.
- Present across domains: "a process can run across different domains, so if a check-out process
  includes a 3rd party payment provider, that would be in scope." A payment or identity provider
  step is evaluated like the site's own steps.
- Not present: no state is a process step and no state has a form that can be submitted and shown
  again (`forms[]` empty, or the only form posts away from the sample set and is never re-shown).
  Record `not-present` and name the states checked.
- Exceptions (normative; any one of the three is enough, the Understanding gloss is how to
  recognise it):
  - Essential: "Essential uses of input re-entry for things like memory games which would be
    invalidated if the previous answers were supplied." Recalling the value is the task itself.
  - Security: "Security measures such as preventing a password string from being shown or copied.
    When creating a password, it should be a unique and complex string and therefore cannot be
    validated by the author. If the system requires the user to manually create a password that is
    not displayed, having users re-validate their new string is allowed as an exception." Recognise
    it as `type="password"`, the confirm field of a new password, a PIN or password asked before a
    sensitive action.
  - No longer valid: "When the previously entered information is no longer valid, it can be
    requested that the user enter that information again." Recognise it as a value the process
    rejected, a value that expired (a one-time code), or a value a later choice invalidated (the
    country changed, so the old postal code no longer fits).
- Where the alternative has to be: "Data which is 'available to select' would need to be on the
  same page. Ideally, it would be visible by default and closely associated with the input where
  the data is required. However, it could be elsewhere on a page, including within a show/hide
  component." A value that only exists on an earlier step or another page is not an alternative.
- What "available to select" may be (Understanding: "The term 'available to select' is not
  prescriptive"): "select and populate a field, including from a drop-down"; "select text from the
  page and copy it into an input"; "tick a checkbox to populate inputs with the same values as
  previously entered (e.g., my billing address is the same as my shipping address)".
- Outside the criterion, never a fail here: data "provided by the user with a different method,
  such as uploading a resume in a document format"; a return "after closing a session or navigating
  away", since "This success criterion does not add a requirement to store information between
  sessions"; the browser filling a password, since "This success criterion does not impact
  Accessible Authentication (Minimum), for which allowing auto-filling of passwords is a sufficient
  technique" — that belongs to 3.3.8.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. `axe-page.mjs` prints
no 3.3.7 row for any state, so neither a violation nor an `incomplete` can arrive from it, and no
rule tagged with another criterion substitutes: re-entry is a relation between two steps of one
process, which a single-page rule engine never sees. Leaves open: all of it — applicability, the
ledger of earlier steps, the alternatives offered on this step, the error state, the return path
and the three exceptions.

## Manual procedure

Forms mode at `set viewport 1280 900`. In a `process/<name>` unit the steps are walked in order and
the ledger of step 3 grows as you go; a `forms` unit on a single process step takes the ledger from
`process--<slug>.md` when it exists and otherwise walks the earlier steps first. Test data and
credentials come from `.notes/sample.md`; the step after the last one without a real-world effect
is not walked, and a repeated field that sits on it makes the row `cannot-tell` with that step
named. The `consistency` pass merges the process rows of every sample into one outcome per process
in `consistency.md` and adds no step of its own.

The whole procedure runs [G221](https://www.w3.org/WAI/WCAG22/Techniques/general/G221)'s test with
the browser: "For each input in a process that requires information to be entered: Check if the
information has already been requested on a previous step of the process; Check that the
information entered previously is prepopulated in the fields or displayed on the page", expected
result "#1 and #2 are true". Steps 1 to 3 answer the first check, steps 4 to 7 the second. G221's
own examples are the shapes of a pass: a checkbox that triggers the shipping address to be
pre-populated from the billing address, a second step that arrives with the business number, name
and address pre-filled, and a second step that lets the user select the business set up in step 1
with all its information. The Understanding page lists one further sufficient approach with no
technique id — "Not requesting the same information twice" — which shows up as a step that simply
does not ask again; record that as `pass` for the purpose, not as `not-present` for the sample.

1. Place the sample in its process. From `index.md` and `.notes/sample.md` record the process name,
   this step's number and total, and the steps before it with the actions they take; from
   `recon/<sample>-states.md` the in-page steps of a one-URL wizard. A third-party step (payment or
   identity provider) stays inside the process. Done when the findings row names the process and
   the step number, or `not-present` with the states checked.

2. Inventory what this step asks for. Run the `forms.js` probe in every state that has a form (the
   initial state, and each state that a menu, tab or disclosure reveals):

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   Keep per field `selector`, `tag`, `type`, `name`, `visibleLabelText`, `legend`,
   `autocompleteCandidate`, `required`, `disabled`, `visible` and `value`. Give every field a
   purpose: `autocompleteCandidate` for a text entry, otherwise the meaning of the label (e-mail,
   given name, address part, phone, date of birth, customer number, search term). Three probe
   facts decide how to read the output:
   - `autocompleteCandidate` is guessed from the name, id, label and placeholder text, so it also
     fires on controls that ask for nothing: the checkbox labelled "Billing address is the same as
     delivery address" comes back as `street-address`. Ignore it for `tag: "button"` and for
     `type` `checkbox`, `radio`, `submit` and `button`, and read the label there.
   - `value` is whitespace-collapsed and cut to the first 40 characters, so compare a long value (a
     full address) on its first 40 characters only; a difference past that is not evidence.
   - Fields with `visible: false` or `disabled: true` are not asked of the user: list them apart. A
     hidden field carrying the value forward does not answer this criterion — the visible field the
     user has to fill is what counts.

   Then list what the page provides rather than asks: run `agent-browser snapshot` and note every
   number or code the site generated on this or an earlier step (reference, customer number, quote
   id, total). Done when every visible enabled field has a purpose and the provided values are
   listed.

3. Build the ledger of the earlier steps. Open the process start and, for each step before this
   one, fill the fields with the test data, run `forms.js`, record purpose → value entered plus any
   value the page itself provides, screenshot the filled step, then advance with the process's own
   control:

   ```bash
   agent-browser open <process start url>
   agent-browser wait --load networkidle
   agent-browser fill "input[name='email']" "j.jansen@example.nl"
   agent-browser fill "input[name='addr']" "Prinsengracht 263-267, 1016 GV Amsterdam"
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.7-step<n>.png --full
   agent-browser find role button click --name "Next"
   agent-browser wait --load networkidle
   ```

   Use complete, distinctive values that occur nowhere else on the site and that stay at least six
   characters long once spaces and punctuation are stripped, so the search of step 4 finds them and
   only them. Done when the ledger holds one row per purpose: step number, field selector, value
   entered or provided.

4. Search this step for every ledger value, on the page as it arrived, before touching a field.
   Put the ledger values in `needles`; the block is an IIFE, so it can be re-run in the same
   session:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const needles = ['j.jansen@example.nl', 'Prinsengracht 263-267, 1016 GV Amsterdam']
     const norm = (s) => (s || '').toLowerCase().replace(/[\s.,\-()/]/g, '')
     const t = (n) => n.localName + (n.id ? '#' + n.id : '') + (n.name ? `[name="${n.name}"]` : '')
     const vis = (e) => e.getClientRects().length > 0 && getComputedStyle(e).visibility !== 'hidden'
     const nodes = []
     const w = document.createTreeWalker(document.body, NodeFilter.SHOW_TEXT)
     while (w.nextNode()) nodes.push(w.currentNode)
     const out = {}
     for (const needle of needles) {
       const k = norm(needle)
       const hit = (s) => k.length > 5 && norm(s).includes(k)
       out[needle] = {
         inputs: [...document.querySelectorAll('input, textarea, select')]
           .filter((i) => hit(i.value))
           .map((i) => ({ el: t(i), visible: vis(i), exact: norm(i.value) === k })),
         options: [...document.querySelectorAll('option, [role="option"]')]
           .filter((o) => hit(o.textContent))
           .map((o) => ({
             el: t(o.closest('select, [role="listbox"], [role="combobox"]') || o.parentElement),
             label: o.textContent.trim().slice(0, 60)
           })),
         text: nodes
           .filter((n) => n.parentElement && hit(n.nodeValue))
           .filter((n) => !n.parentElement.closest('script, style, option'))
           .map((n) => ({
             el: t(n.parentElement),
             visible: vis(n.parentElement),
             text: n.nodeValue.trim().slice(0, 80)
           }))
       }
     }
     out.frames = [...document.querySelectorAll('iframe')]
       .map((f) => ({ el: t(f), src: f.getAttribute('src') }))
     return out
   })()
   EOF
   ```

   Read the result per needle: an entry in `inputs` with `visible: true` is auto-populated; a
   non-empty `options` is selectable from a control and its `el` names the select, listbox or
   combobox; an entry in `text` with `visible: true` is on the page to select and copy. `exact:
false` means the value sits inside a longer string: read the string and decide whether it is the
   same information (a reformatted phone number is, a different order number that happens to
   contain yours is not). A non-empty `frames` means part of the step renders in an iframe, so
   repeat the block inside each one and come back:

   ```bash
   agent-browser frame "iframe[src*='pay']"
   agent-browser frame main
   ```

   Done when every ledger purpose this step asks for again is marked auto-populated, selectable,
   shown as text, or nowhere.

5. Look for the alternatives that stay hidden until used. For every purpose marked "nowhere", and
   for every hit that came back only with `visible: false`, open the disclosures, accordions,
   "show details" links and dialogs near the field and run the block of step 4 again; a value
   revealed that way is an alternative, because it "could be elsewhere on a page, including within
   a show/hide component". Then read the form's own controls for a "same as", "use previous" or
   "copy from" checkbox or button and operate it:

   ```bash
   agent-browser snapshot -i -s "form#checkout"
   agent-browser find role button click --name "Show my details"
   agent-browser check "#billing-same"
   agent-browser is checked "#billing-same"
   agent-browser wait 800
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   `is checked` printing `true` while the target fields' `value` stays empty is a control that does
   not populate: record it as a defect, not as an alternative. Done when every "nowhere" purpose is
   either found inside a component whose opening control is named, or confirmed absent from the
   page in every state.

6. Error state. Fill every field of this step with valid distinctive values, make one value invalid
   (an e-mail without `@`, a required field left empty), submit with the form's own button, then
   compare what came back:

   ```bash
   agent-browser find role button click --name "Pay"
   agent-browser wait --load networkidle
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   Compare `value` per field (first 40 characters) with what was filled. The W3C example of a pass
   is exactly this case: "A user submits a checkout form with an incorrect credit card number in
   it. The page updates, showing an error message. Submitted information, such as credit card
   number, is not cleared from the form." A `type="password"` field reports `(set)` when it holds
   anything and an empty string when it does not, so an empty password field after re-display is
   the security exception and not a finding. Done when the row reads "error keeps: all" or "error
   clears: <fields>".

7. Test the way back inside the process. From the step after this one, activate the process's own
   Back control, not the browser's:

   ```bash
   agent-browser find role button click --name "Back"
   agent-browser wait --load networkidle
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   Check every `value` against the ledger. `agent-browser back` restores form state through the
   browser's own history and says nothing about the content, so use the page's control and, when
   the process has no Back control of its own, record "no back control" instead of a finding.
   Done when the row reads "back keeps: all", "back clears: <fields>" or "no back control".

8. Classify every "nowhere" and every "clears" row against the exceptions in "Applies when":
   password or PIN (security), a task whose point is recall (essential), a value the process
   rejected, that expired or that a later choice invalidated (no longer valid), a value first
   supplied by upload and a return after the session ended (outside the criterion). What is left is
   a finding. Done when every row carries one label: auto-populated, selectable, shown as text,
   essential, security, no longer valid, outside, or finding.

9. Evidence per finding. Take the step-3 screenshot of the earlier step with the value entered,
   then on this step mark the empty field and capture it:

   ```bash
   agent-browser highlight "input[name='email']"
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.7-<slug>.png
   agent-browser record start .notes/audit/evidence/<sample>-3.3.7-<slug>.webm
   agent-browser record stop
   ```

   For a value that disappears, start the recording first, redo the fill and the submit (or the
   Back activation), `agent-browser wait 1500`, then stop it. Done when every finding carries both
   screenshots, or the recording for a value that disappears.

What the browser cannot show: why the owner re-asks (is this step's recall essential? is this field
a security measure?), whether a value was invalidated out of view, and anything behind a step with
a real-world effect. Record `cannot-tell` with the step named when a repeated field sits on a step
that could not be walked. agent-browser carries no autofill profile and `fill` never triggers one,
so a `value` already present on arrival was put there by the content, which is what this criterion
asks for.

## Deciding

- Fail (certainty ≥ 90): a field asks for a purpose the ledger holds from an earlier step of the
  same process, arrives empty, the step-4 search finds no `inputs`, no `options` and no visible
  `text` with the value, step 5 finds no working "same as" or "use previous" control in any state,
  and none of the three exceptions applies — 95; a number or code the process itself provided
  earlier (reference, customer number, quote id) has to be typed again and appears nowhere on this
  page — 90; the error state after an invalid submit re-displays the form with entered values
  cleared, passwords excepted — 90; the only copy of the earlier value on this page is a hidden
  input or an `aria-hidden` container, so the user still types it — 90.
- Fail (70–89): a "same as" or "use previous" control that `is checked` confirms is on while the
  target fields stay empty — 85; the earlier value exists only on another step or another page (a
  summary on step 2, the empty field on step 4), against "would need to be on the same page" — 85;
  a billing address asked after the delivery address, or the reverse, with neither pre-population
  nor a "same as" control — 80; a third-party payment or identity step that asks again for the
  name, e-mail or address entered on the site's own steps — 80; a results page whose search field
  arrives empty while the query appears nowhere on the page — 75; the process's own Back control
  returning to a step whose fields are cleared — 75; a step re-asking one value under a different
  label with the same meaning ("e-mail" on step 1, "contact address" on step 3) — 70.
- Needs confirmation (50–69): the re-entry may be essential because the task is a test, a memory
  game or a recall exercise — ask the owner what the step is for — 60; the earlier value may be no
  longer valid because it was rejected or expired out of view, or a later choice changed its format
  — ask what invalidated it — 60; a "confirm your e-mail address" or "repeat the account number"
  field on the same form, for which W3C names only the security exception while the plain-English
  source treats confirmation fields as acceptable — ask whether the second entry is a security
  measure — 55; the two forms may be separate activities rather than one process (a contact form
  after a quote form) — ask which activity the user is completing — 55.
- Pass: every purpose entered or provided at an earlier step arrives pre-populated, or its value is
  offered on this same page (a select or list of the earlier entries, a "same as" control that
  fills the fields, the value as visible text, or either of those inside a component the user can
  open); the error state and the process's own Back control keep every entered value except
  passwords; a field that defaults to the earlier value and still lets the user change it passes,
  as in the W3C example of a corporate ID re-shown in step 3 defaulting to the one entered in step
  1; and every re-entry left over is one of the three exceptions.
- Not present: no state is a process step, and no form can be submitted and shown again.
- False positives to avoid: the confirm field of a new password and a password or PIN asked before
  a sensitive action (security); a one-time code, a CAPTCHA or a Turing test, which was never
  entered before; information first asked on this step; different information under a similar label
  (a second address for a second recipient, a second passenger's name); a return after the session
  ended or after leaving the site, which the criterion does not reach; a review step that shows the
  entered data as text, which is the technique rather than a defect; a value the browser filled in
  the test session, which agent-browser never does; a `value` that looks shortened because the
  probe cuts it at 40 characters.

## Reporting

- File under: 3.3.7, one issue per piece of information per process, naming the step where it was
  entered or provided and the step where it is asked for again; a form that clears on error is one
  issue for the form; a step shared by several samples is one issue that names them. A password
  that must be retyped with no alternative is 3.3.8; data lost when a time-out forces
  re-authentication is 2.2.5; a field without an `autocomplete` token is 1.3.5; an error that is
  not identified in text on the re-displayed form is 3.3.1.
- Title patterns: "The delivery step asks again for the e-mail address entered at registration",
  "Entered values are cleared when the checkout form shows an error", "The customer number from
  step 1 has to be typed again in step 3", "No option to reuse the delivery address for billing",
  "The search results page leaves the search field empty"
- Severity: High when the repeated information is long or hard to recall (an ID or reference
  number, a full address, a bank account), or a whole form is cleared on error, in a process the
  user cannot avoid (checkout, registration, application); Medium when one short item (name,
  e-mail, phone) has to be retyped once, or the earlier value is only reachable through a component
  the user has to find and open; Low when one short value is re-asked once in a two-step process
  that is easy to restart.
- Type: Technical when the step does not carry the data forward, when the error handler resets the
  form, or when the "same as" control is missing or does not populate; Design when the flow itself
  is drawn to re-ask (a confirmation screen built as a second empty form).
- Evidence: two screenshots — the earlier step with the value entered, and this step with the empty
  field — each with `highlight` on the field in question, so the pair shows the same information
  twice; a recording when the value disappears on submit or on Back, because a still image cannot
  show a value that was there a moment earlier.
- Recommendation: carry the data forward and pre-populate the field from the earlier step, or offer
  it on the same page as a "same as" checkbox, a select of the earlier entries, or visible text
  beside the field ([G221](https://www.w3.org/WAI/WCAG22/Techniques/general/G221)); re-display the
  submitted values when a form comes back with errors; while doing so, "ensure data protection when
  storing information even temporarily during a process".

  ```html
  <input id="email" name="email" type="email" autocomplete="email" value="j.jansen@example.nl" />

  <input type="checkbox" id="same" name="same" />
  <label for="same">Billing address is the same as delivery address</label>

  <p id="ref">Your reference is <strong>ORD-99817-KLM</strong></p>
  <label for="ref-input">Reference</label>
  <input id="ref-input" name="ref" aria-describedby="ref" value="ORD-99817-KLM" />
  ```

- Related: 3.3.8 Accessible Authentication (Minimum) — retyping a password is the security
  exception here and a cognitive function test there, so file the password there and the rest here;
  2.2.5 Re-authenticating — data kept across a time-out; 1.3.5 Identify Input Purpose — the
  `autocomplete` token helps the browser, which does not satisfy 3.3.7, so file a missing token
  separately; 3.3.1 Error Identification — the error text on the re-displayed form, split from the
  cleared values; 3.3.4 Error Prevention (Legal, Financial, Data) — a review step that shows the
  entered data serves both criteria.
