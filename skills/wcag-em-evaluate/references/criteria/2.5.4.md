# 2.5.4 Motion Actuation

Level A · WCAG 2.1+ · Guideline 2.5 Input Modalities · Group: `pointer`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/motion-actuation.html)
· [Spec](https://www.w3.org/TR/WCAG22/#motion-actuation)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#motion-actuation)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-5-4-motion-actuation/)
· ACT: [7677a9](https://www.w3.org/WAI/standards-guidelines/act/rules/7677a9/),
[c249d5](https://www.w3.org/WAI/standards-guidelines/act/rules/c249d5/)

## Requirement

> Functionality that can be operated by device motion or user motion can also be operated by user
> interface components and responding to the motion can be disabled to prevent accidental
> actuation, except when:
>
> - Supported Interface: The motion is used to operate functionality through an accessibility
>   supported interface;
> - Essential: The motion is essential for the function and doing so would invalidate the
>   activity.

Terms (WCAG 2.2 glossary):

**functionality**: "processes and outcomes achievable through user action". The response has to
reach an outcome before it is functionality, and c249d5 states that limit as an assumption rather
than a test: "The event listeners listening to device motion events trigger a functionality in the
web page. If they do not trigger any such functionality failing this rule might not be a failure of
the success criterion." A handler that only moves decoration goes to the confirmation queue.

**user interface components**: "a part of the content that is perceived by users as a single
control for a distinct function". Note 1: "Multiple user interface components may be implemented as
a single programmatic element. 'Components' here is not tied to programming techniques, but rather
to what the user perceives as separate controls." Note 2: "User interface components include form
elements and links as well as components generated by scripts" — a link, a menu item or a scripted
widget is an acceptable equivalent. Its Example carries the operative rule here: an applet control
that moves "by line or page or random access" is three components, "Since each of these would need
to have a name and be settable independently, they would each be a 'user interface component.'"
Every direction and every distinct outcome the motion produces needs its own named control:
tilt-left and tilt-right are two functions and need two.

**accessibility supported**: "supported by users' assistive technologies as well as the
accessibility features in browsers and other user agents", where "both 1 and 2 must be satisfied":
"The way that the web content technology is used must be supported by users' assistive technology
(AT)" **AND** "The web content technology must have accessibility-supported user agents that are
available to users." The Supported Interface exception is therefore about motion that reaches the
page _through_ such an interface, which is what the Understanding's note spends it on: incidental
motion, quoted under "Applies when". A page's own `devicemotion` handler is not accessibility
supported for being popular, and both ACT rules assume the exception away — "The motion to operate
the device is not used through an accessibility supported interface" — so claim it only on the
owner's evidence, never on the handler's existence.

**essential**: "if removed, would fundamentally change the information or functionality of the
content, **and** information and functionality cannot be achieved in another way that would
conform". Both halves must hold. A pedometer fails neither; a tilt-to-pan viewer fails the second
half the moment a drag or a pair of buttons could pan it, so it is not essential.

## In plain terms

Whatever the page does when the phone is shaken, tilted or turned, or when the user gestures at a
camera, must also be doable with an ordinary control, and the user must be able to switch the
motion response off — G213 states both duties: "A button, link, or other conventional control is
provided that does not rely on sensor input", **and** "A setting is provided to allow the user to
turn off the sensor data." W3C's goal line is "Content is not dependent on a user's ability to
move a device", because "Some people cannot hold or move a device steadily": it is mounted on a
wheelchair, or tremors make the motion imprecise and set functions off by accident. Honouring the
operating system's own motion setting is an accepted way to provide the off switch.

## Applies when

- Present: the sample, or a frame it embeds, registers a device motion listener. Both ACT rules
  apply to the same thing; 7677a9 words it "any HTML document with an associated Window object
  that has an event listener list with one or more event listeners for device orientation events
  or device motion events" (c249d5 says "an HTML document"). That means `deviceorientation`,
  `deviceorientationabsolute` or `devicemotion`, added with `addEventListener` or assigned to
  `window.ondeviceorientation` / `window.ondevicemotion`.
- Present, beyond the ACT rules: a Generic Sensor class (`Accelerometer`, `Gyroscope`,
  `GravitySensor`, `LinearAccelerationSensor`, the absolute and relative orientation sensors), or
  camera frames read as gestures (`getUserMedia` plus a hand, face or pose library). The criterion
  covers them — the Understanding names "explicit eye, face, or hand gestures to a camera" — while
  both ACT rules return inapplicable, so steps 1, 2 and 6 carry these alone.
- Behaviour to look for once a listener is found: shake to undo or refresh, tilt to scroll or to
  page, pan a panorama, advance a carousel, steer a game, a hero image that follows the phone.
- Every state: repeat steps 1 and 2 in each state listed in `.notes/audit/recon/<sample>-states.md`
  and once under `set device "iPhone 13"`; a viewer, map or gallery often registers its listener
  only when its panel opens, or only under a phone user agent.
- Not present: no sensor code and no change on synthetic motion, in the page and in every frame.
  This is the outcome for most samples; record it with the search result.
- Exceptions: **Supported Interface** — the motion reaches the page through an accessibility
  supported interface; the Understanding spends this exception on incidental motion (quoted below).
  **Essential** — "The motion is essential for the function and doing so would invalidate the
  activity"; Intent: "Some applications are specifically created to use device sensor data.
  Examples of content that are exempt from this requirement include a pedometer that relies on
  device motion to count steps."
- Out of scope, from the Understanding's note — quote it in the finding whenever it decides the
  outcome:

  > This criterion concerns content that interprets motion such as explicit eye, face, or hand
  > gestures to a camera, or tilting and shaking a device, as an input. It does not cover the
  > movement of users through space as registered by geolocation sensors or beacons, the movement
  > necessary to point a device camera at a particular object (such as a QR code, a document, or an
  > image for the purpose of recognizing it), or events observed by the device other than
  > intentional input gestures and movements by the user. The "Supported Interface" exception
  > directly exempts incidental user motion – such as the movement necessary to type on/operate a
  > keyboard, move/click a mouse, the hand and finger movements used to operate a touchscreen, or
  > any movement necessary to operate assistive technology.

- Passing both ACT rules is not a pass for the criterion. Their outcome mapping reads "All passed
  outcomes: success criterion needs further testing" and "An inapplicable outcome: success
  criterion needs further testing": record `pass` only after step 6 has judged the exceptions.

## Manual procedure

Work at `set viewport 1280 900`; the search does not depend on the viewport. Repeat steps 1 and 2
after `set device "iPhone 13"` (or `"Pixel 7"` for an Android user agent; `set device` prints the
supported names when one is unknown) and `open <url>`, then return with `set viewport 1280 900`.
Save the scripts as `.notes/audit/motion-search-2.5.4.js` and `.notes/audit/motion-fire-2.5.4.js`
so every state and every frame is driven by the same code.

1. Find sensor code in the page's scripts (ACT 7677a9 and c249d5 applicability):

   ```bash
   agent-browser eval --stdin <<'EOF'
   (async () => {
   const strong = new RegExp('\\b(' + ['(on)?deviceorientation(absolute)?', '(on)?devicemotion',
     'Device(Motion|Orientation)Event', 'accelerationIncludingGravity', 'rotationRate',
     'Accelerometer', 'Gyroscope', 'GravitySensor', 'LinearAccelerationSensor',
     '(Absolute|Relative)OrientationSensor'].join('|') + ')\\b', 'g');
   const weak = /\b(shake|tilt|gyro|parallax|getUserMedia|mediapipe|handpose|facemesh)\b/gi;
   const ifr = [...document.querySelectorAll('iframe')];
   const out = { hits: [], unreadable: [], frames: ifr.map(f => f.src).filter(Boolean) };
   const urls = new Set([...document.scripts].map(s => s.src).filter(Boolean));
   for (const e of performance.getEntriesByType('resource'))
     if (e.initiatorType === 'script') urls.add(e.name);
   const sources = [...document.scripts].filter(s => !s.src).map(s => ['inline', s.text]);
   for (const f of ifr) if (f.srcdoc) sources.push(['srcdoc', f.srcdoc]);
   const fetched = await Promise.all([...urls].map(u => fetch(u).then(r => r.text())
     .catch(() => null)));
   [...urls].forEach((u, i) => sources.push([u, fetched[i]]));
   for (const [src, t] of sources) {
     if (t === null) { out.unreadable.push(src); continue; }
     const s = [...new Set(t.match(strong) || [])], w = [...new Set(t.match(weak) || [])];
     if (!s.length && !w.length) continue;
     const at = s.length ? t.search(strong) : t.search(weak);
     out.hits.push({ src, strong: s, weak: w,
       excerpt: t.slice(Math.max(0, at - 80), at + 160).replace(/\s+/g, ' ') });
   }
   return out;
   })()
   EOF
   ```

   `hits[].strong` lists the event names and sensor classes found, `weak` library words that only
   hint, `excerpt` the code around the first match, `unreadable` the cross-origin scripts `fetch`
   could not read: for each, `tab new`, `open <src>`, `get text body`, search for the same tokens,
   `tab close`. For each `frames` entry other than `about:blank`: `tab new`, `open <src>`, run this
   step and step 2 there, `tab close` (`frame` does not redirect `eval`). A strong hit inside a
   bundle (a 3D library, a panorama viewer, a parallax plugin) is a candidate only; step 2 decides.

   Then confirm the listener list itself, which is the thing both ACT rules apply to:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
   const orig = EventTarget.prototype.addEventListener;
   window.__motion = [];
   EventTarget.prototype.addEventListener = function (type, fn, opts) {
     if (/^device(orientation|motion)/i.test(type))
       window.__motion.push({ type, target: this === window ? 'window' : String(this.nodeName),
         stack: (new Error().stack || '').split('\n').slice(2, 4).join(' ').trim() });
     return orig.call(this, type, fn, opts);
   };
   return { patched: true, onOrientation: !!window.ondeviceorientation,
     onMotion: !!window.ondevicemotion };
   })()
   EOF
   ```

   `onOrientation` or `onMotion` true is proof on its own: it is the property form of registration.
   With the patch in place, operate whatever may register a listener late — `click` an "enable
   motion", "3D view" or "AR" control, open each panel from `recon/<sample>-states.md`,
   `scroll down` — then read the log with `agent-browser eval --stdin` on
   `(() => window.__motion)()`. Every entry is a test target of 7677a9 and c249d5, and `stack`
   names the file to quote. The patch is lost on `reload` and on `open`: re-apply it after either.
   Done when every script, frame and state is searched and each hit is on file with `src`, `stack`
   and excerpt, or the search came back empty everywhere.

2. Fire synthetic motion and compare the content. Capture the "before" of all three kinds of change
   first: `screenshot --full .notes/audit/evidence/<sample>-motion-before.png`,
   `snapshot --json > .notes/audit/motion-tree-before.json`. When `snapshot -i` lists a control
   named motion, gyroscope, tilt, sensor or enable, `click` it before firing (a page built for iOS
   registers its listener once `requestPermission()` resolves, and that branch is taken here):

   ```bash
   agent-browser eval --stdin <<'EOF'
   (async () => {
   const FIRE = true; // set to false for the step 3 control run: same timing, no events
   if (typeof DeviceOrientationEvent === 'undefined' || typeof DeviceMotionEvent === 'undefined')
     return { unavailable: true, secure: isSecureContext };
   const sleep = ms => new Promise(r => setTimeout(r, ms));
   const media = () => [...document.querySelectorAll('video,audio')].map(m => ({
     src: m.currentSrc || m.src, paused: m.paused, muted: m.muted, volume: m.volume,
     t: Math.round(m.currentTime) }));
   const state = () => ({ url: location.href, scrollX, scrollY, title: document.title,
     nodes: document.getElementsByTagName('*').length,
     text: (document.body.innerText || '').length, media: media() });
   let count = 0; const mo = new MutationObserver(rs => { count += rs.length; });
   mo.observe(document, { subtree: true, childList: true, attributes: true, characterData: true });
   await sleep(2000); const idleRate = count / 2; count = 0; const before = state();
   const t0 = Date.now();
   const fire = (type, init) => FIRE && window.dispatchEvent(type === 'devicemotion'
     ? new DeviceMotionEvent(type, init) : new DeviceOrientationEvent(type, init));
   const motion = (x, g) => ({ acceleration: { x, y: 0, z: 0 },
     accelerationIncludingGravity: { x, y: 0, z: 9.8 },
     rotationRate: { alpha: g, beta: g, gamma: g }, interval: 50 });
   for (let i = -60; i <= 60; i += 10) {
     fire('deviceorientation', { alpha: (i + 60) * 3, beta: i, gamma: i });
     fire('deviceorientationabsolute', { alpha: (i + 60) * 3, beta: i, gamma: i });
     fire('devicemotion', motion(i / 6, i)); await sleep(50); }
   for (let i = 0; i < 30; i++) { fire('devicemotion', motion(i % 2 ? 25 : -25, 0));
     fire('deviceorientation', { alpha: 0, beta: 45, gamma: 45 }); await sleep(50); }
   await sleep(3000); mo.disconnect(); const after = state();
   return { fired: FIRE, idleRate, motionRate: +(count / ((Date.now() - t0) / 1000)).toFixed(1),
     before, after, stateChanged: JSON.stringify(before) !== JSON.stringify(after) };
   })()
   EOF
   ```

   The script counts DOM mutations per second for 2 s without motion (`idleRate`), sweeps tilt on
   both axes past the thresholds real handlers use, shakes at ±25 m/s² while holding a 45° tilt for
   1.5 s, waits 3 s, and reports the rate over that window (`motionRate`). Then take the "after"
   captures: `screenshot --full <...>-motion-after.png` and `snapshot --json > <...>-after.json`.
   Compare all three kinds the ACT glossary names, because any one of them is a change:

   > A event originated change in the content of a web page occurs when, by comparing the web page
   > before and 1 minute after the event firing, at least one of the following occurs:
   >
   > - visible changes: the rendered pixels change in any part of the document that is currently
   >   within the viewport or that can be brought into the viewport via scrolling; or
   > - accessibility tree changes: any state, property or event of a node representing an
   >   accessible object of the accessibility tree changes, or any node is inserted in, or removed
   >   from the accessibility tree; or
   > - audible changes: the audio rendered by the web page changes.

   So: the two `--full` screenshots answer "visible changes", and only `--full` does, because the
   definition includes pixels "that can be brought into the viewport via scrolling"; the two
   `snapshot --json` files answer "accessibility tree changes"; the `media` array in `before` /
   `after` (`paused`, `muted`, `volume`, `t`) answers "audible changes". `motionRate` clearly above
   `idleRate` and `stateChanged` are corroboration, not the verdict — a canvas or WebGL viewer
   redraws without a single mutation, and there the screenshots decide alone.
   The 1 minute in the definition is ACT's own working limit, "not included in WCAG": when all
   three comparisons come back equal, `wait 60000` and re-take them once before writing "no
   change". When a step-1 excerpt tests a threshold or a hold time the sweep misses (`> 30`, a 2 s
   timer), edit the values and rerun. `unavailable` true means the browser exposes neither event
   constructor on this document, and `secure` false is the usual reason (they are secure-context
   only): re-open the sample over https, or record `cannot-tell` with that reason. A Generic Sensor
   class or a camera library cannot be fed values at all: read the handler for what it changes, or
   record `cannot-tell`.
   Done when each listener is marked "changes content: <what, in which of the three kinds>" or "no
   change", with its before/after paths.

3. Attribute each change to the event before believing it. Both rules assume "that there are no
   changes in the content of the web page caused by another event. If this is not the case, changes
   may be attributed to the wrong event and the rule may fail while Success Criterion 2.5.4: Motion
   Actuation is still satisfied." So `reload`, `wait --load networkidle`, re-apply the step-1 patch,
   and run the step-2 script again with `FIRE` set to `false`: identical timing, no events. Take the
   same three captures. A difference that also appears in this control run belongs to a ticker, a
   carousel, an advertisement or a poll, not to the motion, and is dropped from the finding.
   Done when every candidate change is marked "event-attributed" or "also in the control run".

4. Find the equivalent user interface component. 7677a9's expectation is two branches — "For each
   registered device orientation event or device motion event in the test target at least one of
   the following is true":

   - "no changes: The registered event does not cause changes to the content of the web page; or"
   - "same result: There is at least one set of instruments, where each instrument is in the same
     web page of the registered event or can be found in a clearly labeled location from that web
     page, causing the same changes in content as the event."

   The first branch closes a listener that only counts or logs, with no equivalent needed (7677a9
   Passed Example 1). For every change step 3 attributed to the event, the second branch has to
   hold. An instrument is "An HTML element that when activated allows an end-user to achieve an
   objective", and a clearly labeled location is defined as: "The location of a target is said to
   be clearly labeled when the target can be found by activating 'identifiable' instruments which
   either lead the user to find the target, or to another page or page state from which this action
   can be repeated until the target is found", where "an instrument is identifiable if any text or
   other content with a text alternative, allows any user to identify an element with a semantic
   role that inherits from widget". It is judged from the sample, not from the site root —
   "Whether or not the content is 'clearly labeled' depends on the starting point of the search" —
   and a panel a labelled button opens counts, because "A web page changes state when the
   document's body changes without a change in the document's URL" (7677a9 Passed Example 4: a
   "Control panel" button reveals the two slider buttons).

   Worked example, from ACT's own test page: `handleOrientation` calls
   `applyChange(event.gamma, 20)`, so a gamma above +20 increases the slider and below -20
   decreases it, and the step-2 sweep crosses both thresholds, so both directions fire. Passed
   Example 2 answers them with a "Decrease Value" and an "Increase Value" button. Failed Example 1
   keeps only "Increase Value": one direction has no equivalent and the rule fails. A partial
   equivalent is a fail, not a pass with a remark.

   Read `snapshot -i` for controls whose name matches the function (next, previous, undo, reset,
   rotate, pan, increase, decrease), `click` each and compare its effect against the step-2 after
   captures (`get text "<selector>"`, `get attr "<selector>" value`, `screenshot`). A drag or swipe
   as the only equivalent satisfies "same result" when its result is the same, and goes on to 2.5.1
   and 2.5.7. The instruments are out of this rule's scope but not out of the criterion's: "The
   instruments used to pass this rule (if any), must meet all level A Success Criteria in order to
   fully satisfy Success Criterion 2.5.4: Motion Actuation. These extra requirements are left out
   of this rule, and should be tested separately." Hand them to the `keyboard` pass and file their
   own defects under 2.1.1 or 4.1.2.
   Done when every attributed change has, per direction, an equivalent's selector or "no
   equivalent".

5. Find the disable mechanism. c249d5's expectation is two branches as well — "For each registered
   device orientation event or device motion event in the test target at least one of the following
   is true":

   - "no changes: The registered event does not cause changes to the content of the web page within
     a 1 minute time span of the event firing; or"
   - "disabled: There is at least one set of clearly labeled instruments to block the event for at
     least 1 minute."

   "A blocked event makes no changes to the content of the web page", and "A set of clearly labeled
   instruments is a set of instruments, where each instrument is in the same web page as the test
   target or can be found in a clearly labeled location from that web page", so the off switch may
   live on a settings page as long as a link on the sample identifies it
   ([G213](https://www.w3.org/WAI/WCAG22/Techniques/general/G213)).

   Read `snapshot -i` for a checkbox, switch, menu item or link named motion, tilt, gyroscope,
   shake, sensor, settings or accessibility, opening the panels that may hold it; a setting behind
   a labelled link is set on that page (`tab new`, `open <href>`, `tab close`) and the sample tab
   reloaded. Operate it (`check "<selector>"` or `click`) and rerun the fire script with `FIRE`
   true: `motionRate` back at `idleRate`, an unchanged tree and unchanged `--full` screenshots mean
   the event is blocked. Then `wait 60000` and rerun once more — it must still block, because
   c249d5 assumes "After being disabled, the event remains disabled until being re-enabled again.
   If the event is re-enabled through other non-user controlled means (e.g. a timeout) then this
   rule may pass while Success Criterion 2.5.4: Motion Actuation is not satisfied."
   A tick-box that resets on `reload` still counts: G213 example 2 is "a tick-box that prevents the
   motion from having an effect". Record that as a note, not a fail.
   With no control anywhere, look for a media-query guard: run the `motion.js` probe and read
   `reducedMotionQueryUsed`; when it is true, `set media reduced-motion`, `reload`, re-apply the
   step-1 patch and rerun the fire script, and when it is false there is no guard to test.
   Done when each attributed change has a verified blocking control or guard, or "cannot be
   disabled".

6. Judge the exceptions and the system-level route. Essential applies only when the function is the
   motion reading itself — a pedometer, a spirit level, a game whose challenge is the motion — and
   not to a viewer, a carousel or an undo: for those the second half of the definition,
   "information and functionality cannot be achieved in another way that would conform", does not
   hold, and both halves must. Supported Interface applies only to motion arriving through an
   accessibility supported interface, not to the page's own sensor handler.
   The system route is a genuine pass: "Applications may be able to meet this requirement by
   supporting operating system settings which allow the user to disable motion detection at the
   system level." The browser cannot emulate those settings, so when the owner claims one, record
   `cannot-tell` for that change and queue the question: which setting, on which platform, and what
   does the handler read. Its opposite is a failure the Understanding lists without an assigned id —
   content that disrupts or disables the system-level features that let the user turn motion
   actuation off. The step-1 excerpt shows it when the handler re-adds its listener on a timer, on
   `visibilitychange`, or after a stored preference already said no.
   Done when every change carries "no exception", an exception with its reason, or a queued
   question.

7. Capture the evidence. For each fail: `highlight "<selector>"` on the changed component, then
   `screenshot --full <path>`; `record start <file.webm>`, the fire script, `record stop` when the
   change is a movement a still cannot show; a screenshot of the settings panel that has no motion
   toggle; the control-run pair from step 3; and the step-1 excerpt with its `src` and `stack`.
   Done when every fail has its evidence paths, its control-run pair and its excerpt on file.

## Deciding

- Fail (certainty ≥ 90): synthetic motion changes content, the control run of step 3 does not, and
  no control on the page or behind a labelled link produces the same change (95, 7677a9 "same
  result" unmet, its Failed Example 1); the same attributed change and no control, setting or guard
  blocks the response once set (90, F106, c249d5 Failed Example 1); a disable control that does not
  stop the change when the fire script reruns, so the event is not a "blocked event" (90).
- Fail (70–89): a control answers some of the changes but not all, or produces a different or
  partial result — 7677a9 Failed Example 1 fails on exactly one missing direction (80); the
  response returns within a minute of the control being set, or after a timeout (80, c249d5); the
  handler re-registers or re-enables itself against a setting the user made, or against the
  platform's own motion setting (80, the Understanding's unassigned system-level failure); the
  equivalent lives on a page no link on the sample names, so the location is not clearly labeled
  from this starting point (75); a panorama, viewer or carousel that follows motion with no way to
  switch it off (75); a Generic Sensor or camera handler whose code shows a change while the
  interface shows no equivalent and no toggle, both ACT rules being inapplicable to it (75); the
  layout that registers the listener has no equivalent control, though another layout has one (70).
- Needs confirmation (50–69): the function may be essential (60): ask the owner what the motion
  does and whether the activity survives without it; the response only moves decoration and reaches
  no outcome (60, c249d5's assumption that the listeners "trigger a functionality"): ask what
  depends on it; the owner claims a system sensor setting disables it (60): ask which and verify on
  a device; the handler's effect cannot be read — camera gestures, minified sensor code, no visible
  feature (55): `cannot-tell`; the fire script returns `unavailable` and the sample has no https
  origin to re-open (55): `cannot-tell`.
- Pass: every attributed change has, in the same state, a named user interface component per
  direction with the same result, and a clearly labelled control or an honoured system setting that
  blocks the event for at least a minute, in the page and in every frame; or the listener causes no
  change at all (the first branch of both rules); or an exception applies with its reason recorded.
- Not present: no sensor code and no content change on synthetic motion, in the page and frames.
- False positives to avoid: a change that also appears in the step 3 control run is another event's
  (both rules' assumption); `orientationchange`, `screen.orientation` and orientation media queries
  are layout (1.3.4); `prefers-reduced-motion` handling of animation is 2.3.3; drags and swipes are
  2.5.1 and 2.5.7; `watchPosition` is geolocation; a barcode or QR scanner aims the camera, exempt
  by the note; a bundle with the tokens that changes nothing is not present; a listener that is
  added and then removed is no longer in the event listener list and the rules do not apply; a
  `motionRate` at `idleRate` (a ticker, an ad) is not a response; a disable control that resets on
  reload still disables (G213 example 2); a listener that only logs or counts is "no changes"
  (7677a9 Passed Example 1); an equivalent behind a labelled "Control panel" button is an
  equivalent, not a missing one (7677a9 Passed Example 4).

## Reporting

- File under: 2.5.4. An equivalent control the keyboard cannot reach goes to 2.1.1, an unnamed
  toggle or button to 4.1.2 — ACT is explicit that those instruments "should be tested separately"
  — an equivalent that is only a drag to 2.5.7 (2.5.1 for a path gesture), a rotation lock to
  1.3.4. One issue per motion-operated function, its missing equivalent and off switch together,
  naming every sample where the same script runs.
- Title patterns: "Shake to undo has no button equivalent", "Tilting the phone moves the product
  view and cannot be turned off", "Motion-controlled carousel has no on-screen controls", "Tilt
  advances the gallery in one direction only", "Hand-gesture navigation has no on-screen
  equivalent"
- Severity: High when motion is the only way to reach a function or content, or accidental motion
  triggers a navigational or destructive action (undo, submit, next page) with no off switch;
  Medium when equivalents exist but the response cannot be disabled and accidental motion disturbs
  a task (a viewer jumps, a carousel advances); Low when the effect stays within one component and
  an equivalent control is present, so only the off switch is missing.
- Type: Technical: the handler, the missing control and the missing setting are script and markup.
  Design when the visual design has to gain a control or a settings panel it lacks.
- Evidence: the before and after `--full` screenshots with the changed component highlighted, or
  the recording when the change is a movement; the control-run pair that shows the page still
  without the events; the settings panel without a motion toggle; the step-1 excerpt.
- Recommendation: add a conventional control for every direction of the function and a labelled
  setting that turns the motion response off, stored per user and read first in the handler
  ([G213](https://www.w3.org/WAI/WCAG22/Techniques/general/G213)); leaving no way out is
  [F106](https://www.w3.org/WAI/WCAG22/Techniques/failures/F106). The shape that passes both ACT
  rules, from their shared test page:

  ```html
  <button type="button" id="decreaseSlider">Decrease value</button>
  <button type="button" id="increaseSlider">Increase value</button>
  <input type="checkbox" id="disableMotion" />
  <label for="disableMotion">Disable motion actuation</label>
  ```

  ```js
  window.addEventListener('deviceorientation', (event) => {
    if (document.getElementById('disableMotion').checked) return
    if (event.gamma > 20) increaseSlider()
    else if (event.gamma < -20) decreaseSlider()
  })
  ```

- Related: 2.1.1 and 4.1.2 (the equivalent and the toggle must be keyboard operable and named, and
  the `keyboard` pass re-tests them); 2.5.1 and 2.5.7 when the equivalent is a gesture or a drag;
  1.3.4 for orientation locks; 2.2.2 and 2.3.3 for motion on the screen rather than of the device;
  3.2.5 when the response navigates.
