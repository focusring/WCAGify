# 2.5.3 Label in Name

Level A · WCAG 2.1+ · Guideline 2.5 Input Modalities · Group: `forms`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)
· [Spec](https://www.w3.org/TR/WCAG22/#label-in-name)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#label-in-name)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-5-3-label-in-name/)
· ACT: [e086e5](https://www.w3.org/WAI/standards-guidelines/act/rules/e086e5/),
[2ee8b8](https://www.w3.org/WAI/standards-guidelines/act/rules/2ee8b8/)

## Requirement

> For user interface components with labels that include text or images of text, the name contains
> the text that is presented visually.
>
> Note:
> A best practice is to have the text of the label at the start of the name.

Terms (WCAG 2.2 glossary): **user interface components**: "a part of the content that is perceived
by users as a single control for a distinct function [...] Note 2: User interface components
include form elements and links as well as components generated by scripts." **labels**: "text or
other component with a text alternative that is presented to a user to identify a component within
web content. Note 1: A label is presented to all users whereas the name may be hidden and only
exposed by assistive technology. In many (but not all) cases the name and the label are the same.
Note 2: The term label is not limited to the label element in HTML." **name**: "text by which
software can identify a component within web content to the user. Note 1: The name may be hidden
and only exposed by assistive technology, whereas a label is presented to all users. [...] Note 2:
This is unrelated to the name attribute in HTML." **text**: "sequence of characters that can be
programmatically determined, where the sequence is expressing something in human language".
**images of text**: "text that has been rendered in a non-text form (e.g., an image) in order to
achieve a particular visual effect. Note: This does not include text that is part of a picture that
contains significant other visual content."

## In plain terms

The words a sighted person sees on or beside a control (button text, a field's label, words in a
graphic button) must also be in that control's accessible name, in the same order, best at its
start. Voice users say what they see ("click Send message"); a different name leaves the command
dead or fires another control, and screen reader users hear a name that contradicts the screen.
Words added around the label are fine as long as the label's own words stay whole and consecutive.
A control with a visible label and no name at all fails here too: "when a user interface component
lacks an accessible name — a failure of 4.1.2 Name, Role, Value — and has a visible text label,
then it also fails this success criterion". Case, punctuation and round brackets do not count; a
control with no visible text label is out of scope.

## Applies when

- Present: in any state, a control with visible text on or beside it: buttons, links, tabs, menu
  items, options, summaries, checkboxes, radios and switches (text from content or the adjacent
  label); fields, selects, textareas, comboboxes and sliders with a visible label (a placeholder
  counts only when it is the sole visible text); controls labelled only by an image of text
  (wordmark logo link, graphic submit button, `input type="image"`). Detect with the helper below,
  `forms.js` `fields[]`, `links.js` `links[]` and `images.js` entries with `inLink`/`inButton`.
- Not present: no control in any state carries visible text or an image of text: icon-only controls
  and unlabelled fields only (4.1.2, 1.1.1 and 3.3.2 own those), or no control at all.
- Which text is the label: "only the text in close proximity", in the positions
  [G162](https://www.w3.org/WAI/WCAG22/Techniques/general/G162) sets out — "immediately to the left
  of comboboxes, dropdown lists, text inputs, and other widgets (or in the absence of left-side
  labels, immediately above and aligned with the left edge of each input)", "immediately to the
  right of checkboxes and radio buttons", "inside buttons and tabs or immediately below icons
  serving as buttons". A hint line between a stacked label and its field leaves the label above it
  as the label: "the concept of 'adjacent text' is a guide for label interpretation, but cannot
  always serve as a hard rule" ([G211](https://www.w3.org/WAI/WCAG22/Techniques/general/G211)).
- Exceptions: none in the criterion; the Understanding bounds what counts as a label:
  - No visible text label: "where a visible text label does not exist for a component, this success
    criterion does not apply to that component". A `title` tooltip is not visible, so a radio in a
    range labelled only at its ends (G211) is out of scope for the middle buttons.
  - Symbolic characters: "text should not be considered a visible label if it is used in a symbolic
    manner" ("×" for close, ">" mimicking a right-facing arrow, "B", "I" and "ABC" on editor icons,
    an icon-font ligature such as "search"). There "the accessible name should be the function the
    button serves (e.g., 'Spell check' or 'Check spelling'), not the visible symbolic characters":
    a functional name over a symbolic label is a pass, not a fail.
  - Mathematics is text: "Mathematical expressions are an exception to the previous subsection about
    symbolic characters" — "A>B" and "11×3=33" are labels, and "The name should match the label's
    formula text".
  - Case, punctuation and round brackets: "differences in capitalization and punctuation are not
    relevant"; "parenthetical text may be optionally considered a description and left out of the
    accessible name" ("Next…" named "Next" passes, "Date (YYYY-MM-DD)" named "Date" passes). Round
    brackets only: the algorithm does not drop "other kind of brackets such as square brackets and
    curly brackets", so "Search [beta]" keeps "beta" in its label.
  - Only adjacent text is the label: headings, instructions and group labels (`fieldset`/`legend`,
    `role="group"`, `role="radiogroup"`) are not, and `aria-describedby` text is no part of the
    name at all.

`label-content-name-mismatch` sits in the **experimental** rule set of axe-core 4.12.1: off by
default, so neither `agent-browser a11y` nor `scripts/axe-page.mjs` returns a result for it. Opt in
per state, next to the helper below:

```bash
agent-browser a11y --tags experimental --json
```

It selects an element only when its role is a widget role that supports name from content, its
`aria-label` or `aria-labelledby` is non-empty, and it has visible text; it reads that text with
icon-font ligatures ignored and returns no violation when either side is not human language
(symbols or emoji alone), which step 5 decides. Settles: nothing by default; with the opt-in run,
ARIA-named widgets whose visible words are absent, reordered or split. Leaves open: ARIA-named
widgets in every state the run did not cover (step 1, where the helper applies the rule's
algorithm); widgets named from their content without ARIA, which the rule never selects; fields
labelled beside them, and unnamed fields under visible text (step 2, ACT e086e5); images of text
(step 3); labels that change with state (step 4); abbreviations, differing spelling or hyphenation,
number words, formulas and symbolic characters, all of which ACT 2ee8b8 drops from its scope
(step 5).

## Manual procedure

This file covers every control with a visible text label; the `forms` pass walks them all once per
state at `set viewport 1280 900`. `snapshot -i` gives the computed name, the string a screen reader
and a speech tool both receive: it decides the name side, a screenshot the label side. The helper
applies the ACT 2ee8b8 label-in-name algorithm (fold case, keep letters and digits, split into
words; the label's words must occur consecutively in the name's, compared with and without bracketed
text) to every widget named from content and lists the misses; its `name` only approximates the
accessible name:

```bash
agent-browser eval --stdin <<'EOF'
(() => {
  const roles = new Set(['button', 'link', 'checkbox', 'radio', 'tab', 'menuitem', 'switch',
    'menuitemcheckbox', 'menuitemradio', 'option', 'treeitem', 'gridcell', 'searchbox']);
  const roleOf = el => el.getAttribute('role')?.split(/\s+/)[0]
    || (el.tagName === 'A' && el.href ? 'link'
    : /^(BUTTON|SUMMARY)$/.test(el.tagName) ? 'button' : null);
  const hidden = el => { const cs = getComputedStyle(el), r = el.getBoundingClientRect();
    return cs.display === 'none' || cs.visibility !== 'visible' || cs.opacity === '0'
      || cs.fontSize === '0px' || /icon/i.test(cs.fontFamily) || r.width <= 1 || r.height <= 1; };
  const visText = el => { let s = ''; (function walk(n) {
    if (n.nodeType === 3) { s += n.data; return; }
    if (n.nodeType !== 1 || hidden(n)) return;
    const inline = getComputedStyle(n).display.startsWith('inline');
    if (!inline) s += ' '; n.childNodes.forEach(walk); if (!inline) s += ' '; })(el); return s; };
  const content = el => [...el.childNodes].map(n => n.nodeType === 3 ? n.data : n.nodeType !== 1
    || n.getAttribute('aria-hidden') === 'true' ? '' : n.getAttribute('aria-label')
    || n.getAttribute('alt') || content(n)).join('');
  const accName = el => (el.getAttribute('aria-labelledby') || '').split(/\s+/).filter(Boolean)
    .map(id => document.getElementById(id)?.textContent || '').join(' ').trim()
    || el.getAttribute('aria-label') || content(el) || el.title || '';
  const tok = (s, drop) => (drop ? s.replace(/\([^)]*\)/g, ' ') : s).toLowerCase()
    .normalize('NFKD').replace(/[^\p{L}\p{N}]+/gu, ' ').trim().split(/\s+/).filter(Boolean);
  const run = (l, n) => !l.length || n.some((_, i) => l.every((t, j) => n[i + j] === t));
  const has = (l, n) => run(tok(l, true), tok(n, true)) || run(tok(l), tok(n));
  return [...document.querySelectorAll('a[href], button, summary, [role]')].map(el => {
    const role = roleOf(el); if (!role || !roles.has(role) || hidden(el)) return null;
    const label = visText(el).trim().replace(/\s+/g, ' ');
    const name = accName(el).trim().replace(/\s+/g, ' ');
    if (!label || has(label, name)) return null;
    return { id: el.id || null, role, label, name,
      aria: el.hasAttribute('aria-label') || el.hasAttribute('aria-labelledby') };
  }).filter(Boolean);
})()
EOF
```

The comparison is word by word, never by substring: every label word must equal a name word, so
"Discover It" is not contained in "Discover Italy" and "1" is not "1a". The roles it walks are the
13 that support name from content (button, checkbox, gridcell, link, menuitem, menuitemcheckbox,
menuitemradio, option, radio, searchbox, switch, tab, treeitem); a `textbox` is not among them,
because "The content of a text field shows its value instead of its label". The bracket-dropping
comparison is the ACT one; the second, which keeps brackets, only prevents a false fail where the
name carries the label's bracketed words.

1. Widgets named from content (ACT 2ee8b8: a widget role supporting name from content, visible text,
   `aria-label` or `aria-labelledby`; the helper also lists misses without ARIA). Its one
   expectation: "For each target element, the visible inner text is contained within the accessible
   name according to the label in name algorithm." Run it in the default state; an empty list passes
   them. For each entry find it in `snapshot -i` by role and text, read the tree's name (a miss the
   tree does not confirm is a note) and `screenshot @<ref> <path>` for the label. `aria: true` with
   the label's words absent or partial in the name is
   [F96](https://www.w3.org/WAI/WCAG22/Techniques/failures/F96), reordered or split by other words
   it is ACT 2ee8b8 failed: either is a fail. `aria: false` means an `aria-hidden` span or a child's
   `alt` or `aria-label` replaced visible words: a fail once the tree agrees. Visually hidden text
   inside the control keeps its position in the name: appended after the label it passes
   (`<button>Send <span class="sr-only"> Mail</span></button>`, G208), pushed between the label's
   words it fails ("Download <span class="sr-only">gizmo</span> specification" named "Download gizmo
   specification", F96 example 2). The other ACT-failed shapes, all with the label's words present:
   a different order (label "you how are", name "how are you"), one word inserted (label "Download
   specification", name "Download the specification"), digits re-tokenized ("1 2 3. 5 5 5. 0 1 2 3"
   for "123.555.0123"), and digits or symbols written out as words. Symbolic-only labels,
   abbreviations, hyphenation, digits versus words and spelled-out formulas go to step 5. Done when
   every entry is a fail, a step 5 hand-off or a note.

2. Fields and `input` buttons, which the helper skips. Run `forms.js`:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   For each `fields[]` entry with `visibleLabelText` apply the algorithm to it and `name`.
   `nameSource` `label`, or `aria-labelledby` pointing at the visible label, passes; `aria-label`,
   `title` or `aria-labelledby` pointing elsewhere must hold the label's words consecutively, else
   F96, a fail. An empty `name` (`nameSource` `none`, in `counts.unnamed`) with visible text beside
   it is [F111](https://www.w3.org/WAI/WCAG22/Techniques/failures/F111) and ACT e086e5 failed: a
   fail filed under 4.1.2 naming this criterion and 1.3.1; with no visible text it is 4.1.2 alone.
   ACT e086e5 covers the 11 field roles checkbox, combobox, listbox, menuitemcheckbox,
   menuitemradio, radio, searchbox, slider, spinbutton, switch and textbox that are included in the
   accessibility tree, and its one expectation is that "Each target element has an accessible name
   that is not empty ("")"; it still applies to a `disabled` field and not to one hidden with
   `display:none` or `aria-hidden`. Read as empty: an `aria-label` of spaces only, an
   `aria-labelledby` naming an id that does not exist (F111 example 2) or an element with no text,
   and a scripted `role="textbox"`, `role="combobox"` or `role="listbox"` wrapped in or referenced
   by a `label` element, which names native fields only. `tag` `input` with `type` `submit`,
   `reset`, `button` or `image`: its face text is the `value` or the image's `alt`, and a
   `nameSource` other than `content` or `alt` must hold those words, else F96, a fail —
   `aria-labelledby` on an `input type="submit"` overrides its `value` (F96 example 3).
   `visibleLabelText` null with a `placeholder`: "in the absence of any other nearby text string
   [...] if an input contains placeholder text, such text may be a candidate for Label in Name", so
   `nameSource` `placeholder` passes and any other name lacking its words goes to the confirmation
   queue. `visibleLabelText` null and no placeholder: `screenshot "<selector>" <path>`; adjacent
   text (`get text` on the preceding element) is a label the probe could not associate, and a miss
   in `name` fails here and under 1.3.1; no text at all is 3.3.2. Where the label carries an
   asterisk or bracketed text the name leaves out ("Name *", "Birth date (YYYY-MM-DD)"), 2.5.3
   passes and that information "must be provided programmatically in some other way": check
   `required`/`ariaRequired` for the asterisk and `describedbyText` for the format, and record a
   1.3.1 finding when neither is set. Done when every field has pass, fail, queue or hand-off.

3. Images of text as the label. From `images.js` take every entry with `inLink` or `inButton` and
   every `kind` `input-image`, plus `links.js` entries with `isImageOnly`; `controlText` holds the
   host's other text or its `aria-label`, so it filters nothing. ACT 2ee8b8 stops here: "If the
   target element contains an image of text, it may pass this rule but fail 2.5.3 Label in Name
   (because the accessible name should then match the text inside the image, which is not taken into
   account by this rule). So further testing is needed." `screenshot "<selector>" <path>` and read
   the words in the image; no words (an icon, a photo) means no text label, nothing to check. Words
   visible: compare them with the control's name in `snapshot -i` (`images.js` `name` is the image's
   own name, not the host's), missing words fail. Words that are part of a photograph are not an
   image of text ("This does not include text that is part of a picture that contains significant
   other visual content"): a name that leaves them out passes. An SVG wordmark: `get text
"<selector>"` returns its `<text>`. An image that did not load (`width` 0, `visible` false) is
   `cannot-tell`. Done when every image-labelled control is judged.

4. States. After every state change the `forms` pass makes, `snapshot -i` and re-run the helper and
   `forms.js`: the error state after `fill` and submit (renamed buttons), each step of a multi-step
   form, every open menu, dialog, listbox, tab panel and expanded section, and every toggle whose
   text changes (`click` "Show password", "Follow", "Play"; `check` a switch). The name must follow
   the visible text in each state: a fixed `aria-label="Toggle password visibility"` under "Show"
   then "Hide" fails in both. Done when every recorded state has a run.

5. Judgement cases, where the ACT rule stops and the Understanding decides. Symbolic characters
   only ("×", ">", "…", a single-letter icon, icon-font text): no text label, pass, note it. A
   formula spelled out in the name ("11×3=33" named "eleven times three"): "The name should match
   the label's formula text", a fail; a formula written with the wrong operator ("11x3", "11*3" for
   "11×3") is a note, since W3C only says "The proper operator symbol [...] should be used".
   Abbreviation ("Ave." for "Avenue") and differences of spelling or hyphenation ("non-standard" for
   "nonstandard") make ACT 2ee8b8 inapplicable: queue them, asking whether the user's speech
   software matches. A number written out in the name ("twenty twenty-one" for "2021") the algorithm
   fails: a fail when the label is a formula, else queue. A label not at the start of the name
   ("Search for a value" for "Search", "Go to search" for "Search"): pass. Capitalization alone
   stays a pass — "normatively this success criterion is 'case-insensitive'" — and where uppercase
   marks an abbreviation, record the recommendation to match the case as a note. A pair that matches
   only once round brackets are dropped: ACT assumes bracketed text can be ignored, which "is known
   to be often false in languages other than English, such as German [...] and Arabic", and fails
   where the brackets tell two controls apart ("Dune (1984 film)" against "Dune (2021 film)") —
   queue it, and check `links.js` `sameNameDifferentHref` for names that lost their distinguishing
   brackets. Record `cannot-tell` where words cannot be split: the greedy whitespace split holds "In
   English and most other European languages", not in "Thai, Chinese, and Japanese". The helper
   reads DOM order, so where CSS (`order`, absolute positioning) shows the label's words in another
   order, judge from the screenshot. Done when each has its question.

6. Evidence for every fail: `highlight "<selector>"`, `screenshot <path>`, and the pair as text
   ("visible: Send message · name: Click me"). For a toggle, `record start <file.webm>`, `click
"<selector>"` twice, `record stop`. Done when each fail has its path.

## Deciding

- Fail (certainty ≥ 90): a button, link, tab, menu item, checkbox, radio or switch whose visible
  words are missing from the tree's name set by `aria-label` or `aria-labelledby` (F96, ACT 2ee8b8
  failed) (95); those words present but reordered or split by other words (ACT 2ee8b8) (90);
  visually hidden text inside the control landing between the label's words in the name (F96 example 2) (90);
  a field with an empty name under visible text beside it (F111, ACT e086e5 failed) (95);
  an `aria-labelledby` naming an id that does not exist, or an `aria-label` of whitespace only, on a
  control with a visible label (F111) (95); a field whose `aria-label` or `title` shares no word
  with its label (90); a name holding the label's letters but not its words ("Discover Italy" for
  "Discover It") (90); visible text kept out of the name by `aria-hidden` (90); a widget whose
  visible text changed on `click` while the name stayed (90); a formula label rewritten in words on
  a widget ACT 2ee8b8 applies to (90).
- Fail (70–89): a graphic button or wordmark whose name lacks the words read from the image (80);
  adjacent text the probe could not associate, missing from the field's name (75); a formula label
  rewritten in words where ACT 2ee8b8 does not apply (75); a toggle whose name follows one state
  only (85); a `label` or `for` attached to a scripted widget it cannot name, leaving it unnamed
  (85); an initialism spaced in the label and run together in the name, or the reverse ("W C A G"
  against "WCAG") (85); a label whose square- or curly-bracketed words are missing from the name
  (80).
- Needs confirmation (50–69): abbreviation, hyphenation or digits-versus-words differences (55): ask
  whether the user's speech software matches them; a placeholder-only field named differently (60):
  ask whether the placeholder is meant as the label; text that may be symbolic or human language
  ("x" on a close button), or words in a photo (55): ask whether they are the label; a match that
  only holds once round brackets are dropped, in a non-English sample or where the brackets tell two
  same-named controls apart (55): ask whether a spoken label still reaches the right control.
- Pass: every control with a visible text or image-of-text label, in every probed state, has a
  computed name in which the label's words, after dropping brackets, case and punctuation, occur
  consecutively. Words added before or after that run do not break it. The label at the start of the
  name is a best practice, not a condition.
- Not present: no control in any state has visible text or an image of text as its label.
- False positives to avoid: case, punctuation, an ellipsis, an emoji, bracketed text kept in the
  name; a name that adds words before or after the label; hidden text appended after the visible
  label rather than inside it (G208); a name that repeats the legend or group label around the
  control's own label; a symbolic character or icon-font ligature as the only text, answered by a
  functional name; visually hidden text (not the label); headings, legends and instructions; a
  `title` tooltip; an `aria-describedby` hint that is no part of the name; a placeholder as the name
  when nothing else is visible; a select whose visible text is its options; a typed value; the
  helper's `name` when the tree disagrees.

## Reporting

- File under: 2.5.3 for every name that lacks the visible label. A control with no name at all goes
  to 4.1.2 naming this criterion and 1.3.1 (F111 names all three); a label never associated also to
  1.3.1; an image of text with a wrong `alt` to 1.1.1. One issue per pattern, listing each control's
  visible text and name, and every sample and state.
- Title patterns: "Button's accessible name differs from its visible text", "Field name does not
  include its visible label", "Hidden text breaks up the link's name", "Password toggle keeps one
  name while its text changes"
- Severity: High when the control is needed to finish a task (submit, next, log in, close a dialog)
  or the pattern covers the main navigation, and whenever the control has no accessible name at all;
  Medium when a secondary control is affected, or the name holds the label's words reordered or
  split so a spoken command may still hit it; Low when the difference is an abbreviation, a number
  form or one trailing word on a control with an obvious alternative.
- Type: Technical by default: an `aria-label` or `aria-labelledby` override, a `label` not tied to
  its field, a `value` or `alt` on a graphic button. Content when the mismatch comes from an
  editorial field (a CMS "screen reader text" or the `alt` of an uploaded image of text).
- Evidence: an element screenshot with `highlight` on the control, captioned with the pair
  ("visible: Send message · name: Click me"); a GIF when the visible text changes with state.
- Recommendation: remove the `aria-label` so the name comes from the visible text, or start the name
  with the visible text ([G208](https://www.w3.org/WAI/WCAG22/Techniques/general/G208)); make the
  name equal the label ([G211](https://www.w3.org/WAI/WCAG22/Techniques/general/G211)) by tying the
  visible label to its field; keep labels adjacent
  ([G162](https://www.w3.org/WAI/WCAG22/Techniques/general/G162)). Where a control needs more
  context than its label, put it after the label in the name, or leave the name alone and add the
  context as a description with `aria-describedby`. For an icon with no text, W3C's advisory option
  is to use its hover text as the accessible name. Examples:

  ```html
  <button aria-label="Send message to support">Send message</button>
  <!-- passes, label first -->
  <button>Send message</button>
  <!-- better: one string -->
  <label for="q">Search</label> <input id="q" />
  <a href="poor.html" aria-label="Read more about Insufficient link names">Read more</a>
  <label for="birth">Birth date</label> (<span id="mask">YYYY-MM-DD</span>)
  <input type="text" id="birth" name="birth" autocomplete="bday" aria-describedby="mask" />
  ```

- Related: 4.1.2 (no name at all) and 1.3.1 (label not associated) share F111; where the name drops
  an asterisk or bracketed text, 1.3.1 still needs `required`/`aria-required` and the format text
  referenced with `aria-describedby`; 3.3.2 (no visible label, out of scope here); 2.4.4 (an
  `aria-label` adding link context must keep the visible text first); 1.1.1 and 1.4.5 (an image of
  text needs an `alt` with its words, real text is better).
