# 3.2.4 Consistent Identification

Level AA · WCAG 2.0+ · Guideline 3.2 Predictable · Group: `consistency`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification.html)
· [Spec](https://www.w3.org/TR/WCAG22/#consistent-identification)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#consistent-identification)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-2-4-consistent-identification/)
· ACT: none

## Requirement

> Components that have the same functionality within a set of web pages are identified consistently.

Terms (WCAG 2.2 glossary), verbatim:

- **same functionality**: "same result when used". Its example is this criterion's own failure:
  'A submit "search" button on one web page and a "find" button on another web page may both have
  a field to enter a term and list topics in the website related to the term submitted. In this
  case, they would have the same functionality but would not be labeled consistently.' Sameness is
  decided by the result of using the component, never by its markup, its class names or its place
  on the page.
- **set of web pages**: "collection of web pages that share a common purpose and that are created
  by the same author, group or organization". Its examples:
  - "a publication which is split across multiple web pages, where each page contains one chapter
    or other significant section of the work. The publication is logically a single contiguous
    unit, and contains navigation features that enable access to the full set of pages."
  - "an e-commerce website shows products in a set of web pages that all share the same navigation
    and identification. However, when progressing to the checkout process, the template changes;
    the navigation and other elements are removed, so the pages in that process are functionally
    and visually different. The checkout pages are not part of the set of product pages."
  - "a blog on a sub-domain (e.g. blog.example.com) which has a different navigation and is
    authored by a distinct set of people from the pages on the primary domain (example.com)."

  Note: "Different language versions would be considered different sets of web pages."

- **web page** (Key Terms of the Understanding page): "a non-embedded resource obtained from a
  single URI using HTTP plus any other resources that are used in the rendering or intended to be
  rendered together with it by a user agent". Its example 2 is a web-mail program that "lives
  entirely at http://example.com/mail, but includes an inbox, a contacts area and a calendar":
  views of one single-page application that never change the URI are states of one web page, not a
  set of web pages. They enter the comparison as states of their own sample under step 4, and a
  scope holding nothing but such views is `not-present`.

## In plain terms

Whatever does the same thing on more than one page of a site keeps the same identification on every
page: the same visible label, the same accessible name and the same text alternative for the search
button, the "Add to cart" button, the download icon, the "Contact" link, the menu button. The
Intent names both halves: "If identical functions have different labels (or, more generally, a
different accessible name) on different web pages, the site will be considerably more difficult to
use", and "This consistency extends to the text alternatives." Consistent is a pattern, not
identity: "Go to page 4" and "Go to page 5" are consistent, and so are "Print receipt" and "Print
invoice" for two different print functions. Screen reader users find a function by the name they
learned on the first page and can search for it by that name; people with cognitive disabilities or
reading in a second language are spared two words for one thing.

## Applies when

- Present: the scope holds two or more samples of one set, and at least one component recurs on two
  of them with the same result when used. Detect the recurrence in the recon outputs: a link to the
  same target (`links[].href` resolved against `links.js`'s `url`, in `<id>-links.json`), a skip
  link (`<id>-structure.json` `skipLinks[]` `text` and `href`), a button or custom control
  (`<id>-focusables.json` `order[]` with `role` `button`, `link`, `tab` or `menuitem`, and
  `<id>-forms.json` `fields[]` with `tag` `button`), a field with the same job (`<id>-forms.json`
  `fields[]` `autocompleteCandidate`, `type` `search`, `forms[].action`, `forms[].submitButtons`),
  an icon inside a control (`<id>-images.json` `images[]` with `inLink` or `inButton`), a landmark
  (`<id>-structure.json` `landmarks[]` `role` and `name`). Every site audit with a shared header or
  footer has this.
- Present in states too: a component that only exists once a menu, a cookie dialog, an account or
  language menu or a login dialog is open counts as repeated when two samples of the set share that
  state; `<id>-states.md` lists the states reached during recon.
- Not present: the scope is one web page (including one single-page application whose views keep
  one URI), or no component recurs on two samples of the same set, because each sample is a set of
  its own or the samples share nothing. Record `not-present`.
- Exceptions: the criterion text has none. Four sentences of the Understanding decide what is
  compared: "3.2.4 Consistent Identification only addresses consistency within a set of web pages
  where something is repeated on more than one page in the set"; "If there are two components on a
  web page that both have the same functionality as a component on another page in a set of web
  pages, then all 3 must be consistent. Hence the two on the same page will be consistent."; "While
  it is desirable and best practice always to be consistent within a single web page", a difference
  that exists only inside one page with no counterpart on another sample is best practice, not a
  failure; and a separate set (checkout template, sub-domain, language version, an area behind a
  login with its own navigation) is compared inside itself only.
- Notes that decide an outcome, both under "Sufficient Techniques" on the Understanding page, the
  first repeated as the note of [F31](https://www.w3.org/WAI/WCAG22/Techniques/failures/F31):
  - "Text alternatives that are 'consistent' are not always 'identical.' For instance, you may have
    a graphical arrow at the bottom of a web page that links to the next web page. The text
    alternative may say 'Go to page 4.' Naturally, it would not be appropriate to repeat this exact
    text alternative on the next web page. It would be more appropriate to say 'Go to page 5'.
    Although these text alternatives would not be identical, they would be consistent, and
    therefore would satisfy this success criterion."
  - "A single non-text-content-item may be used to serve different functions. In such cases,
    different text alternatives are necessary and should be used. [...] A check mark icon may
    function as 'approved', 'completed', or 'included', to name a few, depending on the situation.
    Using 'check mark' as text alternative across all web pages does not help users understand the
    function of the icon. Different text alternatives can be used when the same non-text content
    serves multiple functions."

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. The `axe-page.mjs`
results contribute nothing here, and the data pack names no rule tagged elsewhere that applies, so
this file cites no rule id. A component that carries no accessible name at all cannot be compared
for consistency: leave it to the 4.1.2 and 1.1.1 rows of that sample's `structure` unit and compare
only components that have a name on at least two samples.

## Manual procedure

Consistency mode, once per report, after every `recon` unit. Inputs: `index.md`, `.notes/sample.md`,
the `links`, `images`, `forms`, `focusables` and `structure` probe outputs and `<id>-tree.txt` of
every sample in `.notes/audit/recon/`, `<id>-states.md`, the full-page screenshots
`evidence/<id>-full.png`, and one browser session for the components that have to be tried. Outcome
and findings go to `consistency.md`; its `Sample` column names the samples where each variant was
seen.

The frame is the test procedure of [F31](https://www.w3.org/WAI/WCAG22/Techniques/failures/F31):
"In a set of web pages, find components with the same function that are repeated in multiple web
pages" (steps 1 to 4 below), then "For each component with the same function found in step #1,
check that the naming is consistent" (steps 5 and 6); "If check #2 is false then this failure
condition applies and content fails the Success Criterion." The sufficient technique
[G197](https://www.w3.org/WAI/WCAG22/Techniques/general/G197) states the two checks that must both
be true: "Check that each component is associated with text that identifies it (i.e., label, name,
or text alternative)" and "Check that this associated text is identical for each user interface
component with the same function." G197 asks for identical; the criterion, F31 and the Understanding
examples accept consistent, so a pattern whose only variable part names the specific target or
function passes. G197 is sufficient only "AND following the sufficient techniques for Success
Criterion 1.1.1 and sufficient techniques for Success Criterion 4.1.2 for providing labels, names,
and text alternatives", which is why a missing name is recorded there and not here.

1. Sort the samples into sets. Reuse the `sample · set · exempt (reason)` table written for 2.4.5,
   or the `sample · set` table written for 3.2.3, when either exists; otherwise give every sample
   its set with the glossary rule and the separate-set cases under "Applies when". 3.2.4 has no
   process exception: checkout and wizard steps form a set of their own and are compared with each
   other. Done when every sample has a set in the notes of `consistency.md`, and every set holding
   one sample is marked as contributing `not-present`.

2. Build the candidate lists the recon outputs can key by themselves: link targets and icon
   controls that carry two different names across the samples of a set. Run this in the recon
   directory, over the samples of one set (move the other sets' files aside or filter on their
   names):

   ```bash
   cd <report-dir>/.notes/audit/recon
   node <<'EOF' > ../findings/3.2.4-candidates.md
   ;(() => {
   const fs = require('node:fs')
   const norm = (s) =>
     (s || '').toLowerCase().replace(/\s+/g, ' ').trim().replace(/[.:;,!?]+$/, '')
   const read = (suffix) =>
     fs.readdirSync('.').filter((f) => f.endsWith(suffix)).map((f) => ({
       sample: f.replace(suffix, ''), data: JSON.parse(fs.readFileSync(f, 'utf8'))
     }))
   const target = (href, base) => {
     if (/^(?:mailto:|tel:|javascript:)/i.test(href)) return null
     if (href.startsWith('#')) return href
     try {
       const u = new URL(href, base)
       u.hash = ''
       return u.href.replace(/\/$/, '')
     } catch {
       return null
     }
   }
   const group = (rows) => {
     const map = new Map()
     for (const r of rows) {
       if (!map.has(r.key)) map.set(r.key, [])
       map.get(r.key).push(r)
     }
     return [...map].filter(
       ([, hits]) =>
         new Set(hits.map((h) => h.sample)).size > 1 &&
         new Set(hits.map((h) => norm(h.name))).size > 1
     )
   }
   const linkRows = []
   for (const { sample, data } of read('-links.json'))
     for (const l of data.links) {
       const key = l.href && target(l.href, data.url)
       if (key) linkRows.push({ key, sample, name: l.name, selector: l.selector })
     }
   const iconRows = []
   for (const { sample, data } of read('-images.json'))
     for (const i of data.images)
       if (i.src && (i.inLink || i.inButton))
         iconRows.push({ key: i.src, sample, name: i.name || i.controlText, selector: i.selector })
   const show = (title, pairs) => {
     const body = pairs
       .map(([key, hits]) =>
         `### ${key}\n` + hits.map((h) => `- ${h.sample} · "${h.name}" · ${h.selector}`).join('\n'))
       .join('\n\n')
     console.log(`\n## ${title}\n\n${body || 'none'}`)
   }
   show('Link targets with two names', group(linkRows))
   show('Icon controls with two names', group(iconRows))
   })()
   EOF
   ```

   The link key is the `href` resolved against the sample's own `url`, with the fragment and a
   trailing slash dropped and the query kept: `/products?page=1` and `/products?page=2` are
   different targets and merging them would pair two unrelated links. A fragment-only `href` keeps
   its fragment as the key, so skip links to `#main` on two samples are compared with each other.
   Both lists are candidates for steps 5 and 6, never verdicts: a printer icon named "Print
   receipt" on one sample and "Print invoice" on another lands in the icon list and passes at step
   6 (Understanding example 4). Done when `3.2.4-candidates.md` exists per set and every group in
   it is carried into the step 3 table.

3. Inventory by hand the repeated functions the script cannot key, one row per function per sample,
   keyed by what the component does:
   - buttons and custom controls: `<id>-focusables.json` `order[]` with `role` `button`, `tab` or
     `menuitem`, and `<id>-forms.json` `fields[]` with `tag` `button`; read the job from the
     `selector`, the enclosing form and the element's line in `<id>-tree.txt` (menu, search submit,
     close, share, print, language switch, add to cart, save); keep `name` and `nameSource`.
   - fields: `<id>-forms.json` `fields[]` keyed by `autocompleteCandidate`, or by `type` `search`
     with `forms[].action`; keep `name`, `nameSource`, `visibleLabelText` and the enclosing form's
     `submitButtons`.
   - landmarks: `<id>-structure.json` `landmarks[]` keyed by `role`; keep `name` (a navigation
     named "Main" on one sample and "Primary" on another is a repeated component too).
   - icons whose `src` differs while the function is the same (two files for one download icon):
     `<id>-images.json` `images[]` with `inLink` or `inButton`, keyed by the enclosing control;
     keep `alt`, `name`, `nameSource`, `controlText`.
     Keep every function that occurs on two or more samples of the set, plus every second copy of
     such a function inside one sample (the header and footer link to the same page), because "all 3
     must be consistent". Done when the notes of `consistency.md` hold the table `function · sample ·
selector · visible label · accessible name · icon` for every kept function.

4. Add the shared states. The probes ran on the initial state; repeated components inside a cookie
   dialog, a menu, an account or language menu and a login dialog count too. For every state in
   `<id>-states.md` that two samples of the set share, reach it and collect its controls:

   ```bash
   agent-browser open <sample url>
   agent-browser wait --load networkidle
   agent-browser find role button click --name "<menu button name>"
   agent-browser eval --stdin <<'EOF'
   (() => {
     const clean = (t) => (t || '').replace(/\s+/g, ' ').trim()
     const sel = '[role=dialog] a[href], [role=dialog] button, nav a[href], nav button, '
       + '[role=menu] [role=menuitem], [role=menubar] [role=menuitem]'
     return [...document.querySelectorAll(sel)]
       .filter((e) => e.getClientRects().length)
       .map((e) => ({
         tag: e.tagName.toLowerCase(),
         href: e.getAttribute('href'),
         text: clean(e.textContent),
         aria: e.getAttribute('aria-label'),
         icon: e.querySelector('img')?.getAttribute('src')
           ?? (e.querySelector('svg') ? 'svg' : null),
         alt: e.querySelector('img')?.getAttribute('alt') ?? null
       }))
   })()
   EOF
   ```

   `href` is read with `getAttribute` so it keys the same way as `links[].href` from step 2. `text`
   and `aria` together are the label; when they disagree, take the computed name from the tree with
   `agent-browser snapshot -i -s "[role=dialog]"` and a second call with `-s "nav"`, because `-s`
   scopes to its first match and a comma list would only show the first container. Done when the
   step 3 table also holds a row per repeated component of every shared state.

5. Compare the identifications per function across the samples of the set. Normalise both values
   (lower case, trimmed, whitespace collapsed, trailing punctuation dropped) and compare the
   visible label, the accessible `name` and, for icon controls, the icon and its text alternative.
   Mark each function:
   - consistent: identical after normalising, or one pattern whose only variable part names the
     specific target or function ("Download <title>", "Go to page 4" / "Go to page 5", "Print
     receipt" / "Print invoice", "Cart (0)" / "Cart (3)");
   - inconsistent: different words for the same result ("Search" / "Find", "Contact" / "Get in
     touch", "Save" / "Save page"), a different accessible `name` behind identical visible text (an
     `aria-label` on one sample only, Understanding example 8), a different `alt` or `name` on the
     same icon file, or a different icon file under the same name;
   - unclear: the same result is not established yet, which step 6 settles.
     Two copies of a function inside one sample count as two rows against every copy on the other
     samples. Names differing only in case, whitespace or trailing punctuation carry the same words
     and are consistent. Done when every function row is marked, with both values quoted verbatim.

6. Establish "same result when used" for every inconsistent or unclear function by trying it.
   Links: an equal normalised target from step 2 is the same result; two targets that may redirect
   to one page are opened in turn and their `get url` and `get title` compared. Buttons, fields and
   forms: activate the component on each sample the same way and compare what follows (URL, dialog,
   result heading, cart count, the `main` subtree):

   ```bash
   agent-browser open <sample A url>
   agent-browser wait --load networkidle
   agent-browser fill "input[type=search], [role=searchbox]" "<term>"
   agent-browser find role button click --name "<label A>"
   agent-browser wait --load networkidle
   agent-browser get url
   agent-browser get title
   agent-browser snapshot -i -u -s "main"
   ```

   Repeat on sample B with the same term and the label used there; equal result page, equal result
   heading and an equal set of result items is the same result. For an icon control, also confirm
   the two icons are the same file: `agent-browser get attr "<selector>" src` on each sample, with
   the selector first. Stop before an action with a real-world effect (order, payment, message, a
   destructive setting); record such a pair as `cannot-tell` with the two labels quoted, or as
   needs confirmation when the surrounding text makes the same result likely. Done when every
   inconsistent row is marked same result or different result (two functions, no finding), with
   what was observed written next to it.

7. Take the evidence and decide per set. For every inconsistent function with the same result, one
   screenshot per variant with the component highlighted, plus the tree line whenever the name
   differs from the visible text:

   ```bash
   agent-browser open <sample A url>
   agent-browser wait --load networkidle
   agent-browser highlight "<selector A>"
   agent-browser screenshot .notes/audit/evidence/<sample A>-<function>-label.png
   agent-browser snapshot -i -s "<selector A>"
   ```

   Repeat on sample B. Record one 3.2.4 row in `consistency.md` for the report: `fail` when any set
   has an inconsistent function with the same result, `not-present` only when every set does,
   `pass` otherwise, with the `Sample` column naming every sample each finding touches. Done when
   the row carries its outcome and every finding its two screenshots.

Worked example, from the candidate lists of a two-sample set: `dl.svg` appears in a link on both
samples, named "Download annual report" on page-a and "PDF" on page-b; step 6 shows both links
reaching a PDF download, so the pattern of Understanding example 1 is broken and this is a fail
at 90. Next, `print.svg` appears in a button named "Print receipt" on page-a and "Print invoice"
on page-b;
step 6 shows one printing a receipt and the other an invoice, two functions under the pattern
"Print x", so example 4 applies and no finding is written. The home target `/` carries "Acme home"
on the logo and "Home" in the navigation on both samples: the pair repeats identically on every
sample and example 6 asks only for consistent, not identical, so this goes to the confirmation
queue rather than into an issue.

What the accessibility tree can and cannot show: `snapshot` gives the accessible name assistive
technology announces, so a `name` that differs across samples is a fact and needs no screen reader.
It cannot show whether a `title` tooltip or the look of an icon is what a magnifier user recognises,
so a different icon glyph under the same name stays below 70 and goes to the confirmation queue.
Record `cannot-tell` for a function whose result cannot be established: a control behind a login
without credentials, a component whose only action has a real-world effect, or a state that could
not be reached on both samples.

## Deciding

- Fail (certainty ≥ 90): a target that two samples of one set both link to, named with words that
  share no key term, in a repeated header, navigation or footer ("Contact" / "Get in touch"), with
  the equal target confirmed in step 6 — 95
  ([F31](https://www.w3.org/WAI/WCAG22/Techniques/failures/F31)); search submit buttons that
  produce the same results page, named "Search" on one sample and "Find" on another — 95 (F31
  example 1 and the Understanding's own failure, example 7); the same action named "Save page" on
  one sample and "Save" on another — 90 (F31 example 2); the same icon file in a control with the
  same tried-out result carrying a different `alt`, `aria-label` or computed `name` on two samples
  ("Download annual report" / "PDF") — 90 (Intent: "This consistency extends to the text
  alternatives"); identical visible text on two samples behind different `aria-label` accessible
  names — 90 (Understanding example 8, which also asks for a 2.5.3 finding when the visible text is
  not contained in the name).
- Fail (70–89): a recurring control whose sameness rests on the page context rather than on a
  try-out (an "Add to cart" on one product page and "Buy" on another, both raising the cart count
  in the tree) — 80; two labels for one function where the second only adds words ("Search" /
  "Search the site", "Print" / "Print this page"), the F31 example 2 shape — 80; a label pattern
  broken on one sample ("Download <title>" everywhere and "PDF" once) — 75; "Log in" on one sample
  and "My account" on another, both leading to the login form — 75; two copies of one function
  inside a sample named differently while another sample of the set carries the same function, and
  no two of the three share a key term — 75 (the Understanding's "then all 3 must be consistent");
  a skip link named differently on two samples of the set while both jump to the same landmark — 75.
- Needs confirmation (50–69): two labels whose results were not tried and may differ ("Subscribe" /
  "Sign up" posting to different endpoints) — 60; ask whether they do the same thing. Two
  components in what may be separate sets (a blog sub-domain, a checkout template, another language
  version) — 55; ask who authors them and whether they are one set. A different icon glyph under
  the same name — 55; ask whether the design intends one icon for this function. An icon link and
  an adjacent text link to the same destination named differently, in the same pairing on every
  sample — 55; example 6 asks only that "the link text for these two links need only be consistent,
  not identical", so ask whether the two names read as one identification. A variant that may be a
  pattern ("Download brochure" / "Get the brochure") — 60; ask which wording is intended.
- Pass: every component that recurs on two or more samples of a set with the same result when used
  carries a visible label, an accessible name and, for icons, a text alternative that are identical
  after normalising, or follow one pattern whose only variable part names the specific target or
  function, on every sample and on every copy within a sample.
- Not present: the scope is one web page, or no component recurs on two samples of the same set.
- False positives to avoid: pattern labels ("page 2" / "page 3", "Print receipt" / "Print invoice",
  "Download <title>", a label carrying a live count); one non-text item serving two functions under
  two names (a check mark "approved" here and "included" there, the second Understanding note);
  differences between separate sets (language versions, checkout template, sub-domain, an area
  behind a login with its own template); a difference that exists only inside one page with no copy
  on another sample, which the Understanding calls best practice and not this criterion; case,
  whitespace and trailing punctuation; two link texts that differ because the links lead to
  different pages (the same name for different targets, and a generic "Read more", are 2.4.4); a
  visible label missing from the accessible name (2.5.3) or a missing name or text alternative
  (4.1.2, 1.1.1) when the names that do exist match; a component present on one sample only.

## Reporting

- File under: 3.2.4, one issue per function (the search button, the download icon, the contact
  link), naming every sample that shows each variant; the same template defect across a set is one
  issue. A visible label not contained in the accessible name is 2.5.3; a control without a name is
  4.1.2 and an icon without a text alternative is 1.1.1; a navigation whose order changes between
  pages is 3.2.3; the same link text for different targets is 2.4.4.
- Title patterns: "Search button is 'Search' on one page and 'Find' on another", "Same download
  icon has two different text alternatives", "Contact link is named differently across pages",
  "Same button is announced with different names", "Skip link has a different name on each page"
- Severity: High when the differently named component is the way into a primary task (site search,
  cart, login, main menu button) or when the text alternative of the same icon differs, so screen
  reader users cannot recognise the function they learned; Medium when a repeated header,
  navigation or footer link or button differs, which affects the whole product while the task stays
  possible; Low when the two labels share the key term ("Search" / "Search the site") or the
  component is a minor one on a single template.
- Type: Content when the label, link text or text alternative is editorial (CMS menu labels, alt
  text on a document icon); Technical when the difference comes from code (an `aria-label` in one
  template only, two components built for one function, a hard-coded button text); Design when the
  icon glyph for one function differs between pages.
- Evidence: two screenshots, one per sample, each with the component highlighted, shown side by
  side in the issue; for a name that differs from the visible text, the element screenshot plus the
  tree line carrying the computed name. No GIF: nothing moves.
- Recommendation: use one label, one accessible name and one text alternative for every component
  with the same function across the set
  ([G197](https://www.w3.org/WAI/WCAG22/Techniques/general/G197)), by rendering the component from
  one shared template; keep a pattern where only the target varies ("Download <title>"), and name
  each function separately when one icon serves several. Name the component that is wrong and give
  the wording to use on every page, for example every page submitting its search with
  `<button type="submit">Search</button>`, linking to the contact page with
  `<a href="/contact">Contact</a>` in both header and footer, and naming the document icon
  `<img src="download.svg" alt="Download annual report 2025">` on both samples; the defect is
  [F31](https://www.w3.org/WAI/WCAG22/Techniques/failures/F31).
- Related: 3.2.3 Consistent Navigation (order there, naming here; a header rebuilt per template
  often fails both); 2.5.3 Label in Name (visible text missing from the accessible name; a mismatch
  that also differs across pages is filed under both); 4.1.2 and 1.1.1 (missing names and text
  alternatives, which are recorded there and make a component uncomparable here); 2.4.4 Link
  Purpose (one name for several targets); 3.3.2 Labels or Instructions (a field label that is
  missing or unclear rather than inconsistent).
