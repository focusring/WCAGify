# 2.1.2 No Keyboard Trap

Level A · WCAG 2.0+ · Guideline 2.1 Keyboard Accessible · Group: `keyboard`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#no-keyboard-trap) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#no-keyboard-trap) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-1-2-no-keyboard-trap/) ·
ACT: [80af7b](https://www.w3.org/WAI/standards-guidelines/act/rules/80af7b/),
[a1b64e](https://www.w3.org/WAI/standards-guidelines/act/rules/a1b64e/),
[ebe86a](https://www.w3.org/WAI/standards-guidelines/act/rules/ebe86a/)

## Requirement

> If keyboard focus can be moved to a component of the page using a keyboard interface, then focus
> can be moved away from that component using only a keyboard interface, and, if it requires more
> than unmodified arrow or tab keys or other standard exit methods, the user is advised of the
> method for moving focus away.
>
> Note:
> Since any content that does not meet this success criterion can interfere with a user's ability
> to use the whole page, all content on the web page (whether it is used to meet other success
> criteria or not) must meet this success criterion. See Conformance Requirement 5:
> Non-Interference.

Terms (WCAG 2.2 glossary): **keyboard interface**: "interface used by software to obtain keystroke
input", Note 1: "A keyboard interface allows users to provide keystroke input to programs even if
the native technology does not contain a keyboard", Note 2: "Operation of the application (or parts
of the application) through a keyboard-operated mouse emulator, such as MouseKeys, does not qualify
as operation through a keyboard interface because operation of the program is through its pointing
device interface, not through its keyboard interface." An exit that works only by driving the
pointer with MouseKeys is therefore not an exit; a component on a device without a physical
keyboard that still takes keystroke input is in scope.

WCAG leaves "standard exit methods" open: "This specification does not define what constitutes a
'standard exit method' – this is dependent on the user's hardware, user agent, and operating
system, and as such will require some interpretation from authors and auditors. Generally, in most
environments with a physical keyboard, pressing the Esc key is a commonly used 'standard exit
method', but other platform-specific methods may be available" (Understanding, Intent). The ACT
glossary **standard keyboard navigation** (80af7b, a1b64e, ebe86a) fixes the set this procedure
presses and the behaviour each key owes: "Tab key: Skipping forward between focusable elements",
"Shift+Tab: Skipping backwards between focusable elements", "Arrow keys: Navigate input elements,
e.g. up/down drop down, between radio buttons etc.", "Esc key: Close or cancel, e.g close a modal",
"Enter key: Select or activate the element in focus (same as clicking with mouse)", "Space key:
Select input elements, e.g. drop downs, radio buttons etc." A browser shortcut is not one of them:
"It is not possible to fulfill this expectation by using browser specific shortcuts to return to
the browser UI" (a1b64e Expectation, ebe86a Expectation 3).

**focusable** (ACT glossary; the applicability of all three rules is "any HTML or SVG element that
is focusable"): "An element is focusable if one or both of the following are true: the element is
part of sequential focus navigation; or the element has a tabindex value that is not null.
Exception: Elements that lose focus and do not regain focus during a period of up to 1 second after
gaining focus, without the user interacting with the page the element is on, are not considered
focusable." Note: "The 1 second time span is an arbitrary limit which is not included in WCAG."
`tabindex="-1"` is a tabindex value that is not null, so a script-focusable element is a test
target; an element that hands focus on by itself inside a second is not one (record it for 2.4.3).

**visible** (ebe86a glossary, decides Expectation 1): "Content is considered visible if making it
fully transparent would result in a difference in the pixels rendered for any part of the document
that is currently within the viewport or can be brought into the viewport via scrolling." Help text
parked off-screen is not visible. **included in the accessibility tree** (ebe86a glossary):
"Programmatically hidden elements are removed from the accessibility tree. However, some browsers
will leave focusable elements with an aria-hidden attribute set to true in the accessibility tree.
Because they are hidden, these elements are considered not included in the accessibility tree." A
focusable element under `aria-hidden="true"` is still reached by Tab and can still trap, and help
information under `aria-hidden="true"` does not satisfy Expectation 1.

## In plain terms

Whatever a keyboard user can move focus into, they can move out of again with Tab, Shift+Tab, the
arrows, Esc or another standard key; when a component needs a different key to leave (an editor
that uses Tab to indent, an embedded applet), the page tells the user which key. The Intent names
where this goes wrong: "when multiple formats are combined within a page and rendered using
plug-ins or embedded applications, or when custom components and widgets are not implemented with
keyboard users in mind". Holding focus inside one part of the page is allowed — "for example, when
the user is inside a modal dialog or popover" — "as long as the user knows how to 'untrap' the
focus and leave that component", so a modal may keep Tab cycling inside itself while Esc or a
Close, Cancel or OK button dismisses it. It matters to people who rely on a keyboard interface: a
trap makes everything after it unreachable, third-party embeds included, so all content must meet
it (Conformance Requirement 5).

## Applies when

- Present: `focusables.js` returns a non-empty `order`, or an element with `tabindex="-1"` exists
  that a script can focus (`get count "[tabindex='-1']"` above 0). The ACT applicability is "any
  HTML or SVG element that is focusable", so a focusable node inside an inline `svg` (an SVG `a`,
  or any node carrying `tabindex`) is a target too, as is every entry of `ariaHiddenFocusable`.
  Every focusable element is a test target (80af7b); the ones that hold focus in practice are
  `iframe`, `object`, `embed`, `canvas`, `[contenteditable]`, `role=application|grid|treegrid|tree`,
  code and rich-text editors, date pickers, `dialog`, `[role=dialog]`, `[role=alertdialog]`,
  `[aria-modal]`, cookie overlays and fields that validate on blur. Detect them with the step-1
  `eval` and `structure.js`.
- Not present: `order` is empty and no element carries `tabindex="-1"`, in every state.
  Disabled, `display: none` and `visibility: hidden` elements are not focusable (80af7b
  inapplicable examples 2, 3 and 4).
- Cannot tell: a cross-origin `iframe` that `frame` cannot enter and whose outer walk is
  inconclusive; a plug-in surface that paints outside the DOM; an exit advised only through a
  `title` tooltip or a live-region message. Record `cannot-tell` and queue it for a human.
- Exceptions: none in the text. Restricting focus is not one of them: "There may be times when it's
  appropriate for a web page to restrict focus to a subsection of the content – for example, when
  the user is inside a modal dialog or popover. This does not fail the requirements of this
  criterion, as long as the user knows how to 'untrap' the focus and leave that component"
  (Understanding). The second clause is a way to pass, not an exception: "Keyboard focus is not
  considered trapped when the user can navigate away from a component using only a keyboard
  interface, and if it only requires unmodified arrow or Tab keys or other 'standard exit
  methods'", and "If untrapping focus requires a different method [...] content can still pass this
  criterion provided that the user is advised how they can untrap focus using their keyboard
  interface." The Note widens the scope to third-party content and content not relied upon.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. Nothing in
`.notes/audit/axe/<sample>[--<state>].json` carries a 2.1.2 tag in any state, so the outcome for
this criterion comes entirely from the walk logs of the manual procedure.

## Manual procedure

1. Inventory. Run `focusables.js` and `structure.js`; keep `order` (`index`, `selector`, `name`,
   `visible`, `inAriaHidden`), `ariaHiddenFocusable`, `tabindexPositive`, `clickableNotFocusable`
   and `iframes`, then list the trap-prone components:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/focusables.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
   agent-browser eval --stdin <<'EOF'
   (() => [...document.querySelectorAll('iframe, object, embed, canvas, [contenteditable], ' +
     'dialog, [role=application], [role=grid], [role=treegrid], [role=tree], [role=dialog], ' +
     '[role=alertdialog], [aria-modal], [tabindex="-1"], svg a, svg [tabindex], ' +
     '.monaco-editor, .cm-editor, .ql-editor')]
     .map(e => e.localName + (e.id ? '#' + e.id : '') + ' ' + (e.title || e.src || '')))()
   EOF
   ```

   N counts the `order` entries with `visible: true`; the browser never focuses the others, so
   their absence from a walk is never a trap. Entries of `ariaHiddenFocusable` are reached by Tab
   all the same and are walked with the rest. N = 0 with an empty candidate list records
   `not-present` and ends the procedure. Done when N, the candidate list and the
   `ariaHiddenFocusable` list are in the findings file.

2. Focus logger, written once per session (a helper, not a probe). It prints the focused element as
   a path in `order[].selector` shape plus its name, or `BODY` when focus sits on the document body:

   ```bash
   cat > .notes/audit/recon/focus-logger.js <<'EOF'
   (() => {
     const e = document.activeElement;
     if (!e || e === document.body || e === document.documentElement) return 'BODY';
     const t = n => { if (n.id) return n.localName + '#' + n.id
       const s = [...(n.parentElement?.children ?? [])].filter(x => x.localName === n.localName)
       return n.localName + (s.length > 1 ? ':nth-of-type(' + (s.indexOf(n) + 1) + ')' : '') }
     const name = (e.getAttribute('aria-label') || e.value || e.textContent || '')
       .replace(/\s+/g, ' ').trim().slice(0, 40);
     const flag = (e.closest('[aria-hidden="true"]') ? ' [aria-hidden]' : '') +
       (['iframe', 'object', 'embed'].includes(e.localName) ? ' [focus is inside this frame]' : '');
     return (e.id || !e.parentElement ? '' : t(e.parentElement) + '>') + t(e) +
       ' "' + name + '"' + flag;
   })()
   EOF
   agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   ```

   In the top document `activeElement` stays the `iframe`, `object` or `embed` element for as long
   as focus is anywhere inside it, so that line means "somewhere in the frame" and never "on the
   frame itself"; step 7 enters the frame to place it. Done when the command prints `BODY` or the
   focused element.

3. Forward walk (a1b64e). Its single Expectation: "For each target element, focus can cycle to the
   browser UI by using standard keyboard navigation", with the Note "It is not possible to fulfill
   this expectation by using browser specific shortcuts to return to the browser UI", on the
   assumptions that "the focus order in keyboard navigation is cyclical, not linear" and "the
   Browser UI is part of the focus navigation cycle of the page". Focus `order[0]` and press Tab
   N + 3 times, one logger line per press; on a long page, start two entries before each step-1
   candidate and press Tab 8 times:

   ```bash
   agent-browser focus "<order[0].selector>"
   for i in $(seq 1 <N+3>); do
     agent-browser press Tab; agent-browser wait 300
     agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   done
   ```

   `BODY` after the last entry means focus cycled to the browser UI and everything before it
   escapes forward; a `BODY` earlier in the walk is focus lost to the document (2.4.3), so keep
   pressing. A log that wraps from the last entry to the first with every visible entry seen and no
   `BODY` counts as reaching the browser UI: "Some browsers have settings that will immediately
   cycle focus back to the web document. This fulfills the expectation because focus can cycle to
   the browser UI and the browser UI cycles focus back to the web document" (a1b64e, accessibility
   support). A line that repeats to the end, or a short cycle of lines that repeats while later
   entries of `order` never appear, is a trap candidate (the component: the nearest common ancestor
   of those lines). A trapped log reads like this, `button#btn2` never handing focus on to
   `a#link2`:

   ```text
   1 a#link1 "Link 1"
   2 button#btn1 "Button 1"
   3 button#btn2 "Button 2"
   4 button#btn1 "Button 1"
   5 button#btn2 "Button 2"
   ```

   Confirm each candidate with `focus "<its selector>"`, `wait 1200` and the logger: focus that
   moved on by itself is the ACT 1-second `focusable` exception, not a trap (note it for 2.4.3). A
   candidate that is the last entry of `order` may fail to reproduce, because "the focus may jump
   to the browser UI before the timeout expires, at which point the this.focus() trap cannot
   trigger anymore" (a1b64e failed example 1); start those two entries earlier so that a following
   focusable element exists. Done when the log is saved as `recon/<sample>-tabwalk.txt` and each
   candidate is named with its first press.

4. Backward walk. Focus the last entry of `order` and press Shift+Tab N + 3 times with the same
   logger, saving `recon/<sample>-shifttabwalk.txt`:

   ```bash
   agent-browser focus "<order[N-1].selector>"
   for i in $(seq 1 <N+3>); do
     agent-browser press Shift+Tab; agent-browser wait 300
     agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   done
   ```

   Compare the two logs per candidate. Trapped in both directions is the ≥ 90 fail. One direction
   free is what 80af7b allows while the criterion may not: "This rule only requires navigation in
   one direction (either forward or backward), not both, and not a specific one. It is clear that
   not being able to escape a focus trap in any direction is a failure of Success Criterion 2.1.2
   No keyboard trap. However, it is less clear that being able to escape in only one direction is
   enough to satisfy it." 80af7b passed example 7 is exactly that case — a button that traps
   forward while backward navigation still reaches every element — and the rule passes it "despite
   being recognized as a poor practice in terms of keyboard accessibility". Done when every
   candidate carries "forward: free | trapped" and "backward: free | trapped".

5. Standard exits from inside each candidate, pressing each key of the ACT set and checking the
   behaviour it owes: `focus "<trapping element css>"`, then `press Shift+Tab` three times
   (skipping backwards), `press Escape` (close or cancel), `press ArrowDown` and `press ArrowUp`
   (navigate input elements), and `press Enter` (select or activate) or `press Space` (select input
   elements) only while a Close, Cancel or OK control has focus, each followed by `wait 300` and
   the logger as in step 3. A line outside the component, or `BODY`, is a standard exit: note the
   key and the direction. An editor that consumes Tab shows the same line while
   `get html "<component css>"` shows an inserted tab or indent. Done when each candidate has
   "exits with <key>" or "no standard exit".

6. Advised exit (ebe86a), for exactly the candidates step 5 left with no standard exit — the rule
   applies "to any HTML or SVG element that is focusable where focus cannot cycle to the browser UI
   by using standard keyboard navigation". It has three expectations and all three must hold.

   Expectation 1: "For each target element help information is visible and included in the
   accessibility tree or can be accessed from within the keyboard trap", with the Note "As per WCAG
   2.0 Success Criterion 2.1.1 Keyboard the help information should be accessible through a
   keyboard interface." Look in three places: `snapshot` for the text before the component,
   `snapshot -s "<component css>"` for text inside it, and `focus "<component css>"`, `wait 500`,
   `snapshot` again for a hint that appears on focus (the Understanding's rich text editor shows
   one only then). Help that is reached from inside the trap counts even when it is not on screen
   yet: ebe86a passed example 3 puts it behind a "help" link inside the trap that exposes the
   instructions once activated. Scan the page text when the snapshot is large:

   ```bash
   agent-browser get text "body" | grep -inE "press|hold|key|toets|ctrl|alt|cmd|option|esc|f10"
   ```

   Expectation 2: "The help information explains how to cycle to the browser UI, or on how to get
   to a point from where it is possible to cycle to the browser UI, using standard keyboard
   navigation." "Press Ctrl+M to Exit" does (ebe86a passed examples 1 and 2); "Go to the next
   element" does not (ebe86a failed example 2).

   Expectation 3: "For each target element focus can cycle to the browser UI by using the method
   advised in the help information", Note: "Cycling back to the browser UI can be done both by
   moving forward through the tab order and by moving backwards. It is not possible to fulfill this
   expectation by using browser specific shortcuts to return to the browser UI." Press the advised
   key from inside and log where focus lands: `focus "<component css>"`, `press Control+m`,
   `wait 300`, then the logger. The Understanding's WYSIWYG editor advises `Alt+F10` /
   `Option+F10` "to move focus back out of the area and to the editor toolbar", so `press Alt+F10`
   is the press for that pattern; an advised key that leaves focus inside is ebe86a failed
   example 3.

   The accessibility tree cannot show whether a screen reader speaks a `title` tooltip or a
   live-region hint (`structure.js` `titleAttrs`, `liveRegions`): record `cannot-tell` for an exit
   advised only that way. Done when each candidate carries a verdict for all three expectations.

7. Frames and embedded formats ([F10](https://www.w3.org/WAI/WCAG22/Techniques/failures/F10): the
   failure is content the user "can enter [...] using the keyboard, but cannot exit [...] using the
   keyboard", and its test asks that focus move out of the plug-in content "without closing the
   user agent or restarting the system"). For each entry of `iframes`, and each `object` or `embed`
   of step 1, that the outer log holds: record the source with `get attr "<iframe css>" src`, then
   `frame "<iframe css>"`, `press Tab`, `wait 300` and the logger until the inner log wraps or
   repeats, then `frame main` and confirm that a later `order` entry follows the frame in the outer
   log, forward or backward. A cross-origin frame that `frame` refuses leaves the outer log as the
   only evidence: a frame line that holds both walks to their end is the finding, a frame line the
   walks pass through is not. A native `alert()` that reopens on every blur (`dialog status`,
   `dialog dismiss`) traps the same way. Done when every frame and embed has "focus passes
   through", "focus passes back in one direction only" or a candidate line.

8. Dialogs, menus and overlays, per state in `recon/<sample>-states.md`. Open each with the
   keyboard (`focus "<trigger css>"`, `press Enter`); an overlay that opens by itself (cookie
   dialog) is the initial state. Log where focus went, Tab through the dialog with the logger —
   cycling inside a modal is allowed, and "depending on implementation, the focus cycle might still
   include user agent controls" (Understanding) — then `press Escape`, `wait 300`, the logger and
   `is visible "<dialog css>"`: a dialog that is hidden, or gone from the DOM so the command
   errors, with focus outside it is an exit. Otherwise reopen, Tab to a Close, Cancel or OK
   control in the log, `press Enter` and check again; a close control under
   `clickableNotFocusable` (`focusables.js` in the open state) is the cause. The Understanding's
   passing modal is dismissed "by activating the 'Cancel' button, the 'OK' button, or the Esc key",
   so any one of the three is enough. Repeat steps 3 and 4 for every state whose focusable set
   changes. Done when every state has its exit recorded.

9. Fields that validate on blur. For a field that repeats in the log while empty, take its
   `forms.js` entry (`selector`, `required`, `ariaInvalid`, and the `visibleErrors` whose
   `forField` points at it), `fill` it with a valid value and walk over it again. A field that
   still holds focus, or releases it only once the value is valid, is a candidate: an error message
   is not a method for moving focus away, and its text is judged against ebe86a Expectation 2 like
   any other help information. Done when each such field has "releases with Tab" or a candidate
   line.

10. Evidence for every candidate that fails: focus the entry two before the trap, then
    `record start .notes/audit/evidence/<sample>-2.1.2-<slug>.webm`, `press Tab` three times with
    `wait 300` between, `record stop`, `highlight "<component css>"` and
    `screenshot .notes/audit/evidence/<sample>-2.1.2-<slug>.png`. For a missing or unusable
    instruction, add `focus "<component css>"`, `wait 500` and
    `screenshot "<component css>" .notes/audit/evidence/<sample>-2.1.2-<slug>-hint.png`, so the
    shot shows what the user is given at the moment of entry. Done when the recording shows focus
    cycling inside the component and the screenshots are saved.

11. Outcome per target (80af7b, the composite rule). Its Expectation: "For each test target, the
    outcome of at least one of the following rules is 'passed'" — a1b64e (steps 3 and 4) or ebe86a
    (step 6). Record per candidate which of the two passed. The mapping is not symmetric: "Any
    failed outcomes: success criterion is not satisfied", while "All passed outcomes: success
    criterion needs further testing", so a pass here is a pass for the sample only together with
    the one-direction judgement of step 4. The same failure settles Non-Interference as well: "Any
    failed outcomes: WCAG 2 conformance requirement is not satisfied". Done when every candidate
    has a passed or failed line and the sample's outcome is written to the findings file.

## Deciding

- Fail (certainty ≥ 90): both walks stay on one element or cycle inside the component, Escape, the
  arrows and Enter/Space on its controls leave focus inside, and no instruction exists (a1b64e and
  ebe86a both fail, so 80af7b fails) — 95; a component that can only be left by closing the tab or
  restarting the browser (F10) — 95; a modal or overlay that cycles Tab, ignores Escape and has no
  focusable control that closes it — 95; a control that takes focus back on blur so that Tab and
  Shift+Tab both return to it — 95; an advised method that, pressed, leaves focus inside (ebe86a
  Expectation 3, failed example 3) — 90; an `iframe`, `object` or `embed` whose inner controls
  never hand focus back to the main document either way (step 7) — 90; an exit that works only
  through a browser shortcut ("It is not possible to fulfill this expectation by using browser
  specific shortcuts to return to the browser UI", a1b64e) — 90; a native `alert()` that reopens on
  blur — 90.
- Fail (70–89): a Tab-consuming editor or widget that Shift+Tab and Escape leave inside, with an
  instruction a keyboard user cannot reach from inside the trap or that is not in the tree (ebe86a
  Expectation 1) — 80; an instruction that names no method ("Go to the next element", ebe86a failed
  example 2) — 80; an instruction present in the DOM but not visible, off-screen or fully
  transparent, and not reachable from inside the trap (ebe86a "visible") — 80; an instruction whose
  only copy sits under `aria-hidden="true"`, which the ACT glossary counts as not included in the
  accessibility tree — 78; a field that releases focus only after a valid value is typed, with an
  error message but no method — 80; a trapping element that is itself in `ariaHiddenFocusable`,
  reached by Tab yet absent from the tree, so no help can be attached to it — 78; one `iframe` line
  holding both walks to their end while `frame` could not enter it — 75.
- Needs confirmation (50–69): focus escapes in one direction only (Shift+Tab leaves, Tab cycles):
  80af7b passes it and its background note leaves the criterion open ("it is less clear that being
  able to escape in only one direction is enough to satisfy it") — 60; ask "must the <component>
  also release focus forward?". An instruction given only as a `title` tooltip or a live-region
  message the tree cannot confirm is announced — 55; ask for a screen-reader run. An advised exit
  key that the operating system or the browser may swallow before the page sees it (a function key,
  a single unmodified letter) — 55; ask which platforms the product supports.
- Pass: every visible `order` entry appears in the forward log before `BODY` (or it wraps fully)
  in the initial state and in every state; every dialog closes with Escape or a focusable Close,
  Cancel or OK control and focus lands outside it; every frame hands focus back; every component
  that consumes Tab leaves with a standard key, or with an advised method that is visible or
  reachable from inside the trap, names the key, and moves focus out when pressed; no field takes
  focus back.
- Not present: nothing on the sample can receive focus in any state.
- False positives to avoid: a modal that wraps Tab inside itself while Escape or a focusable
  Close, Cancel or OK control leaves it (Understanding "A modal dialog box", a1b64e passed example
  4); the focus sentinels of that example, off-screen links under `aria-hidden="true"` that bounce
  focus to the top or the bottom of the dialog — they keep the modal usable and are not the trap;
  radio groups, `select`, tab lists and menus that move with arrows and leave with Tab; a widget
  whose controls are simply part of the page tab order (Understanding "A calendar widget"); a `div`
  with `tabindex="1"` or `tabindex="-1"` that holds focus once and releases it (80af7b passed
  examples 2 and 3); a `BODY` line in the middle of the log (focus lost to the document: 2.4.3); an
  `order` entry with `visible: false`, which the browser never focuses; an element that loses focus
  by itself within a second and does not regain it (the ACT `focusable` exception); an element the
  walk never reaches (2.1.1 or 2.4.3) and a positive `tabindex` jump (2.4.3); two lines that look
  alike (compare the whole path); a native `alert()` shown once; an on-focus hint naming the exit
  key.

## Reporting

- File under: 2.1.2 for every trap, including one inside third-party content (name Conformance
  Requirement 5 in the body when the trapping content sits outside the audited product); a dialog
  whose only closing control is not focusable is one issue here that names 2.1.1 as the cause, and
  help information that exists but cannot be reached with the keyboard is 2.1.1 too (ebe86a
  Expectation 1 note) and is named in the 2.1.2 body. A component the user cannot enter at all is
  2.1.1; focus that drops or skips is 2.4.3. One issue per trapping component; the same widget or
  overlay on several samples is one issue naming them.
- Title patterns: "Keyboard focus is trapped in the <component>", "The <dialog> cannot be closed
  with the keyboard", "The <editor> captures Tab without a way out", "The <field> takes focus
  back until it is filled in", "The embedded <player> keeps keyboard focus", "There is no
  instruction for leaving the <component>"
- Severity: High when the trap sits in the page's Tab order or opens by itself (cookie dialog,
  splash), so every keyboard user hits it and everything after it is unreachable, and High as well
  when the only way out is closing the tab or restarting the browser; Medium when it is entered
  only by choosing an optional widget, or when a standard exit exists in one direction only, so the
  task is still finishable but markedly harder; Low when a working exit exists and only the
  instruction is missing or misplaced.
- Type: Technical (focus handling in script, dialog close handling, an embedded format); Content
  when the exit works and only the instruction text is missing or wrong.
- Evidence: the recording of the Tab presses with the focus ring cycling inside the component,
  plus the screenshot with `highlight` on the component; for a missing instruction, the on-focus
  screenshot of the component showing what the user is given at the moment of entry; quote the walk
  log lines of both directions in the body, trimmed to the repeating cycle.
- Recommendation: [G21](https://www.w3.org/WAI/WCAG22/Techniques/general/G21) offers three
  mechanisms, in this order of preference: let the key that advances focus "exit the subset of the
  content after it reaches the final navigation location"; or provide "a keyboard function to move
  the focus out of the subset of the content. Be sure to document the feature in an accessible
  manner within the subset"; or, where the technology has a native "move to parent" command,
  document "that command before the user enters the plug-in so they know how to get out again". In
  practice: no `preventDefault` on Tab and no `focus()` in a `blur` handler; close dialogs on
  Escape and through a focusable Close, Cancel or OK button, then return focus to the trigger; give
  an editor that needs Tab a documented exit key shown when it receives focus — the Understanding's
  editor uses Alt+F10 / Option+F10 to reach the toolbar, and its puzzle applet repeats the exit
  keystroke "prior to the applet as well as within the applet itself". Where the embedded format
  itself keeps focus, G21 leaves two ways out: "build such a capability into their content or not
  use the technology" ([F10](https://www.w3.org/WAI/WCAG22/Techniques/failures/F10)). Example:

  ```js
  // Escape closes, and focus goes back to whatever opened the dialog
  dialog.addEventListener('keydown', (e) => {
    if (e.key === 'Escape') {
      dialog.close()
      trigger.focus()
    }
  })
  // An editor that uses Tab to indent: advise the exit key on focus and implement it (G21)
  editor.addEventListener('focus', () => {
    hint.textContent = 'Press Alt+F10 to move focus to the toolbar'
  })
  editor.addEventListener('keydown', (e) => {
    if (e.altKey && e.key === 'F10') {
      e.preventDefault()
      toolbar.focus()
    }
  })
  ```
