# 2.4.3 Focus Order

Level A · WCAG 2.0+ · Guideline 2.4 Navigable · Group: `keyboard`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#focus-order) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#focus-order) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-4-3-focus-order/) ·
ACT: none mapped to this criterion

## Requirement

> If a web page can be navigated sequentially and the navigation sequences affect meaning or
> operation, focusable components receive focus in an order that preserves meaning and operability.

Terms (WCAG 2.2 glossary): **navigated sequentially**: "navigated in the order defined for
advancing focus (from one element to the next) using a keyboard interface". The order under test is
the one `press Tab` and `press Shift+Tab` produce — not the reading order of the tree, not arrow-key
movement inside a widget, not the order a mouse would take. A **keyboard interface** is an
"interface used by software to obtain keystroke input", and "operation of the application (or parts
of the application) through a keyboard-operated mouse emulator, such as MouseKeys, does not qualify
as operation through a keyboard interface", so the presses of the walk logs are the only instrument.

**web page**: "a non-embedded resource obtained from a single URI using HTTP plus any other
resources that are used in the rendering or intended to be rendered together with it by a user
agent", Example 2: "A web mail program built using Asynchronous JavaScript and XML (AJAX). The
program lives entirely at http://example.com/mail, but includes an inbox, a contacts area and a
calendar. Links or buttons are provided that cause the inbox, contacts, or calendar to display, but
do not change the URI of the page as a whole." Every state in `recon/<sample>-states.md` is that
same web page: judge each state's sequence here and name the state in the finding, never split it
off as another sample.

## In plain terms

Tab and Shift+Tab move through the page's links, controls and widgets in a sequence set by the
source order, `tabindex` and scripts. That sequence has to keep the relationships the content shows:
one form section's fields before the next section's, a dialog or menu right after the button that
opened it and focus back on that button when it closes, no control focused twice, no focus vanishing
into hidden content. It need not copy the layout: any one order that preserves meaning and operation
is enough, and arrow keys inside a tree, menu or tab list are not sequential navigation. It assesses
the order interactive elements receive focus, not the reading order of the text (1.3.2): a page
whose text reads correctly can still tab wrongly. It matters to keyboard-only users, to people who
become disoriented when tabbing lands somewhere unexpected, and to magnifier users, of whom the
Understanding says "only a small portion of the page may be visible" and "such a user may interpret
a field in the wrong context if the focus order is not logical".

## Applies when

- Present: a sample state with two or more focusable components (step 1's `count` is two or more), a
  trigger of step 1 that opens a dialog, menu, popover or expanded region with controls, or a script
  that moves or removes the focused element; every state in `recon/<sample>-states.md` counts.
- Not present: `count` is below two in every state and no trigger of step 1 opens anything: there is
  no sequence to preserve.
- Cannot tell: a PDF sample, which the browser session cannot tab through — record `cannot-tell` and
  queue the PDF3 questions of the preamble; and any state the keyboard cannot reach (a widget that
  only opens on hover, a flow behind a login the audit has no account for), named with what blocked
  it.
- Exceptions: none normative. The criterion is conditional instead — it bites only where the page
  "can be navigated sequentially" and "the navigation sequences affect meaning or operation" — and
  the Understanding's notes narrow it further, each below.
- Where the sequence comes from: "The way that sequential navigation order is determined in web
  content is defined by the technology of the content. [...] If no scripting or tabindex attributes
  are used, the navigation order is the order that components appear in the content stream." So in
  plain HTML the source order is the finding; `tabindex` and scripted `focus()` are the two things
  that move it away from the source.
- More than one order may be right: "There may be different orders that reflect logical
  relationships in the content. For example, moving through components in a table one row at a time
  or one column at a time both reflect the logical relationships in the content. Either order may
  satisfy this success criterion." And: "If there is more than one order that preserves meaning and
  operability, only one of them needs to be provided." Never report an order merely because another
  order would read better.
- Not the layout: "Focus order does not necessarily need to follow the visual layout of the web
  page, as long as the order in which elements receive focus is logical, and the hierarchy and
  relationship of content implied by the visual presentation is preserved." The second half is the
  test: a departure from the layout fails only where it breaks a hierarchy or relationship the
  layout implies.
- Independent columns: "in a two-column layout, the assumption in western left-to-right systems may
  be that focus moves through the elements in the left-hand column first, from the top to the bottom
  of the column, and then proceed to the right-hand column. However, if the two columns are
  independent of each other, and meaning/operation are not affected, it is not a failure if elements
  in the right-hand column receive focus first, followed by the elements in the left-hand column."
  The best-practice sentence that follows ("make sure the focus order reinforces the reading order
  implied by the visual layout") is advice, not a requirement: it never carries a fail on its own.
- Not the reading order: "The focus order may not be identical to the programmatically determined
  reading order (see Success Criterion 1.3.2 Meaningful Sequence) as long as the user can still
  understand and operate the web page. Since there may be several possible logical reading orders
  for the content, the focus order may match any of them." A mismatch between `snapshot -i` order
  and the walk log is a question, not a verdict.
- Arrow keys: "An example of keyboard navigation that is not the sequential navigation addressed by
  this success criterion is using arrow key navigation to traverse a tree component." Items a node
  expands or collapses "are added or removed from the navigation sequence" — a tree, menu bar, tab
  list, radio group, listbox or grid that holds one tab stop and moves an inner roving focus with
  arrows is correct, and its inner order belongs to 2.1.1.
- Focusable static content, the Understanding's note, verbatim: "This requirement does not specify
  what should or should not receive focus, but rather assesses the order in which elements receive
  focus. This success criterion does not prohibit making non-operable content (e.g., static text)
  focusable, or programmatically moving focus to such content. However, it is a failure of Focus
  Order if items receive focus in an order that impedes the meaning or operation of content, or
  creates confusing or illogical focus orders — for example, a control appearing to receive focus
  multiple times due to the use of nested focusable elements", illustrated with:

  ```html
  <div tabindex="0"><button>...</button></div>
  ```

  So `tabindex="0"` on a heading, a card or a paragraph is not by itself the finding; the extra
  press it costs on a wrapper around a control is.

## Manual procedure

Default state first, then every state in `recon/<sample>-states.md`. The 2.1.2 step 3 Tab walk log
(`recon/<sample>-tabwalk.txt`) and logger (`.notes/audit/recon/focus-logger.js`) are the ground
truth; produce them first when missing. `snapshot -i` lists the interactive elements in the
programmatic reading order a screen reader follows; the logger shows where keyboard focus is.
Neither shows whether two regions are related by intent: that goes to the confirmation queue. A PDF
sample cannot be tabbed through: record `cannot-tell`, and queue it with the three PDF3 questions —
is the page's Tab Order set to "Use Document Structure" ("for tagged documents, moves in the tag
order specified by the authoring application"), rather than "Unspecified", under which "form fields
are tabbed through first, followed by links and then comments ordered by row"; are any form fields
"missing from the tagged content"; are any "in the wrong location in the PDF content; e.g., at the
end of non-interactive content" ([PDF3](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF3)).

1. Inventory the sequence. Run `focusables.js`, save it as `recon/<sample>-focusables.json` and
   keep `order` (`index`, `selector`, `tag`, `role`, `name`, `tabindex`, `visible`, `box`),
   `tabindexPositive` and `ariaHiddenFocusable`; run `structure.js` for `landmarks` and
   `skipLinks`. Then flag candidates in page:

   ```bash
   agent-browser eval --stdin <<'EOF' > .notes/audit/recon/<sample>-2.4.3-seq.json
   (() => {
     const t = n => n.localName + (n.id ? '#' + n.id : '') +
       (!n.id && n.classList[0] ? '.' + n.classList[0] : '') +
       ' "' + (n.textContent || n.value || '').replace(/\s+/g, ' ').trim().slice(0, 30) + '"';
     const all = [...document.querySelectorAll('a[href],area[href],button,input,select,' +
       'textarea,summary,iframe,audio[controls],video[controls],[contenteditable="true"],' +
       '[tabindex]')].filter(e => !e.disabled && e.tabIndex >= 0 && e.getClientRects().length &&
       !e.closest('[inert]') && getComputedStyle(e).visibility !== 'hidden');
     const seq = [...all.filter(e => e.tabIndex > 0).sort((a, b) => a.tabIndex - b.tabIndex),
       ...all.filter(e => e.tabIndex === 0)];
     const jumps = [];
     seq.forEach((e, i) => { if (!i) return;
       const r = e.getBoundingClientRect(), p = seq[i - 1].getBoundingClientRect();
       if (!r.width || !p.width) return;
       const up = r.bottom <= p.top, left = !up && r.top < p.bottom && r.right <= p.left;
       if (up || left) jumps.push({ press: i, from: t(seq[i - 1]), to: t(e), dir: up ?
         'up ' + Math.round(p.y - r.y) + 'px' : 'left ' + Math.round(p.x - r.x) + 'px' }) });
     return { count: seq.length, jumps: jumps.slice(0, 40),
       positive: seq.filter(e => e.tabIndex > 0).map(e => t(e) + ' tabindex=' + e.tabIndex),
       demoted: seq.filter(e => e.tabIndex === 0 && all.some(o => o.tabIndex > 0 &&
         (e.compareDocumentPosition(o) & Node.DOCUMENT_POSITION_FOLLOWING))).map(t),
       nested: seq.filter(e => seq.some(o => o !== e && e.contains(o))).map(t),
       triggers: seq.filter(e => e.matches('[aria-haspopup],[aria-expanded],[aria-controls],' +
         '[popovertarget],[commandfor],[data-toggle],[data-modal]')).map(e => t(e) +
         ['aria-haspopup', 'aria-expanded', 'aria-controls'].filter(a => e.hasAttribute(a))
         .map(a => ' ' + a.slice(5) + '=' + e.getAttribute(a)).join('')) };
   })()
   EOF
   ```

   The ordering this models is the one [C27](https://www.w3.org/WAI/WCAG22/Techniques/css/C27)
   states: "A tabindex of 0 makes an element focusable, but adds it to the focus order in the order
   of source elements. The focus order will follow positive values of tabindex in ascending order."
   Equal positive values keep source order (the sort is stable). `jumps` lists every press that
   moves up or left on the page, `nested` a focusable inside a focusable, `demoted` every ordinary
   control the page puts before a positive-`tabindex` control and the sequence therefore reaches
   last, `triggers` every opener; every label carries the element's text, as the logger's lines do,
   so a press in the walk log matches an entry here. Add the buttons in `snapshot -i` that open a
   dialog or menu without those attributes (Log in, Filter, Menu). Done when the findings file
   lists them all and `recon/<sample>-2.4.3-seq.json` holds the run.

2. Forward walk. Read `recon/<sample>-tabwalk.txt` beside `snapshot -i` and a full-page screenshot
   (`screenshot .notes/audit/evidence/<sample>-2.4.3-layout.png --full`). Apply
   [G59](https://www.w3.org/WAI/WCAG22/Techniques/general/G59)'s three checks in order: determine
   the order of the interactive elements in the content, determine their logical order, check the
   two are the same. G59's own worked example is the yardstick for grouped content: "A form contains
   two, side-by-side sections of information. One section contains information about an applicant;
   the other section contains information about the applicant's spouse. All the interactive elements
   in the applicant section receive focus before any of the elements in the spouse section. The
   elements in each section receive focus in the reading order of that section." The Understanding's
   failing counterpart is the shape to match against: a form with a marketing-data section (name,
   street address, city, state or province, postal code) and a newsletter section of checkboxes,
   where "the tab order for the form skips between fields in different sections of the form, so that
   focus moves from the name field to a checkbox, then to the street address, then to another
   checkbox". For each `jumps` and `positive` entry, find the press in the log and judge what it
   crosses: a relationship the content shows (a field of one group between fields of another, a
   submit button before its fields, a menu item between page content) or independent regions (the
   sidebar before the main column). A `nested` entry shows as two consecutive log lines for one
   control; a skip link first and navigation before the main content are in order. Done when every
   jump is "crosses a relationship", "independent regions" or "in order" and every nested entry has
   its two presses.

3. Backward walk. `focus` the last `order` entry with `visible: true` and check with the logger that
   focus landed there (`focus` on an entry no Tab reaches reports success while the logger prints
   `BODY`: step back one). Then `press Shift+Tab` step 1's `count` + 3 times with `wait 300` and the
   logger after each; save the lines as `recon/<sample>-tabwalk-back.txt`. A sound sequence mirrors:
   an element in one direction only, or a run in a different order, is a candidate (positive
   `tabindex` and script `focus()` calls are the usual causes). Done when the two logs are "mirror"
   or every difference has its press number.

4. Hidden stops. For each `order` entry with `visible: false` or a `box` outside the page (`x + w
<= 0`, `y + h <= 0`): `focus` the previous `visible: true` entry, `press Tab`, the logger,
   `screenshot` the page. A logger line other than that entry means Tab skips it and it is no stop
   — controls in a closed dialog or menu sit in `order` but are `display: none`. A line on it with
   the entry in the screenshot is in order: a skip link parked at `y: -40` until `:focus` is the
   common case. A line on it with nothing to see is a stop the user cannot find (closed mobile
   menu, off-screen slide, collapsed panel). `ariaHiddenFocusable` goes to 4.1.2. Done when each
   entry has "not in the sequence", "visible on focus" or "hidden in <region>, N presses".

5. Dialogs, menus and popovers ([F85](https://www.w3.org/WAI/WCAG22/Techniques/failures/F85)).
   F85 applies "for each menu or dialog on a web page that is opened via a trigger control", in all
   technologies. For every trigger that opens a container shown in `snapshot -i` as `dialog`,
   `alertdialog`, `menu` or `listbox`, or a region with `aria-modal`:

   ```bash
   agent-browser focus "<trigger>"
   agent-browser press Enter; agent-browser wait 500
   agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   agent-browser press Tab; agent-browser wait 300
   agent-browser eval --stdin < .notes/audit/recon/focus-logger.js
   agent-browser snapshot -i
   ```

   F85 step 1 has two points and needs one of them: "Check whether focus has been set to the menu,
   dialog, or a logical focusable descendent of the widget" — the container itself, its first field,
   its close button — and "If not, check whether moving the focus forward once in the sequential
   navigation order puts focus in the menu or dialog". "If both points under step 1 are false, then
   this failure condition applies and the content fails this success criterion": neither the first
   logger line nor the second is in the widget.

   F85 step 2 has two points as well. Close the widget once with a control in it — "activate a
   control in the menu or dialog that causes it to close. This could be a cancel or delete button or
   another action that causes changes to the page and at the same time closes the menu or dialog"
   (`focus` the Close, Cancel, OK or Delete control, `press Enter`) — then `wait 300` and the
   logger. Point one: "check whether keyboard focus is put back on the trigger control". Point two
   applies only when the action removed the trigger: "if the trigger control itself was removed as
   a result of the activation, check if the focus has been put on the interactive element
   immediately preceding or following the removed trigger control, or wherever is logical". "If
   both points under step 2 are false, then this failure condition applies": `BODY`, or the start
   of the page, is the fail. Close it a second time with `press Escape`, which F85's procedure does
   not name but its note treats as dismissal — "Dismissing a dialog or menu means to close it
   without taking any action on it. [...] A user dismisses the dialog by either pressing a 'close'
   button or using the Escape key" — and record the logger line for that route too.

   Recognise the two F85 examples: a dialog "marked up at the end of the DOM" with no script to move
   focus, so "the user will need to tab through the rest of the web page before they can interact
   with the dialog"; and a menu that on dismissal is "removed or hidden from the web page and focus
   is set to the document", so "the user must tab from the beginning of the navigation sequence to
   reach the point from which the menu was opened". Count the presses in the log to name either.

   Check whether the container is a native modal, which settles most of this in the browser:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => [...document.querySelectorAll('dialog')].map(d => ({
     id: d.id || d.className || d.localName, open: d.open, modal: d.matches(':modal'),
     first: (d.querySelector('a[href],button,input,select,textarea,[tabindex]') || {}).outerHTML
       ?.slice(0, 60) })))()
   EOF
   ```

   For `modal: true` ([H102](https://www.w3.org/WAI/WCAG22/Techniques/html/H102), `showModal()`)
   the browser handles "keyboard focus is moved to the newly-opened modal dialog", "keyboard focus
   returns to the invoking element (assuming the element is still on the page) when the modal dialog
   is closed", "keyboard focus is limited to the contents of the modal dialog and the browser's
   chrome", inertness of the rest and "the use of the Escape key to close the modal dialog": confirm
   with the two logger lines and record a pass rather than hunting further. H102 also fixes which
   control gets the first line: "the browser automatically sets focus to the first focusable element
   in the dialog's DOM", which may not be the visually first — in its example the close button "is
   visibly before the h1" but "is the last item in the dialog's DOM", so the `h1[tabindex="-1"]`
   takes focus. A `first` that is a logical descendent is in order whatever the layout says.

   For a scripted modal (`aria-modal="true"`, `inert` on the rest): with it open, `press Tab` M + 2
   times (M = its focusables) with the logger; a line on the page behind it is a candidate, `BODY`
   is the browser UI. A consent dialog shown on load has no trigger: `reload`,
   `wait --load networkidle`, `press Tab` and the logger three times; it has focus or its controls
   are the first stops. Done when each trigger has "focus on open", "Tab enters", "focus on close
   (control)", "focus on close (Escape)" and "modal contained" recorded.

6. Revealed and inserted content
   ([SCR26](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR26)). SCR26 places
   inserted elements "into the DOM immediately following the element that was activated to trigger
   the script", so that "focus remains on the activated element and the new content, inserted after
   it, becomes the next thing in both the tab order and screen-reader reading order"; its own test
   is that the trigger is a link or a button and that "the dialog is next in the DOM". With the
   panels of the state open, count the stops between each trigger and its panel before walking:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const sel = 'a[href],button,input,select,textarea,summary,[tabindex]';
     const f = [...document.querySelectorAll(sel)].filter(e => e.tabIndex >= 0 &&
       e.getClientRects().length);
     return [...document.querySelectorAll('[aria-controls]')].map(tr => {
       const p = document.getElementById(tr.getAttribute('aria-controls'));
       const label = (tr.textContent || tr.value || '').replace(/\s+/g, ' ').trim().slice(0, 30);
       if (!p) return { trigger: label, panel: 'not found by id' };
       const i = f.indexOf(tr), j = f.findIndex(e => p === e || p.contains(e));
       if (i < 0) return { trigger: label, panel: 'trigger is not a tab stop' };
       return { trigger: label, expanded: tr.getAttribute('aria-expanded'),
         between: j < 0 ? 'no focusable control in the panel' : j - i - 1 };
     });
   })()
   EOF
   ```

   `between: 0` is SCR26 satisfied — the panel's first control is the next stop. A positive number
   is that many stops in between; a negative number puts the panel before its trigger; `no
focusable control in the panel` on a panel that is still closed is not a finding, so open it and
   re-run; `not found by id` covers a multi-id `aria-controls` and `trigger is not a tab stop`
   sends the trigger to 2.1.1, both checked by hand. Then confirm in the browser: for
   each trigger with `aria-expanded` and no dialog role (accordion, disclosure, filter panel) and
   each action that inserts controls (add a row, an "added to basket" panel, inline errors with
   links): `focus` the trigger, `press Enter`, `wait 500`, `press Tab`, the logger: the line is the
   first control of the revealed or inserted region; elsewhere means the region sits at another
   point of the sequence. SCR26 "works for synchronous updates"; for an asynchronous insertion "an
   additional technique is needed to inform the assistive technology that the asynchronous content
   has been inserted", which is 4.1.3, not this criterion. Skip link and in-page anchors: `focus`
   the link, `press Enter`, `wait 300`, `press Tab`, the logger: the first control inside the target
   region; a line at the top of the page means the anchor did not move the sequence start. A control
   that reorders content ([SCR27](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR27)
   up/down menus, drag-and-drop with a keyboard alternative): `press Enter` on it, `wait 500`, the
   logger, and re-run step 1 — SCR27 reorders "in the Document Object Model (DOM), not just
   visually" and sets "focus back on the menu item which launched the whole thing", so a new `seq`
   that matches the new visual order with focus still on the control is the pass. Done when each
   trigger, action and anchor has "next stop: <where>".

7. States and evidence. Repeat steps 1 to 4 in each state of `recon/<sample>-states.md` (menu open,
   dialog open, expanded, error state), opening it with the keyboard (`focus "<trigger>"`,
   `press Enter`). For every fail:
   `record start .notes/audit/evidence/<sample>-2.4.3-<slug>.webm`, `focus` the `order` entry two
   before the defect (for a dialog: `focus "<trigger>"`, `press Enter`), then `press Tab` and
   `wait 400` three times, `record stop`; then `highlight "<selector of the out-of-place stop>"`
   and `screenshot .notes/audit/evidence/<sample>-2.4.3-<slug>.png`. For a positive-`tabindex`
   defect add the markup with `get html "<selector>"` and for the values
   `get attr "<selector>" tabindex`. Done when every fail has the recording, the annotated
   screenshot and its press numbers in the walk log.

## Deciding

- Fail (certainty ≥ 90): positive `tabindex` whose ascending order interleaves related controls (a
  field of one section between fields of another: the Understanding failing form) or runs related
  links out of content order ([F44](https://www.w3.org/WAI/WCAG22/Techniques/failures/F44)
  Example 1, where `tabindex` 1, 4, 3, 2 on four list links makes the walk "Homepage, chapter 3,
  chapter 2, chapter 1") — 95; a dialog or menu opened by keyboard where neither the trigger's Enter
  nor the next Tab puts focus on or in it (F85 step 1, both points false) — 95; a dialog or menu
  closed with one of its controls that leaves focus on `BODY` or at the start of the page (F85
  step 2, both points false) — 95, the same after Escape — 90; a focusable wrapper around a
  focusable control, one control taking two presses (Understanding note,
  `<div tabindex="0"><button>`) — 90; a control the content places before a positive-`tabindex`
  control that the sequence reaches only after every positive value (F44 Example 2, step 1's
  `demoted`) — 90.
- Fail (70–89): a walk that crosses a relationship shown visually or in the tree without
  `tabindex` (fields out of group order, a menu item between page content, a submit before its
  fields) — 85; a dialog marked up at the end of the DOM that the walk reaches only after the rest
  of the page while it is shown over the content (F85 Example 1) — 85; Tab leaving an open modal for
  the page behind it — 80; revealed or inserted controls that are not the next stops after their
  trigger (step 6 `between` above 0, confirmed by the logger) — 80; a stop Tab reaches inside a
  region the state hides, visible neither on focus nor after scroll — 80; focus on `BODY` after an
  action removed the focused control outside a dialog or menu — 80; a load-time consent dialog that
  blocks the page and is reached only after the page's stops — 80; a backward walk that is not the
  mirror of the forward one — 75; a skip link or in-page link after which Tab restarts at the top —
  75; a reorder control whose new order shows visually while step 1's `seq` is unchanged (SCR27
  applied in CSS only) — 75.
- Needs confirmation (50–69): an order that differs from the layout between regions that may be
  independent (right column first, cards column-wise) — 55: ask whether the regions depend on each
  other; a focusable static element (`tabindex="0"` on a heading) that blocks nothing — 50: ask
  whether it confuses; focus after a removal on an unexpected neighbour — 55: ask which control is
  the logical one there; a PDF sample — 55: ask the three PDF3 questions of the preamble and record
  `cannot-tell` until they are answered.
- Pass: in every state the forward walk follows the relationships the content shows, the backward
  walk mirrors it, every stop is visible once focused, every dialog, menu and popover takes focus on
  open or the next Tab and returns it on close, revealed controls follow their trigger, no stop
  repeats. The Understanding's three passing examples give the shapes to match: a non-modal dialog
  whose "interactive elements [...] are inserted in the focus order immediately after the button",
  so open the order is "from the button to the elements of the dialog, then to the interactive
  element following the button" and closed "from the button to the following element"; a modal where
  "focus is set within the dialog", the rest "becomes inert and cannot receive focus" and on dismiss
  "focus returns to the button or the element following the button"; and left-hand navigation placed
  "in the HTML after the main body content, and styled with CSS to appear on the left hand side",
  with the note that "it is not necessarily true that all CSS positioning would" pass — "more
  complex positioning examples may or may not preserve meaning and operability", so check each
  repositioned block against its own layout.
- Not present: fewer than two focusable components in every state and no trigger that opens one.
- False positives to avoid: DOM order that differs from the layout while meaning holds ("it is
  not a failure if elements in the right-hand column receive focus first" when the columns are
  independent; the navigation after the main content); rows-first or columns-first through a
  table, where "either order may satisfy this success criterion"; arrow keys inside a tree, menu
  bar, tab list, radio group, listbox or grid; a modal whose Tab cycle passes through the browser UI
  (`BODY`), which both the Understanding ("the focus cycle might still include user agent
  controls") and H102 ("limited to the contents of the modal dialog and the browser's chrome")
  allow; a native `<dialog>` whose first focus lands on a `tabindex="-1"` heading rather than the
  visually first control; focus after the trigger was deleted on a different control, since
  "placing focus onto a different, but logical, control is not a failure of Success Criterion
  2.4.3" (F85 note); `tabindex="-1"` targets that never appear in the walk; static text made
  focusable that impedes nothing; and the controls of a closed dialog or menu, which `order` lists
  but Tab never reaches.

## Reporting

- File under: 2.4.3 for every wrong, lost, hidden or duplicated stop and for a dialog, menu or
  revealed region focus does not enter or return from; a control Tab never reaches is 2.1.1, focus
  that cannot leave 2.1.2, a visible stop with no indicator 2.4.7, an obscured stop 2.4.11, a
  context change on focus 3.2.1, the reading order of text 1.3.2, `aria-hidden` focusables 4.1.2.
  One issue per sequence defect; the same component on other samples is one issue naming them.
- Title patterns: "The Tab order in the <form> jumps between sections", "Focus does not move into
  the <dialog> when it opens", "Focus is lost after closing the <menu>", "Tab moves through the
  hidden <menu> links", "Positive tabindex values scramble the Tab order", "The <panel> opens far
  from the button that opened it in the Tab order", "Tab returns to the top of the page after the
  skip link"
- Severity: High when the order defeats a task (fields filled in the wrong section, a consent or
  checkout dialog focus never enters, a form whose fields a magnifier user reads "in the wrong
  context"); Medium when every control is reached but the sequence disorients (jumps between
  regions, a revealed panel far from its trigger); Low when one stop is out of place with its
  context obvious.
- Type: Technical (source order, `tabindex`, focus management in script, the `dialog` element).
- Evidence: the recording of the presses that jump, vanish or lose focus and the page screenshot
  with `highlight` on the out-of-place stop; for a dialog, Enter on the trigger and the Tab after.
  Quote the walk-log lines with their press numbers in the issue body, so the reader can repeat the
  presses, and for a `tabindex` defect include the markup with its values.
- Recommendation: put the elements in the source in the order the content reads and let CSS place
  them ([G59](https://www.w3.org/WAI/WCAG22/Techniques/general/G59),
  [C27](https://www.w3.org/WAI/WCAG22/Techniques/css/C27)); remove positive `tabindex` values, so
  that the source order is the Tab order:

  ```html
  <!-- fails (F44 Example 1): the walk runs Homepage, Chapter 3, Chapter 2, Chapter 1 -->
  <li><a href="main.html" tabindex="1">Homepage</a></li>
  <li><a href="chapter1.html" tabindex="4">Chapter 1</a></li>
  <li><a href="chapter2.html" tabindex="3">Chapter 2</a></li>
  <li><a href="chapter3.html" tabindex="2">Chapter 3</a></li>
  <!-- passes: no tabindex, so the content order is the Tab order -->
  <li><a href="main.html">Homepage</a></li>
  <li><a href="chapter1.html">Chapter 1</a></li>
  <li><a href="chapter2.html">Chapter 2</a></li>
  <li><a href="chapter3.html">Chapter 3</a></li>
  ```

  Place a revealed region right after its trigger in the DOM
  ([SCR26](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR26)), so the panel's first
  control is the next stop and no focus call is needed:

  ```html
  <button type="button" aria-expanded="true" aria-controls="filters">Filters</button>
  <div id="filters"><!-- inserted here, immediately after the button --></div>
  ```

  For a modal, let the browser do the entry, the containment and the return with the HTML `dialog`
  element opened by `showModal()` ([H102](https://www.w3.org/WAI/WCAG22/Techniques/html/H102));
  `show()` is the non-modal form, and a close button in a `<form method="dialog">` returns focus to
  the invoking element without script:

  ```html
  <button type="button" class="open-modal">Sign up to our mailing list!</button>
  <dialog aria-labelledby="dialog-heading">
    <h1 id="dialog-heading" tabindex="-1">Sign up to our mailing list</h1>
    <form><!-- fields, then the submit button --></form>
    <form method="dialog"><button aria-label="close">&times;</button></form>
  </dialog>
  <script>
    document
      .querySelector('.open-modal')
      .addEventListener('click', () => document.querySelector('dialog').showModal())
  </script>
  ```

  Where a script must keep managing focus, move it into the widget on open and back to the trigger
  on close, and where the trigger is removed, to the control immediately preceding or following it;
  reorder rebuilt sections in the DOM, not with CSS
  ([SCR27](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR27)), returning focus to
  the control that performed the reorder; for a PDF, set the tab order from the document structure
  and put the form fields in the tagged content in the right place
  ([PDF3](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF3)).
