# 3.2.6 Consistent Help

Level A · WCAG 2.2+ · Guideline 3.2 Predictable · Group: `consistency`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/consistent-help.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#consistent-help) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#consistent-help) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-2-6-consistent-help/) ·
ACT: none published for this criterion

## Requirement

> If a web page contains any of the following help mechanisms, and those mechanisms are repeated on
> multiple web pages within a set of web pages, they occur in the same order relative to other page
> content, unless a change is initiated by the user:
>
> - Human contact details;
>
> - Human contact mechanism;
>
> - Self-help option;
>
> - A fully automated contact mechanism.
>
> Note 1:
> Help mechanisms may be provided directly on the page, or may be provided via a direct link to a
> different page containing the information.
>
> Note 2:
> For this success criterion, "the same order relative to other page content" can be thought of as
> how the content is ordered when the page is serialized. The visual position of a help mechanism is
> likely to be consistent across pages for the same page variation (e.g., CSS break-point). The user
> can initiate a change, such as changing the page's zoom or orientation, which may trigger a
> different page variation. This criterion is concerned with relative order across pages
> displayed in the same page variation (e.g., same zoom level and orientation).

Note 2 is the operative sentence of the whole criterion: the subject of the test is the **serialized
order**, not the visual position, and the comparison is only valid between pages rendered in the
**same page variation**.

Terms (WCAG 2.2 glossary), verbatim; these decide which pages are compared, what counts as a
mechanism, and what counts as one page:

- **set of web pages**: "collection of web pages that share a common purpose and that are created by
  the same author, group or organization". Its examples give the three splits you will meet in a
  sample set. Split by template: "an e-commerce website shows products in a set of web pages that
  all share the same navigation and identification. However, when progressing to the checkout
  process, the template changes; the navigation and other elements are removed, so the pages in that
  process are functionally and visually different. The checkout pages are not part of the set of
  product pages." Split by sub-domain and authorship: "a blog on a sub-domain (e.g.
  blog.example.com) which has a different navigation and is authored by a distinct set of people
  from the pages on the primary domain (example.com)." Held together by a common purpose and shared
  navigation: "a publication which is split across multiple web pages, where each page contains one
  chapter or other significant section of the work. The publication is logically a single contiguous
  unit, and contains navigation features that enable access to the full set of pages." And its Note:
  "Different language versions would be considered different sets of web pages."
- **mechanism**: "process or technique for achieving a result". Note 1: "The mechanism may be
  explicitly provided in the content, or may be relied upon to be provided by either the platform or
  by user agents, including assistive technologies." Note 2: "The mechanism needs to meet all
  success criteria for the conformance level claimed." Note 2 is why a help link that cannot be
  reached by keyboard or carries no accessible name is also reported under its own criterion; it
  does not change this criterion's outcome (see "Reporting").
- **web page**: "a non-embedded resource obtained from a single URI using HTTP plus any other
  resources that are used in the rendering or intended to be rendered together with it by a user
  agent". Note 2: "For the purposes of conformance with these guidelines, a resource must be
  "non-embedded" within the scope of conformance to be considered a web page." A chat widget served
  in an `iframe` is therefore part of the page that embeds it, never a page of the set on its own:
  judge the position of the `iframe` element or of its launcher inside the embedding page.

## In plain terms

When a site offers a way to get help — a phone number, e-mail address or opening hours; a contact
form, chat or messaging channel; an FAQ, "How Do I" or support page; a chatbot — and that way is
repeated across the pages of one set, it sits at the same point in the serialized page order on
every page of the set that has it, compared at the same zoom, orientation and viewport. Offering
help at all remains the author's choice, and a page of the set that carries no help mechanism does
not fail. W3C's stated intent: "when the placement of the help mechanism is kept consistent across a
set of pages, users looking for help will find it easier to identify", and this is "distinct from
interface-level help, such as contextual help, features like spell checkers, and instructional text
in a form". It matters most for people with cognitive and learning disabilities, who may otherwise
abandon a task or "require assistance from people who do not necessarily keep private information
secure", and for screen reader and magnifier users, who reach help through tab order and landmarks
rather than by seeing it.

## Applies when

- Present: two or more samples of the same set carry the same help mechanism, either on the page or
  through "a direct link to a different page containing the information" (Note 1). The Understanding
  fixes the four types by example — "Human contact details such as a phone number, email address,
  hours of operation"; "Human contact mechanism such as a messaging system, chat client, contact
  form, social media channel"; "Self-help option such as an up-to-date Frequently Asked Questions,
  How Do I page, Support page"; "A fully automated contact mechanism such as a chatbot" — and adds
  that "the order of the types of help listed in the success criterion does not imply priority", so
  the type label never changes the outcome; only membership of the four does. Detect candidates in
  `recon/<sample>-links.json` (`links[].href` starting `tel:` or `mailto:`, or `links[].text`,
  `links[].name` or `links[].href` holding contact, help, support, faq, chat, hulp, klantenservice,
  veelgestelde), `recon/<sample>-forms.json` (`forms[].action` holding contact or support),
  `recon/<sample>-structure.json` (`iframes[]` whose `src` or `title` names a chat or support
  vendor; `landmarks[]` for the region sequence), and the step 3 outline, which is the only input
  that also finds buttons, `<address>` blocks and plain-text phone numbers, e-mail addresses and
  opening hours.
- Not present: counting only sets with two or more samples in scope, no sample carries any of the
  four types, or every mechanism found occurs on one sample only within its set, so nothing is
  "repeated on multiple web pages". Record `not-present` and name the samples that were compared.
  A set with a single sample in scope that does carry a mechanism is `cannot-tell`, not
  `not-present` (step 8): there is related content, and no second page in scope to compare it with.
- Exceptions — "unless a change is initiated by the user": the Understanding limits this to display
  changes, "such as changing the zoom level, orientation, or viewport size", and adds that "this
  exception is not intended to treat every action that a user might initiate as a 'change'; to
  qualify for the exception, the user must be initiating an action that would reasonably be expected
  to change the relative order of components within a page. For example, merely navigating between
  pages within a set of web pages is not a 'change initiated by the user' for the purposes of this
  exception. Similarly, logging into or out of a page would not typically qualify, unless logging in
  would present the user with a distinct set of web pages." It follows that "this exception allows
  the location in a smaller viewport to be different than in a larger viewport" — so every sample is
  compared at one fixed viewport (step 2) and a difference seen only at another viewport is not a
  finding here.
- Exceptions — outside the set: "It does not require authors to provide help information on PDFs or
  other static documents that may be available for viewing/download from the web pages. PDFs and
  other static documents are not considered part of the 'set of web pages' from which they are
  downloaded." And different sets of one site may place help differently: "a web-based spreadsheet
  application might have one set of pages for editing spreadsheets and a separate set of pages for
  marketing the application. This success criterion would allow the different sets of web pages to
  use different help mechanism locations."
- Exceptions — availability: "It is also not the intent of this success criterion to require a human
  be available at all times." A phone line or chat that is closed outside office hours, or a chatbot
  that answers poorly, is not a failure of 3.2.6.
- Published failure: the Understanding lists one failure, "Inconsistent Help Location", with no
  technique number and no link, so there is no `F` id to cite for this criterion. Cite
  [G220](https://www.w3.org/WAI/WCAG22/Techniques/general/G220) and quote the Understanding instead.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. `axe-page.mjs` prints no
3.2.6 row for any sample, and no rule in any rule set compares two pages with each other, so a clean
axe run over every sample decides nothing here. Where an axe violation lands on the help link or
launcher itself (no accessible name, not focusable), it is reported under its own criterion and
leaves this criterion's outcome untouched.

## Manual procedure

Consistency mode, once per report, after every `recon` unit has run. Inputs: `index.md`,
`.notes/sample.md`, the `links`, `structure` and `forms` probe outputs plus `<sample>-tree.txt` in
`.notes/audit/recon/`, and the full-page screenshots in `.notes/audit/evidence/`. Outcome and
findings go to `consistency.md`, whose `Sample` column names every sample compared. No ACT rule
exists for 3.2.6, so the published test procedure followed here is G220's: "Determine if this is a
set of web pages with blocks of content that are repeated on multiple pages"; "Determine if at least
one of the following is included or linked in a consistent location: Human contact details, Human
contact mechanism, Self-help option, A fully automated mechanism"; "Without changing the viewport
size, check that the identified help is present on all other web pages within that set of web
pages." Both expected results decide an outcome: "If #1 is true, #2 and #3 are true" is the pass,
and "Otherwise, #1 is false" is the not-applicable case — the samples are not one set of web pages
with repeated blocks of content, which step 1 settles before anything is compared.

1. Sort the samples into sets. Reuse the `sample · set · reason` table from the 2.4.5 and 3.2.3
   steps when it exists; otherwise record per sample which set it belongs to, putting a sample in a
   separate set only for a reason the glossary gives: a checkout or wizard template from which the
   site navigation has been removed, a sub-domain with its own navigation and its own authors,
   another language version, or an application behind a login that presents its own template.
   Shared navigation plus a common purpose keeps pages in one set even when their layouts differ.
   Done when every sample carries a set id, every set holding two or more samples is queued for
   comparison, and every set holding one sample is marked for step 8.

2. Fix one page variation for the whole comparison and keep it for every sample, as G220 requires
   ("without changing the viewport size"):

   ```bash
   agent-browser set viewport 1280 900
   agent-browser set media light
   ```

   One colour scheme is pinned as well, so that a theme-dependent layout cannot differ between two
   samples for a reason the criterion does not test. Done when the session reports the viewport and
   every outline written in step 3 carries `"width": 1280`; an outline with another `width` is
   discarded and re-taken.

3. Write a serialized outline of every sample of every queued set. Open the sample, let a
   script-injected widget mount, then run the outline (the 5 s wait is a tool timeout for late
   widget injection, not a threshold of the criterion):

   ```bash
   agent-browser open <sample url>
   agent-browser wait --load networkidle
   agent-browser wait 5000
   agent-browser eval --stdin > .notes/audit/recon/<sample>-help.json <<'EOF'
   (() => {
     const clean = (s) => (s || '').replace(/\s+/g, ' ').trim().slice(0, 60);
     const lmSel = 'header,nav,main,footer,aside,[role=banner],[role=navigation],[role=main],'
       + '[role=contentinfo],[role=complementary],[role=search],[role=dialog]';
     const lmOf = (el) => { const l = el.closest(lmSel); if (!l) return 'none';
       const n = l.getAttribute('aria-label');
       const t = l.getAttribute('role') || l.tagName.toLowerCase();
       return t + (n ? '[' + clean(n) + ']' : ''); };
     const phone = /\+?\d[\d ()./-]{7,}\d/;
     const mail = /[\w.+-]+@[\w-]+\.[a-z]{2,}/i;
     const hours =
       /\b(mon|tue|wed|thu|fri|sat|sun|ma|di|wo|do|vr|za|zo|open|hours|geopend|24\/7)\b/i;
     const words =
       /contact|help|support|faq|chat|hulp|klantenservice|veelgestelde|bel ons|how do i/i;
     const typeOf = (label, href) => { const s = label + ' ' + (href || '');
       if (/^(tel|mailto):/i.test(href || '') || phone.test(label) || mail.test(label)
         || (hours.test(label) && /\d/.test(label))) return 'contact-details';
       if (/chatbot|virtual assistant|virtuele assistent|\bbot\b/i.test(s)) return 'automated';
       if (/chat|messag|whatsapp|contact|bel ons|klantenservice/i.test(s)) return 'human-mechanism';
       if (/faq|help|support|veelgestelde|how do i/i.test(s)) return 'self-help';
       return 'unclear'; };
     const shown = (el) => el.getClientRects().length > 0
       && getComputedStyle(el).visibility !== 'hidden';
     const anchors = 'a[href], button, [role=button], summary, iframe, h1, h2, h3, h4, h5, h6';
     const out = [];
     const walker = document.createTreeWalker(document.body,
       NodeFilter.SHOW_ELEMENT | NodeFilter.SHOW_TEXT);
     for (let n = walker.nextNode(); n; n = walker.nextNode()) {
       if (n.nodeType === 3) {
         const p = n.parentElement, t = clean(n.nodeValue);
         if (!p || !t || /^(script|style|noscript)$/i.test(p.tagName)) continue;
         if (p.closest(anchors) || !shown(p)) continue;
         if (!(phone.test(t) || mail.test(t) || (hours.test(t) && /\d/.test(t)))) continue;
         out.push({ i: out.length, node: 'text', label: t, href: null, landmark: lmOf(p),
           help: 'contact-details', fixed: false,
           ariaHidden: Boolean(p.closest('[aria-hidden=true]')) });
         continue;
       }
       if (!n.matches(anchors) || !shown(n)) continue;
       const href = n.getAttribute('href') || n.getAttribute('src');
       const label = clean(n.textContent || n.getAttribute('aria-label')
         || n.getAttribute('title'));
       const heading = /^h[1-6]$/i.test(n.tagName);
       out.push({ i: out.length, node: n.tagName.toLowerCase(), label, href, landmark: lmOf(n),
         help: (!heading && (words.test(label + ' ' + (href || ''))
           || /^(tel|mailto):/i.test(href || ''))) ? typeOf(label, href) : null,
         fixed: getComputedStyle(n).position === 'fixed',
         ariaHidden: Boolean(n.closest('[aria-hidden=true]')) });
     }
     return { url: location.href, width: innerWidth, total: out.length, order: out,
       help: out.filter((o) => o.help) };
   })()
   EOF
   ```

   `order` is every link, button, `summary`, `iframe` and heading in document order, plus every
   visible text node that looks like a phone number, an e-mail address or opening hours; `i` is the
   position in that serialization and is page-local, never compared as a number across samples.
   `help` holds the candidates. A link inside a **closed `<details>`** is included at its serialized
   position — it still has client rects — which is exactly the case G220 example 3 describes; a
   panel hidden with `display: none` or `hidden` is absent and is reached in step 6 instead.
   Done when `.notes/audit/recon/<sample>-help.json` exists for every sample of every queued set and
   each holds `"width": 1280`.

4. Read the `help` array of each outline and keep only real help mechanisms. Drop a candidate whose
   label merely contains a matching word (a product named "Help", "chat" inside an article title, a
   "Support us" donation link), and add any candidate the regexes missed that the landmark text or
   `<sample>-tree.txt` shows (an icon-only launcher with no accessible name, a social channel the
   site offers for support). Assign each kept candidate one of the four types; record `unclear`
   candidates as kept, because the type does not decide the outcome. Done when a table
   `sample · mechanism (label, href) · type · landmark · i · fixed · ariaHidden` is in the notes of
   `consistency.md` for every sample of every queued set.

5. Compare the serialized order pairwise inside each set. The Understanding's test is: "other
   content that is present across the set of web pages and is before the help item should be before
   the help item on this page. Items which are after the help item on other pages should be after
   the help item on this page." Run it as a measurement — only items that appear exactly once on
   both pages are compared, so content one sample lacks can never produce a finding:

   ```bash
   node - .notes/audit/recon/<sample-a>-help.json .notes/audit/recon/<sample-b>-help.json <<'EOF'
   (() => {
     const fs = require('node:fs');
     const [fa, fb] = process.argv.slice(2);
     const A = JSON.parse(fs.readFileSync(fa, 'utf8'));
     const B = JSON.parse(fs.readFileSync(fb, 'utf8'));
     const key = (o) => (o.href
       ? o.href.replace(/^https?:\/\/[^/]+/, '').replace(/#.*$/, '') : 't:' + o.label);
     const index = (page) => { const m = new Map();
       for (const o of page.order) { const k = key(o); m.set(k, [...(m.get(k) || []), o.i]); }
       return m; };
     const ia = index(A), ib = index(B);
     const shared = [...ia.keys()]
       .filter((k) => ib.has(k) && ia.get(k).length === 1 && ib.get(k).length === 1);
     console.log(`${A.url} (w=${A.width}) vs ${B.url} (w=${B.width}) — ${shared.length} shared`);
     for (const k of [...new Set(A.help.map(key))]) {
       const label = A.help.find((o) => key(o) === k).label;
       if (!ib.has(k)) { console.log(`  ${label} [${k}]: absent on B — not a failure`); continue; }
       let best = null;
       for (const ai of ia.get(k)) for (const bi of ib.get(k)) {
         const swapped = shared
           .filter((s) => s !== k && (ia.get(s)[0] < ai) !== (ib.get(s)[0] < bi));
         if (!best || swapped.length < best.swapped.length) best = { ai, bi, swapped };
       }
       console.log(`  ${label} [${k}] A i${best.ai} / B i${best.bi} -> ` + (best.swapped.length
         ? `DIFFERENT ORDER (${best.swapped.length}): ${best.swapped.join(', ')}` : 'same order'));
     }
   })()
   EOF
   ```

   Read three things from the output: `w=` on both sides must be equal, or the pair is not one page
   variation and is re-taken; `absent on B` is never a finding; and a `DIFFERENT ORDER` line names
   the shared items that swap sides, which is the evidence the finding quotes. A mechanism that
   occurs twice on one sample is matched against its best-fitting occurrence, so an extra copy is
   not a finding. Run the pair in both directions when the two samples carry different numbers of
   copies. Done when every ordered pair of every queued set has been run and each mechanism is
   marked same order, or different order with the two samples and the swapped items listed.

6. Reach the mechanisms that live in a state. A help link inside a menu, a footer accordion or a
   "More" disclosure that the outline did not see is opened and the sample re-outlined, because
   G220 example 3 passes a link "within a disclosure widget which is in the same relative order as
   the link that is directly on the page" — with the Note that "although this example technically
   passes the Success Criterion, it creates a less consistent user experience and is less preferable
   than consistently placing a link directly on the page":

   ```bash
   agent-browser snapshot -i
   agent-browser find role button click --name "Menu"
   agent-browser snapshot -i -u -s "nav[aria-label='Main']"
   ```

   `-s` scopes to the first match in document order, whatever order the selector list is written in,
   so name one container. Re-run the step 3 outline with the state open, save it as
   `<sample>--<state>-help.json`, and re-run step 5 against the other sample's matching state. A
   chat widget that opens a panel is judged by its launcher, not by the panel. Done when every
   mechanism that needed a state has an outline taken in that state and a step 5 verdict.

7. Record the visual position as an observation only. Compare the `landmark` and `fixed` fields and
   the full-page screenshots. W3C is explicit: "if the help item is visually in a different
   location, but in the same serial order, that is not helpful from a user's point of view, but it
   would not fail this criterion." Done when every mechanism that moved visually while keeping its
   serial order is written into the notes of `consistency.md` with the outcome left unchanged.

8. Settle the sets that hold one sample and the unstable widgets, then take evidence. For a set with
   a single sample that carries a help mechanism, there is no second page in scope to compare, so
   record `cannot-tell` and put the question in `confirm.md`: "does `<mechanism>` sit at the same
   point in the page order on the other pages of `<set>`?". For a launcher injected by a script, run
   `agent-browser reload`, re-run steps 3 and 5, and record `cannot-tell` when its position differs
   between two loads of the same sample. For every confirmed different order, capture both sides:

   ```bash
   agent-browser open <sample url>
   agent-browser wait --load networkidle
   agent-browser highlight "a[href='/contact']"
   agent-browser screenshot .notes/audit/evidence/<sample>-help-order.png --full
   ```

   Repeat with the other sample's selector, confirming first with
   `agent-browser get attr "a[href='/contact']" href` that the selector picks the intended link —
   `get attr` takes the selector first and the attribute second. Done when the 3.2.6 row in
   `consistency.md` carries its outcome, its certainty and the samples compared, and every finding
   names both samples and both screenshots.

What the browser cannot show: whether two areas are "created by the same author, group or
organization" and whether they "share a common purpose" — that is the human's answer, asked in
`confirm.md`; and whether a third-party widget lands at the same point on every load for every
visitor, which step 8 can only sample.

## Deciding

- Fail (certainty ≥ 90): the step 5 comparator reports `DIFFERENT ORDER` for one mechanism between
  two samples of one set with equal `w=`, and the swapped items belong to a component both samples
  repeat (the navigation links, the footer links) — 95. The comparator reports `DIFFERENT ORDER`
  where the swap is confined to one landmark both samples have, for example the mechanism first
  among the footer links on one sample and last on the other while the remaining footer links keep
  their order — 90.
- Fail (70–89): a script-injected launcher whose `DIFFERENT ORDER` verdict repeats after `reload`
  on both samples — 80. A mechanism directly on the page on one sample and inside a disclosure or
  menu on another, still reported `DIFFERENT ORDER` after step 6 opened the state on both — 75. A
  plain-text phone number, e-mail address or opening-hours line matched as a `text` node whose
  `DIFFERENT ORDER` verdict rests on the footer's own repeated links swapping — 75, because the text
  match is looser than an `href` match.
- Needs confirmation (50–69): the two samples may belong to different sets — a sub-domain, a
  checkout or wizard template, an area behind a login, another language version — 60; ask who
  authors them and whether they share a common purpose. A `DIFFERENT ORDER` verdict whose swapped
  items are all matched by label rather than by `href`, so two different items may share a label —
  55; ask which of them is the repeated component. A launcher whose position differs between two
  loads of the same sample — 55; ask how the widget is inserted.
- Pass: for every mechanism of the four types that two or more samples of a set share, the step 5
  comparator reports `same order` for every pair, at one `width`, in the state the mechanism lives
  in; record the samples compared and the mechanisms checked.
- Not present: no multi-sample set carries any of the four types, or no mechanism recurs on two
  samples within a set.
- Cannot tell: the set holds one sample in scope and it carries a mechanism; or the launcher's
  position is unstable between loads; or the set membership is unresolved and the outcome turns on
  it. Each lands in `confirm.md` with the question from step 8.
- False positives to avoid: a sample of the set without the mechanism — "the absence of a help
  mechanism on certain pages within a set does not constitute a violation"; a mechanism present
  twice on one sample and once on another, where one occurrence keeps the order; a visual move with
  the same serial order (step 7); a different position at another viewport, zoom or orientation,
  which the user-initiated-change exception allows and which step 2 excludes by construction;
  content that only one sample has sitting between the mechanism and the shared items, which the
  shared-item intersection already drops; different sets of the same site; a link inside a
  disclosure in the same relative order (G220 example 3); contextual help, form instructions and
  spell checkers, which are "interface-level help" and belong to 3.3.5 (AAA); a help link whose
  label or icon differs between pages while its position holds (3.2.4); the navigation itself
  reordered (3.2.3); a PDF or other static document that carries no help; a phone line or chat
  closed outside office hours; a chatbot that gives a poor answer — the Understanding's advice that
  a chatbot "provide human contact details if the chatbot is unable to provide a satisfactory
  response after 3 attempts" is explicitly "not required by the Consistent Help success criterion".

## Reporting

- File under: 3.2.6, one issue per mechanism, naming every sample on which it moves — the defect is
  the template, not one page. Split off: the navigation itself reordered is 3.2.3; a help link named
  or iconed differently per page is 3.2.4; a help link or chat launcher the keyboard cannot reach is
  2.1.1; a launcher with no accessible name is 4.1.2; a contact form without labels is 3.3.2; a
  "skip to chat" link is 2.4.1.
- Title patterns: "Contact link moves between header and footer", "Chat button sits at a different
  point in the page order", "Help link changes place across pages", "Phone number sits in the body
  on one page and in the footer on the others"
- Severity: High when the mechanism is the only way to complete a task in scope (a phone number to
  book, a form to apply) and it leaves the repeated component on the pages of that task; Medium when
  it changes landmark between the templates most pages of the set use, so the whole product is
  affected; Low when it shifts a few positions inside one landmark, or moves on a single page of the
  set.
- Type: Technical when one template renders the component at different points, or a widget script is
  inserted at different positions in the markup; Design when two templates of one set place help in
  different regions; Content when an editor typed contact details into the body of one page while
  the other pages carry them in a repeated component.
- Evidence: two full-page screenshots at the comparison viewport, one per sample, the mechanism
  highlighted on each, named `<sample>-help-order.png`; where a state had to be opened, the
  screenshot of the open menu or panel. Quote the comparator's swapped-item list in the issue body
  so the reader sees which repeated items changed sides. No GIF: nothing moves.
- Recommendation: place the help mechanism in one repeated component, at one fixed point in that
  component's order, in every template of the set
  ([G220](https://www.w3.org/WAI/WCAG22/Techniques/general/G220)) — for example one footer partial
  included by every template, with the contact link first among its links:

  ```html
  <footer>
    <ul>
      <li><a href="/contact">Contact us</a></li>
      <li><a href="/faq">FAQ</a></li>
      <li><a href="/terms">Terms</a></li>
    </ul>
  </footer>
  ```

  G220's other two shapes are equally sufficient: a "Contact Us" link among the first links of the
  page, so that it is "one of the first links that the user reaches when tabbing through the page",
  or a link inside a disclosure widget kept "in the same relative order as the link that is directly
  on the page" — while noting G220's own remark that the disclosure shape "creates a less consistent
  user experience and is less preferable". Mount a chat launcher from the same script at the same
  DOM position on every page, for example as the last child of `body`, rather than wherever the
  template happens to call it.
