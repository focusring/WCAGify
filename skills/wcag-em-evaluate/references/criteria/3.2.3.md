# 3.2.3 Consistent Navigation

Level AA · WCAG 2.0+ · Guideline 3.2 Predictable · Group: `consistency`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#consistent-navigation) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#consistent-navigation) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-2-3-consistent-navigation/)
· ACT: none

## Requirement

> Navigational mechanisms that are repeated on multiple web pages within a set of web pages occur
> in the same relative order each time they are repeated, unless a change is initiated by the
> user.

Terms (WCAG 2.2 glossary). Each one draws a boundary the outcome turns on, so use the wording:

- **same relative order**: "same position relative to other items". Note: "Items are considered to
  be in the same relative order even if other items are inserted or removed from the original
  order. For example, expanding navigation menus may insert an additional level of detail or a
  secondary navigation section may be inserted into the reading order." The note is the whole
  test for insertions and removals: strike them, then compare what is left.
- **set of web pages**: "collection of web pages that share a common purpose and that are created
  by the same author, group or organization". Note: "Different language versions would be
  considered different sets of web pages." The glossary examples draw the other boundaries, and
  each names the condition under which the pages leave the set: "an e-commerce website shows
  products in a set of web pages that all share the same navigation and identification. However,
  when progressing to the checkout process, the template changes; the navigation and other
  elements are removed, so the pages in that process are functionally and visually different. The
  checkout pages are not part of the set of product pages."; "a blog on a sub-domain (e.g.
  blog.example.com) which has a different navigation and is authored by a distinct set of people
  from the pages on the primary domain (example.com)."; and one set that spans a whole work: "a
  publication which is split across multiple web pages, where each page contains one chapter or
  other significant section of the work. The publication is logically a single contiguous unit,
  and contains navigation features that enable access to the full set of pages."
- **web page**: "a non-embedded resource obtained from a single URI using HTTP plus any other
  resources that are used in the rendering or intended to be rendered together with it by a user
  agent". Glossary Example 2 settles single-page applications: "A web mail program built using
  Asynchronous JavaScript and XML (AJAX). The program lives entirely at http://example.com/mail,
  but includes an inbox, a contacts area and a calendar. Links or buttons are provided that cause
  the inbox, contacts, or calendar to display, but do not change the URI of the page as a whole."
  Those views are one web page, so switching between them is not "multiple web pages".

## In plain terms

Components that come back on page after page (the main menu, the footer links, the skip link, the
search field, a breadcrumb) keep the same order among their items and the same place among each
other, in the source and on screen. The place itself is free: a search field that is the last item
on every page, or navigation that sits at the end of every page, is consistent. A sub-menu that
unfolds for the current section, a secondary navigation block, or an item that appears or
disappears does not break that order. Magnifier users find the menu by remembering where it was,
blind users who read sequentially expect it at the same point in the reading order, and people with
cognitive or intellectual disabilities depend on the predictability. A change of order the user
asked for, through a preference or an adaptive user agent, is allowed.

## Applies when

- Present: the scope in `index.md` covers two or more web pages of one set, and a navigational
  mechanism recurs on at least two samples of that set: a main menu, a footer link list, a skip
  link, a search field, a breadcrumb, utility links (login, language, cart), a table of contents,
  next/previous links, a pagination. Detect it from `<id>-structure.json` (`landmarks` with `role`
  `navigation`, `search`, `banner` or `contentinfo`; `skipLinks`) and `<id>-links.json` (`links`
  whose `href` recurs on other samples) in `recon/`, and confirm it with the dump of step 2. For a
  PDF sample the mechanisms are its running headers, footers and page numbering.
- Not present: the scope is one web page (one URI, including a one-page application whose views
  keep the URI — the glossary's AJAX web-mail example), or no mechanism recurs on two samples of
  the same set (the samples share no header, footer, menu, search or skip link, or every set holds
  one sample). Record `not-present`.
- Exceptions, and the differences W3C states are not differences:
  - "unless a change is initiated by the user": an order the user chose through a control or a
    preference (a customisable dashboard, a "recently visited" list, a remembered sort) and that
    holds until they change it again; recognise it by the control that sets it, on the page or in
    the account settings. The Intent names the two forms: "Users may initiate a change in the
    order by using adaptive user agents or by setting preferences so that the information is
    presented in a way that is most useful to them."
  - Items inserted or removed, per the `same relative order` note: an unfolded sub-menu, an
    inserted secondary block, Log in that becomes Log out, a cart badge that appears — as long as
    the remaining items keep their sequence.
  - Secondary navigation sitting between the items, per the F66 note, quoted whole: "Same
    relative order" means that secondary navigation items may be in between the link items on some
    pages. They can be present without affecting the outcome of this test.
  - Sub-navigation and secondary blocks as such, per the Intent: "It is important to note that the
    use of the phrase 'same order' in this section is not meant to imply that sub-navigation menus
    cannot be used or that blocks of secondary navigation or page structure cannot be used."
  - A repeated component missing from one page, per the G61 example: "On one page the search form
    is missing but the other items are still in the same order." Absence is not a reorder.
  - Set boundaries: a checkout whose template changes and drops the navigation, a sub-domain with
    its own navigation and its own authors, and each language version are compared inside their
    own set only.

## axe-core

No axe-core rule is tagged with this criterion and no ACT rule is mapped to it; everything below is
manual. The `axe-page.mjs` results contribute nothing here, and no rule tagged with another
criterion applies: axe examines one page at a time, and this criterion compares pages.

## Manual procedure

Consistency mode, once per report, after every `recon` unit. Inputs: `index.md`, `.notes/sample.md`,
the `structure` and `links` probe outputs and the `<id>-tree.txt` snapshots in
`.notes/audit/recon/`, the full-page screenshots `evidence/<id>-full.png`, and one browser session
for the opened states and the evidence. Outcome and findings go to `consistency.md`; its `Sample`
column names the samples where the order differs. Where a recon file is missing, re-make it:

```bash
agent-browser open <sample url>
agent-browser wait --load networkidle
agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js \
  > .notes/audit/recon/<id>-structure.json
agent-browser eval --stdin < <skill-dir>/scripts/probes/links.js \
  > .notes/audit/recon/<id>-links.json
```

Two W3C procedures frame the pass and the fail. Each has two conditions; keep them apart.

[G61](https://www.w3.org/WAI/WCAG22/Techniques/general/G61) (sufficient) — Tests: (1) "List
components that are repeated on each web page in a set of web pages"; (2) "For each component,
check that it appears in the same relative order with regard to other repeated components on each
web page where it appears"; (3) "For each navigational component, check that the links or
programmatic references are always in the same relative order." Expected results: #2 is true **and**
#3 is true. A menu whose links never move can still fail (2) by changing place among the other
repeated components, and a menu that keeps its place can still fail (3): step 3 below tests (3),
step 4 tests (2), and a pass needs both.

[F66](https://www.w3.org/WAI/WCAG22/Techniques/failures/F66) (failure) — Tests: (1) "Check to see
if a navigation mechanism is being used on more than one web page."; (2) "Check the default
presentation of the navigation mechanism on each page to see if the list of links are in the same
relative order on each web page." Expected result: "If #1 is true and #2 is false, then this
failure condition applies and content fails the Success Criterion." Both conditions carry weight: a
mechanism that occurs on one page only is not F66 (1 is false), and a difference that appears only
after the user changes something is not F66 (2 asks about the default presentation).

1. Sort the samples into sets. For every sample record its set: the main site, unless it matches
   a separate-set case under "Applies when" (a checkout whose template changes, sub-domain,
   language version, an area behind a login with its own navigation). 3.2.3 has no process
   exception of its own: checkout and wizard steps that keep the site template stay in the site's
   set, and ones that drop it form a set of their own and are compared with each other. Done when
   a table `sample · set` is in the notes of `consistency.md`, and every set with one sample is
   marked `not-present`.

2. Dump the navigational mechanisms of every sample in source order. Read `landmarks` and
   `skipLinks` from `<id>-structure.json`, then open each sample and run:

   ```bash
   agent-browser open <sample url>
   agent-browser wait --load networkidle
   agent-browser eval --stdin <<'EOF' > .notes/audit/recon/<id>-navorder.json
   (() => {
     const sel = 'header, [role=banner], nav, [role=navigation], footer, [role=contentinfo], '
       + '[role=search], form[role=search], [aria-label*="breadcrumb" i], '
       + '.breadcrumb, .breadcrumbs';
     const depth = c => { let d = 0, p = c.parentElement;
       while (p) { if (p.matches(sel)) d++; p = p.parentElement; } return d; };
     const href = e => {
       const h = e.getAttribute('href');
       if (h == null) return '';
       if (h.startsWith('#')) return ' → ' + h;
       try { const u = new URL(h, location.href); return ' → ' + u.pathname + u.search; }
       catch { return ' → ' + h; }
     };
     const label = e => {
       const t = (e.textContent || '').trim().replace(/\s+/g, ' ');
       const n = t || e.getAttribute('aria-label') || e.getAttribute('title')
         || e.getAttribute('placeholder') || e.value || '';
       return n.slice(0, 40) + href(e);
     };
     return [...document.querySelectorAll(sel)].map(c => {
       const r = c.getBoundingClientRect(), cs = getComputedStyle(c);
       return {
         container: c.tagName.toLowerCase() + (c.id ? '#' + c.id : '')
           + (c.classList.length ? '.' + [...c.classList].join('.') : ''),
         role: c.getAttribute('role') || '', name: c.getAttribute('aria-label') || '',
         depth: depth(c),
         visible: cs.display !== 'none' && cs.visibility !== 'hidden'
           && r.width > 0 && r.height > 0,
         x: Math.round(r.x), y: Math.round(r.y + scrollY),
         items: [...c.querySelectorAll('a[href], button, [role=menuitem], '
           + 'input:not([type=hidden])')].map(label)
       };
     });
   })()
   EOF
   ```

   Keep the same block in `.notes/audit/recon/navorder.js` and run the remaining samples with
   `agent-browser eval --stdin < .notes/audit/recon/navorder.js`. The array order is the source
   order of the containers; `x` and `y` give their place on screen; `depth` is 0 for a top-level
   container and 1 or more for one nested in another (a `nav` inside a `header` is dumped twice,
   once on its own and once inside the header's `items`). A mechanism is repeated when a container
   with the same `role` and `name`, or the same `container` string, exists on two or more samples
   of the set. Where the markup differs per template, pair two containers only when they hold the
   same component: the same `depth`, the same place relative to `main`, the same `x`/`y` band, and
   the same `items` apart from insertions; a header menu and a footer list that share a few links
   stay separate mechanisms. Pair a `visible: false` container (the small-viewport copy of a menu
   that a template renders alongside the desktop one) with its counterpart on the other sample,
   never with the visible one: F66 asks about the default presentation. Done when every sample has
   its `-navorder.json` and each set lists its repeated mechanisms with the samples that carry each.

3. Compare the link order inside every repeated mechanism (F66 test 2, G61 test 3; the DOM order in
   `<id>-tree.txt` is what assistive technology reads). Strike the items that occur on only some
   samples, then require the rest to be identical in sequence:

   ```bash
   jq -r --arg c "<container>" '.[] | select(.container == $c) | .items[]' \
     .notes/audit/recon/<a>-navorder.json > .notes/audit/recon/<a>-<mech>.txt
   jq -r --arg c "<container>" '.[] | select(.container == $c) | .items[]' \
     .notes/audit/recon/<b>-navorder.json > .notes/audit/recon/<b>-<mech>.txt
   comm -12 <(sort -u .notes/audit/recon/<a>-<mech>.txt) \
            <(sort -u .notes/audit/recon/<b>-<mech>.txt) > .notes/audit/recon/<mech>-shared.txt
   diff <(grep -Fxf .notes/audit/recon/<mech>-shared.txt .notes/audit/recon/<a>-<mech>.txt) \
        <(grep -Fxf .notes/audit/recon/<mech>-shared.txt .notes/audit/recon/<b>-<mech>.txt)
   ```

   No output: the shared items are in the same sequence, and the insertions and removals are
   allowed by the `same relative order` note. Any output: the shared items are in a different
   sequence, which is F66. F66's own example worked through: page 1 lists Brazil, Canada, Germany,
   Poland and page 2 lists Canada, Brazil, Germany, Poland; all four items are shared so nothing is
   struck, and the diff shows the swapped pair. Where one item text occurs twice inside one
   mechanism (a footer that repeats "Home") and only once in the other, the surplus occurrence
   shows up as a diff line; strike it by hand and judge the rest. Where the mechanism is built per
   request, load one sample twice and compare it with itself:

   ```bash
   agent-browser reload
   agent-browser wait --load networkidle
   agent-browser eval --stdin < .notes/audit/recon/navorder.js \
     > .notes/audit/recon/<id>-navorder-2.json
   diff <(jq -r '.[].items[]' .notes/audit/recon/<id>-navorder.json) \
        <(jq -r '.[].items[]' .notes/audit/recon/<id>-navorder-2.json)
   ```

   A difference between two loads of one URL means the sequence is generated per request, so it
   will differ across the pages of the set too; confirm it on a second sample before recording.
   Done when every repeated mechanism of every set is marked same or differs, with the samples and
   the items of each difference noted.

4. Compare the order of the mechanisms among each other (G61 test 2). List the top-level containers
   of each sample in source order and line the lists up the same way as step 3:

   ```bash
   jq -r '.[] | select(.visible and .depth == 0)
     | "\(.container) [\(.role)] \(.name)"' .notes/audit/recon/<id>-navorder.json
   ```

   Strike the containers that exist on only one of the two samples (G61: a page where the search
   form is missing keeps the order of the rest) and require the remaining sequence to be identical:
   skip link, header, main navigation, search, breadcrumb, footer. A mechanism that moves into
   another container (the search in the header on one template and in the footer on another) or
   past another repeated mechanism is a difference. Done when every set has its container sequence
   compared and each pair is marked same or differs.

5. Compare the visual order. Read the full-page screenshots side by side, one sample per template
   of the set plus a second sample of any template whose menu is built per page, and place every
   repeated mechanism: the menu left or right of the logo, the search before or after the menu, the
   breadcrumb above or below the title, the footer groups left to right. Settle close calls with
   `x` and `y` from step 2. A mechanism that sits lower on one page because a banner is above it
   keeps its order; a mechanism that changes sides, moves from header to footer, or shows its items
   in another sequence (CSS `order`, `flex-direction`) is a difference. Done when every repeated
   mechanism is marked same or differs visually.

6. Compare the opened states that repeat: a collapsed menu behind a button, a mega menu, an account
   menu. On one sample per template of the set:

   ```bash
   agent-browser open <sample url>
   agent-browser wait --load networkidle
   agent-browser get attr "<menu button css>" aria-controls
   agent-browser find role button click --name "<menu button name>"
   agent-browser snapshot -i -s "<#aria-controls-value, or the step 2 container css>"
   agent-browser screenshot "<the same selector>" .notes/audit/evidence/<id>-menu-open.png
   agent-browser press Escape
   ```

   When the menu collapses only at a narrower viewport, `set viewport 640 900` first and return
   with `set viewport 1280 900`; compare a collapsed menu with the collapsed menu of the other
   sample, not with the desktop menu. Compare the item order of the opened list between samples as
   in step 3, reading the names from the `snapshot` output. Done when every repeated opened state
   is marked same or differs.

7. Classify every difference: (a) inserted or removed items only, the rest in sequence: no defect;
   (b) the samples belong to different sets (step 1): no defect, compare inside the set; (c) the
   order follows a user choice (a control on the page, an account preference, an adaptive user
   agent, an action in the "Processes" section of `.notes/sample.md`): user-initiated, no defect,
   note the control that sets it; (d) anything else: F66. Done when every difference has its class
   and every (d) has a finding.

8. Evidence for every (d) difference: the mechanism highlighted in its page (the outline falls
   outside an element crop); run this on sample A and again on sample B:

   ```bash
   agent-browser open <sample url>
   agent-browser wait --load networkidle
   agent-browser scrollintoview "<container css>"
   agent-browser highlight "<container css>"
   agent-browser screenshot .notes/audit/evidence/<id>-nav-order.png
   ```

   Done when the 3.2.3 row in `consistency.md` has its outcome and its `Sample` column, and every
   finding names both samples and both screenshots.

What the browser cannot show: pages outside the sample set (the samples are the proxy for the set,
so a menu edited per page in a CMS can differ on pages nobody sampled) and the order a screen
reader hears (the DOM order in `<id>-tree.txt` is the proxy). Record `cannot-tell` when a mechanism
repeats only on samples whose states could not be reached, or when a template of the set has one
sample only and its mechanism cannot be compared, naming the samples and the template.

## Deciding

- Fail (certainty ≥ 90): the same mechanism on two samples of one set lists the shared items in a
  different sequence in the default presentation (step 3 diff non-empty), with no user action
  behind it (F66) — 95; a repeated mechanism that changes its position among the other repeated
  mechanisms in source order (the search before the menu on one template and after it on another;
  the skip link first on most samples and after the menu on others) — 90; a repeated component
  that sits inside a different repeated container on some samples (the search in the header on one
  template, in the footer on another; a utility link that moves from header to footer) — 90.
- Fail (70–89): the opened menu lists its items in another sequence than the same menu opened on
  another sample of the set — 85; two loads of one URL produce different item sequences and no
  control sets the order, so the pages of the set cannot share one — 85; the visual order of a
  repeated mechanism differs while the source order is the same (CSS reorders the menu, or moves
  the search to the other side of the header) — 80; the footer link groups are arranged in another
  sequence on some templates — 80; the breadcrumb sits above the title on some templates and below
  it on others — 75.
- Needs confirmation (50–69): the differing order may follow a user choice the notes do not show
  (a "recent" or "favourite" list, a personalised dashboard, a remembered sort) — 60; ask what
  sets the order. The order differs only between a logged-in and a logged-out state — 60; ask
  whether the account area is meant as a set of its own. The samples with the other order may be
  a set of their own (another template, other authors, a sub-domain) — 55; ask who owns and
  authors them, and whether the template keeps the site's navigation.
- Pass: every mechanism that repeats within a set keeps the sequence of its items (G61 test 3) and
  its position among the other repeated mechanisms (G61 test 2), in source order and on screen, on
  every sample and in every repeated opened state; the only differences are inserted or removed
  items, a missing component, or a user's choice.
- Not present: the scope holds one web page, or no mechanism recurs on two samples of one set.
- False positives to avoid: a sub-menu unfolded for the current section or a secondary navigation
  inserted (same relative order per the glossary note, and per the Intent note that sub-navigation
  and secondary blocks are allowed); Log in that becomes Log out, a cart badge that appears, a
  "current page" item that is unlinked or marked but stays in place; a mechanism at another
  vertical position because the content above it differs; a mechanism absent on some pages (G61's
  missing search form — a missing skip link is 2.4.1, an unreachable page 2.4.5); navigation
  placed at the end of every page, or a search field that is the last item on every page (the
  Understanding examples: consistent wherever it sits); a small-viewport copy of the menu compared
  against the desktop menu; a checkout, sub-domain or language version compared against the main
  site (another set); the same component with another label or icon (3.2.4); a visual order that
  differs from the DOM order in the same way on every page (1.3.2); a tab order that differs from
  the visual order (2.4.3).

## Reporting

- File under: 3.2.3, one issue per mechanism (the main menu, the footer, the skip link, the search)
  naming every sample where the order differs; the defect is the template, not one page. Another
  name or icon per page is 3.2.4; a help mechanism that moves is 3.2.6; a skip link missing on some
  pages is 2.4.1; a page no mechanism reaches is 2.4.5; a wrong reading order on every page is
  1.3.2; a mouse-only menu is 2.1.1.
- Title patterns: "Main menu items change order between pages", "Search field and menu swap places
  on some pages", "Skip link moves behind the menu on some pages", "Footer link groups appear in a
  different order per section"
- Severity: High when the main navigation, the search or the skip link changes order or place
  between the main templates (every task starts from it; magnifier and screen reader users lose it
  on every page change); Medium when a secondary mechanism (footer, utility links, breadcrumb) is
  reordered across several templates; Low when one page differs or one rarely used item swaps.
- Type: Design when the templates place or order the components differently and the layout has to
  be unified; Technical when one template renders the items in a varying order (a menu built from
  an unsorted data source, a CSS `order` or `flex-direction` that differs per page).
- Evidence: two screenshots, one per sample, of the page with `highlight` on the mechanism so its
  sequence and its place are both readable; for a collapsed menu, the screenshot with the menu
  open. Set the issue's `sample` to the sample whose order deviates from the one the other samples
  share, and name the compared sample in the first paragraph so the reader can line the two
  screenshots up. No GIF: nothing moves.
- Recommendation: render the repeated components from one shared template and one data source, in
  the same order on every page
  ([G61](https://www.w3.org/WAI/WCAG22/Techniques/general/G61)); other items may be inserted or
  removed between them as long as the remaining order does not change. F66's example, shortened —
  the two pages that fail:

  ```html
  <!-- page 1 -->
  <nav>
    <ul>
      <li><a href="brazil.html">Brazil</a></li>
      <li><a href="canada.html">Canada</a></li>
      <li><a href="germany.html">Germany</a></li>
    </ul>
  </nav>

  <!-- page 2: Canada and Brazil swapped, so the same links are in a different relative order -->
  <nav>
    <ul>
      <li><a href="canada.html">Canada</a></li>
      <li><a href="brazil.html">Brazil</a></li>
      <li><a href="germany.html">Germany</a></li>
    </ul>
  </nav>
  ```

  and the fix: one sequence on every page, the current page marked in place instead of moved, the
  section's sub-menu inserted under its own item:

  ```html
  <nav aria-label="Main">
    <ul>
      <li><a href="brazil.html">Brazil</a></li>
      <li>
        <a href="canada.html" aria-current="page">Canada</a>
        <ul>
          <li><a href="canada-visa.html">Visa</a></li>
        </ul>
      </li>
      <li><a href="germany.html">Germany</a></li>
    </ul>
  </nav>
  ```

  For a PDF set: running headers and footers
  ([PDF14](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF14)) with the same content in the same
  place on every page, and page numbering in the viewer that matches the numbering printed in the
  document ([PDF17](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF17), the `/PageLabels` entry).

- Related: 3.2.4 Consistent Identification (same function, same name: order here, naming there);
  3.2.6 Consistent Help (WCAG 2.2, Level A: a help mechanism must keep its relative order too, so
  a moving contact or help link is 3.2.6 first and 3.2.3 as well when it sits inside a repeated
  navigational mechanism); 2.4.1
  Bypass Blocks (the skip link exists on every page; its place is 3.2.3); 2.4.5 Multiple Ways (the
  mechanisms exist; their order is 3.2.3); 1.3.2 Meaningful Sequence (visual versus DOM order on
  one page); 2.4.3 Focus Order (a reordered DOM changes the tab order on that page).
