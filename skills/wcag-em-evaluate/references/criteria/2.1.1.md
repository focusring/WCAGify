# 2.1.1 Keyboard

Level A · WCAG 2.0+ · Guideline 2.1 Keyboard Accessible · Group: `keyboard`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#keyboard) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#keyboard) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-1-1-keyboard/) ·
ACT: [akn7bn](https://www.w3.org/WAI/standards-guidelines/act/rules/akn7bn/),
[0ssw9k](https://www.w3.org/WAI/standards-guidelines/act/rules/0ssw9k/)

## Requirement

> All functionality of the content is operable through a keyboard interface without requiring
> specific timings for individual keystrokes, except where the underlying function requires input
> that depends on the path of the user's movement and not just the endpoints.
>
> Note 1:
> This exception relates to the underlying function, not the input technique. For example, if
> using handwriting to enter text, the input technique (handwriting) requires path-dependent input
> but the underlying function (text input) does not.
>
> Note 2:
> This does not forbid and should not discourage providing mouse input or other input methods in
> addition to keyboard operation.

Terms (WCAG 2.2 glossary): **functionality**: "processes and outcomes achievable through user
action". The unit under test is the outcome a user can reach, never the control that happens to
trigger it: one finding per function, and a control Tab skips is a fail only when the outcome
behind it has no keyboard route at all (step 2). **keyboard interface**: "interface used by
software to obtain keystroke input", Note 1: "A keyboard interface allows users to provide
keystroke input to programs even if the native technology does not contain a keyboard" — speech
input, sip-and-puff, switch, scanning and on-screen keyboards all reach the page through the same
key events `press` produces, so a touch-first design is never an excuse. Note 2 in full: "Operation
of the application (or parts of the application) through a keyboard-operated mouse emulator, such
as MouseKeys, does not qualify as operation through a keyboard interface because operation of the
program is through its pointing device interface, not through its keyboard interface." The Intent
restates it: "The use of MouseKeys would not satisfy this success criterion because it is not a
keyboard equivalent to the application; it is a mouse equivalent (i.e., it looks like a mouse to
the application)." Nothing driven through `click`, `dblclick`, `hover`, `drag`, `mouse move`,
`mouse down` or `mouse up` ever demonstrates a pass; only `press`, `keyboard type`, and `focus`
followed by a key do.

"Specific timings for individual keystrokes" is defined by the Intent as "situations where a user
would be required to repeat or execute multiple keystrokes within a short period of time or where a
key must be held down for an extended period before the keystroke is registered". W3C puts no
number on "short period of time" or "extended period", so step 6 tests the two shapes (a repeat and
a hold) and records which one the page needs, never a threshold.

## In plain terms

Everything a mouse or touch user can do on the page, a keyboard user can do too: reach it with Tab
or the arrows and trigger it with one discrete key press, never a held key or a fast double press.
W3C's own summary is the whole test in one line — "Everything can be done with a keyboard except
freehand movements", by making sure "pointer actions have a keyboard equivalent". The unit is the
function, not the control: a submit button that Tab skips passes when Enter in the search field
submits, and a close icon passes when Escape closes the panel. Only functions whose outcome is the
path of the movement (freehand drawing, painting, a flight simulator) are exempt; moving, sorting,
resizing and connecting points are not. It matters to blind users, to users of keyboard emulators
(speech, sip-and-puff, switches, on-screen keyboards) and to users with tremor.

## Applies when

- Present: any function. `focusables.js` returns a non-empty `order` or `clickableNotFocusable`,
  `structure.js` lists `iframes` or `accesskeys`, `media.js` lists `media` (a player's controls are
  functions), or one of step 1's lists — `pointerOnly`, `unpairedHover`, `fakeLinks`,
  `cursorPointer`, `draggable`, `hoverMenus`, `pointerSurfaces`, `timingText` — is non-empty. Every
  recorded state counts: a cookie dialog, an open menu, an expanded section and an error state each
  bring their own functions.
- Not present: a sample state where `order`, `clickableNotFocusable`, `iframes`, `media` and every
  step 1 list are empty. A state with one link is `pass` or `fail`, never `not-present`.
- Exception (normative): "except where the underlying function requires input that depends on the
  path of the user's movement and not just the endpoints". The Intent draws the line and it is
  narrow: "Most actions carried out by a pointing device can also be done from the keyboard (for
  example, clicking, selecting, moving, sizing). However, there is a small class of input that is
  done with a pointing device that cannot be done from the keyboard in any known fashion without
  requiring an inordinate number of keystrokes. Free hand drawing, or watercolor painting require
  path dependent input. Drawing straight lines, regular geometric shapes, re-sizing windows and
  dragging objects to a location (when the path to that location is not relevant) do not require
  path dependent input."
- Note 1 puts the exception on the function, not on the input device: a handwriting field, a swipe
  carousel and a pinch-zoom map all have endpoint-only functions (enter text, next slide, zoom in)
  and are not exempt. A signature pad is the judgement call of "Deciding".
- Understanding examples that calibrate the exception: Example 4, a watercolor painting program,
  "passes as an exception because the brush strokes vary depending on the speed and duration of the
  movements"; Example 5, a model helicopter flight simulator, "passes as an exception because the
  nature of the simulator is to teach real-time behavior of a model helicopter"; Example 3, a
  connect-the-dots program that "allows the user to move between dots on a screen and use the
  spacebar to connect the current dot to the previous one", is not an exception — moving between
  and connecting discrete points is endpoint input; Example 1, a drawing program that "allows users
  to create, size, position and rotate objects from the keyboard", shows that create, size, position
  and rotate are expected from the keyboard even on a drawing surface.
- What the Understanding notes let pass without being an exception (an Enter-only or custom-key
  control, a separate mode of operation for keyboard users, Example 7's pointer-only submit button)
  is quoted in full under "False positives to avoid".
- Out of this browser's reach: a PDF opened in the browser's plugin viewer or embedded in an
  `object`/`embed`/`iframe`. Its tab order is not in the DOM, so step 10 records `cannot-tell` and
  queues it rather than guessing.

## axe-core

| Rule                          | Decides                | Result → outcome                            |
| ----------------------------- | ---------------------- | ------------------------------------------- |
| `frame-focusable-content`     | akn7bn, tabbable frame | violation → fail (100); incomplete → step 7 |
| `scrollable-region-focusable` | 0ssw9k, scroll region  | violation → fail (100); no incomplete       |
| `server-side-image-map`       | `img[ismap]` in a link | incomplete only, never a violation → step 9 |

`frame-focusable-content` applies to a non-inert `iframe` holding a visible element that is in the
frame's own focus order, and reports both violations and incompletes;
`scrollable-region-focusable` applies to an element that scrolls further than its own padding and
has visible children, and reports violations only, so step 8 re-checks its assumptions by hand;
`server-side-image-map` never reports a violation, only an incomplete per `img[ismap]`. All three
sit in axe-core's "WCAG 2.0 Level A & AA Rules" section, so `agent-browser a11y` runs them by
default; this criterion has no experimental or deprecated rule to switch on. Impacts are Serious,
Serious and Minor; impact never sets severity here, the rubric in "Reporting" does.
`scrollable-region-focusable` is tagged `wcag213` too, so the same violation is the 2.1.3 fail when
the report targets AAA.

Settles: same-origin frames excluded from the Tab order by a negative `tabindex`; scroll regions
with nothing focusable in or on them. Leaves open, and this list drives the procedure: controls a
pointer reaches that no key reaches (F54, F42); controls the keyboard reaches that no key operates;
every handler the DOM cannot show — `addEventListener` click and key handlers, hover menus, drag and
drop, double click, wheel, long press, swipe, `canvas` and `role="application"` surfaces; focus
removed on receipt (F55); functions that need a repeat or a hold; hover-only reveals with no focus
counterpart (SCR20, SCR2); cross-origin frames, whose inner focus order axe cannot read;
server-side image maps; keys swallowed by script inside a focusable scroll region — 0ssw9k is
explicit that its own rule does not cover this: "If scripts are used to prevent the keyboard events
from reaching the scrollable region, this could still cause a keyboard accessibility issue. This
must be tested separately."; and every state that only appears after an interaction.

## Manual procedure

The whole procedure is the test of
[G202](https://www.w3.org/WAI/WCAG22/Techniques/general/G202): "Identify all functionality on the
content. Check that all functionality can be accessed using only the keyboard or keyboard
interface." Work at `set viewport 1280 900`, default state first, then every recorded state. The Tab
walk log of 2.1.2 step 3 (`recon/<sample>-tabwalk.txt`) and its logger
(`.notes/audit/recon/focus-logger.js`) serve here too; produce them first when missing. `snapshot
-i` shows what is focusable and named, never whether a key handler exists: only a key press
followed by an observation decides. Wrap every `eval --stdin` body in `(() => { ... })()`, so a
second run does not throw on an already-declared identifier. Keep one row per function in the
findings file: `function`, `element`, `pointerOutcome`, `route`, `keys`, `verdict`.

1. Inventory the functions a pointer user has. Run the probes, then scan the DOM for the
   pointer-only signals it can show; `addEventListener` handlers stay invisible and steps 3 to 6
   are what catch those.

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/focusables.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/links.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/media.js
   agent-browser eval --stdin <<'EOF'
   (() => {
     const sel = e => e.localName + (e.id ? '#' + e.id : '');
     const q = s => [...document.querySelectorAll(s)];
     const F = 'a[href],button,input,select,textarea,summary,[tabindex],[contenteditable]';
     const vis = e => { const r = e.getBoundingClientRect();
       return r.width > 1 && r.height > 1 && getComputedStyle(e).visibility !== 'hidden' };
     return {
       pointerOnly: q('[onmousedown],[onmouseup],[onmouseover],[onmouseenter],[ondblclick],' +
         '[onmousemove],[onwheel],[oncontextmenu],[ondragstart],[ontouchstart],[onpointerdown]')
         .filter(e => !e.matches('[onkeydown],[onkeyup],[onkeypress],[onclick],' + F)).map(sel),
       unpairedHover: q('[onmouseover]:not([onfocus]),[onmouseout]:not([onblur]),' +
         '[onmousedown]:not([onkeydown]),[onmouseup]:not([onkeyup])').map(sel),
       fakeLinks: q('a:not([href])').filter(e => getComputedStyle(e).cursor === 'pointer').map(sel),
       cursorPointer: q('body *').filter(e => vis(e) && getComputedStyle(e).cursor === 'pointer' &&
         !e.closest(F) && !e.querySelector(F)).map(sel).slice(0, 40),
       draggable: q('[draggable="true"],[aria-grabbed],[class*="drag"],[class*="sort"]').map(sel),
       hoverMenus: q('nav li,[class*="menu"] li,[class*="dropdown"]').filter(e => e.querySelector(
         'ul,[role="menu"]') && !e.querySelector('button,[aria-expanded]')).map(sel),
       pointerSurfaces: q('canvas,[role="application"],img[ismap],object,embed,[class*="map"]')
         .filter(vis).map(sel),
       timingText: (document.body.innerText.match(
         /.{0,25}(press and hold|hold down|double[- ]?(click|tap)|long[- ]press|swipe).{0,25}/gi
       ) || [])
     };
   })()
   EOF
   ```

   `cursorPointer` is capped at 40 entries, so a full list is a sign to read the page rather than a
   complete inventory. Done when every function a pointer user has — each link, control, widget,
   menu, drag, frame, media player, surface and map — is a row in the findings file with the element
   that performs it and the outcome it produces.

2. Reach. Every function's element, or one that reaches the same outcome, appears in the walk log
   (Tab) or is reached with arrows from a logged element (composite widget: `focus` the logged item,
   `press ArrowDown`, run the logger). G202 is explicit that the individual control need not be the
   one reached: "This does not necessarily mean that each of the individual controls can be used
   from the keyboard as long as there are multiple methods to perform the same function available on
   the page." So for every `clickableNotFocusable`, `pointerOnly`, `fakeLinks` and `cursorPointer`
   entry — an `a` without `href` that navigates is
   [F42](https://www.w3.org/WAI/WCAG22/Techniques/failures/F42) — hunt for the second route: a
   `links.js` link with the same `href`, an `order` entry with the same `name` (`find role button
--name "<name>"`), Enter in the text field of the same form, Escape for a close icon, or an
   `accesskey` from `structure.js` (`press "Alt+<key>"` and observe; an accesskey counts as a
   keyboard route here and raises 2.1.4 separately). Worked example, Understanding Example 7:
   `focusables.js` lists the search field but not the submit button; `focus "<search field css>"`,
   `keyboard type "wcag"`, `press Enter`, `get url` shows the results URL — the function "submit the
   search" is reached, the sample passes for it, and no issue is filed for the skipped button. Done
   when every function reads "reached by <element>", "same outcome via <route>" or "unreachable".

3. Operate every reachable element: `focus "<selector>"`, run the logger, `press <Key>`, `wait 300`,
   then `snapshot -i` and `get url`. Keys: link Enter; button Enter then Space; checkbox and switch
   Space (`is checked "<selector>"`); radio and tab arrows; select, combobox and menu button
   ArrowDown then Enter, Escape to close; slider and spinbutton ArrowRight, Home, End (`get attr
"<selector>" aria-valuenow`); listbox, tree and grid arrows then Enter; disclosure Enter (`get
attr "<selector>" aria-expanded`); dialog Escape; `contenteditable` `keyboard type` a word (`get
html "<selector>"`). A logger line other than the element after `focus` is focus removed on
   receipt ([F55](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55): `onfocus="this.blur()"`).
   Compare with the pointer outcome (`reload`, `click "<selector>"`, same observation): the same
   URL, tree change, attribute or value is operable; a different outcome is comparable only when it
   reaches the same end. For an `a` or `button` whose action is scripted
   ([SCR35](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR35)) check both halves on
   Enter: the scripted action runs, and `get url` does not show the raw `href` (`#` or a fallback
   page) being followed instead. A control that answers Enter but not Space is still a pass — "If a
   custom button control in a web application instead only reacts to Enter (or even a completely
   custom key or key combination), this still satisfies the requirements of this success criterion."
   Record the key it needs as a usability note. Done when each element reads "operates with <keys>"
   or "no key".

4. Pointer-only functions ([F54](https://www.w3.org/WAI/WCAG22/Techniques/failures/F54)). Hover
   menu: `hover "<selector>"`, `snapshot -i`, note the submenu links; `press Escape`, `focus` the
   top-level link, `press Tab` and `press ArrowDown` with the logger: it passes when a logged line
   lands in the submenu or the link's `href` opens a page listing the same links (`get attr
"<selector>" href`, `open <href>`, run `links.js`, `back`). Drag (sortable lists, cards, a knob,
   a map): `drag "<src>" "<dst>"` to learn the outcome, `reload`, `focus "<src>"`, try ArrowUp,
   ArrowDown, Space then arrows, and look in `snapshot -i` for a Move up, Move down, Send to or Zoom
   control or a field taking the same value — the two sufficient shapes are Understanding Example 2,
   "An application that uses drag and drop also supports 'cut' and 'paste' or form controls to move
   objects", and [G90](https://www.w3.org/WAI/WCAG22/Techniques/general/G90) Example 2, "a list of
   the questions followed by a text field that allows users to re-order questions as needed by
   entering the desired question number". Double click and mouse move have no key of their own —
   [SCR20](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR20): "Some mouse-specific
   functions (such as dblclick and mousemove) do not have a corresponding keyboard-specific
   function. This means that some functions may need to be implemented differently for each device
   (for example, including a series of buttons to execute, via keyboard, the equivalent
   mouse-specific functions implemented)" — so run `dblclick "<selector>"` for the outcome, then
   look for a separate control that reaches it, not for a key on the same element. `canvas`,
   `role="application"` or a map (`pointerSurfaces`): `screenshot "<selector>" <before.png>`, `press
ArrowRight`, `keyboard type "+"`, `screenshot "<selector>" <after.png>`; identical images with no
   pan, zoom or select control in `snapshot -i` is "no route"; images that differ for another reason
   (an animation) with no such control is `cannot-tell`. Done when each entry has a route or none.

5. Hover-and-focus parity (SCR20,
   [SCR2](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR2)). For each
   `unpairedHover` entry and each element whose hover changed the page in step 4: `reload`, `hover
"<selector>"`, `wait 300`, `snapshot -i > .notes/audit/recon/<sample>-hover.txt`, then
   `reload`, `focus "<selector>"`, `wait 300`, `snapshot -i >
.notes/audit/recon/<sample>-focus.txt`, and diff the two. SCR20 gives the pairing to expect:
   mousedown with keydown, mouseup with keyup, click with keypress, mouseover with focus, mouseout
   with blur — and notes that click needs no duplicate on a natively focusable element, because most
   user agents fire it "regardless of whether it was activated with the mouse or the keyboard". What
   only the hover snapshot contains decides the split: links, buttons or fields are functionality
   and belong here when step 2 finds no other route; text, an image or a tooltip with no control in
   it is information and goes to 1.4.13 instead. Done when each entry reads "focus reveals the
   same", "information only → 1.4.13" or "functionality reachable only by hover".

6. Timing and modifiers. For each `timingText` hit and each control whose pointer outcome needed a
   held button or a double click, `press` the key once: the outcome must follow one down-up pair.
   Then, through `eval --stdin`, `focus()` the element, dispatch a `keydown` `KeyboardEvent`, wait
   1500 ms and dispatch the `keyup`; an outcome that appears only after that hold is a hold-to-act
   timing. Repeat quickly for the other shape (`press Enter`, `wait 100`, `press Enter`) and record
   an outcome that needs the pair. Neither shape has a W3C threshold: record what the page required.
   Then the modifier case — the Intent assumes "that the design of user input features takes into
   account that operating system keyboard accessibility features may be in use. For example,
   modifier key locking may be turned on. Content continues to function in such an environment, not
   sending events that would collide with the modifier key lock to produce unexpected results."
   Sticky keys cannot be emulated here, so a function that needs a held modifier (Ctrl+drag,
   Shift+click, Alt+key) is recorded for the confirmation queue. Done when each is "single", "timed"
   or "modifier, to confirm".

7. Frames (akn7bn, `frame-focusable-content`). The rule "applies to any iframe element that is not
   inert and that contains at least one element for which all the following are true: the element is
   visible; and the element is part of the sequential focus navigation order of the iframe's
   document" — both conditions, so a frame whose only link carries its own `tabindex="-1"` is
   inapplicable, and so is a frame that is `hidden`, sized down to nothing, or inert. Inert is "it
   has an inert attribute value of true; or one of its ancestor elements in the flat tree has an
   inert attribute value of true; or it is blocked by a modal", which is why a frame behind an open
   `showModal()` dialog is out of scope in that state. The single Expectation is "The test target
   does not have a negative number as a tabindex attribute value." Collect the facts, then look
   inside:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => [...document.querySelectorAll('iframe, frame')].map(f => {
     const r = f.getBoundingClientRect(), cs = getComputedStyle(f);
     return { selector: f.localName + (f.id ? '#' + f.id : ''), src: f.getAttribute('src'),
       tabindex: f.getAttribute('tabindex'), title: f.getAttribute('title'),
       inert: f.inert || !!f.closest('[inert]'), w: Math.round(r.width), h: Math.round(r.height),
       hidden: f.hasAttribute('hidden') || cs.display === 'none' || cs.visibility === 'hidden' };
   }))()
   EOF
   ```

   For every entry whose `tabindex` parses to a negative number and that is neither inert nor
   hidden: `frame "<iframe css>"`, run `focusables.js`, `frame main`; when `frame` is refused
   (cross-origin): `tab new`, `open <src>`, run `focusables.js`, `tab close`. A visible `order`
   entry inside is the akn7bn fail. Then Tab into every non-negative frame from the outer walk log
   and apply the step 3 keys to the inner controls. The rule's own assumption limits the fail: "This
   rule assumes that interactive content inside iframe elements is used to provide functionality. If
   the interactive content does not provide functionality, for example a button that does nothing
   when clicked, success criterion 2.1.1 may be satisfied, even if the rule is failed." Done when
   every frame reads "in Tab order, operable", "inapplicable (<reason>)", the akn7bn fail, or
   `cannot-tell` for a `src` that refuses to open on its own.

8. Scroll regions (0ssw9k, `scrollable-region-focusable`). The rule "applies to any HTML element
   that has visible children in the flat tree, and for which at least one of the following is true:
   the element has a horizontal scroll distance greater than the computed left or right padding of
   the element; or the element has a vertical scroll distance greater than the computed top or
   bottom padding of the element" — horizontal counts as much as vertical, and a region whose
   overflow is smaller than its own padding is out of scope. The Expectation has two ways to pass:
   "Each test target is either included in sequential focus navigation or has a descendant in the
   flat tree that is included in sequential focus navigation." Check both before accepting an axe
   violation: `get attr "<selector>" tabindex` (`0` on the region itself satisfies the first branch)
   and an `order` entry inside the region satisfies the second. `focus "<selector>"` then `press
ArrowDown` does scroll it in Chromium, which focuses scroll regions by itself — the rule's
   Accessibility Support warns that this is not universal ("Some browsers will automatically make
   any scrollable element focusable to ensure keyboard accessibility. However, the browser does not
   include these elements in sequential focus navigation when it has a negative number as a tabindex
   attribute value.") and that the content-box/border-box difference makes an element "scrollable
   with a browser but not with another" — so the markup verdict stands over what Chromium does.
   Downgrade to a note only for the rule's assumptions: content that is "purely decorative", a
   "scroll area [that] is whitespace", or scroll that "can be controlled in some other keyboard
   accessible way such as through a button or custom scrollbar" — verify that control by pressing
   Enter on it and reading the region's offsets:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => { const el = document.querySelector('<region css>');
     return { top: el.scrollTop, left: el.scrollLeft, h: el.scrollHeight, ch: el.clientHeight };
   })()
   EOF
   ```

   Run that before and after `press ArrowDown` with focus in the region as well: offsets that do not
   move while `scroll down` does move them is script swallowing the keys, which 0ssw9k leaves to
   this step ("This must be tested separately"). Scrollable `iframe` content is not this rule's
   business ("it is the embedded document that scrolls") and is step 7's. Done when each region
   reads "in the focus order", "focusable descendant", "exempt (<assumption>)" or the fail.

9. Server-side image maps (`server-side-image-map` incomplete). Every hit is an `img[ismap]` inside
   a link, whose destination is the pixel coordinate the pointer hit — a coordinate no keystroke can
   supply. Run `agent-browser eval --stdin < <skill-dir>/scripts/probes/images.js` and, for each
   hit, look beside the image for an equivalent: a client-side map (`images.js` entries with `kind:
'area'`, each with a `name` and an `href`) or text links (`links.js`) to the same
   destinations. None of either is the fail. Done when each `ismap` image reads "equivalent via
   <route>" or "no equivalent".

10. Embedded and linked documents. `get count "object, embed"` above 0, an `iframes` entry whose
    `src` ends in `.pdf`, or a `links.js` `href` ending in `.pdf` means part of the sample's
    functionality lives in a format this browser cannot walk: the plugin viewer's tab order is not
    in the DOM, and `press Tab` inside it produces no logger line. Record those functions as
    `cannot-tell` with the file name and queue them for a human, who tests the document's own tab
    order and form controls
    ([PDF3](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF3),
    [PDF11](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF11),
    [PDF23](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF23) are the fixes to cite there). Done
    when each embedded or linked document is listed with its URL and its queue entry.

11. States and evidence. Repeat steps 1 to 6 in each recorded state, opened with the keyboard
    (`focus "<trigger>"`, `press Enter`); a state that only `click` opens is itself a step 4
    candidate. The consent dialog is the first state: its accept, reject and settings controls pass
    step 3 or the sample fails. For each fail: `record start
.notes/audit/evidence/<sample>-2.1.1-<slug>.webm`, `focus` the `order` entry before the element,
    `press Tab`, `press Enter`, `press Space`, `record stop`, then `highlight "<selector>"` and
    `screenshot` to the same name with `.png`. Done when every fail has a recording of the keys
    doing nothing and a screenshot of the element.

## Deciding

- Fail (certainty ≥ 90): a `frame-focusable-content` or `scrollable-region-focusable` violation
  (100); a `clickableNotFocusable`, `pointerOnly` or `cursorPointer` element whose function has no
  other keyboard route (F54) — 95; an `a` without `href`, or a `span`, `div` or `img` with a click
  handler, that navigates and never gets focus (F42) — 95; a reachable control (a consent dialog's
  buttons above all) whose pointer outcome no key reproduces, no key documented — 95; a hover menu
  whose submenu links no key reveals and no landing page lists — 90; a sortable, movable or
  resizable object with no key, control or field for the same end — 90; a control that drops focus
  on receipt (F55) — 90; an `img[ismap]` link with no client-side map and no equivalent text links
  — 90; an `iframe` with a negative `tabindex` that is not inert or hidden and holds a visible
  element in its own focus order (akn7bn) — 90; a scroll region that focus reaches while script
  swallows its arrow keys (offsets unchanged after `press ArrowDown`, moved by `scroll down`) — 90.
- Fail (70–89): a double-click-only action whose single press does something lesser and that has no
  separate control for the same end — 85; a swipe carousel whose Next and Previous controls are not
  in `order` and no key advances — 85; a function that fires only after a held key or only after a
  quick repeat — 80; a `canvas`, `role="application"` surface or map that no key pans, zooms or
  selects while `snapshot -i` shows no control for it — 80; hover-revealed links or controls that
  `focus` does not reveal and step 2 finds no route to (SCR20, SCR2) — 80; a keyboard route that
  ends short of the pointer outcome (arrows skip slider values the pointer reaches) — 75.
- Needs confirmation (50–69): a path-exception candidate (signature pad, drawing surface, a game)
  — 60: ask "is the drawn path itself the outcome, or only its endpoints?"; a cross-origin frame
  whose `src` refuses to open on its own — 55: ask the human to Tab into it; a function that needs
  a held modifier (Ctrl+drag, Shift+click) — 55: ask the human to try it with modifier key locking
  on, which this browser cannot emulate; a PDF or other embedded document carrying part of the
  functionality — 50: record `cannot-tell` and ask the human for its tab order.
- Pass: every function of step 1, in every state, is reached (step 2) and operated (steps 3 to 5)
  with single presses (step 6) to the same or a comparable outcome; every frame and scroll region is
  reachable or inapplicable; every `img[ismap]` has an equivalent; path exceptions are recorded with
  their reason. A route that needs MouseKeys or a screen reader's virtual cursor is not a route (the
  glossary's Note 2), and neither is an outcome only `click` or `drag` produced.
- Not present: a sample state with no function at all: empty `order`, `clickableNotFocusable`,
  `iframes`, `media` and step 1 lists.
- False positives to avoid: a control Tab skips while the same outcome has a keyboard route —
  Understanding Example 7 in full: "A search form includes a text input field followed by a submit
  button. The submit button itself has been coded so that it does not receive focus, and can only be
  activated using a pointer input. However, since keyboard users can submit the search by pressing
  Enter in the text input after typing their search terms, the form passes this success criterion."
  The Understanding states the general rule too: "This success criterion does not require that every
  visible control that can be activated using a mouse or touchscreen must also be focusable and
  actionable using the keyboard. The normative requirement is only that there must be a way for
  keyboard interface users to perform the same, or comparable, actions and to operate the content.
  [...] if a web application implements a separate mode of operation for keyboard interface users,
  it will not fail the success criterion." A non-standard key is not a fail either: "Platforms and
  user agents usually have conventions for how web content or applications are controlled with a
  keyboard interface. [...] However, deviating from these conventions does not fail the normative
  requirement of this success criterion." An emulated link that does work from the keyboard is not
  this criterion's fail — F42 Example 3 has `tabindex="0"` and a key handler and still says "the
  element will not be recognized as a link", which is 1.3.1 and 4.1.2, not 2.1.1. Also not fails
  here: `tabindex="-1"` items of a composite widget reached with arrows from its one tabbable item;
  a skip-link target; an `iframe` with a negative `tabindex` that is `hidden`, inert, blocked by a
  modal, sized to nothing, whose tabbable content is not visible, or whose only focusable child
  carries its own negative `tabindex`
  (akn7bn inapplicable examples); a scroll region with a tabbable descendant, with `tabindex="0"` on
  itself, or whose content is decorative or whitespace, or which an external control scrolls (0ssw9k
  assumptions); an invisible focus ring (2.4.7); a surprising focus order (2.4.3).

## Reporting

- File under: 2.1.1 for every function without a keyboard route. Focus that cannot leave is 2.1.2; a
  wrong or lost order 2.4.3; an invisible ring 2.4.7; a focusable element without name or role 4.1.2
  (F42: a second issue there when the role is missing too, and one under 1.3.1 when the element is a
  link in appearance only); focus dropped on receipt is one issue here naming 2.4.7 and 3.2.1 (F55);
  a drag with no single-pointer alternative is a second issue under 2.5.7; hover-revealed content
  that is information rather than functionality belongs to 1.4.13. One issue per function or widget,
  naming every sample it occurs on.
- Title patterns: "The <menu> cannot be opened with the keyboard", "The <control> is skipped by Tab
  and has no keyboard alternative", "<Items> can only be reordered by dragging", "The cookie dialog
  cannot be accepted with the keyboard", "<Widget> is left out of the Tab order", "The <panel> can
  only be scrolled with the mouse", "The <map> can only be zoomed and panned with the mouse", "The
  <submenu> only appears on hover", "<Action> requires a double click"
- Severity: High when the function is on a task path (navigation, search, submit, consent, login,
  close a blocking overlay) or hides content; Medium when it is optional, has a comparable but
  longer route, or works in one state only; Low when a convenience has an equivalent nearby.
- Type: Technical (markup and script: the element, `tabindex`, key handlers, frame attributes).
- Evidence: the recording of Tab skipping the control or of Enter and Space doing nothing on it,
  plus a page screenshot with `highlight "<selector>"` on the control, frame or scroll region. For a
  drag or a hover menu, record the pointer doing the thing first and the keyboard failing after, in
  one GIF, so the reader sees the function exists.
- Recommendation: use the native element
  ([H91](https://www.w3.org/WAI/WCAG22/Techniques/html/H91)) and hang the action on its click, which
  "is actually mapped to the default action of a link or button" and therefore fires on Enter and
  Space as well as on a pointer
  ([SCR35](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR35)):

  ```html
  <button type="button" onclick="nextPage()">Go to next page</button>
  <a href="/survey-results">View the results of the survey</a>
  ```

  Where a native element is impossible, make the static element focusable, named and keyed —
  `tabindex="0"` plus a key handler beside the click handler
  ([SCR29](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR29) uses `onkeyup` or
  `onkeypress`; `keydown` with `preventDefault()` also stops Space scrolling the page,
  [G90](https://www.w3.org/WAI/WCAG22/Techniques/general/G90)). SCR29 warns that such a control
  "must still satisfy Success Criterion 4.1.2 Name, Role, Value", so the role belongs in the same
  fix:

  ```html
  <span
    role="button"
    tabindex="0"
    onclick="go()"
    onkeydown="if (event.key === 'Enter' || event.key === ' ') { event.preventDefault(); go() }"
    >Do something</span
  >
  ```

  Pair every pointer handler with its keyboard counterpart — mousedown with keydown, mouseup with
  keyup, mouseover with focus, mouseout with blur
  ([SCR20](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR20),
  [SCR2](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR2)); click needs no
  duplicate on a natively focusable element:

  ```html
  <a
    href="menu.php"
    onmouseover="swapImageOn('menu')"
    onfocus="swapImageOn('menu')"
    onmouseout="swapImageOff('menu')"
    onblur="swapImageOff('menu')"
    ><img id="menu" src="menu_off.gif" alt="Menu"
  /></a>
  ```

  Give drag, hover, double-click and gesture actions a keyed equivalent
  ([G202](https://www.w3.org/WAI/WCAG22/Techniques/general/G202)): arrows or Move up and Move down
  buttons for sorting, a text field for the target position, a Next button for a swipe, ArrowDown on
  a hover menu's top item, cut and paste for a drag. Remove `onfocus="this.blur()"` and anything
  else that discards focus (F55). Take the negative `tabindex` off a frame that holds controls, and
  make a scrollable region reachable itself or through a focusable descendant:

  ```html
  <iframe title="Video player" src="/player"></iframe>
  <section tabindex="0" style="height: 100px; width: 500px; overflow: scroll;">…</section>
  ```

  For functionality that lives in a PDF, cite PDF3, PDF11 and PDF23 for its tab order, links and
  form controls.

  `scrollable-region-focusable` is tagged for it); 2.4.3 and 2.4.7 (reachable but disorienting or
  invisible); 4.1.2 and 1.3.1 (the custom control's role, name and state); 2.5.7 (the pointer side
