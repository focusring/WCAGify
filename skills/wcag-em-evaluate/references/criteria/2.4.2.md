# 2.4.2 Page Titled

Level A · WCAG 2.0+ · Guideline 2.4 Navigable · Group: `structure`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/page-titled.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#page-titled) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#page-titled) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-4-2-page-titled/) ·
ACT: [2779a5](https://www.w3.org/WAI/standards-guidelines/act/rules/2779a5/),
[c4a8a4](https://www.w3.org/WAI/standards-guidelines/act/rules/c4a8a4/)

## Requirement

> Web pages have titles that describe topic or purpose.

Terms (WCAG 2.2 glossary), verbatim; these decide what counts as one page and what counts as empty:

- **web page**: "a non-embedded resource obtained from a single URI using HTTP plus any other
  resources that are used in the rendering or intended to be rendered together with it by a user
  agent". Note 1: "Although any "other resources" would be rendered together with the primary
  resource, they would not necessarily be rendered simultaneously with each other." Note 2: "For
  the purposes of conformance with these guidelines, a resource must be "non-embedded" within the
  scope of conformance to be considered a web page." Note 2 is the clause that takes `iframe`,
  `object` and `svg` documents out of scope; Note 1 is the clause that keeps one URI with several
  areas a single web page.
- Its **Example 2**, verbatim: "A web mail program built using Asynchronous JavaScript and XML
  (AJAX). The program lives entirely at http://example.com/mail, but includes an inbox, a contacts
  area and a calendar. Links or buttons are provided that cause the inbox, contacts, or calendar to
  display, but do not change the URI of the page as a whole." One title can therefore serve all
  three areas: a view at an unchanged URI is not automatically a page of its own.
- Its **Example 3**: "A customizable portal site, where users can choose content to display from a
  set of different content modules." Its **Example 4**: a shopping environment at one URI, "[...]
  This might be a single-page website or just one page within a website." Where the sample set
  itself lists such a view as a distinct sample, treat it as a page and title it (step 5).
- ACT glossary, **web page (HTML)** (the scope both ACT rules use): "An HTML web page is the set of
  all fully active documents which share the same top-level browsing context." Note: "Nesting of
  browsing context mostly happens with iframe and object." Note: "Web pages as defined by WCAG are
  not restricted to the HTML technology but can also include, e.g., PDF or DOCX documents."
- ACT glossary, **whitespace**: "Whitespace are characters that have the Unicode "White_Space"
  property in the Unicode properties list" — all characters in the Unicode Separator categories
  (which includes the no-break space U+00A0), plus character tabulation (U+0009), line feed
  (U+000A), line tabulation (U+000B), form feed (U+000C), carriage return (U+000D) and next line
  (U+0085). A title holding only these characters is empty for ACT 2779a5 even when it looks like
  text in the terminal (step 2).

## In plain terms

Each web page carries a title that names what the page is about or what it is for, so that a person
identifies the page from the browser tab, the window bar, the history, a bookmark, a site map or a
list of search results without reading or interpreting the content. For a document or a web
application the name of the document or application is enough, and W3C adds that "it is not
required to use the name of the document or web application; other things may also describe the
purpose or the topic of the page". A single-page application changes the title as its views change.
Screen reader users hear the title first on every load and tell open tabs apart by it; people with
cognitive disabilities, limited short-term memory and reading disabilities recognise content by it;
people with severe mobility impairments "whose mode of operation relies on audio when navigating
between web pages" decide by it whether to stay.

## Applies when

- Present: on every HTML sample — the document at the sample's address is a web page, with or
  without a title. Also on every recorded state that is a page of its own: a view whose URL changed
  (`get url` differs from the sample's address) or, at one URI, a view the sample set lists as a
  distinct sample (a route, a wizard step, a search result set). `get title` and the `title` field
  of `structure.js` read the title. A PDF sample is a web page as well; its title is the Title entry
  of its document information dictionary
  ([PDF18](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF18)).
- Not present: never. A WCAG-EM sample is always a web page; every sample ends in `pass`, `fail`
  or `cannot-tell`.
- Exceptions: none in the criterion text. Scope limits from the ACT rules, all decided before any
  judgement:
  1. Embedded documents. 2779a5 Background: "This rule is only applicable to non-embedded HTML
     pages. HTML pages embedded into other documents, such as through iframe or object elements are
     not applicable because they are not web pages according to the definition in WCAG." c4a8a4
     Background adds `svg` to that list. Judge the top-level document only; ignore every `title`
     whose `namespaceURI` is not the HTML namespace, and every `title` inside an embedded document.
  2. A higher-level protocol. 2779a5 assumes "that the title of the page is not provided by a
     higher-level protocol. For example, the subject field of an email authored in HTML can provide
     a title without requiring a title element." This does not occur on a sampled page; record it
     only if the sample is an HTML email body.
  3. Several `title` elements, or one outside `head`. Both rules assume 2.4.2 "does not require that
     a document only has one title element, nor that it is a child of the head element" and that
     "neither of these validation issues causes a conformance problem for WCAG". They are HTML
     validity faults, not WCAG faults: browsers use the first, and so do you.
  4. c4a8a4 is inapplicable when "The html web page has no document title" or "The document title
     contains only whitespace text nodes" — those cases are already decided by 2779a5, so record the
     fail from step 2 and do not re-judge descriptiveness.
- Outcome mapping the two rules publish, which fixes how far a pass carries: for 2779a5, "Any
  failed outcomes: success criterion is not satisfied" and "All passed outcomes: success criterion
  needs further testing" — a non-empty title is never a pass on its own. For c4a8a4, "Any failed
  outcomes: success criterion is not satisfied" and "All passed outcomes: success criterion is
  satisfied" — step 3 is what produces a `pass`.

## axe-core

| Rule             | Decides                               | Result → outcome                      |
| ---------------- | ------------------------------------- | ------------------------------------- |
| `document-title` | first HTML `title` non-empty (2779a5) | violation → fail (100); pass → step 3 |

The rule is in the "WCAG 2.0 Level A & AA Rules" set, on by default, and its `issueType` is
`failure` only: it never returns incomplete, so there is no incomplete result to chase here. On a
state the axe run did not cover, the rule decides nothing and step 2 takes its place.
Settles: existence and non-emptiness of the first HTML `title` element on every state the axe run
covered. Leaves open: everything descriptive — whether the text describes the topic or purpose of
this page (ACT c4a8a4, [G88](https://www.w3.org/WAI/WCAG22/Techniques/general/G88),
[F25](https://www.w3.org/WAI/WCAG22/Techniques/failures/F25)); a placeholder, authoring-tool
default, filename, URL or bare site name as the whole title; one title shared by distinct pages of
the site; a single-page application whose title does not follow its views; the title on a state axe
did not run on; and the Title entry and `DisplayDocTitle` viewer preference of a PDF sample
(PDF18). No axe rule implements c4a8a4.

## Manual procedure

Structure mode: read the sample as loaded, then each recorded state that is a page of its own. The
accessibility tree (`snapshot`) does not contain the document title, so `snapshot` decides nothing
here. `get title` returns `document.title`: the child text content of the first `title` element
with ASCII whitespace stripped and collapsed, which is what the tab, the window bar, the history
and a screen reader's page announcement use. Because the HTML getter strips only _ASCII_ whitespace,
a title made of no-break spaces or other Unicode separators comes back looking non-empty — step 2
is what settles that.

1. Read the title after the page has settled (a single-page application sets it by script):

   ```bash
   agent-browser wait --load networkidle
   agent-browser get title
   agent-browser get url
   agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
   ```

   Write one line into `.notes/audit/findings/<sample>--structure.md`, in this exact shape, so that
   step 4 can grep it across samples:

   ```text
   2.4.2 | <url> | title: "<exact string get title returned>" | h1: "<first level-1 heading>"
   ```

   Take the h1 from the first `structure.js` `headings` entry with `level: 1`; write `h1: none`
   when there is none. Check that `structure.js` `title` and `get title` agree; when they differ,
   the title changed between the two reads (a late script) — re-run both and record the settled one.
   Done when the exact title, or its absence, is in the findings file with the URL.

2. Confirm ACT 2779a5 where axe did not run on this state, where `get title` is empty, and where
   the returned title looks like blank space:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const ws = /^[\s\u0085]*$/;
     const titles = [...document.getElementsByTagName('title')]
       .filter(t => t.namespaceURI === 'http://www.w3.org/1999/xhtml');
     return {
       root: document.documentElement.tagName.toLowerCase(),
       count: titles.length,
       titles: titles.map((t, i) => {
         const text = [...t.childNodes]
           .filter(n => n.nodeType === 3).map(n => n.data).join('');
         return {
           i,
           inHead: !!t.closest('head'),
           inEmbedded: t.ownerDocument !== document,
           text,
           whitespaceOnly: ws.test(text),
           codePoints: [...text].slice(0, 8).map(c => c.codePointAt(0).toString(16)),
         };
       }),
     };
   })()
   EOF
   ```

   Applicability: "This rule applies to the root element of the web page, if it is an html
   element" — `root` is `html`. Expectation 1: "Each target element has at least one descendant
   that is a title element" — `count` is at least 1. Expectation 2: "For each target element, the
   first HTML title element that is a descendant of the document element has children that are text
   nodes that are not only whitespace" — `titles[0].whitespaceOnly` is `false`. Both expectations
   must hold; a rule outcome of passed needs each one, and one of them alone is not an outcome.
   `codePoints` names the characters in a title that prints as blank: `a0` is a no-break space and
   `85` is next line, both whitespace for this rule (JavaScript's `\s` covers every Unicode
   White_Space character except next line, which is why the test adds `\u0085`).

   Read the result against the rule's own examples: `count: 0` fails (Failed Example 1); a first
   entry with `whitespaceOnly: true` fails whatever the later entries hold (Failed Example 4: "This
   page has two title elements and the first is empty"); a title of one separator character fails
   (Failed Example 5). Two titles of which only the first has content passes (Passed Example 5), and
   `inHead: false` alone passes (Passed Example 4). `inEmbedded: true` entries are out of scope, and
   a page whose only title sits inside an `iframe` document still fails: "The title element in the
   content of the iframe does not function as the title for the entire page" (Failed Example 3).
   A failure here settles the criterion — "Regardless of whether this is required by 2.4.2 Page
   Titled, failing this rule means the success criterion is not satisfied". Done when the state has
   a 2779a5 outcome of passed or failed recorded next to its title line.

3. Judge whether the title describes topic or purpose (ACT c4a8a4, G88). Gather the page's own
   description of itself and compare:

   ```bash
   agent-browser get count "h1"
   agent-browser get text "h1"
   agent-browser get attr "html" lang
   agent-browser screenshot .notes/audit/evidence/<sample>--2.4.2-title.png --full
   ```

   With `get count "h1"` at 0, skip `get text "h1"` (it reports the element as not found) and take
   the page's own wording from the first `headings` entry of step 1 and from the screenshot; a page
   without an h1 still passes here. Read the screenshot and answer c4a8a4's single expectation: the
   target "describes the topic or purpose of the overall content of the document".

   Apply G88's checklist to the recorded string. The title of each web page should: "Identify the
   subject of the web page"; "Make sense when read out of context, for example by a screen reader or
   in a site map or list of search results"; "Be short". G88 adds two that "may also be helpful":
   "Identify the site or other resource to which the web page belongs" and "Be unique within the
   site or other resource to which the web page belongs". Only the first two decide the outcome; a
   long title, a missing site name and a duplicate on a page of the same purpose are not failures on
   their own.

   It describes when a person who sees only the title, in a list of tabs or the history, knows which
   page this is: the h1 or the page's task is named in it, or it is the name of the document or web
   application the page is. Worked comparison, from c4a8a4 Failed Example 3: title "University of
   Arkham", h1 "Search results for "accessibility" at the University of Arkham" — the title "does
   not describe the page", it names only the site, so the outcome is failed. It does not describe
   when the title names another topic than the content (Failed Example 1: title "Apple harvesting
   season" over a page about clementines), or when the first of two titles is the wrong one (Failed
   Example 2: "Most browsers, and this rule, only look at the first title element").

   Match the string against F25's list of text that is not a title: "Authoring tool default titles,
   such as "Enter the title of your HTML document here," "Untitled Document," "No Title," "Untitled
   Page," "New Page 1""; "Filenames that are not descriptive in their own right, such as report.html
   or spk12.html"; "Empty text"; "Filler or placeholder text". Modern equivalents of the same defect
   are build and framework defaults ("Document", "React App", "Vite App") and unsubstituted template
   tokens ("{{ title }}", "%PAGE_TITLE%"). Wording that differs from the h1, the site name placed
   before or after the page name, and the length of the title do not decide.

   Where the sample set holds two editions or dates of the same page, G88's Example 4 sets the bar:
   "A website that only permits viewing of the current edition titles its web page "National News,
   Front Page". A website that permits editions from different dates to be viewed titles its web
   page, "National News, Front Page, Oct 17, 2005"." Done when the title is marked "describes" or
   "does not describe" on its findings line, with the h1 text next to it.

4. Compare with the other samples. Read the title lines already written for the samples evaluated
   before this one:

   ```bash
   grep -h '^2\.4\.2 |' .notes/audit/findings/*--structure.md | sort -u
   ```

   One title standing on samples whose h1 and content differ cannot describe each of them; F25's
   Example 2 is exactly this: "A site generated using templates includes the same title for each
   page on the site. So the title cannot be used to distinguish among the pages." Two samples that
   are the same page reached by two URLs are not this defect. The Understanding's own passing set
   shows how far a shared suffix may go: "Patterns | APG | WAI | W3C", "Alert and Message Dialogs
   Pattern | APG | WAI | W3C", "Practices | APG | WAI | W3C", "Index | APG | WAI | W3C" — the site
   name repeats, the leading part does not. Done when the title is marked "shared" or "distinct",
   naming the samples it is shared with.

5. Repeat steps 1 to 3 in every recorded state that is a page of its own: after the state is
   reached, `get url` and `get title` again, and compare both against the values from step 1. A view
   with its own URL (client-side routing) is a web page and needs its own describing title. At an
   unchanged URI, the Understanding asks: "In cases such as Single Page Applications (SPAs), where
   various distinct pages/views are all nominally served from the same URI and the content of the
   page is changed dynamically, the title of the page should also be changed dynamically to reflect
   the content or topic of the current view." The Intent also allows the application's own name —
   "In cases where the page is a document or a web application, the name of the document or web
   application would be sufficient to describe the purpose of the page" — so a static application
   name across distinct views is a judgement call, not a deterministic fail (see Deciding). W3C's
   own web application example shows what the title is expected to do: "A banking application lets
   users inspect their bank accounts, view past statements, and perform transactions. The web
   application dynamically generates titles for each web page, e.g., "Bank XYZ, accounts for Alex
   Smith" "Bank XYZ, December 2005 statement for Account 1234-5678"." An open menu, dialog, expanded
   section or error state on the same page keeps the page's title and needs no new one. Done when
   every recorded state has a title and a URL on its own findings line.

6. A PDF sample is outside this procedure: the browser exposes neither its Title entry nor its
   `DisplayDocTitle` viewer preference, and PDF18 applies to tagged PDF documents. Record
   `cannot-tell` and queue it for a human with the two checks PDF18 names — "check that the document
   title is specified" and "view the /Title entry and /DisplayDocTitle flag settings" — plus where
   to look in Adobe Acrobat Pro: File → Properties → Description tab for the Title field, and File →
   Properties → Initial View → Window Options → Show → Document Title for the flag. Done when the
   queue entry names the sample, its URL and both checks.

What the tree cannot show: whether a screen reader announces a title changed by script on a view
change (screen readers read the title on load and on tab switch, not on `document.title` writes).
That is not a 2.4.2 question: record the title itself; a view change a screen reader user does not
notice is a focus management matter (2.4.3).

## Deciding

- Fail (certainty ≥ 90): no HTML `title` element in the document (axe `document-title`: 100; by the
  step 2 result `count: 0` on a state axe did not cover: 95); the first `title` element empty
  (100 / 95); the first `title` element whitespace only by the ACT definition — spaces, a lone
  separator character, a no-break space (`codePoints` `a0`) or next line (`85`) — 95; the page's
  only title sits inside an `iframe`, `object` or `svg` document (2779a5 Failed Example 3) — 95; a
  title that is an authoring-tool, build or template default ("Untitled Document", "No Title",
  "Untitled Page", "New Page 1", "Enter the title of your HTML document here", "Document", "React
  App", "{{ title }}") — 90 (F25).
- Fail (70–89): the title is the site or company name alone on a page that is neither the site's
  home page nor the application itself (c4a8a4 Failed Example 3) — 85; the title names a different
  topic than the h1 and the content (a copied page, c4a8a4 Failed Example 1) — 85; the first of
  several titles is the non-descriptive one while a later one describes the page (c4a8a4 Failed
  Example 2) — 85; one title shared by samples whose h1 and content differ (F25 Example 2) — 80; a
  filename, path or URL as the title ("report.html", "spk12.html") — 80; filler or placeholder text
  left in the title field — 80; a view with its own URL in a single-page application that keeps the
  previous view's title — 75.
- Needs confirmation (50–69): a static application name on every view of a single-page application
  at one URI ("Bank XYZ" on the accounts and on the statements view) — 60; ask whether the views are
  meant as distinct pages, because the Intent allows the application's name for the application as a
  whole. A title that is accurate but vague ("Overview", "Details", "Step 2") — 60; ask what the
  page is for. Two samples that are different editions or dates of one page under one title (G88
  Example 4) — 60; ask whether both editions stay reachable. A title that describes the page in
  another language than the page's `lang` — 55; ask whether it is intended.
- Pass: the first HTML `title` element of the sample, and of every recorded state that is a page of
  its own, holds text that is not whitespace (2779a5 Expectations 1 and 2) and that names the topic
  or purpose of that page — its subject, its task, or the document or application it is (c4a8a4
  Expectation) — is not a placeholder, an authoring-tool default, a filename or a URL, is not the
  bare site name unless the page is the site's home page or the application itself, and differs from
  the title of samples with other content. Only a passed c4a8a4 outcome makes the criterion
  satisfied; a passed 2779a5 alone leaves it open.
- Not present: never; every sample is a web page.
- False positives to avoid: several `title` elements, or a `title` inside `body` (the first one
  counts, and c4a8a4 Passed Example 3 passes it "because the browser fixes it and it doesn't cause
  any known accessibility issues"); an `iframe` whose document has no `title` of its own (the
  parent's title serves both, 2779a5 Passed Example 2); `<title>` inside `svg` (a graphic's name,
  Inapplicable Example 1 of both rules); the site name before or after the page name ("Patterns |
  APG | WAI | W3C"); the site or application name as the whole title of the home page or of the
  application itself; a page name that reads like a tool default while naming the page ("Index |
  APG | WAI | W3C"); a title worded differently from the h1 while naming the same page; a title that
  does not use the document or application name at all, since "it is not required to use the name of
  the document or web application; other things may also describe the purpose or the topic of the
  page"; a long title (G88's "Be short" is advice, not a failure condition); a title not unique in
  the site while the pages share their purpose (G88 lists uniqueness under "may also be helpful");
  a dialog, menu, expanded section or error state that keeps the page title; a title update that
  screen readers do not announce; the `title` attribute on elements, which H25 calls out as "the
  (mandatory) title element [...] is different from the title attribute"; a missing h1 (2.4.6, not
  here).

## Reporting

- File under: 2.4.2. A missing `title` attribute on an `iframe` is 4.1.2; a missing or vague h1 is
  2.4.6; link text that disagrees with the target's title is 2.4.4; a title in the wrong language
  points to the page `lang` (3.1.1). A missing, empty, placeholder or site-name-only title comes
  from the template: one issue naming every sample it is on; a wrong title on one page is its own
  issue; an application whose title never follows its views is one issue naming the views.
- Title patterns: "Pages have no title", "Page title is empty", "Page title is blank space only",
  "Every page carries the same title", "Page title is the site name only", "Page title does not
  describe the page", "Page title is a template placeholder", "Title does not change between views
  of <app>"
- Severity: High when the title is missing, empty or identical on every page, or is the site name
  only across the site: users cannot tell pages apart in tabs, history, bookmarks or on load;
  Medium when a subset of pages or the views of one application share a title while the h1 tells
  them apart; Low when one page's title is vague or outdated and the h1 makes it clear.
- Type: Technical when the template omits `<title>`, ships a build token, or the router does not set
  `document.title` on navigation; Content when an editor filled the CMS title field with the site
  name, a placeholder or another page's title.
- Evidence: the full-page screenshot with `highlight "h1"` (or the first heading) before it, and the
  title quoted verbatim in the body next to the h1 text ("title: 'University of Arkham', h1: 'Search
  results for "accessibility" at the University of Arkham'"); for a missing or empty title the
  `get html "head"` excerpt; for a blank-looking title the code points from step 2 written out
  ("the title is one no-break space, U+00A0"); for an application the two URLs or two views with
  the unchanged title. No GIF: headless screenshots show no tab bar.
- Recommendation: give each page a `<title>` in `head` that names the page first and the site after
  it ([H25](https://www.w3.org/WAI/WCAG22/Techniques/html/H25),
  [G88](https://www.w3.org/WAI/WCAG22/Techniques/general/G88)); where the page belongs to a
  collection, name its place in the title
  ([G127](https://www.w3.org/WAI/WCAG22/Techniques/general/G127)), the way an online textbook puts
  the chapter number and title beside the book's title.

  ```html
  <!doctype html>
  <html lang="en">
    <head>
      <title>Order history – My account – Example Shop</title>
    </head>
  </html>
  ```

  G88's own patterns for the same shape: `<title>Working with us: The Small Group: The Big
Organization</title>` and `<title>Computer Hardware Corporation - Laptop Division - Laptop
FAQs</title>`. In a single-page application set the title on every route change, in a
  `router.afterEach` hook:

  ```js
  router.afterEach((to) => {
    document.title = `${to.meta.title} – Example Shop`
  })
  ```

  For a PDF set the Title entry in the document information dictionary and the `DisplayDocTitle`
  flag ([PDF18](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF18)):

  ```text
  1 0 obj
    << /Title (Order history – Example Shop)
       /Author (Example Shop)
    >>
  endobj
  ```

  In Adobe Acrobat Pro that is File → Properties → Description → Title, then File → Properties →
  Initial View → Window Options → Show → Document Title.

- Related: 2.4.6 Headings and Labels (the h1 usually mirrors the title; judge the h1 there); 2.4.4
  and 2.4.9 Link Purpose — the Understanding notes that "the name of a document or web application
  being linked to would be sufficient to describe the purpose of the link" and that "Having the link
  and the title agree, or be very similar, is good practice", so a mismatch alone fails neither;
  2.4.8 Location, which G127 serves with the same title change; 4.1.2 (frame names); 3.1.1 (a title
  in another language than the page); 2.4.3 (a view change a screen reader user does not notice is
  focus management, not a title defect).
