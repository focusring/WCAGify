# 1.4.10 Reflow

Level AA · WCAG 2.1+ · Guideline 1.4 Distinguishable · Group: `visual`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#reflow) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#reflow) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/1-4-10-reflow/) · ACT:
[b4f0c3](https://www.w3.org/WAI/standards-guidelines/act/rules/b4f0c3/)

## Requirement

> Content can be presented without loss of information or functionality, and without requiring
> scrolling in two dimensions for:
>
> - Vertical scrolling content at a width equivalent to 320 CSS pixels;
> - Horizontal scrolling content at a height equivalent to 256 CSS pixels.
>
> Except for parts of the content which require two-dimensional layout for usage or meaning.
>
> Note 1:
> 320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom.
> For web content which is designed to scroll horizontally (e.g., with vertical text), 256 CSS
> pixels is equivalent to a starting viewport height of 1024 CSS pixels at 400% zoom.
>
> Note 2:
> Examples of content which requires two-dimensional layout are images required for understanding
> (such as maps and diagrams), video, games, presentations, data tables (not individual cells),
> and interfaces where it is necessary to keep toolbars in view while manipulating content. It is
> acceptable to provide two-dimensional scrolling for such parts of the content.

Terms (WCAG 2.2 glossary): **CSS pixel**: "visual angle of about 0.0213 degrees [...] A CSS pixel
is the canonical unit of measure for all lengths and measurements in CSS. This unit is
density-independent, and distinct from actual hardware pixels present in a display." The 320 is the
emulated CSS-pixel width, never device pixels; changing the device pixel ratio tests nothing here.
**viewport**: "object in which the user agent presents content", Note 1: "Viewports include windows,
frames, loudspeakers, and virtual magnifying glasses. A viewport may contain another viewport (e.g.,
nested frames). Interface components created by the user agent such as prompts, menus, and alerts
are not viewports." So an iframe is a viewport of its own and is measured inside it with `frame`,
while the browser's own chrome is not measured; the native scrollbar "is not included in the
viewport dimensions" ([G225](https://www.w3.org/WAI/WCAG22/Techniques/general/G225)), so the width
to judge against is `document.documentElement.clientWidth`, not `innerWidth` (step 1 calibrates it).
The Understanding measures the same loss itself (figure 17): "The viewport is 318 pixels wide due to
the browser needing to present the page's vertical scrollbar." An overflow no wider than that
scrollbar is therefore never the finding. 400 % is a scale on each dimension and not on the area —
"It means four times the default zoom level viewport width and four times the default zoom level
height" — so vertically scrolling content is judged on width alone at `set viewport 320 900`, never
at 320 x 256; the 256 is the height figure for content designed to scroll horizontally (step 5).

## In plain terms

Everything on the page stays readable and usable in a window 320 CSS pixels wide (a 1280 px window
at 400 % zoom) with scrolling in one direction only: lines wrap, columns stack, navigation folds
into a menu button, nothing is lost or out of reach. What counts is the size of the viewport, not
how the user reached it — half a screen at 960 px zoomed 300 % is the same 320 px. Only parts that
need two dimensions to make sense (a data table, a map, a video, a toolbar) may scroll sideways, and
the exception stops at their edge. It matters for people who zoom to read, and for people with motor
or cognitive impairments for whom sideways scrolling on every line is exhausting.

## Applies when

- Present: every sample that renders text, controls or images, which is every sample; measured at
  `set viewport 320 900` with `reflow.js` and the screenshot; vertical text is step 5. The
  Understanding is explicit that the route to the size does not matter: "someone with a browser
  window docked to one half of their display could have a viewport width of 960 CSS pixels. A user
  could then zoom the browser 300% and achieve a viewport of 320 CSS pixels wide."
- Not present: a sample that renders nothing that could reflow: no visible text, control or image,
  or only one excepted part filling the window (a full-window map or canvas game).
- Cannot tell: content the viewport commands cannot resize, in practice a PDF shown in the browser's
  plugin viewer (the Understanding's "PDF offering reflow" example) — record `cannot-tell`, name the
  file, and send it to the confirmation queue instead of guessing.
- Exception, normative: "Except for parts of the content which require two-dimensional layout for
  usage or meaning." Note 2 lists "images required for understanding (such as maps and diagrams),
  video, games, presentations, data tables (not individual cells), and interfaces where it is
  necessary to keep toolbars in view while manipulating content".
- The exception is per part and never spreads: "If a section of content meets the exception for
  two-dimensional scrolling, the exception only applies to that section [...] the exception does not
  automatically extend to other content that doesn't need two-dimensional scrolling for
  understanding or functionality." Inside an excepted part the content still reflows: "sections of
  content within the two-dimensional layout, such as each cell within a table, would still need to
  meet this success criterion."
- Around a table or grid: "Other content that is related to the table or grid, such as a preceding
  heading, a search field, or an accompanying pagination to load different sets of data are not
  excepted from meeting Reflow." The exception reaches past classic tabular data — an "electronic
  program guide" counts as a grid — but its cells' own content (poster art, how to watch) must fit.
- Page-level scrollbars are allowed when they come from an excepted part: "Reflow does not prohibit
  web pages from presenting both horizontal and vertical scrollbars for individual sections of
  content. Nor does it disallow the use of bidirectional scrollbars at the page (viewport) level in
  order to support the viewing of excepted content, so long as the non-excepted content only needs
  scrolling in one direction" (figures 11 and 12).
- A section with a sideways scrollbar of its own is not a defect by itself: "Conforming to this
  success criterion doesn't mean all sections of content need to stack in a single column within
  smaller viewports. Nor does it require all sections of content scroll in a single direction, so
  long as each can be read without two-dimensional scrolling to read the lines of text they
  present." Judge the lines of text inside the section, not the presence of its scrollbar.
- Scrolling sideways to reach content can be acceptable when reading it does not need it:
  [G206](https://www.w3.org/WAI/WCAG22/Techniques/general/G206) notes "it is also sufficient to lay
  out the content in such a way that horizontal scrolling is required to access content, but that it
  is not necessary to scroll horizontally in order to read a line of text" — "a spreadsheet that
  requires horizontal scrolling is acceptable if no horizontal scrolling is necessary for each
  column individually (i.e., scrolling is only necessary to see other columns, but not for the left
  or right edges of each individual column)". It rescues a column-structured layout only; a
  paragraph, label or link whose own line runs past the edge is still the defect of step 2.
- Further excepted parts named in the Understanding: meaningful indentation in nested lists and code
  ([G224](https://www.w3.org/WAI/WCAG22/Techniques/general/G224)); carousel panels and two-column
  diff views whose panels each fit 320 px
  ([G225](https://www.w3.org/WAI/WCAG22/Techniques/general/G225), figures 6 and 8); an editor's
  persistent toolbar, whose "panels and dialogs are resizable and can be made to fit within a 320px
  wide viewport" (figure 14); a document set to print dimensions, beside which the related content
  is not excepted — a comment "is expected to reflow so that it can fit within a 320 CSS pixel wide
  viewport, while the rich text document can maintain its necessary height and width" (figure 15);
  presentation interfaces, where "it would be expected that such interfaces provided content authors
  with a means to create an alternative presentation that does meet the requirements".
- Viewports below the requirement are out of scope: "If zooming in a web page by 200% results in a
  viewport that is smaller than the sizing requirements of Reflow, then two-dimensional scrolling
  may occur. This would not be a failure of Reflow, as the sizing of the viewport would be smaller
  than what Reflow requires."
- A device that cannot reach the size decides nothing either way: "it is not the intent of this
  criterion to mandate devices need to support these specific sizes for presenting content, nor is
  it to be assumed that if content cannot be presented within such sizes on specific devices that
  the web page would pass or fail Reflow. If a web page can be viewed on a device where the sizing
  requirements of this criterion can be accurately tested, then it is on such devices where a web
  page's ability to meet Reflow is best to be determined." The headless browser is such a device:
  reach 320 px with `set viewport 320 900` on the desktop user agent, never with `set device
"iPhone 13"` (a phone user agent can be served another document, which is not this sample), and
  never record a fail because a phone could not be resized.
- Meaningful layout inside text is excepted as well: preformatted text "where the layout has
  specific meaning, such as code indentation for Python or "ascii art"" — "This success criterion
  does not apply where that meaning would be lost." It covers a `pre`/`code` block and the
  indentation of a nested list ([G224](https://www.w3.org/WAI/WCAG22/Techniques/general/G224));
  running text that is merely indented for looks still has to wrap.
- A persistent toolbar may scroll on its own: "the toolbar may need to scroll in the direction of
  text, or might even need to remain fully visible and scroll along with the rich text content or
  editable canvas area that it provides features for editing". A sideways-scrolling toolbar over an
  editor is a pass; a sideways-scrolling site navigation or tab bar is not.
- Truncated text is allowed only with a route to the whole string: the Understanding's example
  passes when "a link is provided to a web page where the content is fully visible without
  truncation, or a mechanism is provided on the web page to reveal the truncated content".
  Truncation with neither is lost information
  ([F102](https://www.w3.org/WAI/WCAG22/Techniques/failures/F102)); step 2's `truncated` list finds
  the candidates.
- Recognise the candidates in `reflow.js` `twoDimensional` and in the step 2 `excepted` field; both
  are heuristics and only the screenshot confirms them.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. Settles: nothing. ACT
b4f0c3 "Meta viewport allows for zoom" is mapped to 1.4.4 and to this criterion — "Because text that
can not be resized up to 200% can not fit in an area of 320 by 256 CSS pixels, this rule maps to
1.4.10 Reflow as well" — and the 1.4.4 pass of this group runs, records and files it. It applies to
a `meta[name="viewport"]` `content` value that carries `user-scalable` or `maximum-scale`, and fails
on `user-scalable=no` (Expectation 1) or a `maximum-scale` below 2 (Expectation 2); read the value
here with `get attr 'meta[name="viewport"]' content` when the 1.4.4 notes are not at hand. A failed
outcome there does not set this criterion's outcome: the rule assumes both criteria can still be
satisfied when "The page has no visible content", when "There is another mechanism available to
resize the text content" or when "The content does not need to reflow in order to fit in an area of
320 by 256 CSS pixels", and its own support note adds that "Desktop browsers ignore the viewport
meta element" and that "This rule is not relevant for desktop browsers" — the browser this pass runs
in — so the measurement below decides. Leaves open: page-level sideways scrolling at 320 px
from non-excepted text, lists,
forms or navigation; excepted parts that drag their surrounding text along; long strings
([C33](https://www.w3.org/WAI/WCAG22/Techniques/css/C33)); content present at 1280 px and gone at
320 px, placeholder-only labels included
([F102](https://www.w3.org/WAI/WCAG22/Techniques/failures/F102)); dialogs, menus and panels wider
than 320 px; fixed or sticky bars that take space from the reflowed text
([C34](https://www.w3.org/WAI/WCAG22/Techniques/css/C34), advisory); iframes; vertical text at 256
px; a switch to a reflowing layout ([G206](https://www.w3.org/WAI/WCAG22/Techniques/general/G206)).

## Manual procedure

No screen reader is involved: snapshots list what exists at each width, screenshots show it, the
scripts measure the boxes. Wrap every `eval --stdin` body in `(() => { ... })()`: a top-level
`const` stays declared for the life of the page, so a second run throws "Identifier ... has already
been declared".

1. Record the 1280 px baseline (the content and controls that must survive reflow), then narrow to
   320 px and measure.

   ```bash
   for w in 1280 320; do
     agent-browser set viewport $w 900
     agent-browser reload
     agent-browser wait --load networkidle
     agent-browser screenshot .notes/audit/evidence/<sample>--1.4.10-$w.png --full
     agent-browser snapshot > .notes/audit/evidence/<sample>--1.4.10-$w.snapshot.txt
     agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
     agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
     agent-browser eval --stdin < <skill-dir>/scripts/probes/links.js
     agent-browser eval --stdin < <skill-dir>/scripts/probes/images.js
     agent-browser eval --stdin < <skill-dir>/scripts/probes/reflow.js
   done
   agent-browser eval "[innerWidth, document.documentElement.clientWidth]"
   ```

   Calibrate first: when the second figure is below the first, the vertical scrollbar is eating into
   the 320 px, and the scrollbar "is not included in the viewport dimensions" (G225), so `set
viewport <320 + the difference> 900`, `reload`, rerun `reflow.js`, and note the width used; from
   then on two dimensions means `scrollWidth` above `clientWidth`, since `reflow.js` compares with
   `innerWidth`. Keep from `forms.js` each field's `selector`, `nameSource` and `visibleLabelText`,
   from `links.js` the `name` of every link, from `images.js` each image's `selector`, `visible` and
   `presentational`, from `structure.js` the `headings`, `landmarks`, the `tables` (`layoutLike:
false` is a data table) and the `iframes`. In `reflow.js`, `textBelow320px: true` confirms the
   width took effect (it reads `innerWidth <= 320`, so a calibrated run turns it false while the
   content box is still 320 px); `horizontalScroll: true` means two-dimensional scrolling at the
   uncalibrated width; `wideElements` are the boxes past the right edge, with a `textSample` each
   and a cap of 30 entries, so a full list is a sign to fix and re-measure rather than a complete
   inventory; `scrollers` are the elements that scroll sideways on their own, with `scrollWidth`,
   `clientWidth` and `containsText` (true above 40 characters of text), capped at 20; `hiddenBlocks`
   are the text blocks set to `display: none` at this width, capped at 20 and limited to blocks
   carrying more than 40 characters whose parent is still displayed, so a lost button, icon or short
   label never appears there and the step 3 snapshot diff is what catches those; `visibleTextChars`
   is the amount of visible text, compared between the two widths in step 3; `twoDimensional` lists
   exception candidates with a `reason` and includes every visible `table` and `canvas` whether or
   not it overflows, so an entry is something to look at and never a measurement. Done when both
   screenshots,
   both snapshots, the five probe outputs per width and the calibrated width are saved.

2. Classify every box that ends past the edge: excepted part, own sideways scroller, or defect.

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
   const vw = document.documentElement.clientWidth, EX = 'table, [role="grid"], pre, img, svg, ' +
     'canvas, video, iframe, embed, object, [role="img"], [role="toolbar"], [role="application"]';
   const path = (el) => el.id ? `#${CSS.escape(el.id)}` : el.localName + (typeof el.className ===
     'string' && el.className.trim() ? '.' + CSS.escape(el.className.trim().split(/\s+/)[0]) : '');
   const scroller = (el) => { for (let a = el.parentElement; a && a !== document.body;
     a = a.parentElement) if (/auto|scroll/.test(getComputedStyle(a).overflowX)) return path(a) };
   const out = { vw, items: [], clipX: [document.documentElement, document.body]
     .map((n) => getComputedStyle(n).overflowX) };
   for (const el of document.querySelectorAll('body *')) {
     const r = el.getBoundingClientRect(), cs = getComputedStyle(el), t = (el.innerText||'').trim();
     if (r.width <= 1 || r.height <= 1 || r.right <= vw + 2 || cs.visibility === 'hidden' ||
       el.closest('[aria-hidden="true"]') || (el.closest('svg') && el.localName !== 'svg') ||
       [...el.children].some((c) => c.getBoundingClientRect().right > vw + 2)) continue;
     out.items.push({ selector: path(el), right: Math.round(r.right), nowrap: cs.whiteSpace ===
       'nowrap', excepted: el.closest(EX) ? path(el.closest(EX)) : null, longString:
       /\S{30,}/.test(t), ownScroller: scroller(el) ?? null, text: t.slice(0, 60) });
   }
   out.truncated = [...document.querySelectorAll('body *')].filter((el) => getComputedStyle(el)
     .textOverflow === 'ellipsis' && el.scrollWidth > el.clientWidth + 1 &&
     el.getBoundingClientRect().width > 1)
     .map((el) => ({ selector: path(el), text: (el.innerText || '').trim().slice(0, 60) }));
   return out; })()
   EOF
   ```

   Read each item with the 320 px screenshot open. `excepted` and `ownScroller` both set: an
   excepted part in its own scroller, a pass. `excepted` set, `ownScroller` null: it widens the
   page; a pass when the paragraphs around it still wrap (Understanding figure 11), a fail when they
   stretch with it (figure 9). `excepted` null, `ownScroller` set: a pass when each carousel panel
   or diff column fits 320 px (G225) or the indentation is meaningful (G224), else a defect. Both
   null: a defect; `highlight "<selector>"`, take a page screenshot, note `nowrap` or `longString`
   as the cause (C33); when `get count "<selector>"` is above 1, highlight the matching
   `wideElements[].selector` from `reflow.js` instead; cell text counts, cells are not excepted.
   `clipX` `hidden` or `clip`: the items are cut off, not scrollable, still a defect. A
   `twoDimensional` `reason` counts only once the screenshot shows the table, map, diagram or
   toolbar — the probe matches `[class*="map"]` and `[class*="toolbar"]` by class name, so a
   `.sitemap` block or a `.toolbar-lite` row arrives flagged and excepted by accident. Measure each
   `reflow.js` `scrollers` entry that has `containsText: true` before granting it G225:

   ```bash
   agent-browser eval "[...document.querySelectorAll('<scroller selector> > *')]
     .map((el) => Math.round(el.getBoundingClientRect().width))"
   ```

   Every panel at 320 or below passes (figure 6); one above it is the figure 7 failure, because each
   panel must be "fully readable without the need for additional horizontal scrolling" (G225's own
   procedure). Measure the indent before granting G224 to a nested list or a code block: `get styles
"<the list>"` at 1280 px and at 320 px. G224's example keeps the hierarchy while shrinking it
   (`padding-inline-start: 1.25em` under 640 px, `1em` under 400 px) so that "once a nested list is
   visible within the viewport, only vertical scrolling will be necessary to read the content of the
   nested list's items"; an indent unchanged at 320 px while the list text still runs past the edge
   goes to the confirmation queue with both measurements rather than to a pass. For each `truncated`
   entry, find its route to the whole string — a link beside or inside it, an expand control, a
   "show more" button — then `click` it, re-snapshot and confirm the full string appears; record the
   route as present or absent. For an `iframe` item that is not a video or map: `frame "<css>"`,
   rerun `reflow.js`, `frame main`. Done when every item is classified, every `truncated` entry has
   its route recorded, and every defect has a screenshot.

3. Account for every baseline element at 320 px (F102: is there "a way to reach the same or
   equivalent content"?).

   ```bash
   diff .notes/audit/evidence/<sample>--1.4.10-1280.snapshot.txt \
        .notes/audit/evidence/<sample>--1.4.10-320.snapshot.txt
   ```

   Lines only in the 1280 px file are the candidates; add the `hiddenBlocks` of the 320 px
   `reflow.js` run, any drop in `visibleTextChars` between the two runs, and the F102 cases the
   probes name: a heading (`structure.js` `headings`), a link (`links.js` `name`), a navigation
   landmark, a search field, an informational image (`images.js` with `visible: false` and
   `presentational: false`), or a field whose `nameSource` moved from `label` to `placeholder`. For
   each, find its replacement in the 320 px snapshot (a menu button, "More", a search icon, a link
   to a full view), `click @<ref>`, re-snapshot, confirm the item is listed, `press Escape`; for a
   placeholder field `focus "<selector>"` and look for a label. Relocation is not loss: "Neither
   adjusting or relocating content is considered a loss of information or functionality, so long as
   users are still able to access the content." In the Understanding's one-column example the
   navigation moves behind "More" and then a hamburger button and still passes, since "All the
   information and functionality is still available from this web page". Done when each candidate is
   recorded as present, reachable, or lost.

4. Test every state and every fixed element at 320 px. Open each state the sample has and measure it
   like the default state: cookie dialog, main menu, modal, expanded section, form error.

   ```bash
   agent-browser click "<the menu button>"
   agent-browser screenshot .notes/audit/evidence/<sample>--1.4.10-320-menu.png --full
   agent-browser eval --stdin < <skill-dir>/scripts/probes/reflow.js
   agent-browser press Escape
   ```

   A dialog wider than 320 px, a sideways-scrolling menu or an off-edge close button is a step 2
   item: rerun the step 2 script with the state open. Then `scroll down 600`, take a viewport
   `screenshot` with no selector, and list what stayed in place:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
   const path = (el) => el.id ? `#${CSS.escape(el.id)}` : el.localName + (typeof el.className ===
     'string' && el.className.trim() ? '.' + CSS.escape(el.className.trim().split(/\s+/)[0]) : '');
   return [...document.querySelectorAll('body *')].filter((el) => {
     const p = getComputedStyle(el).position, r = el.getBoundingClientRect();
     return (p === 'fixed' || p === 'sticky') && r.height > 1 && r.width > 1;
   }).map((el) => { const r = el.getBoundingClientRect(); return { selector: path(el),
     position: getComputedStyle(el).position, height: Math.round(r.height),
     width: Math.round(r.width), leavesForContent: Math.round(innerHeight - r.height),
     close: !!el.querySelector('[aria-label*="clos" i], [aria-label*="dismiss" i], ' +
       '[class*="close" i], [class*="dismiss" i]') }; }); })()
   EOF
   ```

   Record every header, cookie bar, chat button and ad the list names, the height it takes from the
   900 px viewport, and whether its `close` control exists and works when clicked; the Understanding
   asks for exactly that (C34, advisory): "It is strongly suggested that at smaller viewport sizes
   that such components are modified to have static positioning, or their display can be toggled by
   the user." Done when every state has a screenshot and every fixed bar an entry with its remaining
   space and dismiss control.

5. Check whether the content is designed to scroll horizontally (Note 1).

   ```bash
   agent-browser eval "['html','body','main','[role=main]'].some((s) => { const el =
     document.querySelector(s); return el && /vertical|sideways/
       .test(getComputedStyle(el).writingMode) })"
   ```

   `false` ends the step; a single vertical element stays a step 2 item at 320 px. On `true`: `set
viewport 1280 256`, `reload`, `wait --load networkidle`, then calibrate the height the way step 1
   calibrated the width, because both axes lose the same room (figure 17: "The viewport is 318
   pixels wide due to the browser needing to present the page's vertical scrollbar. The viewport is
   236 pixels tall due to the browser's tabs and address bar UI taking up their own vertical
   space.").

   ```bash
   agent-browser eval "[innerHeight, document.documentElement.clientHeight]"
   ```

   When the second figure is lower, a horizontal scrollbar is eating into the 256, so `set viewport
1280 <256 + the difference>`, `reload`, and note the height used. Then `screenshot
.notes/audit/evidence/<sample>--1.4.10-256.png --full` and `eval
"document.documentElement.scrollHeight - document.documentElement.clientHeight"`; a value above 2
   is two-dimensional scrolling when the step 2 script, rerun with `r.bottom`, `innerHeight` and
   `overflowY` for `r.right`, `vw` and `overflowX`, lists an item with `excepted` and `ownScroller`
   null. Done when the calibrated height, the figure and the screenshot are recorded and `set
viewport 320 900` has restored the width.

6. When steps 2 to 4 found a defect, take G206's two routes in order. First, when the page scrolls
   sideways but every column still reads without it, measure one column at the calibrated width.

   ```bash
   agent-browser get box "<the column>"
   ```

   A column width at or under the calibrated 320 px records a pass for that section on G206's
   spreadsheet case: "scrolling is only necessary to see other columns, but not for the left or
   right edges of each individual column". Second, look for the author's switch: at `set viewport
1280 900` and `reload`, search `snapshot -i` for "mobile view", "single column" or "reader view";
   operate it and repeat steps 1 to 3. A mode that passes them satisfies the sample, provided the
   switch is reachable from the sample itself — G206's test opens the page "on a full screen window"
   and then checks "that there is an option within the content to switch to a layout that does not
   require the user to scroll horizontally to read a line of text". Done when both routes are
   recorded and the viewport is back at 1280 × 900.

## Deciding

- Fail (certainty ≥ 90): `horizontalScroll` true at 320 × 900 (`scrollWidth` above `clientWidth`
  after step 1's calibration) and a step 2 item with `excepted` and `ownScroller` both null whose
  screenshot shows text, fields or links past the right edge (95); such an item cut off by `clipX`
  `hidden` or `clip` (92); a `nowrap` or `longString` item that widens its column (C33) (90); a
  baseline control (search field, nav link, submit button) absent at 320 px and from every
  disclosure opened in step 3 (F102) (90); content designed to scroll horizontally (vertical
  `writing-mode` on the root or main container) whose `scrollHeight` exceeds `innerHeight` at
  1280 × 256 with a non-excepted item in the step 5 script (90).
- Fail (70–89): an excepted part without `ownScroller` whose neighbouring paragraphs stretch with it
  (figure 9) (88); a data table that is not in its own scroll container and drags its heading,
  search field or pagination past the edge with it (figure 13) (88); a dialog, menu or panel wider
  than 320 px, or with its close or submit button past the edge (85); a baseline text block, link
  list or informational image missing at 320 px with nothing that reaches it (F102) (85); a comment,
  note or chat column beside a fixed-dimension document that does not fit 320 px (figure 15) (80); a
  field whose `nameSource` went from `label` to `placeholder` with no label on focus (F102) (82); a
  long string or `nowrap` cell text alone past the edge, with no link to the full text (80); a
  carousel panel or diff column wider than 320 px (G225, figure 7) (78); an editing interface whose
  panels or dialogs cannot be resized to fit 320 px (figure 14) (75); a step 2 `truncated` entry
  with neither a link to a page "where the content is fully visible without truncation" nor a
  control that reveals it (F102) (82); a site navigation, tab strip or filter bar that at 320 px is
  reachable only by scrolling it sideways, which Note 2 does not except since it covers "interfaces
  where it is necessary to keep toolbars in view while manipulating content" and not the site's own
  navigation (75).
- Needs confirmation (50–69): fixed or sticky content that leaves the reflowed text hard or
  impossible to read and cannot be dismissed (Understanding, "Focus Not Obscured (Minimum)" overlap;
  C34 is advisory): ask whether information or functionality is lost (60); a sideways-scrolling
  component that may need two dimensions (timeline, kanban, gantt): ask whether stacking loses
  meaning (60); a code block or nested list whose indentation may be meaningful (G224) (55); a
  presentation or slide editor with no means of producing an alternative presentation that reflows:
  ask what the product offers (55); content dropped at 320 px that looks like trimming (an ad, a
  teaser): ask if it carries information (55).
- Pass: `horizontalScroll` false at 320 × 900, or every step 2 item is an excepted part in its own
  scroll container or one whose neighbours still wrap; every baseline element is present or
  reachable; every opened state reflows; vertical text holds at 256 px.
- Not present: nothing rendered that could reflow, or only one excepted part filling the window.
- False positives to avoid: a page-level scrollbar caused only by an excepted part while all else
  reflows (figure 11); a data table in an `overflow-x: auto` wrapper (figure 10); carousel panels
  that each fit 320 px (G225) and kept indentation (G224); an off-canvas menu parked past the edge
  until opened (relocation, not loss); a `hiddenBlocks` entry that is a collapsed accordion, an
  inactive carousel panel or the desktop copy of a duplicated menu rather than content that is gone;
  a `twoDimensional` entry matched only on a class name, or one for a table or canvas that does not
  overflow at all (the probe lists every visible one); an overflow no wider than the scrollbar the
  step 1 calibration removed; page-level sideways scrolling where every column still reads without
  it (G206's spreadsheet case); text shrunk at the breakpoint or sideways scroll at 640 px only
  ("Reflow does not specifically require any text size enlargement be reached"; 1.4.4 judges 200 %,
  and a viewport "smaller than the sizing requirements of Reflow [...] would not be a failure of
  Reflow"); truncated text with a link or a control that reveals the full string.

## Reporting

- File under: 1.4.10. A viewport meta tag that blocks zoom goes under 1.4.4 and names 1.4.10 (b4f0c3
  maps to both); text clipped at 640 px but fine at 320 px is 1.4.4; overflow that appears only once
  the text-spacing metrics are applied is 1.4.12; a sticky bar hiding the focused control is 2.4.11.
  One issue per component or breakpoint rule, naming every sample it appears on.
- Title patterns: "The page scrolls sideways at 320 px because of the <component>", "The <component>
  is cut off at 320 px width", "The <content> disappears in the narrow layout", "The table pushes
  the page sideways at 320 px", "The <control> sits outside the screen in the narrow layout"
- Severity: High when the main content or a control needed for the task needs sideways scrolling, is
  cut off or is gone at 320 px, since the task is then blocked for everyone who zooms; Medium when
  one section, a secondary component or a shared header or footer does, which is harder work on
  every page but still finishable; Low when one element pokes past the edge, the text stays readable
  and the reader can ignore the scrollbar.
- Type: Technical for fixed widths, `nowrap`, missing `max-width` or media queries, rules that hide
  content at a breakpoint, and unwrapped tables; Design when the narrow layout has to be decided
  first; Content when an editor pasted a fixed-width table, image or embed into the body.
- Evidence: the 320 px full-page screenshot with `highlight "<selector>"` on the container past the
  edge or on the spot where the content used to be, beside the same region of the 1280 px baseline;
  for a disappeared item, the two snapshots' lines as the caption; a GIF from `record start` /
  `record stop` when a control is reachable only sideways.
- Recommendation: stack columns with grid or flexbox under a media query
  ([C32](https://www.w3.org/WAI/WCAG22/Techniques/css/C32),
  [C31](https://www.w3.org/WAI/WCAG22/Techniques/css/C31)), fit labels and inputs
  ([C38](https://www.w3.org/WAI/WCAG22/Techniques/css/C38)), give media `max-width: 100%`
  ([C37](https://www.w3.org/WAI/WCAG22/Techniques/css/C37)), scale script-set sizes with the text
  ([SCR34](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR34)), break long strings
  ([C33](https://www.w3.org/WAI/WCAG22/Techniques/css/C33)), wrap tables in a scrolling box, unfix
  sticky bars ([C34](https://www.w3.org/WAI/WCAG22/Techniques/css/C34)), keep every part reachable
  ([F102](https://www.w3.org/WAI/WCAG22/Techniques/failures/F102)), fit carousel panels in 320 px
  ([G225](https://www.w3.org/WAI/WCAG22/Techniques/general/G225)), keep indentation
  ([G224](https://www.w3.org/WAI/WCAG22/Techniques/general/G224)) or offer a reflowing layout
  ([G206](https://www.w3.org/WAI/WCAG22/Techniques/general/G206)). Where the exception does apply,
  still ask for less scrolling in the issue: "authors can improve the user's experience by making
  efforts to reduce scrolling for that type of content".

  /* C32: one column by default, more columns only where there is room */
  .grid {
    display: grid;
    grid-template-columns: minmax(0, 1fr);
  }
  @media all and (min-width: 576px) {
    .grid {
      grid-template-columns: minmax(0, 1fr) minmax(0, 1fr);
    }
  }
  /* C33: let long URLs and tokens break */
  a {
    overflow-wrap: break-word;
    word-wrap: break-word;
  }
  /* C37 and figure 12: keep media inside its container */
  .img-responsive,
  video {
    max-width: 100%;
  }
  /* Figure 10: the data table keeps its two dimensions inside its own box */
  .table-wrap {
    overflow: auto;
  }
  /* G225: every carousel panel fits the 320 px viewport */
  .carousel > * {
    width: 320px;
    max-width: 100%;
  }
  /* G224: keep the hierarchy, shrink the indent as the viewport narrows */
  @media screen and (max-width: 640px) {
    ul {
      padding-inline-start: 1.25em;
    }
  }
  @media screen and (max-width: 400px) {
    ul {
      padding-inline-start: 1em;
    }
  }
  /* C34: stick only when there is vertical room */

    position: static;
  }
  @media (min-height: 480px) {
    header {
      position: sticky;
      top: 0;
    }
  }
