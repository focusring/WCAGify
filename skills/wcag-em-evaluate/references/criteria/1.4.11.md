# 1.4.11 Non-text Contrast

Level AA · WCAG 2.1+ · Guideline 1.4 Distinguishable · Group: `visual`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
· [Spec](https://www.w3.org/TR/WCAG22/#non-text-contrast)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#non-text-contrast)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/1-4-11-non-text-contrast/)
· ACT: none mapped to this criterion.

## Requirement

> The visual presentation of the following have a contrast ratio of at least 3:1 against adjacent
> color(s):
>
> - User Interface Components: Visual information required to identify user interface components
>   and states, except for inactive components or where the appearance of the component is
>   determined by the user agent and not modified by the author;
> - Graphical Objects: Parts of graphics required to understand the content, except when a
>   particular presentation of graphics is essential to the information being conveyed.

Terms (WCAG 2.2 glossary): **contrast ratio**: "(L1 + 0.05) / (L2 + 0.05), where L1 is the relative
luminance of the lighter of the colors, and L2 is the relative luminance of the darker of the colors
[...]". **user interface components**: "a part of the content that is perceived by users as a single
control for a distinct function [...] include form elements and links as well as components
generated by scripts." **states**: "[...] Examples include focus, hover, select, press, check,
visited/unvisited, and expand/collapse." **essential**: "if removed, would fundamentally change the
information or functionality of the content, and information and functionality cannot be achieved in
another way that would conform".

## In plain terms

Whatever tells a sighted user that a control exists and what state it is in — a field border, a
checkbox tick, a switch knob, the focus ring — must reach 3:1 against the colours next to it, and so
must every part of a graphic a reader needs to understand it: an unlabelled icon, chart lines, the
edges between pie slices. Luminance, not hue, decides, which serves low vision and colour vision
deficiency alike. Inactive controls, the browser's own styling and graphics whose colours carry the
information are out. 3:1 is a threshold: "2.999:1 would not meet" it.

## Applies when

- Present: a sample state with an operable control (`snapshot -i` lists a link, button, field or
  widget; `nontext-contrast.js` returns `controls` or `focusIndicators` entries) or an informative
  graphic: an icon-only link or button (`images.js` entry with `inLink` or `inButton` and an empty
  `controlText`), a status icon without text, a chart, diagram, map or rating widget, a character
  used as an icon (× for close). Every recorded state counts.
- Not present: a sample state with no control and no informational graphic (a text-only page without
  links, fields or icons). A state with one link, button or field is `pass` or `fail`.
- Exceptions: "inactive components": `disabled`, or `aria-disabled` that the script enforces.
  "determined by the user agent and not modified by the author": native fields, checkboxes, radios
  and selects with `appearance` still `auto` and no author colours, and the browser's focus ring,
  recognised by a `focusStyle.outline` in `focusables.js` beginning with `auto` (e.g. `auto 1px
rgb(0, 95, 204)`), which "is exempt from contrast requirements (but must still be visible)".
  "essential": logos in brand colours, flags, photos, diagrams in the colours of their subject. Nor
  is a graphic "required for understanding" when its values are in visible text (chart labels), when
  it is there "for aesthetic purposes", or when the information is "available in another form".

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual. The 1.4.3 pass measures
the text inside controls and graphics; borders, fills, marks, rings and shapes are measured here.

## Manual procedure

Work at `set viewport 1280 900`, in the default state first, then in each recorded state (open menu,
dialog, expanded section, error state). At `set viewport 320 900` (reached for 1.4.10) run
`nontext-contrast.js` and `images.js` once more; entries absent at 1280 (menu button, mobile
navigation, tab bar) get steps 1, 2 and 4. Wrap every `eval --stdin` body in `(() => { ... })()`: a
top-level `const` stays declared for the life of the page, so a second run throws "Identifier ...
has already been declared". The probe rounds `ratio` to two decimals, so recompute anything between
2.9 and 3.1 with this helper (kept as `.notes/audit/ratio-1.4.11.js`, `pairs` edited per run):

```bash
agent-browser eval --stdin <<'EOF'
(() => {
  const pairs = [['<colour A>', '<colour B>']];
  const rgb = s => s.match(/[\d.]+/g).slice(0, 3).map(Number);
  const ch = v => { v /= 255; return v <= 0.04045 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4 };
  const lum = s => { const [r, g, b] = rgb(s); return 0.2126*ch(r) + 0.7152*ch(g) + 0.0722*ch(b) };
  return pairs.map(([a, b]) => { const [h, l] = [lum(a), lum(b)].sort((x, y) => y - x);
    return { a, b, ratio: (h + 0.05) / (l + 0.05) } });
})()
EOF
```

1. Measure what identifies each control. Run `nontext-contrast.js` and read `controls`:
   `indicatorType` names the part measured (`border`, `background`, `icon`, `none`), `ratio` and
   `passes3` compare it with `adjacentBackground`, the colour the component sits on. Words identify
   a control only when an element screenshot shows them: `get text` also returns hidden labels and
   every option of a select, so `get count "<selector> .sr-only, <selector> [class*=hidden]"` above
   0, or a `clip` or 1 px box in `get styles`, means the control counts as textless. Every field
   role (`text`, `email`, `search`, `password`, `number`, `tel`, `url`, `date`, `select`,
   `textarea`, `combobox`, `textbox`) is identified by its boundary, never by its value or its
   options. Without visible text, `icon` goes to step 4; on `border` or `background` run `get count
"<selector> svg, <selector> img, <selector> [class*=icon]"` — above 0 the icon identifies the
   control ("Boundaries"), so judge it in step 4 and leave the boundary alone; otherwise `passes3:
false` is a fail and `ratio: null` (`adjacentBackground` is `image`) goes to step 5. `none` on a
   field: `get styles "<selector>"` and read `border-bottom-width`, `border-bottom-color` and
   `box-shadow`, past the probe's top-border reading; a bottom border or an inset shadow is the
   boundary, so feed its colour against `adjacentBackground` into `pairs`; queue for confirmation
   only when all three are absent. Sentence links: an underline in the text colour always passes;
   one in another colour (`text-decoration-color`), as the only link cue, goes into `pairs` against
   the page background; no underline and no other cue is 1.4.1. Done when every textless control and
   every sentence link has a ratio, a hand-off or a note.

2. Measure focus indicators; their visibility is 2.4.7, in the `keyboard` pass. Run
   `nontext-contrast.js` and `focusables.js` right after `reload`, before any `click`: once a
   pointer click has happened Chrome stops matching `:focus-visible` on programmatic focus, and both
   probes then report no indicator for controls that still ring on Tab. Read `focusIndicators`,
   `focusStyleChanged` and `focusStyle` per selector. A `focusStyle.outline` beginning with `auto`
   is the browser's ring: record the exemption. `solid`, `dashed` and `double` outlines and
   `box-shadow` values are author indicators: `passes3: false` on one of them is a fail, an
   indicator outside the component below 3:1 against the background it lies on. An `inset`
   `focusStyle.boxShadow` or a negative `focusStyle.outlineOffset` lies inside: compare it with the
   control's `backgroundColor`; one partly inside and partly outside passes when "either part [...]
   can contrast with the adjacent colors". A two-colour ring
   ([C40](https://www.w3.org/WAI/WCAG22/Techniques/css/C40)) passes when its two colours reach 9:1
   against each other, each band is at least 2 CSS px thick and the ring lies over one solid colour
   (at least one band then reaches 3:1 against it); over an image, gradient or another component go
   to step 5. With `outlineColor` null and `focusStyleChanged: true`, find the changed property:
   compare `focusStyle.border` and `focusStyle.background` with the same selector's blurred
   `borderColor` and `backgroundColor` in `controls`. A changed border on the component's outer edge
   must reach 3:1 against both the inside colour and the colour outside it, one inside the visible
   boundary against the inside only, and a `background` change alone is "not in scope" here (2.4.7
   and 1.4.1 judge it). With both null and false, an author `caret-color` below 3:1 as a text
   field's only focus cue fails, the default caret passes. Confirm every null, false and failing
   entry with the keyboard: `scrollintoview "<selector>"`, `focus "<selector>"`, `press Shift+Tab`,
   `press Tab`, then a viewport `screenshot <path>` with no selector, since an element screenshot
   clips to the box and cuts the ring off (`highlight` the parent when the control is small); only
   when that shot shows no ring was the indicator removed
   ([F78](https://www.w3.org/WAI/WCAG22/Techniques/failures/F78)): file under 2.4.7 naming this
   criterion. Done when every focusable element has a ratio, a recorded exemption or a 2.4.7
   hand-off.

3. Measure state marks and hover. For every `role` of `checkbox`, `radio`, `switch`, `tab`, `option`
   or `slider` in `snapshot -i`, every element with `aria-pressed`, `aria-expanded`, `aria-selected`
   or `aria-current`, put it in each state (`check "<selector>"`, `click "<selector>"`) and read the
   mark's colours and `appearance`: `get styles` on the visible mark, or `getComputedStyle(el,
'::after')` in `eval --stdin` for a pseudo-element; aim at the visible box when a `label` stands
   in for a hidden native input. `appearance` `auto` with no author colours is the browser's own
   drawing: exempt. Otherwise the mark goes into `pairs` against the colour it sits on: the box when
   it sits inside it, the page background when the filled state replaces the box. Hover: `hover
"<selector>"` one control of each kind and rerun the probe; hover treatments "do not themselves
   need to contrast 3:1", but a control whose `passes3` turns false on hover has lost its
   identification. Done when every state of every stateful control and hover on each kind has a
   verdict.

4. Measure graphical objects. Read `graphics` from the probe (inline SVG and icon fonts up to 200 px
   wide: `fill` against `adjacentBackground`) and `images.js` for raster icons and charts. A graphic
   is "required for understanding" when it is the only content of a control (`inButton` or `inLink`
   with an empty `controlText`), a status icon with no text beside it, or a chart, diagram or map
   whose values are not in visible text; not when a label says the same, `presentational` is true,
   or the data sits in a visible table. A required icon with `passes3: false` fails
   ([G207](https://www.w3.org/WAI/WCAG22/Techniques/general/G207)). For an SVG chart feed the
   distinct `fill` and `stroke` of its `path`, `rect`, `circle` and `line` children against the
   chart's `background-color` into `pairs` (`getComputedStyle` in `eval --stdin`); adjoining areas
   (pie slices, stacked bars, map regions) go in as neighbour pairs, and a 3:1 border between them
   counts ([G209](https://www.w3.org/WAI/WCAG22/Techniques/general/G209)). For a raster chart
   `screenshot "<selector>" <path>` and apply the Understanding's test to the least-contrasting area
   of each object a reader needs: "assume that area is invisible, is the graphical object still
   understandable?" A symbolic character used as an icon (×, ›) is a graphical object at 3:1. Done
   when every required graphic has a ratio or a screenshot verdict and every skipped one has its
   reason.

5. Judge indicators on images and gradients: every entry from steps 1 to 4 whose
   `adjacentBackground` is `image`. `scrollintoview "<selector>"`, `get styles` of the parent for
   `background-image`, then an element `screenshot "<selector>" <path>` for a border, mark or icon
   and a viewport `screenshot <path>` for a focus ring. For a CSS gradient feed each colour stop
   against the indicator into `pairs`: fail when the least-contrasting stop, taken as invisible,
   leaves the indicator unrecognisable ("Gradients"). For a photo read the screenshot: fail when the
   indicator vanishes over part of the image, pass when it stays discernible everywhere,
   `cannot-tell` when the image did not load. Done when no `null` remains.

6. Repeat steps 1 to 5 in every author-shipped colour scheme: `set media dark`, `reload`, `wait
--load networkidle`, `get styles body` — a changed `background-color` is a dark scheme the author
   ships — then `set media light`. A control named theme, dark or contrast in `snapshot -i` gets the
   same run after `click`; a switch ([G174](https://www.w3.org/WAI/WCAG22/Techniques/general/G174))
   carries the sample only when it reaches 3:1 itself and the switched presentation passes
   everywhere. Done when each scheme has its own entries.

## Deciding

- Fail (certainty ≥ 90): an author focus indicator (`focusStyle.outline` not `auto`) below an
  unrounded 3:1 against the colour behind it (95); the only identification of an empty field,
  select, custom checkbox, switch or slider — border, fill, state mark or icon — below 3:1 on a
  solid background (90); an author `caret-color` or a coloured underline as the only cue, below 3:1
  (90); chart lines or bars below 3:1 against the chart background (90).
- Fail (70–89): a labelled field whose border falls short and nothing else bounds it (75); adjoining
  pie slices or map regions below 3:1 with no border or labels (80); a raster graphic whose
  least-contrasting area fails in the screenshot (75); a control identified only until hover (80); a
  focus ring lost over part of an image (80); a border-change indicator below 3:1 against the
  component's inside, or against the page when the border is its outer edge (85); a two-colour ring
  under 9:1 between its bands, both below 3:1 on the colour behind (80); a logo greyed below 3:1 by
  author choice, its low-contrast state not being essential (70).
- Needs confirmation (50–69): a graphic whose values may be carried by nearby text (60): ask whether
  that text is the intended equivalent; an icon beside a label that may be supplemental (60): ask
  whether users must recognise it; a control greyed by CSS but operable (55): ask whether it is
  meant to be inactive; brand colours below 3:1 on a logo used as a link (55): ask whether the
  guidelines mandate them; a field with no border, no bottom border and no inset shadow (60): ask
  whether the design intends no boundary; an image that did not load (50).
- Pass: every identifying indicator and state mark of every operable control, every author focus
  indicator and every required graphic, in every state and scheme, reaches an unrounded 3:1 against
  its adjacent colour or is a recorded exemption.
- Not present: only a sample state with no control and no informational graphic.
- False positives to avoid: a control with visible text or a contrasting icon needs no contrasting
  border; the browser's ring (`auto` outline), unstyled native inputs and disabled controls are
  exempt; a probe run after a click reports no indicator where Tab still shows one; hover effects,
  thin dividers and graph lines that do not touch need no contrast of their own; logos, flags and
  photos are essential.

## Reporting

- File under: 1.4.11, except a removed or invisible focus indicator → 2.4.7
  ([F78](https://www.w3.org/WAI/WCAG22/Techniques/failures/F78) names both; mention this one), a
  link told apart by colour alone → 1.4.1, text inside a control or chart → 1.4.3, an unnamed icon →
  1.1.1 or 4.1.2. One issue per indicator kind and colour pair (all fields with the same grey
  border; the focus ring; one chart), naming every sample and state it covers.
- Title patterns: "Form field borders are too faint to see", "Focus ring is barely visible on the
  white background", "Custom checkboxes have a low-contrast tick", "Icon-only toolbar buttons are
  too light", "Pie chart slices cannot be told apart", "Links in body text have a faint underline"
- Severity: High when the failing indicator is the only way to find a field, a control or the
  keyboard focus, or the focus ring fails everywhere; Medium when text carries part of the meaning,
  or the fail is limited to one state, scheme or graphic; Low when a supplemental cue misses
  narrowly and another remains.
- Type: Design by default, the colours were chosen. Technical when a rule causes it: `outline: none`
  or `appearance: none` without a replacement (F78), an inherited `border-color`, a library's
  default palette. Content when an editor uploaded the image.
- Evidence: an element screenshot for a border, state mark or icon; for a focus ring `scrollintoview
"<selector>"`, `focus "<selector>"` and a viewport `screenshot <path>` with no selector, since an
  element shot would clip the ring off; `highlight` the parent when the control is small; the pair
  and ratio beside it ("border #cccccc on #ffffff = 1.6:1, needs 3:1"); a GIF via `record start` /
  `record stop` when the defect is a focus movement or a hover sequence.
- Recommendation: darken the border, fill, mark or ring until the pair reaches 3:1 — icons
  [G207](https://www.w3.org/WAI/WCAG22/Techniques/general/G207), adjoining areas
  [G209](https://www.w3.org/WAI/WCAG22/Techniques/general/G209) — and give focus an author indicator
  that contrasts with every background it lands on
  ([G195](https://www.w3.org/WAI/WCAG22/Techniques/general/G195)), or a two-colour ring whose bands
  are 9:1 apart ([C40](https://www.w3.org/WAI/WCAG22/Techniques/css/C40)). A contrast switch
  ([G174](https://www.w3.org/WAI/WCAG22/Techniques/general/G174)) is a last resort. Examples:
  `border-color: #767676` on white is 4.5:1; `:focus-visible { outline: 2px solid #fff; box-shadow:
0 0 0 4px #1a1a1a }` puts a light band and a dark band 17:1 apart, so one of them contrasts with
  any solid background.
- Related: 2.4.7 (the indicator must also be visible), 2.4.13 at AAA (its size and change of
  contrast); 1.4.1 when colour is the only cue; 1.4.3 for the text in the same component; 1.1.1 for
  charts and icons needing a text alternative; 2.5.8 when the faint control is also small.
