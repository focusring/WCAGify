# 3.3.2 Labels or Instructions

Level A · WCAG 2.0+ · Guideline 3.3 Input Assistance · Group: `forms`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)
· [Spec](https://www.w3.org/TR/WCAG22/#labels-or-instructions)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#labels-or-instructions) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-3-2-labels-or-instructions/)
· ACT: none is mapped to this criterion

## Requirement

> Labels or instructions are provided when content requires user input.

Terms (WCAG 2.2 glossary): **labels**: "text or other component with a text alternative that is
presented to a user to identify a component within web content [...] A label is presented to all
users whereas the name may be hidden and only exposed by assistive technology. In many (but not all)
cases the name and the label are the same. [...] The term label is not limited to the label element
in HTML."

The Understanding reads "requires" as a synonym for "accepts", "expects", or "allows": the criterion
"applies to all form fields, whether they're required or optional".

## In plain terms

Every control that takes data from the user (text field, select, radio or checkbox set, slider, file
picker, custom widget) shows every user, not only assistive technology, a label that says what goes
in it, plus an instruction wherever the input has a format or rule a plain label does not make
obvious (date order, password rules, which fields are mandatory). Each option of a set has its own
label and the set says what is being chosen. People with cognitive disabilities need it most.

## Applies when

- Present: the sample, in any state, has a data-entry control: an `input` other than `type` button,
  submit, reset, image or hidden; a `select`; a `textarea`; a `contenteditable` region; or an
  element with role `textbox`, `searchbox`, `combobox`, `listbox`, `spinbutton`, `slider`,
  `checkbox`, `radio` or `switch`. Detect with `forms.js` (`fields[]`) and `snapshot -i`. Dialog,
  expanded, multi-step and error states count.
- Not present: `forms.js` returns no data-entry field in any state and `snapshot -i` lists none of
  the roles above. Links, buttons, tabs, menus and disclosure widgets are not data entry.
- Exceptions: the normative text has none. Scope limits from the Understanding: it "does not apply
  to links or other controls (such as an expand/collapse widget, or similar interactive components)
  that are not associated with data entry"; a hidden name is no label, content can "pass Success
  Criterion 4.1.2, but [...] still fail this success criterion (if the labels or instructions aren't
  presented to all users [...])"; association is 1.3.1, clarity 2.4.6; instructions may be
  "available to users only when the individual control has focus"; "Using images as labels meets the
  requirements" when the image is widely understood (a search loupe).

## axe-core

| Rule                         | Decides                                 | Result → outcome    |
| ---------------------------- | --------------------------------------- | ------------------- |
| `form-field-multiple-labels` | several `<label>` elements on one field | incomplete → step 3 |

Settles: nothing. The rule is `needs review` only (WCAG 2.0 A & AA set, on by default) and never
reports a violation, so axe never produces a 3.3.2 fail; its incomplete result lists fields whose
several labels must be read to see which is visible. axe's accessible-name rules sit under 4.1.2.
Leaves open (steps 2 to 7): whether each field has a visible label or cue at all; labels present
only as `aria-label`, a hidden `<label>`, `title` or a placeholder; group labels for radio, checkbox
and split fields (F82); format and rule instructions; required-field indication; label position;
fields in dialogs, later form steps and frames.

## Manual procedure

1. Read axe. The `scripts/axe-page.mjs` output per sample state gives a `3.3.2 review` line with the
   rule id and a node count; take its node targets from `.notes/audit/axe/<sample>[--<state>].json`
   into step 3's list. Done when that list exists, empty or not.

2. Inventory and visible label. In the default state:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.2-form.png --full
   ```

   For each entry of `fields[]` note `selector`, `tag`, `type`, `role`, `visibleLabelText`,
   `placeholder`, `nameSource`, `describedbyText`, `inFieldset`, `legend`, `required` and
   `ariaRequired` (the raw attribute, so only `"true"` marks a field required); drop `disabled`
   fields and `type` button, submit, reset, image, hidden, and leave radio, checkbox and switch
   options and split-field parts to step 3. Note `counts.placeholderOnly` and
   `counts.requiredWithoutIndication`. `visibleLabelText` holds the `label` elements' text unchecked
   for visibility: a visually hidden label fills it and `is visible` answers `true` for its clipped
   1 px box, so judge each label on the screenshot and with `get box "label[for='email']"`, where a
   1 × 1 box or a negative x or y is a name and not a label — a large y is only a label further down
   the page. Label text in view → labelled. None in view → look for another cue presented to all
   users: the text an `aria-labelledby` points at, when `get text "#labelspan"` finds it on the
   screenshot ([ARIA9](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA9)); a `placeholder`; an
   adjacent button or icon naming the purpose (a "Search" button or loupe,
   [G167](https://www.w3.org/WAI/WCAG22/Techniques/general/G167)); a `legend`, heading or sentence
   naming this single field ([G184](https://www.w3.org/WAI/WCAG22/Techniques/general/G184)); an
   image beside it (`images.js` `nearbyText`, `name`). Decide: no cue in view of any kind, whatever
   `nameSource` says and whatever `visibleLabelText` holds → fail 90; `nameSource` `title` and
   nothing else in view → fail 85; placeholder only → fail 75 (`fill` a value and screenshot again:
   the cue is gone); an icon whose meaning depends on the audience → confirmation queue 60. Done
   when every data-entry field is labelled, left to step 3, or has a fail.

3. Groups and split fields. For every `type` radio, checkbox or role `radio`, `checkbox`, `switch`:
   the option needs visible text, an image, or row or card text beside it that names it
   (`visibleLabelText` read against the screenshot, since a hidden `label` fills it too; nothing in
   view → fail 90), and the set a visible group label: `legend` when `inFieldset`
   ([H71](https://www.w3.org/WAI/WCAG22/Techniques/html/H71)), otherwise a heading or sentence
   directly before the set ([ARIA17](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA17)); read
   the container with `snapshot -s "fieldset.delivery"`. Options that do not state the question
   ("Yes" / "No", a row of stars) with no group text → fail 80. A set of short fields for one value
   (three phone parts, day/month/year, six code boxes) with punctuation or spacing as the only cue →
   fail 90 ([F82](https://www.w3.org/WAI/WCAG22/Techniques/failures/F82)); one text label on the set
   with `title` or hidden names on the parts → pass (Understanding phone example). Resolve step 1's
   `form-field-multiple-labels` nodes here: one label visible and naming the field → no 3.3.2 defect
   (note the duplicate for 1.3.1 and 4.1.2). Done when every set and every axe node has a note.

4. Position ([G162](https://www.w3.org/WAI/WCAG22/Techniques/general/G162)). Where a label is not
   directly above or before its text field, or directly after its radio or checkbox, compare `get
box "label[for='city']"` with `get box "#city"`: a label closer to another field than to its own
   → confirmation queue 60 with a screenshot. Done when every unusual placement is listed.

5. Format and rule instructions ([G89](https://www.w3.org/WAI/WCAG22/Techniques/general/G89)). For
   every field whose input has a format or rule a plain label does not make obvious (date, time,
   phone, postcode, IBAN, amount, username, password creation, file type or size, character limit),
   find the instruction: in `visibleLabelText`, in `describedbyText` when that text is on screen
   ([ARIA1](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA1)), in text near the field, or shown
   on focus (`focus "#birthdate"`, then `snapshot -s "form.register"`). A native `date`, `time` or
   `number` control states its format in its own widget: record it met and run no fill test there —
   `fill` leaves `date` and `time` empty whatever it is given, and strips non-numeric characters in
   `number`. On any other field, test a plausible value in another common format:

   ```bash
   agent-browser fill "#birthdate" "12/03/1990"
   agent-browser click "button[type='submit']"
   agent-browser wait --load networkidle
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   `visibleErrors[]` naming a format or rule that nothing stated before submit → fail 80: for a
   format, text shown only after the submit comes too late. The value is accepted, or the rule was
   visible in the label, near it or on focus → pass. Customary formats (email, free text, a plain
   number) need no instruction. Skip a submission that would create an account, place an order or
   send a message: record `cannot-tell` for the instruction check of that form and say why. Done
   when every constrained field has a decision.

6. Required fields ([H90](https://www.w3.org/WAI/WCAG22/Techniques/html/H90)). From step 2 take
   fields with `required` or `ariaRequired` `"true"` whose label carries no asterisk or word like
   "required", read the form (`get text "form.contact"`) for a sentence such as "All fields are
   required" or an asterisk key, then submit it empty and read `visibleErrors[]` again. Page text
   naming the fields left blank is [G83](https://www.w3.org/WAI/WCAG22/Techniques/general/G83) and
   meets this criterion together with descriptive labels: record no 3.3.2 defect, the wording of
   that text is 3.3.1's. Fail 75 only when nothing marks the fields beforehand and no page text
   names them afterwards either — the browser's own "Please fill out this field" bubble is not in
   the DOM and is not that text. Every field required and nothing saying so → confirmation queue 55.
   Done when `counts.requiredWithoutIndication` is explained field by field.

7. States and evidence. Repeat steps 2 to 6 in every state that adds fields: open the login, search,
   newsletter or filter dialog (`click`, then a fresh `snapshot`), expand collapsed sections, walk
   each step of a multi-step form, read the error state after a submit. Fields in a frame: `frame
"<css>"`, run `forms.js`, then `frame main`; a frame that cannot be entered → `cannot-tell` for
   its fields, naming its `src` from `structure.js` `iframes[]`. For every fail, draw the field in
   the state that shows the defect (a value typed into a placeholder-only field, the error state for
   a missing instruction):

   ```bash
   agent-browser highlight "#search"
   agent-browser screenshot .notes/audit/evidence/<sample>-3.3.2-search.png
   ```

   Done when the findings file lists every state probed, what the user is told before submitting
   each field, and a screenshot path for every fail.

## Deciding

- Fail (certainty ≥ 90): a data-entry field with nothing on the screenshot that identifies it — no
  label text in view, no `placeholder`, no adjacent button, icon, legend or sentence naming it —
  whatever its `nameSource` holds, since a hidden or clipped `label` fills `visibleLabelText` too
  (90). A radio, checkbox or switch option without visible text or image of its own (90). Split
  fields for one value with punctuation or spacing as the only cue and no text label on the set
  ([F82](https://www.w3.org/WAI/WCAG22/Techniques/failures/F82)) (90).
- Fail (70–89): `title` as the only label outside a set with a visible group label, a hover tooltip
  shown to nobody else (85). Input rejected on submit for a format or rule that no label, nearby
  text, on-focus text or form instruction stated, password rules revealed only in the error included
  (80). An option set with labelled options and no visible group label, where the options do not say
  what is being chosen (80). A placeholder as the only label, gone once a value is typed (75).
  Required fields marked nowhere before submit and named by no page text after an empty submit
  either (75).
- Needs confirmation (50–69): an icon as the only label whose meaning is not general knowledge (a
  funnel, a pin): ask who the audience is and whether text can be added (60). A label placed so it
  could belong to two fields: ask which field it labels (60). A form where every field is required
  and nothing says so: ask whether users are expected to know (55).
- Pass: every data-entry field in every probed state has, before or while it is filled in, a visible
  label or a visible instruction saying what goes in it; every option of a radio, checkbox or switch
  set has visible text and every set that leaves the question open has a group label in view; every
  non-customary format or rule shows in the label, near the field or on focus; required fields are
  marked, the form says all are, or an empty submit names the ones left blank.
- Not present: no state of the sample has a data-entry control.
- False positives to avoid: a visible label not associated in markup (1.3.1); a vague label (2.4.6);
  a visible label plus a different `aria-label` (2.5.3, 4.1.2); a search field labelled by its
  "Search" button or loupe (Understanding example); a group legend with `title` on the parts
  (Understanding phone example); instructions shown only on focus or given once at the beginning of
  the form (G184); customary formats without instruction; required fields named by the page's own
  error text after an empty submit (G83); links, buttons, tabs, disclosure widgets; `disabled` and
  hidden fields; a `form-field-multiple-labels` incomplete where one label is visible; an asterisk
  whose key sentence sits elsewhere in the form.

## Reporting

- File under: 3.3.2 for a field or group without a visible label, a missing format or rule
  instruction, and unmarked required fields; the criteria under "Related" take the rest, one issue
  per criterion when two hold. One issue per form or component (search field, newsletter block,
  checkout address step) listing the fields concerned, a site-wide one naming the other samples.
- Title patterns: "Search field has no visible label", "Newsletter field is labelled only by its
  placeholder", "Date of birth field states no format before submitting", "Required fields are not
  marked in the contact form"
- Severity: High when the form is needed for a task (login, checkout, application, contact) and the
  user cannot tell what a field is for, or a format rule blocks submission with no way to learn it
  beforehand; Medium when a whole form relies on placeholders or leaves required fields unmarked, or
  the defect sits in a site-wide component; Low when one field of an otherwise labelled form misses
  an instruction, or a group label that context makes obvious is missing.
- Type: Content when the fix is writing text (a format hint, "(required)", a legend, a sentence
  before the form); Technical when a label or legend exists in the code but is hidden or misplaced;
  Design when the layout dropped the label on purpose (placeholder-only pattern, icon-only fields)
  and must make room for one.
- Evidence: element or page screenshot with `highlight` on the field, in the state that shows the
  defect: a value typed into a placeholder-only field, the error state for a missing instruction,
  the empty submit for unmarked required fields. No GIF: nothing moves.
- Recommendation: a visible text label directly before each field
  ([H44](https://www.w3.org/WAI/WCAG22/Techniques/html/H44)); `fieldset` and `legend` for option
  sets and split fields (H71); the expected format in the label or in visible text tied with
  `aria-describedby` (G89); required fields marked in the label (H90); a placeholder as an example
  only. Example: `<label for="dob">Date of birth (dd-mm-yyyy)</label> <input id="dob"
aria-describedby="dob-hint"> <span id="dob-hint">For example 31-12-1990</span>`.
- Related: 1.3.1 (label not associated); 4.1.2 (no accessible name; a hidden name alone does not
  meet 3.3.2); 2.4.6 (label unclear); 2.5.3 (visible text missing from the name); 1.3.5 (purpose
  token); 3.3.1 and 3.3.3 (errors after submit). Each its own defect.
