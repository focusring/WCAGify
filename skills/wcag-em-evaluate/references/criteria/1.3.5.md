# 1.3.5 Identify Input Purpose

Level AA · WCAG 2.1+ · Guideline 1.3 Adaptable · Group: `forms`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html)
· [Spec](https://www.w3.org/TR/WCAG22/#identify-input-purpose)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#identify-input-purpose)
· [Plain
English](https://aaardvarkaccessibility.com/wcag-plain-english/1-3-5-identify-input-purpose/)
· ACT: [73f2c2](https://www.w3.org/WAI/standards-guidelines/act/rules/73f2c2/)

## Requirement

> The purpose of each input field collecting information about the user can be programmatically
> determined when:
>
> - The input field serves a purpose identified in the Input Purposes for user interface components
>   section; and
>
> - The content is implemented using technologies with support for identifying the expected meaning
>   for form input data.

Terms (WCAG 2.2 glossary): **programmatically determinable**: "determined by software from
author-supplied data provided in a way that different user agents, including assistive
technologies, can extract and present this information to users in different modalities [...]".

The "Input Purposes" section is [WCAG 2.2 §7](https://www.w3.org/TR/WCAG22/#input-purposes): 53
tokens that "relate to the user of the content": `name`, `honorific-prefix`, `given-name`,
`additional-name`, `family-name`, `honorific-suffix`, `nickname`, `organization-title`, `username`,
`new-password`, `current-password`, `organization`, `street-address`, `address-line1`,
`address-line2`, `address-line3`, `address-level4`, `address-level3`, `address-level2`,
`address-level1`, `country`, `country-name`, `postal-code`, `cc-name`, `cc-given-name`,
`cc-additional-name`, `cc-family-name`, `cc-number`, `cc-exp`, `cc-exp-month`, `cc-exp-year`,
`cc-csc`, `cc-type`, `transaction-currency`, `transaction-amount`, `language`, `bday`, `bday-day`,
`bday-month`, `bday-year`, `sex`, `url`, `photo`, `tel`, `tel-country-code`, `tel-national`,
`tel-area-code`, `tel-local`, `tel-local-prefix`, `tel-local-suffix`, `tel-extension`, `email`,
`impp`. In HTML the token goes in the `autocomplete` attribute of `input`, `select` or `textarea`
([H98](https://www.w3.org/WAI/WCAG22/Techniques/html/H98)).

## In plain terms

Every field that asks the person filling in the form for their own name, address, telephone,
email, login, payment card, birthday, gender, language, website or job title carries a
machine-readable purpose token next to its visible label. Browsers then autofill the value and
assistive technology can swap the author's wording for an icon or a familiar term, which helps
people with cognitive, language and memory disabilities understand the field and spares people with
motor impairments the typing. The token is a fixed vocabulary that works in every language, so the
label alone is not enough. Fields about other people or about things (a recipient's address, a
search term, a message) need no token even when one exists. The fix is an attribute in the code.

## Applies when

- Present: the sample, in any state, has an `input` with a text-like `type` (text, email, tel, url,
  password, number, date, month, search or none), a `select` or a `textarea` whose visible label,
  placeholder, legend or surrounding heading asks the user for one of the 53 purposes about
  themselves. Detect with `forms.js`: `autocompleteCandidate` flags the commonest purposes from
  `type`, name, id, accessible name and placeholder; read `visibleLabelText` and `legend` for the
  rest (city, job title, country, card expiry) and for every field with an `autocomplete` value.
- Not present: `forms.js` returns no fields, or every field is a search box, quantity, coupon,
  order number, subject, message, one-time code or filter, or cannot carry a token (checkbox, radio,
  file, button, submit, reset, image, hidden). Record `not-present` and list the fields ruled out.
- Exceptions:
  - Purpose not in the list ("How did you hear about us", "Order number"): no token required.
  - Not about the user: "An input field for information that is not about the user does not need
    to programmatically expose its purpose, even if that purpose is included in the Input Purposes
    list." Recognise it by a label or legend naming someone else ("Recipient", "Friend's email",
    "Contact person", "Guest 2"). A separate shipping address is still the user's.
  - Two purposes in one field: "If an input field accepts two different types of input purpose (as
    in combined user name/user email fields) and the technology used does not allow multiple purpose
    values to be defined, it is valid to provide either one or the other value or leave out the
    designation of input purpose altogether." An "Email or username" login field may carry
    `username`, `email` or nothing.
  - Technology without support: HTML carries the token on native controls only; a custom widget
    (`div` with `role="textbox"`, `contenteditable`) has no attribute for it (step 6).

## axe-core

| Rule                 | Decides                   | Result → outcome                            |
| -------------------- | ------------------------- | ------------------------------------------- |
| `autocomplete-valid` | token syntax (ACT 73f2c2) | violation → fail (100); incomplete → step 4 |

Settles: the syntax of a present, non-empty `autocomplete` value on an `input`, `select` or
`textarea`: optional `section-*`, optional `shipping`/`billing`, optional
`home`/`work`/`mobile`/`fax`/`pager` (then only `tel`, `tel-*`, `email` or `impp` may follow), one
field token, optional trailing `webauthn`. Violations: an unknown token (`birthday`, `firstname`,
`phone`), two field tokens, a modifier alone, wrong order, commas, extra tokens. `off`, `on` and
the state words `none`, `false`, `true`, `disabled`, `enabled`, `undefined`, `null`, `xoff`, `xon`
pass the rule. Skipped by its matcher: `readonly` or `aria-readonly="true"`, `disabled` or
`aria-disabled="true"`, `type` submit, reset, button or hidden, and negative-`tabindex` elements
with a non-widget role or hidden. It only sees nodes in the DOM at scan time: one run per state.

Leaves open (steps 2 to 6):

- in-scope fields with no `autocomplete`, an empty one, or `off`/`on`/a state word (the commonest
  defect), and a `shipping`/`billing` modifier contradicting its address block;
- a well-formed token naming a different purpose than the label
  ([F107](https://www.w3.org/WAI/WCAG22/Techniques/failures/F107)): axe reads no labels;
- the values `text`, `pronouns`, `gender`, `message`, `content`: axe returns incomplete;
- whether the token fits the control's `type`: axe 4.12.1 no longer checks it, and it is no 1.3.5
  defect (ACT 73f2c2 passed example 8);
- fields inside an iframe, which the axe run of the main document may not reach, and custom
  widgets (`role="textbox"`, `contenteditable`), which the matcher never selects.

## Manual procedure

1. Read axe. From the `scripts/axe-page.mjs` output for this sample and each state (`fail` lines
   are violations, `review` lines incomplete results) take every `autocomplete-valid` node:
   violation → fail 100 (on `type` checkbox, radio, file or image: a note only, ACT 73f2c2 fixed
   value), noting selector, raw value and the step 2 label; incomplete → step 4. Done when every
   node of this rule has a note.

2. Inventory the fields in the default state:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   For each entry of `fields[]` read `tag`, `type`, `role`, `visibleLabelText`, `placeholder`,
   `legend`, `autocomplete`, `autocompleteCandidate`, `disabled`. Classify each field as in scope
   (the label, placeholder or legend asks the user for a listed purpose about themselves; write down
   the expected token, starting from `autocompleteCandidate` and correcting it from the label and
   the block: "Postcode" under a "Shipping address" heading expects `postal-code`, the `shipping`
   modifier being a recommendation only; "First name" `given-name`, a lone "Name" `name`, "City"
   `address-level2`; "Password" on a login form `current-password`, on a registration or
   change-password form `new-password` — the probe returns `current-password` for every password
   field, and either token on the other form names a listed purpose, never an F107 fail), out of
   scope (not a listed purpose, or about someone else: quote the wording that says so), or fixed
   value (checkbox, radio, file, button types). `disabled` fields collect nothing: out of scope.
   Done when every field has a class and every in-scope field an expected token.

3. Compare, for each in-scope field, `autocomplete` with the expected token. Confirm a doubtful raw
   value straight from the element:

   ```bash
   agent-browser get attr "input[name='email']" autocomplete
   ```

   Attribute absent, empty, `off`, `on` or a state word → fail (Deciding, 70 to 85). A token that
   names another listed purpose than the label → fail
   ([F107](https://www.w3.org/WAI/WCAG22/Techniques/failures/F107), 75 to 90). Field token right →
   pass for this field; note a missing `shipping`/`billing` modifier on a two-address form as a
   recommendation only. Case does not matter. `type="email"` or `type="tel"` without a token is
   still a fail: the Understanding calls the type "only very broad categories". Done when each
   in-scope field has a pass or a fail with certainty.

4. Resolve axe incomplete values. `gender` on a field asking gender identity: the listed token is
   `sex`, so the purpose is not exposed → fail 85. `pronouns` on a pronouns field, or `text`,
   `message`, `content` on free text: not a listed purpose, no defect. Done when none is undecided.

5. Repeat steps 2 and 3 in every state that adds fields; the `forms` pass reaches them anyway. Open
   the login, register, newsletter or search dialog (`click`, then a fresh `snapshot`), expand
   collapsed sections, tick every toggle that reveals fields (a "Billing address differs", company
   or delivery-address switch: `check "input[name='billing-differs']"`), then fill and submit each
   step of a multi-step form:

   ```bash
   agent-browser fill "input[name='email']" "test@example.org"
   agent-browser click "button[type='submit']"
   agent-browser wait --load networkidle
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   ```

   Run `scripts/axe-page.mjs` for each state so step 1 covers it. Payment or address fields in an
   iframe: `snapshot` to find the frame, `frame "<css>"`, run `forms.js`, then `frame main`. A
   frame that cannot be entered → `cannot-tell` for its fields, naming the frame `src` from
   `structure.js` `iframes[]`. Done when the findings file lists every state probed.

6. Custom widgets. `snapshot -i` shows `textbox`, `combobox` and `searchbox` roles; where
   `forms.js` reports such a `role` with a `tag` other than `input`, `select` or `textarea`, there
   is no `autocomplete` to read and the purpose is not exposed. A widget collecting a listed
   purpose about the user goes to the confirmation queue (Deciding, 60): the accessibility tree
   shows role and name, never a purpose token. Done when every custom text widget is classified.

7. Evidence for every fail: a page screenshot with the fields drawn:

   ```bash
   agent-browser highlight "form.checkout input, form.checkout select"
   agent-browser screenshot .notes/audit/evidence/<sample>-1.3.5-checkout.png
   ```

   Record per field the label, the selector, the raw `autocomplete` value and the expected token.
   Done when every fail has a screenshot path and this list.

## Deciding

- Fail (certainty ≥ 90): `autocomplete-valid` violation: unknown token, two field tokens, modifier
  without field token, wrong order, comma separation, tokens after `webauthn` (100). A well-formed
  token naming a different listed purpose than a plain one-word label, `email` on "Name" or `bday`
  on "Postcode" ([F107](https://www.w3.org/WAI/WCAG22/Techniques/failures/F107)) (90).
- Fail (70–89): no `autocomplete`, an empty value, `off`, `on` or a state word on an in-scope
  field whose label is a plain word for a listed purpose about the user ("E-mail", "Telephone",
  "First name", "Postcode", "Password", "Card number", "Date of birth", "Country") (85); `gender`
  as the token of a gender-identity field, where `sex` is the listed purpose (85); the same
  omission where the owner is read from a heading or legend (a bare "Name" or "Address" in a form
  that could describe a venue or a third party) (70); a token of the wrong granularity (`name` on a
  first-name field beside a last-name field) (75); a modifier contradicting its block (`billing` on
  the shipping address), as an F107 mismatch (70).
- Needs confirmation (50–69): a custom widget (`role="textbox"`, `combobox`, `contenteditable`)
  collecting a listed purpose about the user: ask whether a native control is possible, since the
  purpose cannot be exposed on the widget (60). A field whose owner the page never states (a
  booking "Guest name" that may be the user) without a token: ask who the field is for (55).
- Pass: every in-scope field in every probed state has an `autocomplete` whose field token names the
  purpose its label asks for. A missing `shipping`/`billing` modifier is not a failure: §7 lists
  neither as a purpose. Working autofill is not required, and `autocomplete="off"` on the `<form>`
  element does not undo the tokens (ACT 73f2c2 passed example 2).
- Not present: no field in any state collects a listed purpose about the user.
- False positives to avoid: a combined "Email or username" field with `username`, `email` or no
  token; fields about other people; purposes outside the list (search, quantity, one-time code,
  order number, message) with or without a custom value; a token that does not fit the control
  `type` (`bday-day` on `type="tel"`) still identifies the purpose; mixed case; a trailing
  `webauthn`; a `section-*` prefix; `type="hidden"`, `disabled` and `readonly` fields; an axe
  violation on a checkbox, radio, file or image input (ACT 73f2c2 "fixed value"): a note, no fail.

## Reporting

- File under: 1.3.5 for every missing, wrong or malformed purpose token. A missing visible label
  goes to 3.3.2, a missing accessible name to 4.1.2, a label not tied to its field to 1.3.1; the
  1.3.5 issue carries the token only. One issue per form (contact form, checkout address block,
  login dialog) listing the fields with label, current value and expected token; a component that
  repeats on other samples (site-wide login dialog, footer newsletter) names the other samples.
- Title patterns: "Contact form fields have no autocomplete purpose", "Wrong autocomplete token on
  the postcode field", "Malformed autocomplete value on the phone field"
- Severity: High when wrong tokens on a login or payment form make the browser fill in wrong data so
  the form cannot be completed; Medium when a form collecting personal data (registration, checkout,
  account, contact) has no or wrong tokens on most fields, or the defect sits in a site-wide
  component; Low when one or two fields in a tokenised form miss or malform the token.
- Type: Technical, always: the fix is an attribute in the markup.
- Evidence: page or element screenshot of the form with `highlight` on the fields concerned; no
  GIF, nothing moves. The text names each field's label, raw attribute value and expected token.
- Recommendation: add `autocomplete` with the WCAG §7 token that matches each label, prefixed with
  `shipping` or `billing` where both blocks exist
  ([H98](https://www.w3.org/WAI/WCAG22/Techniques/html/H98)); replace wrong or made-up values
  ([F107](https://www.w3.org/WAI/WCAG22/Techniques/failures/F107)); use a native `input`, `select`
  or `textarea` where a custom widget collects user data. Example:
  `<label for="pc">Postcode</label> <input id="pc" name="pc" autocomplete="shipping postal-code">`.
- Related: 3.3.2 Labels or Instructions and 4.1.2 Name, Role, Value (no visible label, no name);
  1.3.1 (label not associated); 3.3.7 Redundant Entry (data asked twice in a process, checked in
  the `consistency` pass; autofill does not excuse it); 3.3.8 Accessible Authentication (a login
  that blocks paste). This criterion carries only the purpose token; each related its own defect.
