# 3.3.4 Error Prevention (Legal, Financial, Data)

Level AA · WCAG 2.0+ · Guideline 3.3 Input Assistance · Group: `forms`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)
· [Spec](https://www.w3.org/TR/WCAG22/#error-prevention-legal-financial-data)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#error-prevention-legal-financial-data)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-3-4-error-prevention-legal-financial-data/)
· ACT: none mapped to this criterion.

## Requirement

> For web pages that cause legal commitments or financial transactions for the user to occur, that
> modify or delete user-controllable data in data storage systems, or that submit user test
> responses, at least one of the following is true:
>
> - Reversible: Submissions are reversible.
> - Checked: Data entered by the user is checked for input errors and the user is provided an
>   opportunity to correct them.
> - Confirmed: A mechanism is available for reviewing, confirming, and correcting information
>   before finalizing the submission.

Terms (WCAG 2.2 glossary): **legal commitments**: "transactions where the person incurs a legally
binding obligation or benefit [...] a stock trade (financial and legal), a will, a loan, adoption,
[...] a contract of any type". **user controllable**: "data that is intended to be accessed by
users [...] This does not refer to such things as Internet logs and search engine monitoring data."
**input error**: "information provided by the user that is not accepted [...] required by the web
page but omitted by the user [...] falls outside the required data format or values".
**mechanism**: "[...] may be relied upon to be provided by either the platform or by user agents".

## In plain terms

Where a submission commits the user to something (an order, a payment, a contract), changes or
deletes data stored about them (an address, a record, an account) or hands in the answers of a
test, the site gives one of three safety nets: it can be undone afterwards, the entered data is
validated and correctable, or the user reviews and confirms it first. One net is enough; the
Intent targets "mass loss of data such as deleting a file or record", not "a confirmation for each
save command". It serves people who transpose digits, hit the wrong key or lose track of a step.

## Applies when

- Present: a state of the sample has a control whose activation submits (A) a legal commitment or
  financial transaction: place order, pay, book, subscribe to a paid plan, sign, accept a contract,
  transfer, donate, file a return; (B) a change or deletion of stored user-controllable data:
  delete or remove a record, address, payment method, file, message or account, cancel a
  subscription, save a profile edit; (C) test responses: submit answers, finish or end a test.
  Detect it in `snapshot -i` button and link names, `forms.js` `forms[].submitButtons` (names,
  not selectors) and `fields[]` (`autocompleteCandidate` reaches `cc-number`; `autocomplete`
  carries `cc-exp` and `cc-csc`), `structure.js` `headings` and `title` ("Checkout", "Delete
  account", "Quiz") and the sample's own description in `index.md` ("<process>, step n/total").
- Not present: no state has such a control. Search, contact, newsletter, comment, login, filter and
  cookie forms, adding to a basket and a Save on a document the user is writing are outside it:
  record `not-present` and name the forms checked.
- Exceptions: none in the normative text; the three conditions are alternatives, one suffices. The
  Intent draws the line for (B): "the simple creation or editing of documents, records or other
  data" needs no confirmation (an edit form with validation passes as Checked); deleting a file,
  record or account is the "mass loss" it targets.

## axe-core

No axe-core rule is tagged with this criterion; everything below is manual.

## Manual procedure

Work in every state of `recon/<sample>-states.md` that holds a submission of situation A, B or C
(form steps, the review step, the error state, account pages with delete controls). The "final
control" is the button or link whose activation causes the commitment, deletion or test
submission. Test data, credentials and a test environment come from `.notes/sample.md`; on a
production target the final control is activated only in step 4's no-network mode and what follows
a real submission (step 5) is "not walked". A process over several samples is decided on its final
step, recorded in `process--<slug>.md` with that step's sample id.

1. Classify every submission. Run `forms.js` and `structure.js`, then `snapshot -i`; list every
   button, link and form whose name, legend or heading matches the (A), (B) or (C) wording of
   "Applies when", in the report's language as well. Give each a situation letter or "out" with the
   reason (no commitment, no stored user data, a simple save, adding to the basket), the final
   control's selector and the committed fields (`fields[]` is one flat page-wide list, not nested
   in `forms[]`: take the controls `snapshot -s "<form selector>"` shows). A one-click delete
   commits no entered data, so Checked cannot carry it; a test submission can, since an omitted
   required answer is an input error. Done when each candidate has a letter or "out", a selector
   and its fields.

2. Read the pre-submit mechanisms without activating anything, per final control:
   - Review ([G98](https://www.w3.org/WAI/WCAG22/Techniques/general/G98)): the state shows the
     committed data as text (order lines, total, address, payment method, answers) beside a way to
     change it: `links.js` `links[].text` or `snapshot -i` names such as Edit, Change, Back,
     Previous. Activate one, `wait --load networkidle`, run `forms.js`: `fields[].value` still
     holds the earlier entries and `is enabled` is true; return with the flow's own Next control.
   - Confirming checkbox ([G155](https://www.w3.org/WAI/WCAG22/Techniques/general/G155)): a
     `fields[]` `checkbox` in the final control's form whose `visibleLabelText` says the user has
     checked the data or wants the action ("I have checked my order", "I understand this cannot
     be undone"); a terms checkbox counts only when its label says that. Read `required` and
     confirm `is checked "<selector>"` is false on load, as G155 asks.
   - Stated reversibility ([G164](https://www.w3.org/WAI/WCAG22/Techniques/general/G164),
     [G99](https://www.w3.org/WAI/WCAG22/Techniques/general/G99)): `get text` on the form and
     `fields[].describedbyText` for a stated window and procedure ("Cancel this order until it
     ships, under My orders"; "Deleted files stay in the bin for 30 days"). G164 asks for both.
   - Prompt wired in the markup ([G168](https://www.w3.org/WAI/WCAG22/Techniques/general/G168)):
     `get attr "<final control css>" onclick` and `get attr "<form css>" onsubmit` containing
     `confirm(`, or `get count "dialog, [role=dialog], [role=alertdialog]"` above zero with Confirm
     and Cancel wording in `get text` on each: a pre-rendered prompt that step 4 will see open.
     Done when each final control has "review: <selector> | none", "checkbox: <selector> | none",
     "stated reversal: <quoted text> | none" and "prompt in markup: yes | no".

3. Checked, only for a submission whose committed data the user enters. Take a form whose
   submission has no real-world effect (an earlier step, an edit form on a test account); the
   final control's own form waits for step 4. `fill` each committed field with an invalid value
   (a required field empty, letters in an amount, `4111 1111 1111 1112` as card number, an expiry
   in the past), then `find role button click --name "<submitButtons[0]>"` (the probe lists submit
   buttons by name) or `focus` the last field and `press Enter`, `wait 1500`, run `forms.js` for
   `visibleErrors[]` and `forms[].novalidate`, and `eval --stdin` with
   `[...document.querySelectorAll(':invalid')].map(e => [e.name || e.id, e.validationMessage])`. A
   check exists when `visibleErrors[]` names the field, the `:invalid` list carries a message on a
   form without `novalidate` (the browser itself blocks the submission) or the server returned an
   error message in `snapshot`. Correction exists when `fields[].value` still holds the entries and
   `fill` with a valid value plus the same submit clears the error. The tree shows the message and
   its `forField`; whether a screen reader hears it is 3.3.1 and 4.1.3. Done when each data-entry
   form has "checked: native | script | server | none" and "correctable: kept | lost".

4. Activate the final control with no request leaving the browser, which keeps the ground rule on
   real-world effects. Route the submission target alone (`forms[].action` where the form has one);
   `"**/*"` also catches an AJAX submit but aborts the page's own reloads, so keep it for the
   sample's last control. On a test environment in `.notes/sample.md` skip the route, do the same
   reads and go on to step 5. Order: the G155 checkbox unticked (`uncheck "<selector>"`), then step
   3's invalid values, then the box ticked (`check "<selector>"`) with valid values:

   ```bash
   agent-browser eval --stdin <<'JS'
   (() => { const f = window.fetch; window.__sent = [];
     window.fetch = (...a) => (window.__sent.push(String(a[0])), f(...a)); return 'armed' })()
   JS
   agent-browser network route "<submission target>" --abort
   agent-browser find role button click --name "Place order"
   agent-browser dialog status
   agent-browser snapshot -i
   agent-browser get url
   ```

   A native dialog blocks `wait`, `snapshot` and `console` until `dialog accept` or
   `dialog dismiss` runs, so resolve it first: `dialog status` naming the action is the G168 prompt,
   and after `dialog dismiss` an unchanged `snapshot -i` is a working cancel. A `dialog` or
   `alertdialog` in the snapshot naming the action with two choices is a custom prompt: `click` its
   cancel choice (page unchanged), then its confirm choice. A request that left the browser shows
   in `get url` (`chrome-error://` or an offline page after a form navigation) and in `eval --stdin`
   with `(() => window.__sent)()`; `console` and `errors` stay silent for an aborted request the
   page swallows. In the unticked and invalid runs a recorded request means that box or that
   validation does not block in the browser and leaves the server's answer to step 5. Recover with
   `open <sample url>`, which `reload` cannot do after an aborted submission. Done when the final
   control has "on activation: native prompt with cancel | custom prompt with cancel | prompt
   without cancel | request sent" and "checkbox / validation blocks in the browser: yes | no | n/a".

5. On a test environment only: submit for real with the test data, `wait --load networkidle`,
   `snapshot`, `structure.js` `liveRegions[].text`, `links.js`. A cancel or amend window with its
   control (G164): activate it and confirm the order shows as cancelled or editable. After a
   deletion, an Undo or Restore (G99) in the status message or the bin: activate it and confirm the
   record is back. The tree shows the Undo control and its text, not whether the message is
   announced (4.1.3) or how long it stays (2.2.1). Done when every mechanism claimed in step 2 has
   been exercised or recorded as "not walked".

## Deciding

- Fail (certainty ≥ 90): on a test environment, a final control of situation A, B or C completes
  with no review state before it, no confirming checkbox, no prompt, no validation of its entered
  fields and no undo, restore or stated cancel window after it — 95; the same for a deletion or a
  finished test that completes with no prompt and no way back — 95.
- Fail (70–89): a submission that completes on a test environment with the confirming checkbox
  unticked, as the only mechanism — 85; in no-network mode the final control sends its request with
  no prompt, step 2 found no review state, no checkbox, no stated reversal and, for entered data, no
  check, and the process notes record no step after it — 80; a "Finish" or "Submit answers" control
  that sends from the last question with no review, no prompt and no unanswered-question warning —
  80; a review state with no way to correct (no Edit or Back, or the earlier step returns with
  `fields[].value` empty), a prompt with no cancel choice or whose cancel sends the request anyway,
  or validation that returns the form with the entries lost, each as the only mechanism — 80; a
  cancel or amend window the page states neither in time nor in procedure — 70.
- Needs confirmation (50–69): whether the submission binds at all (a reservation without payment, a
  job or benefit application, a quote): ask the commissioner — 55; whether removing one item (a
  basket line, a wishlist entry, a draft) is stored user-controllable data or the simple editing the
  Intent excludes — 55; a statutory right of withdrawal, stated nowhere on the page, offered as the
  Reversible mechanism — 55; a review step outside the sample set, a final control that needs a real
  card or identity check, or a request sent in no-network mode behind which a server-rendered
  review, rejection or bin may sit: `cannot-tell`, queued with the step reached — 60.
- Pass: every submission of situation A, B or C, in every state, has one verified mechanism: a
  review state with a working way back to editable entries (G98); a confirming checkbox that
  blocks when unticked (G155); a prompt on activation with a working cancel (G168); a stated and
  working cancel or amend window (G164); a working undo or restore after deletion (G99); or, for
  data the user enters, a check that rejects invalid entries and keeps them editable.
- Not present: no state submits a commitment, a transaction, a data change or deletion, or a test.
- False positives to avoid: search, contact, newsletter, login, comment and filter forms; a Save on
  a document the user is writing, and the "confirmation for each save command" the Intent excludes;
  one mechanism suffices; the browser's own validation blocking a submission is a check; a cancel
  procedure that runs offline counts when the page states its time and its steps (G164); a request
  sent in no-network mode does not show what the server answers; a Cancel button that abandons the
  form is no confirmation; error wording is 3.3.1 and 3.3.3, an expiring Undo 2.2.1, a prompt not
  announced or trapping focus 4.1.3 or 2.1.2; they still count.

## Reporting

- File under: 3.3.4. Errors not identified or described go to 3.3.1 and 3.3.3; a confirming
  checkbox or delete control without an accessible name to 4.1.2, without a visible label to
  3.3.2; a prompt that traps focus to 2.1.2, one not announced to 4.1.3; a review step that
  re-asks what the user typed to 3.3.7. One issue per submission (one checkout, one delete control,
  one test), naming every step and sample of the process it sits in.
- Title patterns: "Orders are placed with no chance to review them", "Deleting an address happens
  at once, with no confirmation or undo", "The test is handed in without a review of the answers",
  "The 'I have checked my details' box does not block the submission"
- Severity: High when a payment, contract, account deletion or final test submission has no
  mechanism, or the only one is broken (a prompt without cancel, a checkbox that does not block);
  Medium when a mechanism exists but is incomplete (a review without a way back, an unstated undo,
  validation that loses the entries) or the loss is a single record the user can re-enter; Low
  when the mechanism works but is hard to find (a cancel window stated only deep in the account).
- Type: Technical for a missing or broken prompt, undo, checkbox binding or validation; Design
  when the flow lacks a review step or a way back; Content when the mechanism exists and only the
  text stating the cancel window or the checkbox label is missing or wrong.
- Evidence: `highlight "<final control css>"` and `screenshot` of the state before activation and
  of what followed (the failed request, the changed list, the review page with no Edit control);
  `record start` / `record stop` around a delete that runs without a prompt gives the GIF.
- Recommendation: add the mechanism that fits the flow: a review step with an Edit link per section
  ([G98](https://www.w3.org/WAI/WCAG22/Techniques/general/G98)); a required checkbox before the
  final control ([G155](https://www.w3.org/WAI/WCAG22/Techniques/general/G155)); a prompt with
  Cancel as the default choice ([G168](https://www.w3.org/WAI/WCAG22/Techniques/general/G168)); a
  stated cancel window with a control that performs it
  ([G164](https://www.w3.org/WAI/WCAG22/Techniques/general/G164)); a bin or Undo for deletions
  ([G99](https://www.w3.org/WAI/WCAG22/Techniques/general/G99)); client-side validation
  ([SCR18](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR18)) and success feedback
  ([G199](https://www.w3.org/WAI/WCAG22/Techniques/general/G199)) support it. Example:
  `<input type="checkbox" id="ok" required> <label for="ok">I have checked my order and want to
place it</label> <button type="submit">Place order</button>`.
- Related: 3.3.1 and 3.3.3 (the quality of the check); 3.3.6 at AAA (the same for every form);
  3.3.7 (data re-asked on the review step); 3.3.2 (the checkbox label); 3.2.2 (a submission fired
  by a setting change); 4.1.3 (the undo toast); 2.2.1 (an undo that expires); 2.1.2 (the prompt).
