# 2.5.7 Dragging Movements

Level AA · WCAG 2.2+ · Guideline 2.5 Input Modalities · Group: `pointer`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#dragging-movements) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#dragging-movements) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/2-5-7-dragging-movements/) ·
ACT: none mapped to this criterion.

## Requirement

> All functionality that uses a dragging movement for operation can be achieved by a single
> pointer without dragging, unless dragging is essential or the functionality is determined by the
> user agent and not modified by the author.
>
> Note:
> This requirement applies to web content that interprets pointer actions (i.e., this does not
> apply to actions that are required to operate the user agent or assistive technology).

Terms (WCAG 2.2 glossary), each quoted because it decides an outcome here.

**functionality**: "processes and outcomes achievable through user action". The unit under test is
the outcome — item at another position, card in another column, value set, view panned, file
attached — never the widget that happens to produce it. One finding per function.

**dragging movements**: "an operation where the pointer engages with an element on the down-event
and the element (or a representation of its position) follows the pointer until an up-event", Note:
"Examples of draggable elements include list items, text elements, and images." "or a
representation of its position" is the clause that widens it: a ghost image, a drop placeholder, a
slider thumb or a map viewport that moves while the element itself stays put is still a drag.

**single pointer**: "an input modality that only targets a single point on the page/screen at a
time – such as a mouse, single finger on a touch screen, or stylus." Note: "Single pointer
interactions include clicks, double clicks, taps, dragging motions, and single-finger swipe
gestures. In contrast, multipoint interactions involve the use of two or more pointers at the same
time, such as two-finger interactions on a touchscreen, or the simultaneous use of a mouse and
stylus." So a swipe is a single pointer interaction and still not an acceptable alternative here
(it is path-based, 2.5.1), and a two-finger pinch or rotate is not a dragging movement at all.

**essential**: "if removed, would fundamentally change the information or functionality of the
content, **and** information and functionality cannot be achieved in another way that would
conform". Both halves must hold; the second almost never does, which is why the exception is rare.

**user agents**: "any software that retrieves and presents web content for users", Example: "Web
browsers, media players, plug-ins, and other programs — including assistive technologies — that
help in retrieving, rendering, and interacting with web content." What the browser provides and the
author has not modified is outside the criterion.

**down-event**: "platform event that occurs when the trigger stimulus of a pointer is depressed";
**up-event**: "platform event that occurs when the trigger stimulus of a pointer is released". W3C
names them "touchstart" or "mousedown" and "touchend" or "mouseup" — the handler names step 1
searches for.

The Intent models a drag as four discrete user actions: "tap or click to establish a start-point,
then", "press and hold that contact while...", "performing a repositioning of the pointer,
before...", "releasing the pointer at the end-point." Step 2 reproduces exactly those four.

## In plain terms

Whatever the page lets a user do by pressing on an element and moving it before releasing
(reordering a list, moving a card to another column, setting a slider, panning a map, drawing a
selection box, dropping a file), it also lets them do with taps or clicks alone: arrows shown after
tapping an item, a "Move to" menu, a click on the slider track, pan buttons, a number field. W3C's
own summary is the whole test: "Don't rely on dragging for user actions", and "For any action that
involves dragging, provide a simple pointer alternative." It serves people who "cannot perform
dragging movements in a precise manner" and people on "a specialized or adapted input device, such
as a trackball, head pointer, eye-gaze system, or speech-controlled mouse emulator", plus
touchscreen users with no physical keyboard, so a keyboard route on its own does not satisfy it. A
path the pointer must follow is 2.5.1; one component can fail both.

## Applies when

- Present: a component that moves an element, or a representation of its position, with the
  pointer between a down-event and an up-event: sortable lists and tables, kanban boards, file
  drop zones, custom sliders and media scrubbers, colour pickers with a draggable marker, maps
  panned by dragging, dragged carousels, resizable panels and splitters, croppers and selection
  rectangles, custom scrollbars that replace the browser's, matching exercises where a connecting
  line is drawn between two columns, and widgets where an object is dropped onto one of several
  targets in a picture. Step 1 lists candidates, step 2 confirms them; every recorded state counts
  (a board behind a tab, a slider in a dialog, a filter drawer, a card expanded in place, the
  error state of a form that holds an upload field).
- Not present: no step 1 candidate in any state, or every candidate ignores the drag of step 2.
- Exception 1, "unless dragging is essential": the drag itself is the outcome — freehand placement
  in a drawing tool, a dexterity game. Both halves of **essential** must hold, so route it to the
  human before recording a pass.
- Exception 2, "or the functionality is determined by the user agent and not modified by the
  author". W3C spells the cases out: "In browsers operated with a mouse, users generally scroll
  content by dragging the browser's scrollbar. In touchscreen browsers, users generally scroll by
  'dragging' the page on the screen. Similarly, most touchscreen browsers provide a 'drag to
  refresh' gesture to refresh/reload a page. In all these cases, the functionality is provided by
  the browser, rather than implemented by the content – so this criterion does not apply. This
  criterion also does not apply to the use of techniques such as CSS overflow that make a section
  of content scrollable, as the actual scrolling mechanism even in these situations is provided by
  the user agent." Text selection, a native `input[type="range"]`, a `<video controls>` scrubber
  and the browser's ghost-drag of links and images are the same case.
- Back in scope: "The criterion does apply if content actively suppresses the user agent's own
  scrolling functionality and/or implements its own scrolling mechanism – in these cases, the
  scrolling/dragging gesture is interpreted and processed by the content itself, and thus falls
  under the responsibility of the content author." The Note excludes only what is "required to
  operate the user agent or assistive technology".
- Not an exception — a keyboard route: "achieving keyboard equivalence for a dragging operation
  does not automatically meet this success criterion, unless that equivalent keyboard operation
  also provides controls that can be clicked or tapped with a pointer. It is possible to create an
  interface that works with dragging and keyboard controls, but still does not work using only
  clicks or taps. [...] the two requirements are evaluated independently."
- Not an exception — a swipe: "the single pointer alternative can't exclusively rely on a
  path-based gesture, such as swiping or 'flicking', as this would fail the requirements of 2.5.1
  Pointer Gestures."
- Where the route may live: "It does not have to be the same component, so long as the
  functionality is equivalent." The Understanding scopes this to alternatives "on the same page",
  so a route that only exists on another page goes to the confirmation queue.
- Boundary with 2.5.1: "Once the pointer engages with a target to pick up/grab it, the direction of
  the dragging movement does not factor into the interaction at all." Both can fail together: "if
  an action involves both a dragging movement (such as grabbing a slider thumb, moving it, and then
  releasing it) and a path-based gesture (if the slider requires the user to exactly follow its
  track, or otherwise the user's grip on the slider thumb is 'lost'), it may fail against the
  requirements of both success criteria." Step 2's bend off the straight line separates the two.

## axe-core

No axe-core rule is tagged with this criterion, and no probe has a dragging field, so everything
below is manual and the inventory of step 1 is the only detection. Two existing probes are read for
the _alternative_ controls, never for detection: `focusables.js` `order` (`name`, `role`, `box`,
`visible`, `obscured`, `obscuredBy`) names Move, Pan, Next and Previous controls that already
exist, and `targets.js` `targets` (`w`, `h`, `passes24`) sizes the control once it is found, for
the 2.5.8 split in "Reporting".

## Manual procedure

Work at phone width: `set device "Pixel 7"`, `reload`, `wait --load networkidle` (move buttons are
often hidden below a breakpoint; 0.37 rejects `"iPhone 13"`, while `"Pixel 7"`, `"iPhone 15"` and
`"iPhone 16"` are accepted). `set device` sets the viewport and the user agent only: touch events
are not emulated and `hover` keeps working, so a component listening for `touchstart` alone may not
respond. Run every step in the default state, in each recorded state, and inside each
`structure.js` `iframes` entry (`frame "<css>"`, `frame main`). Only a performed drag followed by a
change shows a drag function; `snapshot -i` shows controls. Record `cannot-tell` for a component
the emulation cannot drag when step 3 finds no control.

1. Inventory the candidates.

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const q = (s) => [...document.querySelectorAll(s)];
     const sel = (e) => e.localName + (e.id ? '#' + e.id : '') + (typeof e.className === 'string'
       && e.className.trim() ? '.' + e.className.trim().split(/\s+/).slice(0, 2).join('.') : '');
     const vis = (e) => { const r = e.getBoundingClientRect(); return r.width > 0 && r.height > 0 };
     const cur = /grab|move|(col|row|ew|ns|nesw|nwse)-resize/;
     return {
       draggable: q('[draggable="true"],[ondragstart],[ondrop],[onmousedown],[onpointerdown],' +
         '[ontouchstart],[aria-roledescription],[data-rbd-draggable-id],[role="slider"],' +
         'input[type="range"]').filter(vis).map(sel),
       cursors: q('body *').filter((e) => vis(e) && (cur.test(getComputedStyle(e).cursor) ||
         getComputedStyle(e).touchAction === 'none')).slice(0, 20).map(sel),
       widgets: q('[class*="sortable" i],[class*="drag" i],[class*="kanban" i],[class*="dnd" i],' +
         '[class*="dropzone" i],[class*="resiz" i],[class*="scrubber" i],[class*="slider" i],' +
         '[class*="carousel" i],[class*="color" i],.leaflet-container,.mapboxgl-map,.gm-style')
         .filter(vis).map(sel),
       ownScroll: q('body *').filter((e) => {
         if (!vis(e)) return false;
         const st = getComputedStyle(e);
         if (!/hidden|clip/.test(st.overflowX + ' ' + st.overflowY)) return false;
         if (!(e.scrollWidth > e.clientWidth + 8 || e.scrollHeight > e.clientHeight + 8))
           return false;
         return st.touchAction === 'none' || cur.test(st.cursor) ||
           e.matches('[onmousedown],[onpointerdown],[ontouchstart],[draggable="true"]');
       }).slice(0, 20).map(sel),
       dragText: [...document.body.innerText.matchAll(
         /.{0,30}\b(drag\w*|drop|versle+p\w*|sle+p\w*)\b.{0,30}/gi)].map((m) => m[0]).slice(0, 10)
     };
   })()
   EOF
   ```

   Handlers added with `addEventListener` stay invisible: a cursor, `touch-action: none`, a
   `widgets` class or a `dragText` hit makes the element a candidate; the candidate is the
   component (list, board, slider, map) plus one item of each kind to drag. An `ownScroll` entry is
   content that clips its own overflow and may be moving it with the pointer itself — the case the
   Understanding puts back in scope. Cross-read `focusables.js` `order` for `name` values like
   "Move up", "Move to", "Pan left", "Next": a component that already has them is likely a pass and
   step 3 only has to confirm it. Done when every candidate is in the findings file with the signal
   that flagged it.

2. Perform the drag and name the function. Reproduce the Intent's four actions: establish the
   start-point, hold, reposition, release. Use `drag` between two items or onto a column, and a
   `mouse` sequence by offset that bends 30 px off the straight line for sliders, maps, splitters
   and croppers:

   ```bash
   agent-browser screenshot "<component>" .notes/audit/evidence/<sample>-2.5.7-<slug>-before.png
   agent-browser get html "<component>" | shasum
   agent-browser drag "<item>" "<target item or column>"; agent-browser wait 800
   agent-browser get box "<handle>"; agent-browser mouse move <cx> <cy>; agent-browser mouse down
   agent-browser mouse move <cx + 40> <cy>; agent-browser mouse move <cx + 120> <cy + 30>
   agent-browser mouse up; agent-browser wait 800; agent-browser get html "<component>" | shasum
   ```

   After each drag: `screenshot "<component>" ...-after.png`, `get url`, `snapshot -i -s
"<component>"`, `get attr "<slider>" aria-valuenow`. Name the function from the difference
   (item at position 3, card in Done, value 40 → 65, map shifted). An element that follows the
   pointer off the line is dragged (here); one dropped when the pointer strays is path-based too
   (2.5.1) and both are recorded. No change from any drag: strike the candidate, unless `dragText`
   says otherwise (then `cannot-tell` when step 3 finds nothing). Done when every candidate is
   "drag → <function>", struck, or `cannot-tell`.

3. Find the single-pointer route without dragging
   ([G219](https://www.w3.org/WAI/WCAG22/Techniques/general/G219), whose test is "Check that there
   is a single pointer activation alternative that does not require dragging to operate the same
   function"; the [F108](https://www.w3.org/WAI/WCAG22/Techniques/failures/F108) test is the same
   check and "If #2 is false, then this failure condition applies and the content fails this
   Success Criterion"). F108 allows a chain: "The alternative may involve a series of single
   pointer interactions (for example, activating a target to be moved; opening a dropdown menu; and
   selecting a drop destination from the list of menu items offered)." `reload`, `click "<item>"`
   (G219 shows controls on selection), `snapshot -i -s "<parent>"`, then per control
   `click "<control>"`, `wait 800`, `get html "<component>" | shasum`. Worked example, a board:

   ```bash
   agent-browser drag ".card[data-id='7']" ".column[data-status='done']"; agent-browser wait 800
   agent-browser get html ".board" | shasum          # note this hash: the drag outcome
   agent-browser reload; agent-browser wait --load networkidle
   agent-browser click ".card[data-id='7']"; agent-browser snapshot -i -s ".card[data-id='7']"
   agent-browser find role button click --name "Move to"; agent-browser snapshot -i
   agent-browser find role menuitem click --name "Done"; agent-browser wait 800
   agent-browser get html ".board" | shasum          # same hash → the taps reach the same outcome
   ```

   Candidates to look for: Move up and Move down arrows, a "Move to" or More actions menu with
   every column, a position field (`fill "<field>" 3`, `press Enter`), Next and Previous on a
   carousel, corner-by-corner clicks for a selection; step 4 takes the sliders, maps, splitters and
   custom scrolling, step 5 the drop targets and drawn shapes. A text field counts: "a text input
   is considered device agnostic; although the purpose is to enter characters, text entry can take
   place through voice, pointer or keyboard", and for touch users "the on-screen keyboard that
   appears [...] offers a single-pointer means of entering an alphanumeric value". A control counts
   when its `click` or `fill` produces the change of step 2. `click` prints "Done" even when
   nothing was hit, and `get box` returns the border box (a clipped `sr-only` button measures
   16 × 6), so hit-test every candidate control before believing it:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const sels = ['<control 1>', '<control 2>'];
     return sels.map((s) => {
       const e = document.querySelector(s);
       if (!e) return { s, found: false };
       const r = e.getBoundingClientRect();
       const st = getComputedStyle(e);
       const hit = document.elementFromPoint(r.left + r.width / 2, r.top + r.height / 2);
       return { s, found: true, w: Math.round(r.width), h: Math.round(r.height),
         display: st.display, visibility: st.visibility, pointerEvents: st.pointerEvents,
         clipped: st.clip !== 'auto' || st.clipPath !== 'none',
         hitsSelf: !!hit && (hit === e || e.contains(hit) || hit.contains(e)),
         hitTag: hit ? hit.localName : null,
         name: (e.getAttribute('aria-label') || e.textContent || '').trim().slice(0, 40) };
     });
   })()
   EOF
   ```

   `hitsSelf: true` with a non-zero `w`/`h` and `pointerEvents` other than `none` means a pointer
   can reach it; `clipped: true` alone does not disqualify it, because the Understanding accepts
   controls that are "visually hidden (but still operable with a pointer)". The route may be
   another component on the same page; a route on another page goes to the queue. Cover the whole
   function: down as well as up, every column, every direction. A swipe or flick does not count.
   Then `set viewport 1280 900`, `reload`, repeat this step and step 2; a control only one layout
   has is recorded for the layout that lacks it, and a control that only `hover "<item>"` reveals
   goes to the queue. Done when every drag function has "tap route: <control>" per layout or
   "none".

4. Continuous controls: sliders, colour wheels, maps, splitters, custom scrolling. A native
   `input[type="range"]` is user-agent functionality: pass, unless step 1 lists a pointer handler
   or `touch-action: none` on it. For a custom slider, scrubber or volume bar, `get box "<track>"`,
   `mouse move` to a quarter of its width, `mouse down`, `mouse up`, `get attr "<slider>"
aria-valuenow` (a video: read `currentTime` with a one-expression `eval --stdin`): a value
   that jumps to the tapped point, steppers, or a value field is the route. Radial control or
   colour wheel: W3C's pass is that the widget "allows picking another color value by tapping or
   clicking on another place in the color wheel" — `get box "<wheel>"`, click a point on the ring
   away from the marker, then `get attr "<wheel>" aria-valuenow` or read the swatch; hex, RGB or
   HSL text fields count too.
   Map: look for pan buttons (`find role button click --name "Pan up"`); neither Leaflet nor a
   Google Maps embed ships them by default; a search field that moves the view to a typed place is
   a partial route; a map with one pinned location and its address in text goes to the queue.
   Splitter: a Collapse, Expand or Maximise button or a size select counts. Custom scrolling (an
   `ownScroll` entry whose content moves with the drag, i.e. content that "actively suppresses the
   user agent's own scrolling functionality"): scroll buttons or in-page links count, and a plain
   `overflow: auto` region is the user agent's own scrolling and passes. Done when each is
   "native", "route: <control>", "queue" or "none".

5. Drop targets and drawn shapes. Drop zone: `get count "<zone> input[type=file]"` above 0 or a
   Browse button that opens the file picker counts. An object dropped onto one of several targets
   (W3C's gift dragged to a person in a group photo): the pass is "a menu alternative where users
   can select the person that should receive the gift from the menu" — `click "<object>"`,
   `snapshot -i`, and check the menu names every target the drag can reach. Selection rectangle on
   an image: the pass is that "the user can enable a selection mode, click/tap the first corner,
   then click/tap the opposite corner" — look for that mode, or numeric x/y/width/height fields.
   Matching exercise with connecting lines: the pass is that users "can also just click/tap on one
   item in the first column, then click/tap on an item in the second column, and the connecting
   line is drawn automatically" — `click "<left item>"`, `click "<right item>"`, `wait 800`,
   `get html "<exercise>" | shasum` against the drag outcome. Dragged carousel: Next and Previous
   controls count whether they are "visible (for instance, as large arrow icons) or visually hidden
   (but still operable with a pointer)", so run the step 3 hit test rather than trusting the
   screenshot. Done when each is "route: <control>", "queue" or "none".

6. Evidence and reset. For every fail record the drag working and the tap failing:

   ```bash
   agent-browser record start .notes/audit/evidence/<sample>-2.5.7-<slug>.webm
   agent-browser drag "<item>" "<target item or column>"; agent-browser wait 800
   agent-browser reload; agent-browser wait --load networkidle
   agent-browser click "<item>"; agent-browser wait 800
   agent-browser click "<target item or column>"; agent-browser wait 800
   agent-browser record stop; agent-browser highlight "<component>"
   agent-browser screenshot .notes/audit/evidence/<sample>-2.5.7-<slug>.png
   agent-browser set viewport 1280 900
   ```

   For a slider or map, replace the `drag` line with the step 2 `mouse` sequence and follow it with
   a single `mouse move` + `mouse down` + `mouse up` on the track or the canvas, so the recording
   shows the tap changing nothing. Done when every fail has the recording and the screenshot, and
   the viewport is desktop again.

## Deciding

- Fail (certainty ≥ 90): a drag changes the component (step 2) and no tap-operable control, menu,
  track click or text field reproduces the outcome in that layout
  ([F108](https://www.w3.org/WAI/WCAG22/Techniques/failures/F108)) — 92; a list reordered or a
  card moved between columns only by dragging (F108 Examples 1 and 2) — 95; a custom slider whose
  track ignores taps, with no stepper or value field on the page — 90; a colour wheel or other
  radial control whose marker only drags, where a tap elsewhere on the wheel does nothing and no
  hex, RGB or HSL field exists — 90; a carousel that only moves when dragged, with no Next or
  Previous control that passes the step 3 hit test — 90; a selection rectangle that exists only by
  dragging a corner, with no click-one-corner-then-the-other mode and no numeric fields — 90; a
  matching exercise whose connecting line must be drawn, with no click-item-then-item route — 90;
  an object dropped onto one of several targets with no menu naming them — 90; a drop zone with
  neither a file input nor a Browse control — 90; arrow keys or Enter as the only alternative,
  with no control a pointer can click ("the two requirements are evaluated independently") — 90.
- Fail (70–89): the only control fails the hit test (`hitsSelf: false`, or `pointerEvents: none`)
  or measures 0 × 0, and `click` changes nothing — 85; the controls exist at 1280 px and are
  `display: none` at the device width — 85; the only route is a swipe or flick, a path-based
  gesture that cannot serve as the alternative — 85; a region that clips its own overflow and
  moves its content with the pointer, with no scroll buttons or in-page links — 85; the control
  covers part of the function (Up without Down, pan buttons for two directions, a column missing
  from the menu) — 80; a map that must be panned for a task, with zoom buttons only — 80.
- Needs confirmation (50–69): the page claims dragging is essential (a dexterity game, freehand
  placement) — 55: ask whether the outcome can be reached in another way that would conform; a
  map with one pinned location and its address in text, or a search field as its only non-drag
  route — 60: ask whether any task needs free panning; a route on another page — 60: ask whether
  it counts as the same functionality; controls only `hover` reveals — 60: ask whether a tap
  reveals them on a touch device; a WebGL map, canvas or cross-origin frame the emulation could
  not drag, or a `dragText` promise that no drag acted on, with no control — 55: ask the human to
  try the component on a touch device.
- Pass: every drag function of step 2, in every state and layout, has a control, menu, track click
  or text field that a pointer can hit and that reaches the whole outcome, on the same page and
  without relying on a swipe or a traced path; a chain of taps (select, open the menu, pick a
  column) is a pass.
- Not present: no drag function in any state, apart from user-agent functionality.
- False positives to avoid: user-agent scrolling, including a plain `overflow: auto` region, "drag
  to refresh", text selection, a native `input[type="range"]` or `<video controls>` scrubber, the
  browser's ghost-drag of a link or image; a two-finger pinch or rotate (multipoint, not a dragging
  movement); a path-following gesture with no drag (2.5.1); a component that only looks draggable
  (a `grab` cursor and no handler) that step 2 struck; a "visually hidden (but still operable with
  a pointer)" control that a `click` does operate; an unlabeled Move button (4.1.2); a control
  smaller than 24 × 24 px that works (2.5.8).

## Reporting

- File under: 2.5.7 for every function operable with a pointer only by dragging. The same
  component without a keyboard route is a second issue under 2.1.1; a route that needs a swipe or
  a traced path is 2.5.1; an unnamed Move or Pan button is 4.1.2; a control under 24 × 24 px is
  2.5.8. One issue per component; the same component on other samples is one issue naming them.
- Title patterns: "The <list> can only be reordered by dragging", "Cards on the <board> can only
  be moved by dragging", "The <slider> can only be set by dragging its thumb", "The map can only
  be panned by dragging", "The colour picker can only be set by dragging the marker", "The
  <carousel> can only be advanced by dragging", "Files can only be added by dropping them"
- Severity: High when the drag is the only route to a task step or to content (moving a task to
  Done, setting a value the form needs, panning a map to pick a location, uploading a file);
  Medium when the outcome is reachable elsewhere on the page less directly or the control covers
  part of the function; Low when the drag is a shortcut with an easy workaround.
- Type: Technical when the fix is script and markup (a click handler on the track, arrows or a
  menu, a file input); Design when the component needs visible controls it was not designed with.
- Evidence: the page screenshot at phone width with `highlight` on the component and no control
  beside it; the step 6 recording as a GIF (drag works, tap does nothing); for a slider or colour
  wheel, the value unchanged after the track or ring tap; for a drop zone, the zone with no Browse
  control in the same shot; for a control that only the desktop layout has, both widths.
- Recommendation: [G219](https://www.w3.org/WAI/WCAG22/Techniques/general/G219): give every
  dragged function a route of taps or clicks on the same page, at every viewport width — Move up
  and Move down buttons on a selected item or a position field for a list; a "Move to" menu for a
  board; a track that sets the value on click plus a number field for a slider; pan buttons for a
  map; Next and Previous for a carousel; a file input beside a drop zone. A list item needs one
  button per direction:

  ```html
  <button type="button" class="move-up" aria-label="Move Pay invoices up">▲</button>
  ```

  ```js
  btn.addEventListener('click', () => {
    const item = btn.closest('li')
    if (item.previousElementSibling) item.parentNode.insertBefore(item, item.previousElementSibling)
  })
  ```

  A custom slider needs the track itself to be clickable, mapping the click position to the value
  and updating `aria-valuenow`:

  ```js
  track.addEventListener('click', (e) => {
    const r = track.getBoundingClientRect()
    const ratio = Math.min(1, Math.max(0, (e.clientX - r.left) / r.width))
    setValue(Math.round(min + ratio * (max - min)))
  })
  ```

- Related: 2.1.1 Keyboard (the keyboard side; W3C: "the two requirements are evaluated
  independently", and 2.1.3 Keyboard (No Exception) carries the same keyboard duty when the report
  targets AAA); 2.5.1 Pointer Gestures (the path-based side, a swipe-only route, and the component
  that fails both when the grip is lost off the track); 2.5.2 Pointer Cancellation (the added
  control acts on the up-event); 2.5.8 Target Size and 4.1.2 Name, Role, Value for the added
  controls.
