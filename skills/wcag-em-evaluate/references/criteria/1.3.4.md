# 1.3.4 Orientation

Level AA · WCAG 2.1+ · Guideline 1.3 Adaptable · Group: `visual`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/orientation.html)
· [Spec](https://www.w3.org/TR/WCAG22/#orientation)
· [Techniques](https://www.w3.org/WAI/WCAG22/quickref/#orientation)
· [Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/1-3-4-orientation/)
· ACT: [b33eff](https://www.w3.org/WAI/standards-guidelines/act/rules/b33eff/)

## Requirement

> Content does not restrict its view and operation to a single display orientation, such as
> portrait or landscape, unless a specific display orientation is essential.
>
> Note:
> Examples where a particular display orientation may be essential are a bank check, a piano
> application, slides for a projector or television, or virtual reality content where content is
> not necessarily restricted to landscape or portrait display orientation.

Terms (WCAG 2.2 glossary): **essential**: "if removed, would fundamentally change the information
or functionality of the content, **and** information and functionality cannot be achieved in
another way that would conform".

## In plain terms

Let the page follow the device: whichever way the screen is turned, the content turns with it and
stays readable and operable. Do not lock the page to portrait or landscape with CSS, script or a
manifest, and do not swap the content for a "please rotate your device" message. It matters for
people whose device is mounted in a fixed position (a wheelchair arm) and for people with low
vision who zoom in landscape. A different layout per orientation is fine; a lock is allowed only
when one orientation is essential. The fix is code.

## Applies when

- Present: every sample that renders in a browser. A restriction shows as a rule under
  `@media (orientation: portrait|landscape)` that rotates an element (`transform` with `rotate`,
  `rotate3d`, `rotateZ`, `matrix` or `matrix3d`, or the `rotate` property; ACT b33eff), content
  replaced by a message asking to turn the device, a script calling `screen.orientation.lock()`,
  a manifest whose `orientation` member is not `any`, or content only usable in one orientation.
- Not present: not used for this criterion. Any page can be restricted, so a sample without a
  restriction is `pass`, never `not-present`.
- Exceptions: "unless a specific display orientation is essential"; the Note names "a bank check, a
  piano application, slides for a projector or television, or virtual reality content". It holds
  when the content is only understandable in one orientation or the target device has only one; a
  designer's preference is not essential. A restriction with a control that turns the content passes
  ([G214](https://www.w3.org/WAI/WCAG22/Techniques/general/G214)). "Changes in content or
  functionality due to the size of display are not covered by this criterion" (Understanding): a
  different layout per orientation is not a restriction, and an orientation lock the user set in
  the operating system is not the author's.

## axe-core

| Rule                   | Decides                  | Result → outcome                            |
| ---------------------- | ------------------------ | ------------------------------------------- |
| `css-orientation-lock` | 90° turn per orientation | violation → fail (100); incomplete → step 2 |

`css-orientation-lock` sits in the **experimental** rule set of axe-core 4.12.1: off by default and
not run by `agent-browser a11y`. It reads the CSSOM for `@media` rules naming `orientation` and
flags a `transform` (rotate, rotateZ, rotate3d, matrix, matrix3d) or `rotate` declared there whose
angle, truncated to whole degrees, lies within 2° of an odd multiple of 90° (`degreeThreshold: 2`:
92.5deg and 88deg are flagged, 93deg is not; 180deg and 1turn pass); it returns incomplete when the
CSSOM is empty (no stylesheet, or none readable). Cross-check a sample with `agent-browser a11y
--tags experimental --json`. Settles: nothing by default; with the cross-check, CSS locks within 2°
of a quarter turn. Leaves open: rotations more than 2° off the quarter turn, the rendered angle
(step 2 repeats ACT b33eff on the live page), reorient messages
([F100](https://www.w3.org/WAI/WCAG22/Techniques/failures/F100)), content hidden or unusable in one
orientation ([F97](https://www.w3.org/WAI/WCAG22/Techniques/failures/F97)), script locks, the
manifest `orientation` member, the essential exception and the presence of a G214 control.

## Manual procedure

Work on a phone emulation. The `orientation` media feature is `portrait` whenever the viewport is
taller than wide, so the 640 × 900 zoom and 320 × 900 reflow viewports of this pass are portrait
too: a "rotate your device" message seen there counts here. Repeat steps 1 and 3 with the cookie
dialog, the menu or a modal open. `snapshot` lists what exists; screenshots show what is upright.

1. Render both orientations: a portrait phone, then the same phone turned to landscape.

   ```bash
   agent-browser set device "iPhone 13"
   agent-browser reload
   agent-browser wait --load networkidle
   agent-browser screenshot .notes/audit/evidence/<sample>--1.3.4-portrait.png
   agent-browser set viewport 844 390
   agent-browser screenshot .notes/audit/evidence/<sample>--1.3.4-landscape.png
   agent-browser reload
   agent-browser wait --load networkidle
   agent-browser screenshot .notes/audit/evidence/<sample>--1.3.4-landscape-reload.png
   ```

   The viewport change without reload catches locks that react to `resize` or `orientationchange`;
   the reload catches locks applied on load. Look for sideways text, content squeezed into a
   square, a reorient message, or content present in one orientation and gone in the other. Record
   `cannot-tell` when the page refuses to render at a phone viewport. Done when the three
   screenshots exist and the step 2 script reports `portrait: false` here, `true` at 390 × 844.

2. Find orientation-conditional rotation and script locks (ACT b33eff: a visible element with a
   `rotate` property or a `transform` using `rotate`, `rotate3d`, `rotateZ`, `matrix` or
   `matrix3d` under an `orientation` media feature must not turn a quarter turn between the
   orientations). Run in landscape (current), then `set viewport 390 844` and run again:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (async () => {
   const fn = /\b(rotate|rotate3d|rotateZ|matrix|matrix3d)\(/;
   const ori = /orientation:\s*(portrait|landscape)/i;
   const lock = /[^\n]{0,80}(orientation\.lock|lockOrientation)\([^\n]{0,80}/;
   const out = { rules: [], elements: [], unreadable: [], lockCalls: [],
     portrait: matchMedia('(orientation: portrait)').matches };
   const sheets = [...document.styleSheets];
   const walk = (rules, cond, sheet) => { for (const r of rules) {
     if (r.styleSheet) { sheets.push(r.styleSheet); continue; }
     if (r.cssRules) {
       walk(r.cssRules, r.media ? `${cond} ${r.media.mediaText}` : cond, sheet); continue; }
     const tf = r.style?.transform ?? '', rot = r.style?.rotate ?? '';
     if (ori.test(cond) && (fn.test(tf) || (rot && rot !== 'none')))
       out.rules.push({ sheet, cond: cond.trim(), sel: r.selectorText, tf, rot });
   } };
   for (const s of sheets) try { walk(s.cssRules, s.media?.mediaText ?? '', s.href ?? 'inline'); }
     catch { out.unreadable.push(s.href); }
   for (const { sel } of out.rules) for (const el of document.querySelectorAll(sel)) {
     const cs = getComputedStyle(el); let a = 0;
     try { const m = new DOMMatrixReadOnly(cs.transform);
       a = Math.atan2(m.b, m.a) * 180 / Math.PI; } catch {}
     a += parseFloat(((cs.rotate ?? '').match(/(-?[\d.]+)deg/) ?? [0, 0])[1]);
     out.elements.push({ sel, visible: el.getClientRects().length > 0, angle: Math.round(a) });
   }
   const scripts = [...document.scripts], texts = await Promise.all(scripts.map(s => s.src
     ? fetch(s.src).then(r => r.text()).catch(() => '') : Promise.resolve(s.text)));
   texts.forEach((t, i) => { const m = t.match(lock);
     if (m) out.lockCalls.push({ src: scripts[i].src || 'inline', call: m[0].trim() }); });
   return out;
   })()
   EOF
   ```

   `rules` lists the offending declarations, `elements` the rendered angle of each matched element
   in this orientation, `unreadable` the cross-origin sheets whose rules could not be read,
   `lockCalls` every `screen.orientation.lock()` or `lockOrientation()` call in inline and
   fetchable scripts. A visible element whose `angle` differs by 90 ± 5 or 270 ± 5 between the
   two runs fails b33eff; the same angle in both passes. For every `unreadable` href: `tab new`,
   `open <href>`, `get text body`, search for `orientation` and `rotate`, `tab close`. Done when
   `rules` and `lockCalls` are empty, or every entry has a measured angle or a reason.

3. Compare the content of the two orientations (F100, F97). In each orientation:

   ```bash
   agent-browser snapshot -i
   agent-browser eval --stdin <<'EOF'
   (() => {
     const rx = new RegExp(['(rotate|turn|flip) (your |the )?(device|phone|tablet|screen)',
       '(portrait|landscape) (mode|only)',
       'draai (je|uw) (toestel|telefoon|scherm)'].join('|'), 'i');
     return document.body.innerText.match(rx)?.[0] ?? null;
   })()
   EOF
   ```

   A match, or a snapshot that lists the main content and controls in one orientation and only a
   message in the other, is the door-slam of F100. Content present in both but sideways in the
   step 1 screenshots is F97. Controls off-screen in one orientation (`is visible <sel>`) restrict
   operation. Done when the snapshots match or every difference is noted with its orientation.

4. Check the remaining lock mechanisms: the web app manifest and the `lockCalls` of step 2.

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => fetch(document.querySelector('link[rel="manifest"]').href, { credentials: 'include' })
     .then(r => r.json()).then(m => m.orientation ?? 'absent'))()
   EOF
   ```

   An error means no manifest: record `absent`. `portrait`, `portrait-primary`,
   `portrait-secondary`, `landscape`, `landscape-primary` and `landscape-secondary` lock the
   installed app to one orientation; `natural` locks it to the device's own default (portrait on
   a phone); `any` and `absent` do not restrict. For each `lockCalls` entry note the argument and
   the trigger: a lock on load restricts; a lock inside a fullscreen game or video handler is a
   candidate for the essential exception (the API acts only in fullscreen or installed contexts,
   so emulation shows no effect). Done when the manifest value and every lock call are recorded.

5. When steps 2 to 4 found a restriction, test the exception and the escape. Judge whether the
   content matches the Note (cheque capture, piano keys, projector slides, VR) and whether the same
   information or function is available another way; record the reasoning. Then look in
   `snapshot -i` for a control named rotate, orientation, landscape or portrait (G214), `click`
   its `@ref` and rerun the step 2 script: a changed `angle` or content that reappears means it
   works. Finish with `set viewport 1280 900`, `reload` and `wait --load networkidle`. Done when
   the restriction is classified as essential, escapable or neither, and the desktop is back.

## Deciding

- Fail (certainty ≥ 90): a visible element's measured `angle` differs by a quarter turn between
  the two runs of step 2 (b33eff fails, F97) (95); a message asking to turn the device replaces
  the content in one orientation, seen in the screenshot and the snapshot (F100) (95);
  `css-orientation-lock` violation in a run that includes the rule (100).
- Fail (70–89): a reorient message is shown while the content stays visible and operable behind
  it (F100: the view is restricted) (75); the main content or its controls are cut off, shrunk to
  a square or unreachable in one orientation only, beyond what a responsive layout explains (75);
  a script locks orientation on load with no way to undo it (75).
- Needs confirmation (50–69): a manifest `orientation` lock and nothing else, so only the
  installed app is affected (60): ask whether the installed app is in scope; a restriction on
  content that may be essential (piano, cheque scan, VR, projector) (60): ask what breaks without
  the lock and whether the function exists another way; a lock call in an untriggered handler (55).
- Pass: both orientations show the same content upright and operable, no reorient message,
  `rules` and `lockCalls` empty, manifest `any` or absent; or every restriction is either
  essential (reasoning recorded) or has a working G214 control.
- Not present: not used; an unrestricted sample is `pass`.
- False positives to avoid: layout differences between orientations (stacked columns, a menu
  button in portrait) are size adaptations, not restrictions; a rotation that is the same in both
  orientations (a 2.5° decorative tilt) or resolves to zero (`rotateZ(1turn)`, an identity
  `matrix`) passes b33eff; `@media (orientation)` used for layout without rotation is fine.

## Reporting

- File under: 1.3.4. Content cut off in portrait because the layout has a fixed width is 1.4.10
  Reflow unless it is fine at 320 px wide and only breaks when the aspect ratio flips. One issue
  per lock mechanism; a site-wide lock (global stylesheet, manifest) names every sample it affects.
- Title patterns: "Page is locked to portrait orientation", "'Rotate your device' message replaces
  the content in landscape", "Installed app restricts orientation to portrait"
- Severity: High when the content or its controls are unusable in one orientation (sideways page,
  door-slam message); Medium when everything stays usable but a message or clipped region hinders
  a task in one orientation; Low when only the installed app or the fullscreen mode is locked.
- Type: Technical (CSS, script or manifest); Design when the second orientation lacks a layout.
- Evidence: the portrait and landscape screenshots of step 1 side by side, with `highlight` on the
  reorient message or rotated container; a GIF from `record start` and `record stop` while the
  viewport changes when the lock appears on rotation.
- Recommendation: remove the orientation-conditional rotation or the door-slam rule and let the
  layout respond to both orientations ([F97](https://www.w3.org/WAI/WCAG22/Techniques/failures/F97),
  [F100](https://www.w3.org/WAI/WCAG22/Techniques/failures/F100)); when a restriction must stay, add
  a control that turns the content ([G214](https://www.w3.org/WAI/WCAG22/Techniques/general/G214)).
  Example: delete `@media (orientation: portrait) { html { transform: rotate(90deg) } }` or set
  `"orientation": "any"` in the manifest.
- Related: 1.4.10 Reflow when the portrait layout also fails at 320 px; 1.4.4 when zoom is lost.
