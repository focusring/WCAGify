# 3.2.1 On Focus

Level A · WCAG 2.0+ · Guideline 3.2 Predictable · Group: `keyboard`

Sources: [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/on-focus.html) ·
[Spec](https://www.w3.org/TR/WCAG22/#on-focus) ·
[Techniques](https://www.w3.org/WAI/WCAG22/quickref/#on-focus) ·
[Plain English](https://aaardvarkaccessibility.com/wcag-plain-english/3-2-1-on-focus/) ·
ACT: none mapped to this criterion

## Requirement

> When any user interface component receives focus, it does not initiate a change of context.

Terms (WCAG 2.2 glossary): **user interface components**: "a part of the content that is perceived
by users as a single control for a distinct function", Note 1: "Multiple user interface components
may be implemented as a single programmatic element. 'Components' here is not tied to programming
techniques, but rather to what the user perceives as separate controls.", Note 2: "User interface
components include form elements and links as well as components generated by scripts." Note 1
makes every perceived control a test target of its own: each item of a roving-`tabindex` widget (a
menu item, a tab, a grid cell, a radio) receives focus in turn although one element carries the
tabindex, and `focusables.js` `order` lists only that one element.

**change of context**: "major changes that, if made without user awareness, can disorient users who
are not able to view the entire page simultaneously. Changes in context include changes of: user
agent; viewport; focus; content that changes the meaning of the web page". Note: "A change of
content is not always a change of context. Changes in content, such as an expanding outline,
dynamic menu, or a tab control do not necessarily change the context, unless they also change one
of the above (e.g., focus)." Example: "Opening a new window, moving focus to a different component,
going to a new page (including anything that would look to a user as if they had moved to a new
page) or significantly re-arranging the content of a page are examples of changes of context." That
parenthesis decides the single-page app: a view swap with no page load and no URL change is a
change of context when it looks to the user like a new page, and "significantly re-arranging the
content of a page" is a change of context by itself, with no navigation and no focus move.

**viewport**: "object in which the user agent presents content", Note 1: "The user agent presents
content through one or more viewports. Viewports include windows, frames, loudspeakers, and virtual
magnifying glasses. A viewport may contain another viewport (e.g., nested frames). Interface
components created by the user agent such as prompts, menus, and alerts are not viewports." A new
window, tab or frame is a new viewport; the browser's own `select` popup, autofill list, password
manager list and `alert()` box are not, so those are judged on the focus and content channels
instead of counting as a viewport change.

**user agent**: "any software that retrieves and presents web content for users" (Example: "Web
browsers, media players, plug-ins, and other programs"). Read together with the list above, a
change of user agent is content handed to other software the moment focus lands: a download that
starts, a PDF or media handler that takes over, a `mailto:` or `tel:` link opening a mail or phone
client. No URL comparison catches it, so step 4 looks at the focused element's `href` scheme.

## In plain terms

Landing on a control, by Tab, Shift+Tab, a script or a click in a text field, changes nothing but
which element has focus: no page load, no submitted form, no new window or tab, no focus thrown to
another element or off the page, no swap of the page's content. What the control does happens on
activation: Enter, Space, a click on a button or link, a value change
([G107](https://www.w3.org/WAI/WCAG22/Techniques/general/G107)). Content that merely appears on
focus (a tooltip, a hint, a suggestion list) is a change of content and is allowed. The Intent puts
the whole test in one sentence: "Any component that is able to trigger an event when it receives
focus must not change the context." It matters to keyboard, screen-reader and magnifier users, who
move through a page one control at a time and cannot see what else changed, and, in the words of
Benefits, to "people with visual disabilities, cognitive limitations, and motor impairments by
reducing the chance that a change of context will occur unexpectedly".

## Applies when

- Present: any state with a focusable component: `focusables.js` `order` is non-empty, or an
  element with `tabindex="-1"` exists that a skip link, dialog or script focuses
  (`get count "[tabindex='-1']"` above 0). Every entry is a test target (G107: "cycle focus
  through all content"); the usual triggers carry `onfocus` or `onblur` attributes or scripted
  focus handlers: fields, links, `select` elements, help widgets bound to fields. Inside a
  composite widget (`[role=menu]`, `menubar`, `toolbar`, `tablist`, `listbox`, `tree`, `grid`,
  `radiogroup`) the items the arrow keys move focus to are components too and are not in `order`:
  step 6 walks them.
- Not present: `order` is empty and nothing carries `tabindex="-1"`, in every state: nothing can
  receive focus.
- Cannot tell: a cross-origin `iframe` that `frame` refuses, so its focus handlers cannot be
  instrumented and only the outer signals remain; a control that appears only behind a login, a
  licence or a payment the audit cannot complete. Record `cannot-tell` and queue it.
- Exceptions: none in the text. Three sentences narrow it. Understanding: "A change of content is
  not always a change of context. This success criterion is automatically met if changes in content
  are not also changes of context." And "clicking on a control may also activate the control (e.g.
  button), which may, in turn, initiate a change in context": activation is out of scope, so every
  test moves focus without activating (Tab, Shift+Tab, `focus`, a `click` in a text field). And
  "Moving the mouse over a control does not move the focus unless scripting implements this
  behavior": hover is out of scope until the page makes it move focus, which step 5 checks.

## Manual procedure

Work at `set viewport 1280 900`, in the initial state, then in every state of
`recon/<sample>-states.md`. This criterion rides on the 2.1.2 step 3 Tab walk (logger
`.notes/audit/recon/focus-logger.js`, log `recon/<sample>-tabwalk.txt`): arm the monitor of step 2
before that walk and run the reader of step 3 after every press, so the sample is walked once.
`snapshot` shows what opened and where focus sits, not a screen reader's reading position; the
controls inside a cross-origin `iframe` that `frame` refuses are `cannot-tell`: queue them.

1. Inventory what can fire on focus, so the walk knows where to look hardest:

   ```bash
   agent-browser eval --stdin < <skill-dir>/scripts/probes/focusables.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/forms.js
   agent-browser eval --stdin < <skill-dir>/scripts/probes/structure.js
   agent-browser eval --stdin <<'EOF'
   (() => {
     const t = e => e.localName + (e.id ? '#' + e.id : '') +
       (!e.id && e.classList[0] ? '.' + e.classList[0] : '');
     const attrs = ['onfocus', 'onfocusin', 'onblur', 'onfocusout', 'onmouseover', 'onmouseenter'];
     return {
       inline: [...document.querySelectorAll(attrs.map(a => '[' + a + ']').join(','))]
         .map(e => ({ el: t(e), ...Object.fromEntries(attrs.filter(a => e.hasAttribute(a))
           .map(a => [a, e.getAttribute(a)])) })),
       composites: [...document.querySelectorAll('[role=menu],[role=menubar],[role=toolbar],' +
         '[role=tablist],[role=listbox],[role=tree],[role=grid],[role=radiogroup]')].map(t),
       selects: [...document.querySelectorAll('select')].map(t),
       schemes: [...document.querySelectorAll('a[href], area[href], [download]')]
         .map(e => e.getAttribute('href') || '').filter(h => /^(mailto:|tel:|blob:|data:)/.test(h))
     };
   })()
   EOF
   ```

   `inline` is the fast lane. The three shapes
   [F55](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55) documents are
   `onFocus="this.blur();"`, `onFocus="this.blur()"` and
   `onfocus="if(this.blur)this.blur();"`, so any `onfocus` or `onfocusin` value containing `blur`,
   `open(`, `submit(`, `location` or `focus(` is a candidate before a single key is pressed.
   Handlers attached with `addEventListener` are invisible here, which is why step 3 reads the
   monitor after _every_ press and not only for this list. The `el` labels match the monitor's
   shape; take the CSS selector for a command from `order[].selector`. Done when `inline`,
   `composites`, `selects`, `schemes` and N (the `order` entries with `visible: true`) are in the
   findings file.

2. Arm the monitor, once per page load and per state (a `reload` or a navigation removes it):

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const t = n => n && n.nodeType === 1 ? n.localName + (n.id ? '#' + n.id : '') +
       (!n.id && n.classList[0] ? '.' + n.classList[0] : '') : 'BODY';
     const L = window.__onfocus = { events: [], url: location.href };
     const push = (kind, x) => L.events.push({ kind, ...x });
     document.addEventListener('keydown', e => push('key', { key: e.key }), true);
     document.addEventListener('focusin', e => push('focusin', { target: t(e.target) }), true);
     document.addEventListener('focusout', e => push('focusout', { to: t(e.relatedTarget) }),
       true);
     document.addEventListener('submit', e => push('submit', { target: t(e.target) }), true);
     const open = window.open; window.open = (...a) => { push('open', { url: String(a[0]) });
       return open.apply(window, a) };
     const alert = window.alert; window.alert = m => { push('alert', { text: String(m) });
       return alert.call(window, m) };
     for (const m of ['submit', 'requestSubmit']) { const f = HTMLFormElement.prototype[m];
       HTMLFormElement.prototype[m] = function (...a) { push('submit', { target: t(this) });
         return f.apply(this, a) } }
     for (const m of ['pushState', 'replaceState']) { const f = history[m];
       history[m] = function (...a) { push('route', { url: String(a[2]) });
         return f.apply(this, a) } }
     new MutationObserver(ms => push('dom', { outside: ms.filter(m =>
       !(document.activeElement || document.body).contains(m.target)).length }))
       .observe(document.documentElement, { childList: true, subtree: true });
     return 'armed';
   })()
   EOF
   ```

   The two prototype hooks close the holes the event listeners leave: a script calling
   `form.submit()` fires no `submit` event at all, and a client-side route change fires nothing
   while the URL moves. A scripted `requestSubmit()` is counted twice (hook plus event); only
   "above 0" is read. Done when it prints `armed`.

3. Read the monitor after every press of the walk (and after every `focus`, `click` or `hover` of
   steps 5, 6, 7 and 8); append the line to `recon/<sample>-onfocus.txt` next to the logger line of
   that press:

   ```bash
   agent-browser eval --stdin <<'EOF'
   (() => {
     const L = window.__onfocus; if (!L) return 'NAVIGATED';
     const E = L.events; L.events = [];
     const k = kind => E.filter(e => e.kind === kind);
     const was = L.url; L.url = location.href;
     return { key: (k('key').pop() || {}).key || 'none',
       focusins: k('focusin').map(e => e.target),
       lostToBody: k('focusout').some(e => e.to === 'BODY'),
       submits: k('submit').length, opens: k('open').map(e => e.url), alerts: k('alert').length,
       routes: k('route').length, domOutside: k('dom').reduce((s, e) => s + e.outside, 0),
       url: location.href === was ? 'same' : location.href, scrollY: Math.round(scrollY),
       dialogs: [...document.querySelectorAll('dialog[open],[role=dialog],[role=alertdialog],' +
         '[aria-modal="true"]')].filter(d => d.getClientRects().length).length };
   })()
   EOF
   agent-browser get url
   ```

   `L.url` is reset on every read, so one route change produces one candidate instead of marking
   every later press of the walk as changed too.

   The sound line for one press: `focusins` ends on the walk's next `order` entry, `lostToBody`
   false, `submits` 0, `opens` empty, `alerts` 0, `routes` 0, `url` `same`, `dialogs` equal to the
   state's count before the press, `domOutside` 0, and `scrollY` either unchanged or, when it
   moved, leaving the focused element inside the viewport (`get box "<selector>"`). Two lines from
   a Tab walk over a form, the first sound and the second a candidate:

   ```text
   {"key":"Tab","focusins":["input#email"],"lostToBody":false,"submits":0,"opens":[],"alerts":0,
    "routes":0,"domOutside":0,"url":"same","scrollY":0,"dialogs":0}
   {"key":"Tab","focusins":["input#zip","div#help"],"lostToBody":false,"submits":0,"opens":[],
    "alerts":0,"routes":0,"domOutside":3,"url":"same","scrollY":0,"dialogs":1}
   ```

   The second is the Understanding's help-dialog failure in one line: two focusins for one press,
   the last one not the walk's next `order` entry, and `dialogs` up by one. Anything unsound is a
   candidate: note the press number and copy the line. `NAVIGATED`, or a `get url` that differs
   from the state's URL, means the page was left: `back`, `wait --load networkidle`, re-arm,
   `focus` the entry two before the candidate and `press Tab` twice to confirm the same result.
   Done when every press of every state has a line and each candidate is named with its press
   number.

4. Confirm each candidate in isolation: `focus` the entry before it, `press Tab`, `wait 500`, the
   reader, the logger, `snapshot -i`, `tab list`, `dialog status`. Classify by what they show:
   - `url` changed or `NAVIGATED`, or `submits` above 0: a page load or form submission on focus.
   - `routes` above 0, or `get url` changed while the monitor still answers: a client-side route
     change on focus. Compare `snapshot -i` before and after: a main region replaced is the
     glossary's "going to a new page (including anything that would look to a user as if they had
     moved to a new page)", which a page that never unloads still commits.
   - `opens` non-empty, or `tab list` one tab longer: a new window or tab on focus (`tab close`
     it, then `tab <id>` back to the sample).
   - the logger, or the last `focusins` entry, on an element other than the walk's next entry:
     focus moved on focus (a `focus` handler fires one focusin, a `focusin` handler two). Two or
     more focusins in one press whose last entry is not the walk's next `order` entry is script
     moving focus, whichever handler did it. A move into a modal opened by this same focus is the
     Understanding failure "A help dialog". A modal's focus sentinel that lands focus on the first
     control of an open modal keeps the user in place (2.1.2 and 2.4.3 judge it).
   - `lostToBody` true with the logger on `BODY` while `order` continues: focus removed on focus
     ([F55](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55)); confirm with
     `get attr "<selector>" onfocus` or `get html "<selector>"` showing `blur()`, in any of the
     three documented shapes (`this.blur();`, `this.blur()`, `if(this.blur)this.blur();`).
   - `dialogs` up by one, `alerts` above 0, or `dialog status` showing an open dialog: a dialog
     on focus (`dialog dismiss` a native one). The box itself is not a viewport change — the
     glossary excludes "prompts, menus, and alerts" created by the user agent — it fails because
     focus leaves the control and the box has to be dismissed before Tab moves on. A non-modal
     popover, tooltip or listbox with focus still on the control is content (1.4.13 judges it).
   - `domOutside` above 0, or `snapshot -i` differing beyond the focused control: `screenshot`
     before and after and judge whether the meaning changed (main content replaced, another form,
     the next step of a process, "significantly re-arranging the content of a page") or only
     expanded (an outline, a dynamic menu, a tab panel).
   - `scrollY` moved and `get box "<selector>"` puts the focused element outside the viewport, or
     the page jumped to another region: a scripted scroll, a viewport-change candidate.
   - nothing in the reader moved while the browser acted on its own: check
     `get attr "<selector>" href` and `get attr "<selector>" download` for a `mailto:`, `tel:`,
     `blob:`, `data:` or downloadable target (step 1's `schemes` lists them up front) and
     `agent-browser errors` for a blocked navigation — content handed to another program is a
     change of user agent.
     Done when each candidate has one class, its reader line and a screenshot.

5. Focus by pointer, by script and by hover (Understanding: focus moves by "the mouse (e.g.
   clicking on a text field)"). For every entry of `forms.js` `fields` with `tag` `textarea`, or
   `input` with a text-like `type` (text, search, email, url, tel, number, password, date):
   `click "<selector>"`, `wait 500`, the reader; `press Escape` when a listbox opened. For every
   `[tabindex="-1"]` element a skip link (`structure.js` `skipLinks`) or a dialog targets:
   `focus "<selector>"`, `wait 500`, the reader. Buttons and links stay with Tab: a click activates
   them. Then hover: for every step-1 `inline` entry carrying `onmouseover` or `onmouseenter`, and
   every composite trigger, `hover "<selector>"`, `wait 500`, the reader. `focusins` non-empty
   there means the page moves focus on hover, against the default that "moving the mouse over a
   control does not move the focus unless scripting implements this behavior", so that component
   also receives focus by pointer: run the step-4 classification on that arrival. Done when every
   field, every `tabindex="-1"` target and every hover trigger has a reader line.

6. Composite widgets, where focus arrives by arrow key. For every `composites` entry: `focus` the
   widget's tabbable item from `order`, then walk it with `press ArrowDown` (menu, listbox, tree,
   radiogroup), `press ArrowRight` (menubar, toolbar, tablist) and `press Home` / `press End`, each
   followed by `wait 500` and the reader, to the last item. Every item that receives focus is a
   component (glossary Note 1) and is classified by step 4, with the glossary Note doing the work:
   a tab control that swaps its panel as focus moves ("a tab control do[es] not necessarily change
   the context"), a menu that opens a submenu, an outline that expands are changes of content and
   pass; an item that loads a page, opens a window or throws focus elsewhere as the arrow key
   reaches it fails. Understanding Example 1 is the passing shape for a navigating dropdown: "if
   the person uses the keyboard to move down to a choice and activates it (with a spacebar or enter
   key) it will jump to a new page. However, if the person moves down to a choice and either hits
   the escape or the tab key to move out of the pulldown menu – it does not jump to a new screen as
   the focus shifts out of the dropdown menu." Test it on every `selects` entry:
   `focus "<select css>"`, `press ArrowDown`, the reader, then `press Escape` and `press Tab`, the
   reader after each. A navigation on the arrow or on the way out fails; a navigation only on Enter
   or Space is activation (G107) and passes, and the value change that carries it is 3.2.2's.
   Done when every composite and every `select` has a reader line per arrow press and per exit key.

7. States. Open each state of `recon/<sample>-states.md` with the keyboard (`focus "<trigger>"`,
   `press Enter`, `wait 500`), re-arm when the page reloaded, run `focusables.js` again and repeat
   steps 3 and 4 over the new `order`: a cookie dialog's buttons, an open menu's items, an
   expanded panel's fields, a form in its error state (`fill` one field with a bad value,
   `press Enter`, `wait 500`, re-arm, Tab through the fields; a form that pulls focus to the first
   invalid field when another one receives focus is a candidate). G107's second example names the
   case to look for at the end of every form — "A submit button is used to move on to the next data
   entry screen rather than having the next screen appear automatically when the user tabbed onto a
   'done' button" — so Tab onto the last control of each form and read the monitor before pressing
   anything else. Done when every state has lines.

8. Frames. For every `structure.js` `iframes` entry whose `src` is same-origin:
   `frame "<iframe css>"`, arm the step-2 monitor inside it, `frame main`, Tab until the logger
   shows the `iframe` element, then keep pressing Tab and read both monitors after each press:
   `frame "<iframe css>"`, the reader, `frame main`, the reader. A frame that `frame` refuses, or
   whose `src` is another origin, leaves only the outer signals: `focusins` on the `iframe` element,
   `url`, `routes`, `tab list` and `dialogs` of the top document. Record `cannot-tell` for its
   inner controls and queue them with the frame's `src`. Done when every frame has either inner
   reader lines or a `cannot-tell` entry naming its `src`.

9. Evidence for every candidate that fails. `focus` the entry two before it,
   `record start .notes/audit/evidence/<sample>-3.2.1-<slug>.webm`, `press Tab` three times with
   `wait 500` between, `record stop`; `back` and re-arm when it navigated. Then
   `highlight "<selector>"` and `screenshot .notes/audit/evidence/<sample>-3.2.1-<slug>.png`; for
   a new tab add the `tab list` output, for a navigation the `get url` after the press. Done when
   every fail has the recording, the screenshot and its reader line in the findings file.

## Deciding

- Fail (certainty ≥ 90): the URL changes or the page unloads on a Tab press alone (`NAVIGATED`,
  `submits` above 0): a form submitted or a page loaded on focus (Understanding: "forms submitted
  automatically when a component receives focus") — 100; a new window or tab opens on focus
  (`opens` non-empty, `tab list` grows; Understanding: "new windows launched when a component
  receives focus") — 100; focus removed by script as soon as it lands (`onfocus` calling `blur()`,
  `BODY` in the logger while `order` continues) (F55) — 95; the logger on an element other than the
  walk's next `order` entry after one press or one `focus`, with no second key press
  (Understanding: "focus is changed to another component when that component receives focus") — 95;
  a modal dialog or native `alert()` opened by focus alone that takes focus or must be dismissed
  before Tab moves on (the Understanding failure "A help dialog": "As a keyboard user tabs through
  the web page, the dialog opens, moving the keyboard focus away from the control every time the
  user attempts to tab past the field") — 95; a client-side route change on focus (`routes` above
  0, or the URL moved with no page load) with `snapshot -i` showing the main region replaced —
  "going to a new page (including anything that would look to a user as if they had moved to a new
  page)" — 90; content handed to another program on focus, seen directly (a download starts, a PDF,
  media, mail or phone handler takes over): a change of user agent — 90.
- Fail (70–89): main content, a form or a process step replaced on focus, judged from the before
  and after screenshots ("significantly re-arranging the content of a page") — 80; a `select` or
  custom combobox that changes the page content on focus, before any value changes — 80; an item
  of a composite widget that loads a page, opens a window or moves focus away as an arrow key
  reaches it — 80; a scripted scroll that leaves the focused element outside the viewport or jumps
  to another region — 75; a modal opened on focus that leaves focus on the control but blocks the
  rest of the page (`aria-modal`, `inert`) — 75; a change of context on focus that matches none of
  the patterns above yet meets the glossary definition — the Intent's list is "include, but are not
  limited to" — 75; a focus move seen in the walk but not reproduced in isolation (a
  timing-dependent handler) — 70.
- Needs confirmation (50–69): a large DOM change on focus whose meaning is unclear (a preview
  replaces a summary, a sidebar swaps) — 55: ask "does the page say something different after
  this?"; focus pulled once onto a related control (the first invalid field, the first item of a
  widget) — 60: ask whether users lose their place; a focus handler inside a cross-origin `iframe`
  that could not be instrumented — 55: queue it for a screen-reader run; a press after which the
  reader shows nothing while the browser acted by itself — 55: ask the human what the browser did
  (a download, an external handler, a blocked popup).
- Pass: every focusable component, in every state, reached by Tab, Shift+Tab, `focus`, an arrow key
  inside a composite widget and (for fields) a click keeps focus where it landed, keeps the URL and
  the history entry, opens no window, tab or modal dialog, hands nothing to another program,
  submits nothing and changes no content beyond what focus reveals, until the next key.
- Not present: no component can receive focus in any state.
- False positives to avoid: content shown on focus that leaves focus in place (a tooltip, a field
  hint, a suggestion listbox, an expanded submenu, a skip link becoming visible: content, 1.4.13);
  a tab control whose panel swaps, an outline that expands or a dynamic menu that opens as focus
  moves through it (the glossary Note names all three as content); the browser's own `select`
  popup, autofill or password list opening on focus (user-agent "prompts, menus, and alerts" are
  "not viewports"); hover that only moves focus while nothing else changes (another way focus is
  received; judge what follows it, not the move); the browser scrolling the focused element into
  view; anything that happens on Enter, Space, a click on a button or link, or a value change
  (activation, G107; a value change is 3.2.2); focus entering a dialog or menu that was opened by
  activation; a modal's focus sentinel or `inert` cycling focus inside an open modal (2.1.2,
  2.4.3); `autofocus` on page load and focus moved by the page after a submit (2.4.3, 3.2.2);
  `BODY` at either end of `order` (the browser UI).

## Reporting

- File under: 3.2.1 for every change of context that focus alone triggers, on any of the four
  channels the glossary names: user agent, viewport, focus, content that changes the meaning. F55
  (`blur()` on focus) is one issue here naming 2.1.1, 2.4.7 and 2.4.13 in the body; the 2.1.1 and
  2.4.7 rows of the findings file point to it. A change on a value change or a keystroke in a field
  is 3.2.2; a dialog that focus cannot leave is 2.1.2; a focus move that keeps the context but
  breaks the sequence is 2.4.3; focus-revealed content that vanishes or obscures is 1.4.13. One
  issue per triggering component; the same component on other samples is one issue naming them.
- Title patterns: "Tabbing to the <field> submits the <form>", "The <control> opens a new window
  as soon as it receives focus", "Focus jumps to the <element> when the <control> receives focus",
  "The <link> drops keyboard focus as soon as it receives it", "A dialog opens when the <field>
  receives focus", "The page loads <url> when the <control> receives focus", "The page switches to
  <view> when the <control> receives focus", "Focus on the <link> starts a download"
- Severity: High when the change stops the keyboard user from getting past the component or
  undoes their work (a form submitted, a page loaded, a dialog reopening on every Tab, focus
  thrown away so the control cannot be used); Medium when the user can recover but loses their
  place (a new tab, focus on another control, the page scrolled elsewhere, content swapped); Low
  when the move is one step within the same widget and everything stays reachable.
- Type: Technical (a `focus`, `focusin` or `blur` handler, focus-management or form scripting).
- Evidence: the recording of the Tab press and what follows (the new page, the new tab, the
  dialog, the focus ring jumping or vanishing) plus the page screenshot with `highlight` on the
  triggering component; quote the reader line and the `onfocus` attribute or handler verbatim in
  the body, and for a route change the URL before and after.
- Recommendation: [G107](https://www.w3.org/WAI/WCAG22/Techniques/general/G107): trigger the
  change on activation, not on focus — "all changes of context would be triggered only by a
  specific action on the part of the user [...] such as clicking on a link or pressing a submit
  button. Actions that simply move the focus to an element would not cause a change of context."
  Move the handler from `focus`/`focusin` to `click` and `keydown` (Enter, Space), to `submit` for
  forms and to `change` for fields; remove `onfocus="this.blur()"`
  ([F55](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55)) and style `:focus-visible`
  instead. The three shapes F55 documents, and what replaces them:

  ```html
  <!-- F55: focus is taken away the moment it lands -->
  <input type="submit" onFocus="this.blur();" />
  <a onFocus="this.blur()" href="Page.html"><img src="myImage.gif" /></a>
  <a href="link.html" onfocus="if(this.blur)this.blur();">Link Phrase</a>
  <!-- the fix is the same in all three: drop the handler, style :focus-visible in CSS -->
  <input type="submit" />
  <a href="link.html">Link Phrase</a>
  ```

  ```js
  // on focus: the page decides for the user
  field.addEventListener('focus', openHelp)
  // on activation (G107): the user decides, from a control that says so
  helpButton.addEventListener('click', openHelp)
  form.addEventListener('submit', save)
  jumpMenu.addEventListener('change', go) // a value change: 3.2.2 judges it
  ```

  So: a visible Help button beside the field instead of a dialog on focus, and, in G107's own
  example, "A page pops up a new window only when the user clicks(or uses spacebar) on a button
  rather than using onfocus to pop up a new window" — with the submit-button example quoted in
  step 7 for the form case.
